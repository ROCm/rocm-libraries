00 / 问题

一次 GEMM，分给 1024 个工作组

要算的是 8192×8192 的输出 D，每个元素是 A 的一行点乘 B 的一列（长度 K=8192）。 kernel 把输出切成 256×256 的瓦片(tile)，于是有 32×32 = 1024 个 tile， 每个 tile 交给一个工作组 (workgroup, WG)。

MI350 有 256 个 CU，1024 个 WG 正好分 4 波铺满整张卡。这一步纯粹是 host 端的网格划分 —— 决定谁算哪块。

01 / 调度 · L2 SWIZZLE

把并发窗口从「长条」捏成「方块」

256 个 CU 同时各跑一个 WG。这 ~256 个在飞的 WG 此刻要读的 A 行块 + B 列块，合起来就是 压在 L2 上的「并发工作集」。它越小，越能塞进 32 MB 的 L2，命中率越高。

关键几何：256 个 WG 覆盖的输出面积是固定的，但它们要加载的输入量 ∝ 这块区域的周长 （A 行 + B 列）。同样面积，方块的周长最小。

某一时刻在飞的 256 个 WG 覆盖的 tile 区域 · M↓ × N→ (示意 6×6)
默认顺序 → 长条
N →A 行=全部 · B 列=少
默认走位让并发窗口是一条「贯穿全部 M、只占几列 N」的长条 → 要载的 A 几乎是整块面板 → 周长大、工作集 > L2 → miss ↑
SWZ=16 → 近似方块
N →A 行≈B 列（方）
沿 M 走、限制在 16-tile 宽的 N-band → 并发窗口变成 ~16×16 方块 → A+B 周长最小、工作集缩小 → 同段 A/B 被一堆 CU 共享留 L2 热 → miss ↓

以 8192³ 为例：默认并发窗口 ≈ 32 M-tile × 8 N-tile，要载 32+8=40 条面板； swizzle 后 ≈ 16 × 16，只要 16+16=32 条 —— 少 20% 的 L2 工作集。 实现是纯 host 端的下标重映射：把线性 WG 号 pid 重排成「沿 M 下行、 限制在 16-tile N-band 内」。不碰 compute、不多搬一个字节。

+4.4%8192³：1491 → 1557
16band 宽 (N-tile)
91%L2 命中（已近顶）

门控：只有 N 足够宽（能填满一条 band）才赢，否则中性偏负 → 按 N 判断（TLDS 路径：N≥M 时启用）。这也是为什么它只在大方阵上有效。

02 / 工作组 → 硬件

4 个 wave，吃满一个 CU 的寄存器

一个 WG = 256 线程 = 4 个 wave（每 wave 64 lane），映射到 1 个 CU 的 4 个 SIMD。 4 个 wave 排成 2×2，每个 wave 负责 tile 里 4×4 = 16 个 32×32 子块。

这 16 个子块的累加器常驻 AccVGPR：16 × 16 寄存器 = 256 个 AccVGPR，刚好把一个 SIMD 的 Acc 寄存器堆占满。 占满 = 每个 SIMD 只能驻留 1 个 wave = occupancy 1。这是整个 kernel 性能特征的根。

1 WG = 4 wave (2×2) · 每 wave 持 16 个累加器
  • 大寄存器 tile → 每次加载的数据能摊到更多 MFMA（高算/载比）
  • 代价：occ1，每个 SIMD 只有一个 wave，没有第二个 wave 来掩盖延迟
03 / 取数 · 异步 DMA

用 global_load_lds 把数据直送 LDS

K 太长（8192），一次装不下，所以沿 K 切成 KT192 的薄片(slab)，一片一片地处理。 取数用的是 CDNA 的杀手锏指令 global_load_lds_dwordx4：

  • 从 HBM 异步搬 16 字节直接落到 LDS —— 完全不经过 VGPR，零寄存器开销
  • 4 个 wave 协作搬运：一个 256×192 的 A-slab + 一个 256×192 的 B-slab
  • 地址连续 → 合并访问；91% 命中 L2，真正打到 HBM 的只有 ~10% 带宽

这一步只负责发射加载请求，不等它回来 —— 数据在飞的同时，计算继续。

04 / LDS 里存的是什么 · 为什么

一个缓冲槽 = 一块 A 板 + 一块 B 板

每个 LDS 槽放的是当前这个 256×256 输出 tile、当前这段 K（KT192）所需的全部输入： 上半是 A-slab：256 行 × 144 字节，下半是 B-slab：256 行 × 144 字节。 合计 72 KB；两个槽双缓冲 = 144 KB。

为什么非要先进 LDS，不直接从寄存器读 global？三个理由叠起来：

  • 修好合并访问：A 是行主序，寄存器直读时每个 lane 要不同的 M 行 → 天生非合并（cache line 只用 37.5%）。改成 global_load_lds 按行连续搬，合并了。
  • 复用：搬进来一次，ds_read 多次 —— 一个 A-block 喂这个 wave 4 个 N-block 的 MFMA，一个 B-block 喂 4 个 M-block。算/载比翻上去。
  • 深 K 装不进寄存器：KT192 的操作数太多，全塞寄存器会 spill；LDS 有 160 KB，装得下。这正是上一步双缓冲能把延迟藏住的前提。
05 / 双缓冲 · 这是关键一招

一边算 buf0，一边把 buf1 灌满

LDS 里开两个缓冲区（各 72 KB，合计 144 KB，逼近 160 KB 上限）。编译期 2× 展开成乒乓：

深-K 双缓冲乒乓 · load 与 compute 重叠
buf0 · MFMA
读 LDS → 算
buf1 · LOAD
glds 在飞
⇄ 下一轮角色互换：算 buf1、灌 buf0

为什么是「深 K」？KT192 让每个 slab 的计算窗口达到 16 acc × 3 × 32 ≈ 1536 周期， 大于一次加载的延迟（~880 周期）。计算的时间足够长，把取数的延迟整个藏进去 —— 这正是 LDS 深-K 范式打赢纯寄存器版本 +3% 的机理。

06 / 上寄存器

从 LDS 读出一个 MFMA 操作数

计算前，每个 lane 用一条 typed LDS load 取出自己的那份操作数： 24 字节 = 32 个 FP6 值，落进 6 个连续 VGPR（类型 v6i）。 编译器把这 24 字节拆成 ds_read_b128 + ds_read_b64（实测 ISA：92× b128 / 36× ds_read2st64 / 20× b64）。

  • 必须是 6 个连续寄存器 —— MFMA 的操作数约束，否则结果会错
  • 用 typed load（非 inline-asm）让编译器自己插 lgkmcnt，自动与 MFMA 重叠
  • __syncthreads 确保 4 个 wave 灌进 LDS 的数据都到齐了再读
  • 实测约 10.5% bank conflict（非零，PMC：SQ_LDS_BANK_CONFLICT/IDX_ACTIVE）：行距 144 B = 36 dword，与 64-bank LDS 不互质（gcd(36,64)=4）→ lane L 与 L+16 撞同 bank（36×16 ≡ 0 mod 64）。把行距 pad 成奇数 dword（如 148 B=37）可消除（未做；kernel 是延迟受限，收益待测）。
07 / 矩阵核心

一条指令：32×32×64

主角指令 v_mfma_scale_f32_32x32x64_f8f6f4：把 A 的 32×64 块乘 B 的 64×32 块， 累加进 32×32 的 C。32 个周期出一块。这里同时吃进两个 E8M0 scale （A 一个、B 一个），在硬件里完成反量化。

每个 wave 每个 K-slab 做 16 累加器 × 3 个 k64 子片 = 48 条 MFMA。 FP6 的理论峰值是 9227 TFLOPs —— 但要喂得动它，难点全在前面那条数据通路。

08 / 累加

结果就地累加在 AccVGPR

MFMA 的输出直接落在 AccVGPR（CDNA4 的独立累加寄存器堆，与算寄存器分池）。 K 循环跑完全部 43 个 slab，16 个累加器里就是这个 256×256 tile 的最终 F32 结果 —— 中途不落地， 不写回内存。

  • AccVGPR 不计入 occupancy 限制，但 256 个用满 → 强制 occ1
  • A、B 操作数走普通 VGPR；累加器走 AccVGPR：两条路互不挤占
09 / 收尾 · Epilogue

写回 HBM：F32 直发，半精度转换

gfx950 的 global_store 能直接从 AccVGPR 读出写回 HBM —— F32 输出零额外开销，4 个 float4 一个 32×32 块拍出去。

  • F32：AccVGPR → HBM 直达
  • F16 / BF16：先转半精度（v_cvt_pk 打包）再写 —— 生产路径实测不慢甚至略快（省一半写带宽）

10 / 为什么是 18%

瓶颈：occ1 单 wave 藏不住的延迟尾

这个 kernel 是延迟受限，不是算力或带宽受限。 深-K 双缓冲把平均加载延迟藏住了，但藏不住那 9% 打到 HBM 的 L2-miss 尾：

单 wave 的 MFMA 窗口 vs 加载延迟
MFMA 窗口 ~1536 cyc（藏住均值）
L2-miss ~880 cyc 尾 → 捅破窗口
计算窗口 L2 命中 ~150cyc L2 miss ~880cyc（暴露）

occ1 意味着每个 SIMD 只有一个 wave —— 它一旦等数据，没有别的 wave 顶上去，延迟就暴露了。 要消除它，要么加 occupancy（但会砍掉算/载比），要么解耦取数与计算（warp specialization）—— 都被 CDNA4 的结构性约束堵死了。

那些撞过的墙

18% 不是没尽力，而是已知的大杠杆都试过并量化证伪了。每一条都有同会话基线对比 + 反汇编佐证。

Warp specialization

1 生产者 + 4 消费者 wave。机器跑通(6/6 正确)，但 HIP 统一寄存器分配把 consumer 锁死在 8 acc → 等强度输对称双缓冲 −29%。

更高 occupancy

occ2 需 ≤128 AccVGPR = 8 acc，算/载比腰斩。occ2 8-acc « occ1 16-acc。

裸计数 manual vmcnt

想用相对 vmcnt 把 prefetch 留在飞 → 无效。编译器仍在每个 ds_read 前强插 vmcnt(0)（asm: 10× vs 我的 2×）。

调度交错 (sched_group_barrier)

把 load 穿插进 MFMA → 编译器每个小 VMEM 组后 drain，摧毁 overlap。最差 −88%。

A 合并 / LDS 中转

occ1 下多一跳全暴露，−18~32%。876cyc 是延迟暴露，不是「非合并」本身。

CK 的 16×16×128 MFMA

FLOPs/指令减半、操作数带宽/FLOP 翻倍，密度错。坚持 32×32×64。

净结论

1671 TFLOPs（~18% 峰值，支持 F32/F16/BF16）是「occ1 + 大寄存器 tile + 每 K 从 global 重读」这个范式在 gfx950 上的实用天花板。 再上台阶需要的不是调参，而是硬件特性（per-wave 寄存器重分配 / TMA）或一个目前看不到的编译器逃逸口。
