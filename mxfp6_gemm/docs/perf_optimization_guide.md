## 1. 硬件模型:只需要记住 6 个数

GEMM 调优本质是"把数据喂给矩阵计算单元"的艺术。芯片只有这么几个关键参数:

| # | 参数 | 数值 | 一句话含义 |
|---|---|---|---|
| 1 | 计算单元 | 256 CU × 4 SIMD | 共 1024 个矩阵计算引擎,每个引擎一次跑一条 MFMA |
| 2 | MFMA 算力 | 4096 FLOP/cyc/SIMD | 一个 SIMD 每周期能做 4096 次浮点运算(见下推导) |
| 3 | 时钟 | ~2.2 GHz(功耗墙下实测 ~2.0) | 每秒 22 亿周期 |
| 4 | HBM 带宽 | ~8 TB/s | 从显存搬数据的水管粗细 |
| 5 | HBM 延迟 | ~800–1000 cyc(估算†) | 从显存取一个数,要等近千个周期才到货 |
| 6 | 片上存储 | VGPR 512/wave · LDS 160 KB/CU | 寄存器和共享内存的容量 |

> **† 关于这个延迟数字(重要,别当精确值):** 本文用 ~880cyc 作 HBM round-trip 的**数量级估算**,
> 它不是直接实测的硬数。ATT/RCV trace 里没有"round-trip"这个单一字段——延迟体现在两处**可实测**的地方:
> ① **发射 stall**:一条 `global_load` 抢不到发射槽干等,实测 ~22 cyc/load(占总 stall 12.9%);
> ② **数据等待**:下游 `s_waitcnt vmcnt(N)` 等数据没回来,实测热点 ~460–500 cyc/hit(占总 stall ~56%)。
> 二者**相加**才是一条 load 的真实代价。由 `round-trip ≈ 计算窗口 + 残余暴露等待` 反推
> (8-acc 窗口 768 + 残余暴露 ~200–500),round-trip 落在 ~970–1270cyc,故 ~880–1000 作数量级**够用**,
> 但下文凡用到 880 处,理解为"近千周期、且不含发射 stall"。结论(窗口要盖过延迟)对延迟取 800 或 1100 都成立。

**峰值算力推导**(把这些数串起来):

一条 `v_mfma_f32_32x32x64` 指令计算 `C[32×32] += A[32×64] × B[64×32]`:
```
乘加次数 (MAC) = 32 × 32 × 64 = 65536
浮点运算 (FLOP) = 2 × MAC = 131072      (一次乘加 = 1 乘 + 1 加 = 2 FLOP)
耗时 = 32 cycles
=> 单 SIMD 算力 = 131072 FLOP / 32 cyc = 4096 FLOP/cyc      ← 这就是表里的 #2
```
全芯片峰值:
```
峰值 = 256 CU × 4 SIMD × 4096 FLOP/cyc × 2.2×10⁹ cyc/s
     = 9.227×10¹⁵ FLOP/s
     = 9227 TFLOPs                                          ← 成绩单里的 100%
```

> **关键直觉**:矩阵单元每 32 周期就能吞下一条 MFMA。32 周期非常短(≈15 纳秒)。
> 而从显存取数要 880 周期。**算得快、取得慢 —— 这就是 GEMM 优化的全部矛盾。**

## 2. 核心概念:算术强度 (Arithmetic Intensity, AI)

### 2.1 定义

> **算术强度 = 每从内存搬 1 字节数据,能做多少次浮点运算。** 单位:FLOP/byte。

```
AI = 总浮点运算量 / 总搬运字节数
```

AI 高 = "搬一次数据能算很久" = 划算;AI 低 = "刚搬来就用完了,又得去搬" = 被内存拖死。
**整个 GEMM 优化的目标,就是把 AI 拉高到内存喂得起的程度。**

### 2.2 为什么 GEMM 天生适合拉高 AI

算一个 M×N 输出、K 维归约的 GEMM tile:
```
计算量   = 2 × M × N × K              FLOP   (每个输出点要 K 次乘加 = 2K FLOP)
搬运量   = (M×K + K×N) × bytes_per_elem   bytes  (搬进 A 块和 B 块各一次)
```
MXFP6 每个元素 6 bit = **0.75 字节**(块 scale E8M0 每 32 元素 1 字节,摊薄后 +0.03,忽略)。

代入:
```
        2 M N K
AI = ─────────────────────
     0.75 K (M + N)

   =  2 / 0.75  ×  M N / (M + N)

   =  2.667  ×  M·N / (M + N)        ★ GEMM 算术强度主公式
```

**注意:K 被约掉了!** AI 只取决于 tile 的 M、N 形状,跟 K 多深无关。
(直觉:K 越深,计算和搬运同比例增加,比值不变。)

### 2.3 "周长 / 面积" 直觉 —— 为什么 tile 要大、要方

把 `M·N/(M+N)` 看成 **面积 / 半周长**。要它大:

**① tile 越大越好(big tile):** 取方形 M=N=T:
```
AI = 2.667 × T²/(2T) = 1.333 × T
```
👉 **AI 与 tile 边长成正比。tile 翻倍,AI 翻倍。**

| tile 边长 T | AI (FLOP/byte) |
|---|---|
| 64  | 85  |
| 128 | 171 |
| 256 | 341 |
| 512 | 683 |

**② 同样面积,方形比瘦长好:** 固定面积 M·N = S,
```
M + N 在 M=N 时最小(均值不等式)→ 分母最小 → AI 最大
```
例:面积 = 128×512 = 65536 的两种切法:
```
方一点 256×256:  AI = 2.667 × 65536/512 = 341
瘦长 128×512:    AI = 2.667 × 65536/640 = 273      ← 低 20%
```
👉 这就是 memory `mxfp6_wave_shape`("方 tile 免费 +4~6%")的来历:**周长/面积 = 算术强度的倒数**,方形周长最短。

> **小结公式(背下来):** `AI ≈ 1.333 × tile边长`(方形)。要快 → tile 要大要方。

<a name="3"></a>
## 3. 第一道关:带宽够不够?(Roofline 屋顶线)

有了 AI,先做一个粗判断:**这个 AI 下,是算力先到顶,还是带宽先到顶?**

### 3.1 屋顶线脊点

```
脊点 AI* = 峰值算力 / 内存带宽
         = 9.227×10¹⁵ FLOP/s / 8×10¹² byte/s
         = 1153 FLOP/byte
```
含义:**对 HBM 的 AI ≥ 1153 → 算力先到顶(compute-bound,理想区);< 1153 → 带宽先到顶(memory-bound)。**
⚠️ 注意脊点要拿"**对 HBM 的 AI**"来比 —— 而"对 HBM 的 AI"取决于**重用假设**,不是一个固定值。

### 3.2 关键:AI 算多少,取决于"tile 之间重不重用"——两个极端

第 2 节那个 `AI=341` 是**单个 tile 自己**的算/载比(它从下一级存储读多少、算多少)。但 roofline 要的是**整个问题对 HBM** 的比值。同一个 8192³ 问题,两种极端假设给出截然相反的结论:

**极端 A — 完全不重用**(每个 tile 各自从 HBM 重读自己的 A 行条 + B 列条):
```
8192³ 有 (8192/256)² = 1024 个 tile,每个读 A条(256×8192×0.75=1.5MB)+ B条(1.5MB)= 3MB
HBM 总读 = 1024 × 3MB ≈ 3.07 GB
AI = 2×8192³ FLOP / 3.07GB = 1.10e12 / 3.07e9 ≈ 358   (≈ 第2节的 tile AI 341)
358 < 1153 → 看着像【带宽瓶颈】,上限 358×8TB/s ≈ 2864 TFLOPs
```

**极端 B — 完美重用**(整个 8192³,每个输入元素从 HBM 只读一次,这才是"按 8192×8192 算"):
```
HBM 总搬 = A + B + 输出D(FP16)
         = 8192²×0.75 + 8192²×0.75 + 8192²×2
         = 50.3MB + 50.3MB + 134MB ≈ 235 MB
AI = 1.10e12 FLOP / 235MB = 1.10e12 / 2.35e8 ≈ 4680 FLOP/byte
4680 ≫ 1153 → 妥妥【算力瓶颈】
```

**同一个问题,no-reuse 算出 358(带宽墙),perfect-reuse 算出 4680(算力墙),差 13 倍。** 真实落在两者之间,由**L2 重用率**决定 —— 这正是上一个问题"为什么不按 8192×8192 算"的答案:**两种都要算,它们是上下界;落点看 L2。**

### 3.3 实测落在算力侧:L2 命中 91%

profile 实测(memory `mxfp6_l2_sq_measurement`):**L2 命中率 91%,HBM 实际只跑 ~10% 带宽。**
- B 矩阵被很多 WG 共享:一个 WG 把 B 的一段拉进 L2,相邻 WG 再读就走 L2(~150cyc)不碰 HBM。
- 91% 命中 ⟹ 实际 HBM 流量 ≈ no-reuse 的 ~9% ≈ 3.07GB×0.09 ≈ 280MB ≈ **贴近极端 B 的 235MB** → 落在**算力瓶颈侧**,与"HBM 只用 10% 带宽"自洽。

> **结论:把问题按 8192³ 整体算(每输入读一次)AI≈4680 ≫ 脊点,本来就该是算力侧;
> 341 是"tile 各读各的"悲观下界。L2 把我们从下界拉到了接近上界 → 带宽不是墙。那墙是什么?——延迟,下一节。**
> 这也解释了 L2 swizzle(让相邻 WG 共享 B 留 L2 热)为什么是真杠杆——它就是在往"完美重用"那端靠。

<a name="4"></a>
## 4. 真正的墙:延迟,不是带宽(延迟藏匿模型)

带宽是"水管多粗",延迟是"水从开闸到流出要多久"。GEMM 在低占用下,死在**延迟**。

### 4.1 问题:计算 32 周期,取数 880 周期

矩阵单元每 32 周期消化一条 MFMA。但它要的数据从 HBM 取要 880 周期。
如果**取一条、等一条**,那 850 周期矩阵单元在干等 → 利用率只有 32/880 ≈ 3.6%。灾难。

### 4.2 解法:预取(prefetch)+ 把延迟藏在计算后面

经典流水线手法:**在用第 t 块数据计算的同时,提前把第 t+1 块取回来**(双缓冲)。
只要"算第 t 块的时间" ≥ "取第 t+1 块的延迟",取数延迟就被**完全藏住**,矩阵单元不停。

```
要藏住延迟的条件:

   计算窗口 (compute window)  ≥  加载延迟 (load latency)
```

### 4.3 计算窗口公式(本文最重要的公式)

一个 wave 处理一个 K-tile(深度 KT)时,它做多少 MFMA?
- 每个 wave 持有 `acc` 个 32×32 累加器(=输出小块数);
- 每个 MFMA 吃掉 64 层 K → 一个 KT 深度要 `KT/64` 轮;
- 所以总 MFMA 数 = `acc × (KT/64)`,每条 32 周期:

```
计算窗口 W = acc × (KT / 64) × 32   [cycles]      ★ 延迟藏匿主公式
```

**藏住延迟的条件就变成:**
```
acc × (KT/64) × 32  ≥  880          (HBM 延迟)
```

### 4.4 用真实数据验证这个公式(它真的对)

| 配置 | acc | KT | 窗口 W = acc×(KT/64)×32 | ≥ 880? | 实测结果 |
|---|---|---|---|---|---|
| 8192³ 主力 | 16 | 192 | 16×3×32 = **1536** | ✅ 远超 | 藏住,2230 TFLOPs |
| 2048×4096 | 8 | 192 | 8×3×32 = **768** | ❌ 不够 | B 延迟暴露,1724 |
| KT256 单缓冲 | 16 | 256 | (丢双缓冲) | — | 1224(差) |

> 🎯 公式算出的 1536 cyc 与 profile 实测的窗口完全吻合(memory `mxfp6_lds_paradigm`)。
> 而 8-acc 的 768 < 880 **精确解释了 2048×4096 为什么 B 延迟藏不住**(profile 实测 56% 时间在等 VMEM)。

### 4.5 怎么把窗口 W 做大?三个旋钮

`W = acc × (KT/64) × 32`,要做大有三条路:
1. **acc 调大** = 大寄存器 tile(第 5 节)—— 代价:吃 VGPR,压 occupancy;
2. **KT 调深** = 深 K 暂存(第 6 节)—— 代价:吃 LDS;
3. **occupancy 调高** = 多个 wave 的窗口叠加(第 8 节)—— 代价:每 wave 的 acc 必须变小。

后面逐个讲。先记住:**它们都是为了让计算窗口盖过那 880 周期的取数延迟。**

<a name="5"></a>
## 5. 杠杆一:大寄存器 tile

### 5.1 它同时干了两件好事

把 `W = acc × (KT/64) × 32` 和 `AI ≈ 1.333 × 边长` 放一起看:
**acc 调大(更大的 per-wave tile)同时拉高 AI(更划算)和拉大窗口 W(更能藏延迟)。** 一石二鸟。这是本项目的头号杠杆(memory `mxfp6_big_tile`:766→1375 就靠它)。

### 5.2 代价:VGPR 预算

每个 32×32 的 f32 累加器,平摊到 64 个 lane,每 lane 存 `32×32/64 = 16` 个 float = **16 个 VGPR**。
```
AccVGPR = acc × 16
16 acc → 256 AccVGPR
 8 acc → 128 AccVGPR
```
还要加上算子寄存器(A/B 操作数、地址、scale 等)≈ 250 个 Arch VGPR。

### 5.3 occupancy 闸门

gfx950 的 VGPR 是 **arch+acc 合并的 512 池**(memory `gfx950_vgpr_merged_pool`)。能同时驻留几个 wave:
```
occupancy(VGPR) = floor( 512 / 每wave总VGPR )      (再被 LDS、8 上限夹)
```
16-acc 例子:
```
总 VGPR = 256 (acc) + ~251 (arch) = 507
occupancy = floor(512 / 507) = 1                    ← 大 tile ⇒ 必然 occ1
```
**这不是 bug,是设计:** 我们故意用满寄存器换最大的 acc。第 8 节解释为什么 occ1 反而对。

> **小结:** 大 tile 是双赢杠杆(↑AI ↑窗口),代价是把 occupancy 压到 1。值不值?看第 8 节。

<a name="6"></a>
## 6. 杠杆二:深 K(LDS 暂存)

### 6.1 动机

`W = acc × (KT/64) × 32`。acc 被 VGPR 卡死在 16(再大就 spill)。**还想把窗口做大,就只能调 KT。**

### 6.2 为什么深 K 必须用 LDS,不能用寄存器

要把更深的 K(比如 KT=192,即 3 轮 64)的 A/B 操作数都备齐,需要的寄存器:
```
深 K 操作数 = acc相关 + KT 深的 A、B 片段
```
寄存器只有 512,深 K 片段放不下 → **spill(溢出到显存)→ 反而更慢。**
而 **LDS 有 160 KB**,放得下深 K 的暂存。这就是"深 K 用 LDS"的根本原因。

数据通路:`global_load_lds`(异步,零 VGPR)→ `__syncthreads` → `ds_read` 出操作数 → MFMA。

### 6.3 LDS 预算公式(双缓冲)

深 K 双缓冲(一边算、一边预取下一块)要存 2 份 tile:
```
LDS = 2 × (M_T + N_T) × (KT × 0.75)   bytes      (纯-LDS:A、B 都进)
LDS = 2 ×  M_T        × (KT × 0.75)   bytes      (hybrid:只有 A 进,见第 7/9 节)
```
例(256×256,KT192):
```
纯-LDS(A、B 都进):  2 × (256+256) × (192×0.75) = 2 × 512 × 144 = 147456 B = 144 KB ≤ 160 ✅
生产 hybrid(只 A 进): 2 ×   256    × (192×0.75) = 2 × 256 × 144 =  73728 B =  72 KB     ← 实际跑的
```
⚠️ **生产 8192³ 主力是 hybrid,实测 LDS = 72 KB(只有 A 暂存,B 直读不进 LDS,见 §7/§9)。**
纯-LDS 的 144 KB 是历史上深-K 范式的数,现在不用了——但它定了 KT 的上限:KT 再大(256)纯-LDS 要
192KB > 160KB 装不下(hybrid 则 96KB 还能装,但 KT256 另有问题见 §6.4);且 scale 一次最多 dwordx4 也限制 KT≤256。

### 6.4 为什么是 KT=192 这个甜点

(LDS 列分两套:纯-LDS / 生产 hybrid。hybrid 只 A 进 → 约一半。)
| KT | 窗口 W(16-acc) | LDS 纯-LDS | LDS hybrid | 实测 |
|---|---|---|---|---|
| 128 | 1024 | 96 KB | 48 KB | 偏小,1465 |
| **192** | **1536** | 144 KB | **72 KB(生产)** | **最优(hybrid 2230)** |
| 256 | 2048(双缓冲丢重叠/砍 8-acc) | 192 KB✗ | 96 KB | 1224 |

KT192 是"窗口已盖过近千周期延迟 + LDS 还塞得下双缓冲"的交点。注意纯-LDS 在 KT256 就爆 160KB,
hybrid 不爆(96KB)——但 KT256 仍输,是因为双缓冲配不上 16-acc / 单缓冲丢重叠,不是 LDS 不够。
👉 我在当前 hybrid kernel 上重扫确认 KT192 仍是峰值(memory `mxfp6_hybrid_tmpl_audit`)。

> **小结:** 深 K 是"不动 occupancy 就把窗口做大"的杠杆,上限由 LDS(160KB)和 scale 宽度(KT≤256)夹住。

<a name="7"></a>
## 7. 杠杆三:MFMA 指令选择(32×32×64 vs 16×16×128)

同样算 FP6,硬件提供两条 MFMA:
| 指令 | 一条算什么 | FLOP/条 | 周期 | FLOP/cyc |
|---|---|---|---|---|
| `32×32×64` (本项目用) | C[32×32]+=A[32×64]·B[64×32] | 131072 | 32 | 4096 |
| `16×16×128` (CK 用) | C[16×16]+=A[16×128]·B[128×16] | 65536 | 16 | 4096 |

**峰值算力一样(都 4096 FLOP/cyc)。** 但产生同样大小的输出,16×16×128 需要:
- **2 倍的指令条数**(输出小一半,要发两条才顶一条);
- **2 倍的操作数带宽 / FLOP**(K=128 比 K=64 要多搬一倍操作数才喂一条)。

```
操作数字节 / FLOP:
  32×32×64 : 读 (32×64 + 64×32)×0.75 = 3072 byte 产 131072 FLOP → 0.0234 byte/FLOP
  16×16×128: 读 (16×128 + 128×16)×0.75 = 3072 byte 产  65536 FLOP → 0.0469 byte/FLOP  ← 翻倍
```
👉 在延迟/操作数带宽受限的世界里,**16×16×128 纯属自找麻烦**。这是 CK 的 mxfp6 比我们慢约 2× 的部分原因(memory `reference_gfx950_mfma_f8f6f4_cycles`)。

> **小结:** 同峰值下,选"输出大、操作数省"的 32×32×64。密度对了是免费的胜利。

<a name="8"></a>
## 8. 杠杆四:occupancy —— 为什么我们故意只要 1

### 8.1 occupancy 是什么

一个 SIMD 上同时驻留几个 wave。多 wave 的好处:**A wave 等数据时,B wave 顶上算 → 用并发藏延迟。** 这是 GPU 的传统藏延迟方式(occupancy hiding)。

它在延迟模型里相当于把窗口"叠加":
```
有效窗口 ≈ occupancy × 单wave窗口
```

### 8.2 那为什么我们反而要 occ1?——因为它和 acc 抢同一份寄存器

occupancy 和大 tile 抢的是同一个 512 VGPR 池,**二者不可兼得**:
```
occ2 要求每 wave 总 VGPR ≤ 512/2 = 256
       → AccVGPR ≤ 256 - 250(arch) ≈ 还剩不够 → acc 必须砍到 ≤ 8
```
于是两条路线:
| 路线 | acc | occ | AI | 单wave窗口 | 有效窗口 |
|---|---|---|---|---|---|
| **occ1 大 tile**(我们) | 16 | 1 | 高(341) | 1536 | 1536 |
| occ2 小 tile | 8 | 2 | 低(~227) | 768 | 768×2=1536 |

有效窗口一样(都能藏延迟),但 **occ1 的 AI 高一倍** → occ1 赢。
实测:occ2 路线 −14~30%(memory `mxfp6_occ2_outcome`)。**所以我们故意把 occupancy 压到 1,把寄存器全给 acc 换 AI。**

> **小结:** occupancy 不是越高越好。当芯片**不缺并发、缺的是算/载比(AI)**时,
> 反其道而行——occ1 + 巨型 tile——才是对的。这是本项目最反直觉的一课。

### 8.3 一个关键前提:占满 CU 也能靠 occ1

有人会问:occ1 不是浪费并发吗?不会 —— 只要 **workgroup 总数 ≥ CU 数(256)**,每个 CU 至少有一个 WG 在跑,机器就喂满了。占满靠的是 **WG 数量**,不是每 CU 的 wave 数量。
(这个前提在第 10 节的 2048×4096 会变成关键:当 WG 数恰好 = 256 时,occ2 一点忙都帮不上,因为没有第二个 WG 来填那个槽。)

<a name="9"></a>
## 9. 综合:一个 tile 配置要同时满足的所有约束

把前面所有公式串成一张"约束网"。选 `(M_T, N_T, KT, acc, occ)` 时必须同时满足:

```
① 藏住延迟:   acc × (KT/64) × 32  ≥  880           (延迟模型, §4)
② VGPR 预算:  acc×16 + arch       ≤  512 × occ_倒数  → 大 acc ⇒ occ1   (§5,§8)
③ LDS 预算:   2 × (用LDS的边) × KT×0.75  ≤  160 KB                    (§6)
④ 填满机器:   (M/M_T) × (N/N_T)   ≥  256 (CU数)      (§8.3)
⑤ scale 宽度: KT/64 ≤ 4  即 KT ≤ 256                                  (§6)
⑥ 高 AI:      M_T·N_T/(M_T+N_T) 尽量大,且 M_T≈N_T(方形)            (§2)
```

**本项目最终选择(8192³ 主力)是这张网的最优解:**
```
M_T=N_T=256, KT=192, acc=16(2×2 waves 各 4×4), occ=1
  ① 16×3×32 = 1536 ≥ 880          ✅ 延迟藏住
  ② 256+251 = 507 ≤ 512           ✅ occ1 卡满
  ③ hybrid 只 A 进 LDS:2×256×144 = 72KB ≤ 160  ✅
  ④ (8192/256)² = 1024 ≥ 256      ✅ 填满(还 4 倍冗余)
  ⑤ 192/64 = 3 ≤ 4                ✅
  ⑥ 256×256 方形,AI=341          ✅ 最大
→ 2230 TFLOPs (24% 峰值)
```

> **hybrid 范式补充**:为什么 A 走 LDS、B 直读寄存器?
> profile 发现"B 经 LDS 的 ds-read"是一堵 40% 的墙(Era-2)。改成 B 从 HBM 直读进寄存器
> (靠 L2 命中,§3.3)绕过这堵墙,同时 A 留 LDS 复用。这是 §6 纯-LDS 的改良版,
> 在大 tile 上 +16~24%(memory `mxfp6_hybrid_b_direct`)。**但它依赖 §4 的窗口够大才藏得住 B 的直读延迟 —— 见下节反例。**

<a name="10"></a>
## 10. 案例研究:2048×4096 为什么卡在 18.7%

现在用整套模型解释成绩单里那个"差生"。

### 10.1 第一步:M=2048 太小,放不下大 tile 还填满机器

用 256×256 大 tile 时:
```
WG 数 = (2048/256) × (4096/256) = 8 × 16 = 128 < 256 (CU)    ✗ 约束④破了!
```
只有 128 个 WG → 一半 CU 闲置 → 直接腰斩。**必须把 tile 砍小来造出更多 WG。**

### 10.2 第二步:填满机器 ⟺ 8-acc,这是面积数学锁死的

要填满 256 个 CU,就要 ≥256 个 tile。固定 M=2048, N=4096:
```
需要 tile 数 = 256
每 tile 面积 = (2048 × 4096) / 256 = 32768 元素
每 wave 的 acc = tile面积 / (32×32 每acc) / (4 waves)
             = 32768 / 1024 / 4 = 8                      ★ 恰好 8-acc
```
👉 **任何"刚好填满 CU"的 tile,在这个形状上都恰好是 8-acc。这是除法的必然,不是没调好。**
(想要 16-acc 就得 65536/tile → 只剩 128 WG → 回到第一步的腰斩。二选一,锁死。)

### 10.3 第三步:8-acc ⇒ 窗口 768 < 880 ⇒ 延迟藏不住

代入延迟公式(§4.3):
```
窗口 W = 8 × (192/64) × 32 = 768 cyc  <  880 cyc (HBM 延迟)     ✗ 约束①破了!
```
窗口盖不住延迟 → 取数延迟暴露。**profile 实锤:56% 的时间在等 VMEM(B 直读)**,而 A-LDS 因为是异步预取、窗口对它够用,等待 = 0%。

### 10.4 第四步:为什么所有补救都无效(都用实验验证过)

| 想法 | 为什么直觉上可能行 | 实测 | 为什么失败(回到公式) |
|---|---|---|---|
| occ2 | 用并发补窗口 | 中性 | 约束④:WG 恰好=256,没有第二个 WG 填 occ2 槽(§8.3) |
| 改 M_PW=4 让窗口翻倍 | §4 窗口 ∝ M_PW | −7~12% | 8-acc 下 M_PW=4 ⇒ N_PW=2 ⇒ B 预取流水瘫痪(N_PW 比 M_PW 重要) |
| 纯-LDS(B 也异步预取) | A 那样就免费了 | −28~35% | 窗口 768 太小,连 B 的 ds-read 墙都藏不住,比直读更糟 |
| split-K | 造更多 WG 开 occ2 | 证伪 | reduce 开销 + 短 K 固定开销吃掉收益 |

### 10.5 结论:18.7% 是这个形状的物理上限

```
M=2048 → 填满CU ⟺ 8-acc ⟺ 窗口768 < 880 ⟺ B延迟暴露 ⟺ ~18.7%
```
每一步都是上面约束网的必然。理论上若 B 延迟能完全藏住,会逼近 8192³ 的 2230;
差距 `1724 → 2230` 就是那段藏不住的 B 延迟,而它被 **8-acc(面积锁死)+ occ1(寄存器锁死)** 双重钉死,
在 gfx950 上**无结构性解法**。这不是代码问题,是 M=2048 太小撞上了硬件的延迟/容量极限。

## 11. 一页速查表

**三个主公式:**
```
算术强度   AI = 2.667 × M_T·N_T/(M_T+N_T) ≈ 1.333 × 边长(方形)     越大越好
计算窗口   W  = acc × (KT/64) × 32  cyc                            要 ≥ 880(藏延迟)
峰值算力   = 256×4×4096×clock = 9227 TFLOPs
```

**调优时按顺序问自己:**
1. **填满机器了吗?** `(M/M_T)(N/N_T) ≥ 256`?不够 → 缩小 tile 造 WG(代价:AI 降、acc 降)。
2. **AI 够高吗?** tile 大、方 → AI 大。优先大方 tile。
3. **窗口盖住延迟了吗?** `acc×(KT/64)×32 ≥ 880`?不够 → 加 acc(大 tile)或加 KT(深 K)。
4. **寄存器/LDS 装得下吗?** `acc×16+arch ≤ 512`、`2·边·KT·0.75 ≤ 160KB`。
5. **occupancy 该高还是低?** 不缺 WG(填满了)→ 压 occ1 换最大 acc/AI;缺并发才提 occ。
6. **MFMA 选对了吗?** 选输出大、操作数省的(32×32×64)。

**最反直觉的三条经验:**
- ⚡ **occupancy 不是越高越好** —— 占满 CU 后,occ1 + 巨型 tile(高 AI)打赢 occ2 小 tile。
- ⚡ **瓶颈通常是延迟不是带宽** —— L2 把带宽问题救掉了,剩下的是 880 周期的取数延迟。
- ⚡ **小矩阵的天花板是数学锁死的** —— 填满 CU 和大 acc 二选一,M 太小就注定低占峰值,非调参可解。

**判定法(屡试不爽):**
> 藏延迟没用 → 不是延迟瓶颈;砍访存量没用 → 不是带宽瓶颈;加指令就更慢 → 是发射/计算瓶颈。
> 改之前先 profile 或隔离实验,改之后必对比**同会话**基线(热漂移!跨会话不可比,且必须交错 A/B)。
