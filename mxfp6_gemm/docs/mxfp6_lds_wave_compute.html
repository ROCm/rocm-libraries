循环层级 · 从 grid 到 MFMA

数据通路：buffer_load_dwordx4 (HBM→LDS, 零VGPR) → __syncthreads → ds_read 取操作数 → 32×32×64 MFMA。深 K（KT=192=3×k64）把每次全局加载所对应的 MFMA 计算窗口放大到 远超 ~880cyc 的加载延迟，这是该范式能赢 V17 register-direct 的核心机制。点击每层展开四轴分解。

L3
K-TILE
深-K 双缓冲流水 (RDB)for(kt; kt+1<43; kt+=2) · 每趟 2 tile · prefetch(kt+1) 与 compute(kt) 重叠
21趟 ×2 +1尾▸
① 职责

沿 K 走 43 个深 tile（每 tile = 192 = 3×k64）

乒乓两个 LDS buffer：buf0 偶 tile / buf1 奇 tile。RDB（重排双缓冲）：每个 barrier 之后才发 prefetch — 一个 barrier 同时担保 RAW（要读的 buffer 已填好）和 WAR（要复用的 buffer 已读完），对所有形状结构性正确。

21 趟主循环算 42 tile（hit=2688=128×21 实测），+1 odd-tail 算第 43 tile。

② 指令 / 趟

2 barrier · 2 prefetch · 2 compute

  • 2× s_barrier（每 tile 一个）
  • 2× prefetch = 36 buffer_load + 4 global_load_dwordx3
  • 2× compute() = 96 MFMA

⚠️ 稳态热循环 无 vmcnt：buffer_load_lds 是 M0-隐式 asm，编译器看不到 load→ds_read 依赖。RAW 靠深-K 时间余量（prefetch 提前一整个 compute 窗口）兜底，bit-exact 已验。

③ 寄存器

scale 双缓冲 + 描述符

sa0/sa1/sb0/sb1 各 [3][1] int（编译期 buffer，无动态索引/spill）；buffer 描述符 V# 在 SGPR；m0 源 VGPR 在搬运时滚动复用 v56–v127。

④ Block

每趟搬运 2× 144B/lane 的 A+B 切片

单 tile LDS 占用：A 36864 + B 36864 = 72KB；双缓冲 144KB。深 K=192 是「装不进寄存器、但能装进 LDS」的甜点深度。

为什么深 K 能赢：occ1 的天花板是「MFMA 窗口(~512cyc) < 加载延迟(~880cyc)」。把 K-tile 做深 → 单次加载对应 48 MFMA 的计算窗口，远超加载延迟，于是延迟被算力盖住 —— 不靠提 occupancy（occ2 已证伪）。
L3a
LOAD
协作搬运 load_tile_lds<ROWS,144,9>每 wave 每 tile：9 issue（A）+ 9 issue（B），每 lane 搬 16B
18load / wave·tile▸
① 职责

HBM→LDS，零 VGPR 直灌

A tile = 256行×9 chunk = 2304 个 16B chunk，/256 thread = 每 lane 9 次。buffer_load_dwordx4 ... offen lds 把数据直接写进 M0 指定的 LDS 地址（不经 VGPR）。chunk 按 m-major/ck-minor 走，匹配 LDS 行主序 LDS[m·144 + ck·16]。

② 指令

每 issue 三件套

  • v_add_u32 算 voffset（描述符里已含 64-bit 基址，故每 load 只需 32-bit 偏移，VALU 减半）
  • s_mov_b32 m0 设 LDS 目标（readfirstlane）
  • buffer_load_dwordx4 ... offen lds

scale 先发：2× global_load_dwordx3 no-wait，抢在 18 个 tile-load 之前进内存队列（否则排在后面被背压）。

③ 寄存器

地址 scratch + scale 落点

9 个预算 chunk 基偏移 v56/58/60…；scale 落 ta[3]/tb[3]→sa/sb；tile 数据本身不占 VGPR（直入 LDS）。

④ Block

填满半个 buffer = 72KB

WG 协作：256 lane × 144B = 36864B = 一个 A tile；B 同。深度 K=192 的 FP6 packed = 144B/row。

无 s_nop（MXFP6_M0_NOP=0）：KT192 下编译器已在 set_m0 与 load 间塞了足够指令，自动越过「SALU 写 M0 → load(LDS=1)」的 1-wait-state hazard。但 buffer_load 的发射/背压仍是第二大 stall 源（实测 8.98M）。

COMPUTE
compute() · 三层嵌套 = 48 MFMA / tilefor sub(3) → for ni(4, N-major) → for mi(4) · b 是贯穿整块的 just-in-time 流
48MFMA / wave·tile▸
① 职责

把一个深 tile 的 192-K 累加进 16 个 acc

sub(3)：tile 的 3 个 64-K 子板，每板一轮 MFMA。
ni(4) 外层：N-major，复用 B 操作数（+1.1%）。
mi(4) 内层：4 个 MFMA 共享同一个 b_cur，变 a[mi]，写 4 个 acc[mi][ni]。

b 走「连续流」：只有 b_cur + b_next 两个 v6i 活着；下一个 b 的 ds_read 在本 ni 的 MFMA 四连发之前发出，让 LDS-read(lgkmcnt) 延迟与 4 个 MFMA 重叠。

② 指令

软件流水的 lgkmcnt 阶梯

  • 48× v_mfma（3 sub × 4 ni × 4 mi）
  • 24× read_op = 12 a-read + 12 b-read，每个 = ds_read_b128(16B)+ds_read_b64(8B)
  • 每四连发前一道 s_waitcnt lgkmcnt(3→2→1→0) 阶梯排空 prefetch 的 b-read
③ 寄存器

活操作数 ~36 VGPR

a[4]×v6i = 24 VGPR（一个 sub 内全活，跨 ni 复用）；b_cur+b_next = 12 VGPR；sav[4]/sbv 标量在 VGPR；目标 16 acc tile 在 AccVGPR。

a[mi] = v[8:13]/[2:7]/[20:25]/[14:19]b = v[32:37]acc = a[0:255]
④ Block

每 MFMA 造 32×32×64 的一刀

单 MFMA = 2·32·32·64 = 262,144 FLOP。48 MFMA/tile/wave = 12.6 MFLOP。每 acc 元素本 tile 吃 3 刀（3 个 k64）。

L5 · 最内 mi 四连发 (一个 ni 的一个 sub)

4 个 MFMA 共享 src0=b_cur(v[32:37]) 与 scale_b(v52)，变 src1=a[mi] 与 scale_a(v46/47/50/51)，分别累加到 4 个 acc tile（同列 ni、4 行 mi）。这是寄存器复用最密的一档：一次 b-read 喂 4 刀 MFMA。

① 职责

收尾不成对/不整除的 K

LDS 布局 · 144 KB 双缓冲

每 WG 动态共享内存 = 2 × (256·144 + 256·144) = 147,456 B。乒乓两个 buffer：compute(buf0) 时 prefetch(buf1) 的 18 个 buffer_load 在飞，反之亦然。深-K=192 让单 buffer 容下 3 个 k64 子板，把计算窗口撑到盖住加载延迟。

停顿热图 · 为什么是 latency-bound

RCV 采样累计 stall（所有采样 wave 求和）。结论与 L2/SQ 实测一致：不是带宽墙（HBM 仅 ~10% 带宽、L2 命中 91%），而是暴露的 LDS-read 延迟 + 预取发射。算力（MFMA）虽是第三大停顿，但那是「操作数没到」的被动等待，非吞吐不足。
