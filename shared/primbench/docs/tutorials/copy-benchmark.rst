======================
Write a copy benchmark
======================

This tutorial walks through a complete Primbench benchmark that measures the throughput of a simple GPU memory-copy kernel. By the end you will understand how to register types, define a benchmark struct, declare throughput metrics, add correctness validation, and compile and run the benchmark. The complete example lives at ``examples/hip/copy_benchmark.cpp`` (HIP) and ``examples/cuda/copy_benchmark.cu`` (CUDA).

Register types
**************

Every C++ type that appears in benchmark results must be registered with ``PRIMBENCH_REGISTER_TYPE`` so that Primbench can produce a human-readable name for it. Place the registrations at file scope, before any benchmark definitions:

.. code-block:: cpp

   PRIMBENCH_REGISTER_TYPE(char, "char")
   PRIMBENCH_REGISTER_TYPE(long long, "long long")

The second argument is the string that appears in JSON and CSV output. You can map ``long long`` to ``"int64_t"`` or ``"i64"`` if you prefer a shorter label. The registered name is retrieved later with ``primbench::name<T>()``.

Define the benchmark struct
***************************

A Primbench benchmark is a class that inherits from ``primbench::benchmark_interface`` and implements two virtual methods: ``meta()`` and ``run()``. Templating the struct on the data type lets you queue multiple specializations from a single definition.

.. note::

   *Source unavailable; see ``examples/hip/copy_benchmark.cpp``, ``examples/cuda/copy_benchmark.cu``, ``primbench.hpp`` for canonical usage.*

The ``meta()`` method returns a ``primbench::json`` object that must contain an ``algo`` key. The ``algo`` value must be identical across all queued specializations so Primbench groups them in one run. Additional keys such as ``type`` distinguish specializations in the output. For more details on ``meta()`` and ``run()``, see :doc:`/reference/api-benchmark-interface`.

Set up device memory and launch parameters
******************************************

Inside ``run()``, the ``state`` object provides the GPU stream and the requested input size. Use ``state.stream`` for all asynchronous operations and ``state.size`` as the byte budget for the benchmark:

.. code-block:: cpp

   const auto& stream = state.stream;
   const auto& bytes  = state.size;

   size_t                 N              = bytes / sizeof(T);
   constexpr unsigned int BlockSize      = 256;
   constexpr unsigned int ItemsPerThread = 4;

   const size_t items_per_block = BlockSize * ItemsPerThread;
   const size_t items = items_per_block * ((N + items_per_block - 1) / items_per_block);

The item count is rounded up to a multiple of ``BlockSize * ItemsPerThread`` so every thread processes a full tile. Using four items per thread amortizes per-thread overhead and helps the compiler emit wider memory transactions.

The default ``state.size`` is 128 MiB (``--size 128MiB``). At that size a ``char`` copy moves 128 million one-byte elements while a ``long long`` copy moves 16 million eight-byte elements — both large enough to saturate memory bandwidth. You can override the size on the command line; see :doc:`Configure benchmark settings </how-to/configure-settings>`.

Progress messages such as ``primbench::log("Allocating device memory")`` print gray text during setup. They help pinpoint slow steps without affecting measurements.

Declare throughput metrics
**************************

Before registering the kernel, tell Primbench how many items are processed and how many bytes are read and written per kernel call:

.. code-block:: cpp

   state.set_items(items);
   state.add_reads<T>(items);
   state.add_writes<T>(items);

Primbench uses these declarations to compute ``items_per_second`` and ``bytes_per_second`` in the output. ``add_reads<T>(items)`` adds ``items * sizeof(T)`` bytes of read traffic; ``add_writes<T>(items)`` does the same for writes. For a copy kernel the total ``bytes_per_item`` equals ``2 * sizeof(T)``. For full documentation of these methods, see :doc:`/reference/api-benchmark-state`.

Add correctness validation
**************************

``state.test()`` registers a lambda that Primbench calls once during warmup to verify the kernel produces correct output. If the check fails, the benchmark exits early instead of reporting invalid throughput numbers:

.. code-block:: cpp

   state.test(
       [&]
       {
           std::vector<T> h_output(3);
           PRIMBENCH_CHECK(
               hipMemcpy(h_output.data(), d_output, 3 * sizeof(T), hipMemcpyDeviceToHost));
           PRIMBENCH_ASSERT(h_output, {0, 1, 2});
       });

If you don't know the expected values yet, pass placeholder values — ``PRIMBENCH_ASSERT`` prints the actual values on failure so you can copy them back into the source. Validation can be disabled at compile time with ``-DPRIMBENCH_NO_TEST``.

Register the kernel lambda
**************************

``state.run()`` accepts a lambda that launches the kernel. Primbench calls this lambda many times, grouping calls into batches and handling all synchronization and timing:

.. code-block:: cpp

   state.run(
       [&] {
           copy_kernel<T, BlockSize, ItemsPerThread>
               <<<grid, block, 0, stream>>>(d_input, d_output);
       });

Primbench doubles the number of kernel calls per batch until each batch takes at least 10 ms of GPU time (``--min-gpu-ms-per-batch``). Batching reduces timing noise because individual kernel launches can complete in microseconds. For more on how noise is managed, see :doc:`/conceptual/noise-reduction`.

Create the executor and queue specializations
*********************************************

In ``main()``, construct a ``primbench::executor`` with the program's command-line arguments, queue each specialization, and call ``run()``:

.. code-block:: cpp

   int main(int argc, char* argv[])
   {
       primbench::executor executor(argc, argv);

       executor.queue<copy_benchmark<char>>();
       executor.queue<copy_benchmark<long long>>();

       executor.run();
   }

The executor parses ``--size``, ``--filter``, and all other command-line options documented in :doc:`Command-line options </reference/cli-options>`.

Compile and run
***************

HIP on Linux
------------

.. code-block:: bash

   hipcc -o copy_benchmark examples/hip/copy_benchmark.cpp -I. -lamd_smi && ./copy_benchmark

HIP on Windows (PowerShell)
---------------------------

.. code-block:: powershell

   hipcc -o copy_benchmark.exe examples/hip/copy_benchmark.cpp -I. -DPRIMBENCH_NO_MONITORING -std=c++17 -g --offload-arch=$(amdgpu-arch) ; ./copy_benchmark.exe

On Windows, AMD SMI is not available, so ``-DPRIMBENCH_NO_MONITORING`` is required.

Examine the output
******************

After the run, Primbench writes ``results.json`` (configurable with ``--json-out``). Below is a shortened excerpt showing one specialization:

.. code-block:: json

   {
       "index": 0,
       "name": "type: char",
       "bytes_per_second": 7.5628e+11,
       "items_per_second": 3.7814e+11,
       "bytes_per_item": 2,
       "items": 134217728,
       "noise_timeout": false,
       "noise_percent": 0.0521193,
       "meta": {
           "algo": "copy",
           "type": "char"
       },
       "calls": {
           "kernel_calls_per_batch": 32,
           "ms_per_batch": 11.3546,
           "batches": 45,
           "kernel_calls": 1440
       }
   }

Key observations:

- ``bytes_per_item`` is 2 for ``char`` (one read byte + one write byte) and 16 for ``long long``.
- ``noise_percent`` is the coefficient of variation across batches. Values well below 1 % indicate stable measurements.
- ``kernel_calls_per_batch`` was auto-tuned so each batch exceeds 10 ms of GPU time.

For a full description of the output schema, see :doc:`/conceptual/output-format`.

Next steps
