# Migrating ck-dsl-provider to embedded MicroPython (Arch A + native comgr)

**Status:** plan (2026-06-01). Prereqs all proven in `spike/` — DSL→IR→HSACO runs in a
frozen, self-contained embed binary with **byte-identical** output to CPython, comgr exposed
as a native module, ck_dsl flow preserved via a `runtime/comgr.py` backend swap.

## Goal & architecture (locked)
Replace the provider's embedded **CPython + pybind11** with embedded **MicroPython**, so the
plugin has **no dependency on a system Python install** (Linux + Windows). It can ship either fully
**self-contained** (ck_dsl frozen into the plugin) or with a **`.py`/`.mpy` tree beside it** — a
build-time toggle (see "Module loading"); the interpreter is embedded in the plugin in all cases.

**Architecture = Arch A with comgr as a native module:**
- MicroPython runs ck_dsl **codegen** (frozen into the plugin, or loaded from an on-disk bundle —
  build-time toggle).
- **comgr stays in C++** (`comgr_compile.c`, links `amd_comgr` / `amd_comgr.dll`; **no `ffi`** → Windows-safe),
  exposed to the interpreter as a native module `comgr` (`modcomgr.c`).
- `ck_dsl/runtime/comgr.py`'s backend swaps ctypes→libamd_comgr for `import comgr` — its public
  interface (`build_hsaco_from_llvm_ir(ir, isa, options) -> (hsaco, ComgrTimings)`) is unchanged, so
  `helpers/compile.py` / `compile_service.compile` are untouched and **still return a HSACO dict**.
- The provider's existing result contract (`compile_service.compile` → HSACO → `HipModule`) is
  preserved; GPU load/launch stays in C++ exactly as today.

## What does NOT change
`CkDslContainer`, `JitCache`, `HipModule`, `runtime/launcher`, the engines/adapters' *logic*, the
plan builder, the SDK plumbing, and the `KernelArtifact` struct + the on-wire result-dict field set
(`hsaco, kernel_name, kind, grid, block, lds_bytes, arg_schema, isa`). The provider keeps getting a
HSACO and launching it.

## What changes (the migration surface)
The pybind/CPython layer is concentrated in `src/python/` + `src/adapters/.../*Payload.cpp` + CMake;
that is what the migration rewrites.

---

## Module loading — build-time distribution toggle (`CKDSL_MICROPYTHON_FROZEN`)
How ck_dsl reaches the interpreter is a **build-time choice**, not fixed to freezing. The same
transformed bundle + the same embedded interpreter support three modes via one CMake flag; pick per
build/platform. The interpreter is embedded **in the plugin in all modes** — none depend on a system
Python install; the modes differ only in *where ck_dsl's code lives*.

| Mode (`CKDSL_MICROPYTHON_FROZEN`) | Ships | Self-contained | Iterate ck_dsl | Source visible |
|---|---|---|---|---|
| **`ON` — frozen** (default release) | one `.so`/`.dll` | ✅ | refreeze + relink | no |
| **`OFF` — `.py` on disk** (dev; optional release) | plugin + `.py` tree | ✗ | **edit + rerun, no relink** | yes |
| **`MPY` — `.mpy` on disk** (optional) | plugin + `.mpy` tree | ✗ | re-`mpy-cross` (no relink) | no |

- **Dev loop:** build with `OFF` → edit a ck_dsl `.py` (or re-run the fast `build_bundle.py`) and rerun;
  no `mpy-cross`, no `frozen_content.c`, no relink. (For pure ck_dsl-logic iteration the unix-port
  spike `spike/mp1/run_conv.py` is faster still — byte-identical, zero C.)
- **Windows:** all three modes work. `.py`/`.mpy`-on-disk uses MicroPython's POSIX file reader, which
  the **MicroPython Windows port already ships** ("based on the Unix port") — it needs the port's small
  Windows helpers (`ports/windows/fmode.c` for the CRT text/binary-mode gotcha, `realpath.c`) carried
  into the embed build. No `ffi`, so no Windows blocker in any mode.
- **Filesystem modes need:** (a) the real reader — `extmod/vfs_posix_file.c` + a real `mp_import_stat`
  / `mp_lexer_new_from_file` / `open` (replacing the frozen-mode stubs), and (b) runtime resolution of
  the on-disk bundle dir relative to the loaded plugin (`GetModuleFileName` on Windows / `dladdr` on
  Linux), prepended to `sys.path`.

The phases below build the **frozen** path first (the clean release artifact), then add the toggle.

## Phase A — ck_dsl bundle (Python side; mostly proven in spike)
Reuse `spike/mp1/build_bundle.py` + `spike/mp2/build_frozen.py`. Finalize:
1. **Source transforms** (the ck_dsl changes; automate now, land upstream with CK later): field()-ify
   every dataclass field; PEP-448 display unpacking → concat; `open(x)→open(str(x))`;
   `os.environ.get→os.getenv`; `object.__setattr__→setattr`. **Add:** make `import subprocess` /
   `import tempfile` lazy in `helpers/compile.py` (only `compile_kernel_via_hipcc` uses them; the
   comgr path never does — so no shim needed for them).
2. **Native-backed `runtime/comgr.py`** (already generated by build_frozen): `build_hsaco_from_llvm_ir`
   → `import comgr; comgr.build_hsaco(...)`; drop the `hip_module` import.
3. **Embed `arch_specs.json`** as `_arch_specs_embedded.py`; patch `arch/target.py` off
   `__file__`/`open`/`json` (done in build_frozen). Do this in **all** modes so one bundle works
   frozen *and* on-disk and `json` is never needed (frozen modules have no `__file__`; embedding
   sidesteps it everywhere).
4. **Closure**: capture the real provider entry — `ck_dsl_provider.compile_service.{compile,
   compile_smoke,is_applicable}` — not just `lower_kernel_to_llvm`. This pulls `helpers/compile.py`
   (needs the lazy-subprocess change) + a `time` shim (`compile_kernel` uses `time.perf_counter()`;
   tiny shim returning a float).
5. **Shims** (bundled — frozen or shipped on disk per mode): `dataclasses` (custom, order-preserving),
   `typing`, `functools`, `pathlib`, `__future__`, `itertools`, `os` (getenv), `time` (perf_counter).
   Built-in in the embed config: `re`. `json` not needed (specs embedded, see A.3).
6. **Decision:** land the transforms as real CK upstream edits (preferred, since the team owns ck_dsl)
   vs. keep `build_bundle.py` as a packaging step. Either way the *frozen artifact* is generated at
   provider-build time.

## Phase B — provider C++ embedding layer (`src/python/` + adapters)
Replace pybind/CPython with the `mp_*` API (patterns proven in `spike/mp2/{main.c,embed_port.c,
modcomgr.c,comgr_compile.c}`):

1. **`EmbeddedInterpreter`** — `Py_InitializeFromConfig` → `mp_embed_init(heap, size, &stack_top)`.
   - Heap: allocate a large GC heap (conv needs >2 MB; size generously, e.g. 256 MB, or make it a
     provider config). One process-singleton interpreter (as today; `CkDslContainer` owns it).
   - **Frozen mode:** the `embed_port.c` stubs (`mp_import_stat`→`NO_EXIST`,
     `mp_lexer_new_from_file` unreachable, `mp_builtin_open_obj` raises `OSError`). **Filesystem
     modes:** swap these for the real reader (`extmod/vfs_posix_file.c` + Windows `fmode.c`/`realpath.c`)
     and resolve the on-disk bundle dir relative to the plugin (`dladdr`/`GetModuleFileName`) onto
     `sys.path`. Selected by `CKDSL_MICROPYTHON_FROZEN` (see the loading-toggle section).
   - The native `comgr` module auto-registers via `MP_REGISTER_MODULE` (no runtime step).
2. **`CompileServiceBridge`** — same method set, reimplemented on `mp_*`:
   - import the **frozen** `ck_dsl_provider.compile_service` via `mp_import_name` (no sys.path baking —
     it's frozen). Cache the module object (rooted).
   - `compile/compileSmoke/isApplicable`: build args, `mp_call_function_n_kw`, marshal the returned
     dict → `KernelArtifact`.
   - Error translation: wrap calls in `nlr_push`; on catch, extract the exception type/message and
     raise `HipdnnPluginException` (replaces `PythonError`/`py::error_already_set`).
3. **Result marshalling** — rewrite `dictToArtifact` to read an `mp_obj_t` dict: `hsaco` via
   `mp_get_buffer`/`mp_obj_str_get_data` (bytes), ints via `mp_obj_get_int`, `grid`/`block` tuples and
   `arg_schema` list via `mp_obj_get_array`. Same `KernelArtifact` fields.
4. **Payload** — `convImplicitGemmSpecToPayload` returns `py::dict` today. **Recommended:** introduce
   an interpreter-neutral payload (a small ordered `key→{int|str|nested}` struct) that the adapter
   fills, and marshal it to an `mp_obj_t` dict in ONE place inside the bridge (GC-rooted there). This
   removes the interpreter type from the adapter's public signature (cleaner than today's `py::dict`).
   *Minimal-churn alternative:* have the adapter build an `mp_obj_t` directly and pass it (mirrors the
   current `py::dict` coupling).
5. **Drop** `PythonError.{cpp,hpp}` (folded into the bridge's nlr handling) and the pybind includes.
6. **Vendor** `comgr_compile.{c,h}` + `modcomgr.c` into `src/` (they're provider C now, not spike).

## Phase C — CMake / build integration
1. **Remove** `find_package(Python3 ...)` + `find_package(pybind11 ...)` and the
   `Python3::Python pybind11::embed` links from all three targets in `src/CMakeLists.txt`.
2. **MicroPython source**: vendor (git submodule / FetchContent) MicroPython at a pinned commit; build
   `mpy-cross` as a build tool.
3. **`CKDSL_MICROPYTHON_FROZEN` toggle** (see the loading-toggle section) selects the bundle path:
   - **`ON` (frozen):** custom command runs `build_bundle.py` → `build_frozen.py` → `embed.mk`
     (`FROZEN_MANIFEST` = the frozen tree) → produces `micropython_embed/` + `frozen_content.c`; the
     plugin depends on + links `frozen_content.c`. Nothing extra ships.
   - **`OFF`/`MPY` (on-disk):** custom command runs `build_bundle.py` (+ `build_frozen.py` for the
     specs-embed/target patch; + `mpy-cross` per file for `MPY`) → stages the `.py`/`.mpy` tree as an
     **install artifact** beside the plugin. Add the filesystem reader sources to the build
     (`extmod/vfs_posix_file.c`, and on Windows `ports/windows/{fmode,realpath}.c`) and the real
     `mp_import_stat`/`mp_lexer_new_from_file`/`open`; resolve the tree's path at load (`dladdr`/
     `GetModuleFileName`) onto `sys.path`.
4. **Compile/link into the plugin** (all modes): `micropython_embed/**/*.c` + `extmod/modre.c` +
   `comgr_compile.c` + `modcomgr.c` + the embed `mpconfigport.h`/`embed_port.c`; plus
   `frozen_content.c` (frozen) **or** the reader sources (on-disk). Link `amd_comgr` + `m`. Keep
   `-fvisibility=hidden` + `--exclude-libs=ALL` (now hides `mp_*`; with no separately-compiled Python
   extensions there is **no symbol re-export problem** — unlike the CPython B2 path, see
   [[ck-dsl-provider-b2-static-libpython]]).
5. **Replace** `cmake/CkDslProviderPaths.cmake`: in frozen mode it's gone (ck_dsl is in the binary);
   in on-disk mode it becomes the install-tree staging + the load-time path resolution (relative to
   the plugin, not baked absolute source paths).
6. **Config**: carry over the embed `mpconfigport.h` (ROM CORE_FEATURES + the enables proven in the
   spike: CPYTHON_COMPAT, EXTERNAL_IMPORT, QSTR_EXTRA_POOL (frozen mode), FROZENSET, str
   partition/center/count/splitlines, MPZ+`MPZ_DIG_SIZE=16`, SYS_PLATFORM, PY_IO). `open` is the
   raising stub in frozen mode, the real reader in on-disk mode.

## Phase D — tests & validation
1. **Rewrite** the unit tests in `tests/` that touch pybind types (`noopSmoke()` returning `py::dict`,
   `moduleForTesting()`): retarget to the new bridge interface / a smoke that imports the frozen
   compile_service and runs `compile_smoke`.
2. **Regression gate**: assert the conv HSACO from the MicroPython provider is **byte-identical** to
   the current CPython provider's (already true in the spike) for the integration shapes.
3. **End-to-end accuracy**: run the existing conv `integration_tests` on **gfx1151** (and gfx942/950
   where available) and validate against `CpuFpReferenceConvolution` via the SDK
   `computeTensorDiff<half>` — the harness already exists (see [[ck-dsl-provider-superbuild]]).
4. **No-Python-install check**: confirm the plugin loads + compiles a conv with no system Python and
   empty `PYTHONPATH`/`sys.path`.

## Phase E — productionization
1. **Windows**: build the embed port + `mpy-cross` (MinGW or MSVC/clang); link `amd_comgr.dll` from the
   Windows HIP SDK. **All three loading modes work on Windows** — frozen needs nothing extra; `.py`/
   `.mpy`-on-disk uses MicroPython's POSIX file reader, which the upstream Windows port already ships
   ("based on the Unix port"), carrying its `fmode.c` (CRT text/binary-mode fix) + `realpath.c`. No
   `ffi` anywhere → no Windows blocker in any mode; this is why Arch A was chosen.
2. **Superbuild**: wire the MicroPython vendoring + freeze step into the rocm-libraries superbuild so
   `cmake --preset ck-dsl-provider` builds it with no extra host deps (drops the `pip install pybind11`
   prereq).
3. **Upstream** the ck_dsl transforms (Phase A.1) into CK with the team.

## Risks & open items
- **Other kernels beyond conv**: the spike proved conv + elementwise. FMHA/gemm/etc. may surface more
  shimmable stdlib or `re` patterns (MicroPython `re` is a subset). Each new op should be run through
  the bundle once to flush its closure. Conv (the POC) is fully clear.
- **`re` subset**: verify each op's regexes parse under MicroPython `re`; fall back to a pure-Python re
  shim if a pattern is unsupported.
- **GC heap sizing**: per-compile peak; size generously and/or expose as config. A frozen bundle +
  256 MB heap is the proven baseline.
- **Determinism**: IR declares come out in a different (but valid) order; HSACO is byte-identical
  regardless (proven). Optional `sorted()` in `lower_llvm` for byte-identical IR *text*.
- **Transforms as a fork**: minimized to one real backend swap (`runtime/comgr.py`) + mechanical
  edits; best landed upstream in CK.

## Sequencing
A (bundle finalize) → B (C++ layer) → C (CMake) can proceed with B/C in parallel once A's frozen
artifact shape is fixed. D gates the merge. E is follow-up. First concrete commit: Phase A.4–A.5
(freeze the real `compile_service.compile` closure standalone) — the last spike step before touching
provider C++.
