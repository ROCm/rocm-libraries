# RFC 0019.13: UHD Training Methodology

- **Parent:** [RFC 0019 Universal Heuristic Descriptor](0019_UniversalHeuristicDescriptor.md) §13 Model Generation Pipeline
- **Status:** Draft — formalizes the methodology for training UHDs across arbitrary operations
- **Contributors:** Chris Erb, Jason Campbell
- **Tooling:** `projects/hipdnn/tools/uhd_gen/`

---

## Abstract

RFC 0019 §13 specifies the high-level training workflow (two-stage delivery, autotune substrate, feature contract enforcement) but leaves **per-operation parameter space exploration**, **corpus generation**, and **model evaluation** unspecified. This companion RFC fills those gaps so that a UHD can be trained for an arbitrary operation without per-operation tooling changes.

It specifies:

1. **An operation metadata schema** — a machine-readable description of an operation's parameter space, cost formulas, stratification axes, and graph construction, sufficient to drive corpus generation mechanically (§4).
2. **Staged corpus generation** — broad exploration first, then evidence-driven backfill, under a budget denominated in benchmark cost rather than shape count (§5).
3. **Kernel variant enumeration and applicability filtering** — including the train/serve candidate-set invariant that makes the trained model valid at runtime (§6, §7).
4. **A configuration-space partition** — configurations grouped into cells that perform alike, refined until splitting no longer separates them, with every sampled problem measuring one member per applicable cell. The partition is derived from the KMD and from measurement rather than authored, so how much is measured at a problem is a consequence of the space rather than a declared number (§5.6.2).
5. **Collection specified independently of strategy** — measurements keyed by problem and kernel values, so a schedule is a view over a dataset rather than a decision taken before any of it exists. A corpus gathered once serves strategies not yet designed, and a targeting strategy can be validated against exhaustive data before future runs rely on it (§8.7, §8.8).
6. **An evaluation protocol** — ranking and calibration metrics tied to the decision the UHD actually makes, with baselines, for judging a model and directing the next round of refinement (§11).

**Key architectural principle:** corpus generation synthesizes **operation-aware sampling** (the operation's full potential parameter space) with **provider applicability filtering** (what the engine's kernels can handle). The provider supplies predicates, not an exhaustive problem list.

This RFC is **descriptive** (documents how CK and rocKE approach the problem) and **prescriptive** (defines what the tooling must do). It specifies behaviour rather than reporting it: a section describing the generator is a requirement on it, and what is not yet built is recorded in §13.

## 2. What RFC 0019 Already Specifies

### 2.1 Two-Stage Workflow (RFC 0019 §13.1)

Ship a working pack first, add the heuristic later.

1. **Stage 1** — ship a functional pack with `static_order` (or no UHD). The catalog returns in deterministic `priority`/`id` order. No benchmarking required.
2. **Stage 2** — generate a data-driven heuristic from on-hardware timings. Update the UED/UHD in place.

### 2.2 Benchmarking Substrate (RFC 0019 §13.2)

Kernels are timed through hipDNN autotune (RFC 0013).

```python
configs = handle.get_engine_configs(graph)
handle.add_engine_variants(engine_id, [(knob1, knob2, ...), ...])
handle.add_engine_sweep(engine_id, knob_ranges, fixed_settings)
results = handle.autotune(mode=EXHAUSTIVE, strategy=RUN_UNTIL_STABLE)
# → [{engineId, knobSettings, minTimeMs, avgTimeMs, stddevMs, ...}]
```

**Key constraint:** autotune addresses kernels via **exposed knobs only**. A kernel the tool cannot name cannot be timed.

**Precondition:** generation runs against a **fully-exposed UED** (every KMD field exposed as a knob) so every catalog entry is individually addressable. The emitted UED then exposes only the features the model kept. How that fully-exposed descriptor is obtained is the UED's concern (RFC 0020), not this document's; generation takes it as an input and §8.2 checks it was one, by treating a knob-tuple collision as proof that exposure was incomplete.

### 2.3 Feature Extraction (RFC 0019 §6)

Features are drawn from three sources, all available at plan time:

| Source | Namespace | Examples | Bindable at training time |
|--------|-----------|----------|---------------------------|
| Device properties | `$device.*` | `cu_count`, `lds_size`, `vgpr_count` | Yes — known per GPU |
| Kernel metadata (KMD) | `$kernel.*` | `tile_m`, `split_k`, `warp_n` | Yes — from UKD metadata |
| Query/problem shape | `$q.*` | `dims[0]`, `dims[2]`, `dtype` | Yes — sweep parameter |

**Computed features** (RFC 0019 §6.4) are expression trees of the form `{"op": [args]}` with bare `$`-prefixed variable references:

```json
{"ceil_div": ["$q.dims[2]", "$kernel.tile_m"]}
{"/": ["$sdpa_fwd.flops", "$sdpa_fwd.bytes"]}
```

This RFC uses the same syntax throughout (§4.3.3).

### 2.4 Feature Contract Enforcement (RFC 0019 §6.3)

`features_hash` pins the feature signature. Training emits `features_signature` + `categorical_encoding` → `sha256:…`. The runtime extractor validates the hash before scoring; a mismatch means refuse to load (fail closed) or degrade to static ordering (fail open).

### 2.5 Training Target and Transform (RFC 0019 §11.3)

The target and transform:

```python
y = np.log1p(df[target_col].values)   # scale-invariant regression target
```

**Objective: `max` on TFLOPS.** A latency target with `objective: min` produces the identical ranking —
the fastest kernel is the fastest kernel either way — so the choice is not about ordering. It is about what
the published number means outside the engine. TFLOPS carries how much work was done and is comparable
across engines; a millisecond does not and is not. `min` is legal, and §15.1 confines it to a UHD
declaring `score.calibrated: false`, which is to say one opting out of cross-engine comparison.

```json
"score": { "units": "tflops", "calibrated": false, "transform": "log1p" }
```

Runtime inverts the transform: `score = expm1(model.predict(features))`.

Note that this is a **pointwise regression** target while the runtime decision is a **ranking** decision. §11 defines the evaluation metrics that make that gap measurable, and §11.5 discusses replacing the objective outright.

### 2.6 Cross-Validation (RFC 0019 §13.2, implicit)

GroupKFold prevents problem leakage — the same problem shape never appears in both train and validation folds.

```python
groups = df.groupby(group_cols).ngroup().values   # e.g. (q.M, q.N, q.K)
folds  = GroupKFold(n_splits=5).split(X, y, groups)
```

Grouping MUST be by problem, so that all kernel variants measured for one problem stay in the same fold. §11.3 adds a second, stricter split.

## 3. The Three Spaces

### 3.1 Decomposition

For every operation the feature space decomposes into three sources (RFC 0019 §6.1):

```
                  Device ($device.*)          Problem ($q.*)                Kernel ($kernel.*)
                  ──────────────────          ──────────────                ──────────────────
Declared by:      GPU hardware                Regimes + semantic bounds     KMD variant declaration
                                              only (§4.3.2)                 (§6.3)
Explored by:      NOT explored                Corpus generator (§5)         Variant enumerator (§6),
                  (one fixed point                                          partitioned into cells
                   per training run)                                        (§5.6.2)
Bounded by:       —                           memory ceiling, then          the declaration itself,
                                              is_applicable (§4.3.2, §7)    or its validator (§6.2)
Obtained from:    HIP runtime query           Generated corpus JSON         KMD, else the catalog
```

The **device space** is a single fixed point per training run. The **kernel space** is enumerable from the compiled catalog. The **problem space** is unbounded and is where operation-specific methodology is required.

### 3.2 Division of Responsibility: Tooling Generates, Provider Filters

**Tooling responsibility.** Generate a representative problem corpus spanning the **operation's full potential parameter space**. Tooling holds the operation-level knowledge — that SDPA has prefill and decode regimes, that GEMM has batch-1 inference and tall-skinny projection shapes.

**Provider responsibility.** Supply **predicates** that answer "can this engine handle this problem?" and "is this variant valid?".

**Explicitly NOT the provider's responsibility.** Enumerating an exhaustive list of supported problems.

Why this split:

1. Providers know their kernel's constraints, not every use case hipDNN must cover.
2. A predicate is cheaper to author and maintain than an exhaustive list, and cannot silently go stale.
3. Synthesis is automatic — tooling generates broad coverage, predicates prune what the engine cannot run, training sees exactly the feasible set.

### 3.3 Device Space Handling

Device properties are queried once per training run via `hipGetDeviceProperties()` / `hipDeviceGetAttribute()`, or loaded from a JSON config when running without hardware.

The field set is the one RFC 0019 §6.1 specifies, extended additively as predictive need is demonstrated: `cu_count`, `lds_size`, `warp_size`, `sgpr_count`, `vgpr_count`, `max_waves_per_cu`, `memory_clock_mhz`, `memory_bus_width`, `peak_bandwidth_gbps`.

**Normative rule — device columns are recorded but are not features in single-arch runs.**

- Every benchmark CSV MUST carry the `device.*` columns (§8.3). They are provenance: they identify what hardware produced the timings.
- For a **single-arch training run**, `device.*` columns are constant across all rows. A zero-variance column can never be split on by a tree model; including it in `--features` adds nothing to accuracy while enlarging `features_signature` and changing `features_hash`. Single-arch runs therefore MUST NOT pass `device.*` columns as features.
- For a **pooled multi-arch training run** (§3.4), `device.*` columns vary and SHOULD be features.

`uhd_gen` SHOULD reject a `--features` list containing a column with zero variance, naming the column, rather than training a model with a dead feature.

### 3.4 Multi-Architecture Coverage

**PARTIALLY SPECIFIED** (RFC 0019 §8.3): arch-keyed UHD selection. The UED maps each architecture to a
UHD **id**, resolved exact-first then `default` (RFC 0019 §3.1); the values are descriptor identities, not
paths.

```json
"sort_kernel_catalog": {
  "gfx942":  "ae896b07-80cd-473c-b3f4-6a8892998519",
  "gfx950":  "7b1e9c40-1f2d-4a55-9c31-0b7e6d2ac418",
  "default": "c93e17aa-5b60-4f0e-8a72-3d1c9f4e2b06"
}
```

**Two strategies, and when to use each:**

| Strategy | Training data | `device.*` as features | Use when |
|----------|---------------|------------------------|----------|
| **Per-arch models** | One run per arch | No (§3.3) | Default. Arch behaviour differs qualitatively; each model stays small. |
| **Pooled arch-aware model** | Runs from ≥3 archs concatenated | Yes | Covering SKU variation within a family (CU-count differences on the same `gfx`) where behaviour differs quantitatively, not qualitatively. |

`$device.arch` itself MUST NOT be a feature — it is a KDP property used for UHD resolution, not a runtime feature (RFC 0019 §6.1). SKU variation is expressed through numeric properties (`cu_count`, `lds_size`, `peak_bandwidth_gbps`) which the model can actually interpolate over. Arch enters the training artifact only as loader-checked coverage metadata (§10.5).

Where an architecture needs materially different behaviour, RFC 0019 §3.3 gives it a **separate engine** rather than a folded-in model. Arch-keyed maps split where arches diverge; they are not a substitute for that decision.

The **mechanism** is decided and implemented: RFC 0019 §3.1's three role-scoped, arch-keyed UHD maps exist, with exact `gcnArchName` resolution falling back to `default`.

What RFC 0019 Open Question 2 still asks is which of the two strategies above should be the *default*, and that turns on cross-arch accuracy data nobody has yet. §11 is the protocol that would produce it; this RFC takes no position on the outcome.

### 3.5 Engine Scope, Not Pack Scope

A UHD belongs to the **UED — the engine** — and is shared by every pack that joins it (RFC 0019 §3.3: "Engine-scoped, never per-pack"). A UHD is never inlined per kernel or per pack.

Two consequences for training:

1. **The corpus must cover the union of every pack on the engine.** A UHD trained against pack A alone will rank A ∪ B once pack B joins, and nothing in the load-time contract check catches it — the model silently extrapolates. RFC 0019 Open Question 5 records this; its v1 recommendation is to retrain over the union and emit a coverage warning. Training that scopes its corpus to one pack violates the intent even though it passes every mechanical check.
2. **The engine, not the pack, is the unit of a training run.** A pack is a shipped kernel collection contributing UKDs; the engine is what owns the heuristic trained over them.

## 4. Operation Metadata Schema

**SPECIFIED HERE.** This is the canonical, machine-readable description of an operation. It is the single input that makes corpus generation mechanical rather than per-operation code.

### 4.1 File Location and Identity

```
projects/hipdnn/tools/uhd_gen/metadata/<operation>.json
```

`<operation>` MUST match the FlatBuffers `NodeAttributes` union member for the op, lowercased with an explicit direction suffix where the schema distinguishes one — e.g. `matmul`, `layernorm_fwd`, `layernorm_bwd`, `sdpa_fwd`, `conv_fwd`.

### 4.2 Schema

```json
{
  "schema_version": "1.0",
  "operation": "layernorm_fwd",
  "display_name": "LayerNorm Forward",
  "description": "Layer normalization over the trailing normalized dimensions.",

  "parameters": {
    "batch":       { "type": "int64" },
    "seq_len":     { "type": "int64" },
    "hidden_dim":  { "type": "int64" },
    "dtype":       { "type": "enum", "values": ["float32", "float16", "bfloat16"] },
    "forward_phase": { "type": "enum", "values": ["INFERENCE", "TRAINING"] }
  },

  // No `range` on the three size dimensions: none is a semantic bound, so the region comes from the
  // memory ceiling and applicability (§4.3.2). No `common_values` either — this operation has no usage
  // record to draw them from (§5.2).

  "stratification_axis": "working_set",

  "regimes": {
    "hidden_dim":  { "parameter": "hidden_dim",
                     "buckets": [768, 1024, 1536, 4096, 5120, 6656, 8192, 12288] },
    "batch":       { "parameter": "batch",  "buckets": [1, 4, 16, 32, 64, 128, 512] },
    "seq_len":     { "parameter": "seq_len","buckets": [128, 512, 2048, 8192, 16384] },
    "alignment":   { "parameter": "hidden_dim", "derived": "alignment",
                     "buckets": ["aligned", "partial_remainder", "full_remainder"] }
  },

  "graph_builder": {
    "function": "createValidLayernormFpropGraph",
    "source": "hipdnn_test_sdk/utilities/FlatbufferGraphTestUtils.hpp",
    "arguments": [
      { "name": "dims",    "kind": "expr",
        "value": ["$q.batch", "$q.seq_len", "$q.hidden_dim"] },
      { "name": "strides", "kind": "strides_of", "of": "dims" },
      { "name": "inputDataType",   "kind": "dtype_of", "source": "$q.dtype" },
      { "name": "computeDataType", "kind": "dtype_of", "source": "$q.dtype" }
    ]
  }
}
```

### 4.3 Field Definitions

#### 4.3.1 Top level

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `schema_version` | string | Yes | Metadata schema version (current `"1.0"`) |
| `operation` | string | Yes | Operation identifier (§4.1) |
| `display_name` | string | No | Human-readable name |
| `description` | string | No | Operation semantics |
| `parameters` | object | Yes | Parameter space (§4.3.2) |
| `stratification_axis` | string | Yes | `arithmetic_intensity` \| `working_set` \| `reduction_ratio` (§4.3.4) |
| `regimes` | object | Yes | Stratification buckets (§4.3.5) |
| `graph_builder` | object | Yes | Graph construction mapping (§4.3.6) |

There is no `tier_sampling` field. Tiers are budget-derived and global (§5.5); an operation does not get to declare its own corpus size.

#### 4.3.2 Parameters

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `type` | string | Yes | `int64` \| `float64` \| `enum` \| `bool` |
| `range` | `[min, max]` | No | A **semantic** bound only — a limit inherent to the operation, such as one dimension that cannot exceed another. Not a judgement about typical sizes. |
| `values` | array | For enum | Permitted values |
| `common_values` | array | No | Representative values, where a usage source exists (§5.2) |
| `description` | string | No | — |

`values` is REQUIRED for `enum`; `bool` has implicit `[true, false]`.

**Numeric dimensions are not bounded by authored ranges.** Two things bound the region a generator draws
from, and neither requires anyone to guess a typical size:

- **Benchmarkability.** A problem whose tensors do not fit in device memory cannot be timed, so it cannot
  enter a training corpus at any budget. That ceiling is computed, not declared: tensor bytes from shape
  and dtype, against the device's memory size. It is the limit that actually binds, and it is sharper than
  any statement about what the hardware can express.
- **Applicability.** Everything below that ceiling is a candidate; the provider's predicate prunes what the
  engine cannot run (§7.5). The feasible region is the intersection, and it is discovered by sampling
  rather than declared up front.

A `range` entry is therefore reserved for bounds intrinsic to the operation itself. Authoring one to
express "sizes we expect to see" is a metadata bug: it silently truncates the space the engine claims to
support, and expected sizes belong in §5.2's weighting instead.

#### 4.3.3 Cost Quantities

Stratification and the throughput target both need an operation's FLOP and byte counts. **Operation
metadata does not define them.** RFC 0019 §13.6 places them in the binding layer as precomputed fields,
published for every op that has them:

```
$<op>.flops        // e.g. $sdpa_fwd.flops — 4·B·H·Sq·Sk·D for SDPA forward
$<op>.bytes        // sum over each tensor of element_count × that tensor's own dtype size
```

The parent is explicit that these are **not** authored as expressions: they are op-intrinsic, identical
for every engine implementing the op, and "what needs a rebuild to change belongs in code, as a
precomputed binding field." Re-declaring them per operation-metadata file would create the second
definition site that rule exists to prevent, and would put the mixed-dtype byte rule — each tensor
contributing its own dtype size — in a place where each author could get it wrong independently.

Consequently this RFC defines no cost expressions, and needs no `sizeof` operator. RFC 0019 §6.2 fixes the
expression operator set and states that no extension is needed; `sizeof` is not in it, and the byte count
that would have required it is the binding layer's to compute.

**Where the generator gets them.** The corpus generator builds a graph per candidate problem (§4.3.6) and
reads the bound fields. Stratification therefore happens after graph construction rather than before it:
candidates are generated, bound, classified by the resulting axis value, then kept or dropped to meet
bucket targets (§5.3).

**Interim, until the binding fields land.** RFC 0019 §13.6 specifies these fields; RFC 0019 Open
Question 4 leaves which counts to publish, and the mixed-dtype byte convention, unsettled, and no
operation publishes them today. Until they land the generator MAY compute the quantities host-side. That
fallback lives in the generator's own per-op table, **not** in the operation metadata file, so there is
one place to delete when the binding fields arrive and no descriptor carries a definition that has to be
migrated. A host-side value MUST match the definition RFC 0019 §13.6 states for that op.

**Ops without a closed form.** Ragged or data-dependent shapes can make an exact count impossible. RFC 0019
RFC 0019 §13.6 directs that the field then expose a documented upper bound or be absent rather than be silently
wrong. An operation with no cost fields cannot use the `arithmetic_intensity` stratification axis and MUST
declare `working_set` or `reduction_ratio`.

**A proposed addition.** The `working_set` axis (§4.3.4) needs a per-group footprint — the bytes one
normalization row, tile or reduction group touches — which is op-intrinsic in exactly the way FLOPs and
bytes are, and which the parent's set does not currently include. RFC 0019 §13.6 notes that the op
vocabulary "should carry a *set* of useful precomputed fields — some universal across ops, some per-op",
and assigns the question of what belongs in that set to the UMD. This RFC therefore **proposes**
`$<op>.working_set_bytes` as an addition to that set rather than defining it here. Until it exists, the
same host-side interim applies.

#### 4.3.4 Stratification Axis

Arithmetic intensity is **not** a universal stratification axis. For a bandwidth-bound elementwise or normalization op it is shape-invariant: LayerNorm moves a fixed number of bytes per element and does a fixed amount of arithmetic on each, so `flops / bytes` reduces to a constant independent of batch, sequence length and hidden size. Stratifying such an op by AI produces exactly one bucket and no coverage.

Each operation therefore declares which axis is informative:

| Axis | Definition | Use for |
|------|------------|---------|
| `arithmetic_intensity` | `$<op>.flops / $<op>.bytes`, thresholded against `peak_flops / peak_bandwidth` | Ops that can be compute-bound: GEMM, Conv, SDPA, MoE |
| `working_set` | `$<op>.working_set_bytes` (§4.3.3, proposed) bucketed against L1 / L2 / LLC / HBM capacity | Bandwidth-bound ops: Norm, Pointwise, Quantize |
| `reduction_ratio` | `input_elements / output_elements` | Reductions, where cost is driven by fan-in, not footprint |

The corpus generator MUST report bucket occupancy for the declared axis (§5.10), so a corpus that collapsed into one bucket is visible rather than silent.

#### 4.3.5 Regimes

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `parameter` | string | Yes | Parameter this regime stratifies |
| `buckets` | array | Yes | Discrete values, or labels when `derived` is set |
| `derived` | string | No | `alignment` — buckets are `aligned`/`partial_remainder`/`full_remainder` relative to the kernel tile sizes discovered in §6 |
| `description` | string | No | — |

Regimes are the axes of the stratified cross-product in §5.3. All declared regimes participate; there is no "primary" regime.

#### 4.3.6 Graph Builder Mapping

Corpus entries are parameter dictionaries; benchmarking needs a serialized FlatBuffers graph. `graph_builder` closes that gap declaratively.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `function` | string | Yes | Builder function name |
| `source` | string | Yes | Header providing it |
| `arguments` | array | Yes | Ordered argument mapping |

Each argument has a `kind`:

| `kind` | Fields | Behaviour |
|--------|--------|-----------|
| `direct` | `source` | Copy the named `$q.*` value |
| `expr` | `value` | Evaluate a §4.3.3 expression (arrays yield dims lists) |
| `strides_of` | `of` | Row-major contiguous strides for a previously-named argument |
| `dtype_of` | `source` | Map a dtype string to the FlatBuffers `DataType` enumerator |
| `constant` | `value` | Literal |

Arguments are resolved in declaration order, so `strides_of` may reference an argument declared earlier.

Every argument named in `arguments` MUST reference only parameters declared in `parameters`. A validator MUST reject metadata that references an undeclared parameter — this is the check that catches a `graph_builder` written against a different parameterization than the op declares.

Builders live in `hipdnn_test_sdk/utilities/FlatbufferGraphTestUtils.hpp`; all 22 ops with FlatBuffers schemas have one. Dispatch is by `graph_builder.function`, so adding an operation requires no change to the generator.

### 4.4 Metadata Validation

`uhd_gen validate-metadata` MUST check:

1. Conformance to the §4.3 field tables.
2. Every `$q.*` reference in `graph_builder` resolves to a declared parameter.
3. Every `regimes[*].parameter` is a declared parameter, and where that parameter declares a semantic `range`, its non-derived buckets fall inside it.
4. `stratification_axis` is one of the three permitted values, and the cost fields that axis reads are available for the operation (§4.3.3).
5. `graph_builder.function` resolves in the declared source header.
6. Expressions parse and evaluate to a positive number on the parameter midpoint.

## 5. Problem Corpus Generation

### 5.1 Sampling Is an Exploration Problem

What makes a corpus effective is coverage of the regions where **which kernel wins changes** — the decision boundaries. Elsewhere the ranking is stable and extra samples buy little.

Those boundaries cannot be targeted up front. Knowing where they lie means already knowing the answer the model is being trained to produce. Boundary location is an *output* of benchmarking, not an input to it, so any single-pass generator is choosing every sample while blind to the thing that determines whether the sample was worth taking.

Corpus generation is therefore staged:

| Round | Informed by | Purpose |
|-------|-------------|---------|
| **0 — exploration** | Nothing but the operation's declared regimes | Broad, unbiased coverage of the feasible region (§4.3.2) |
| **1..N — backfill** | Measurements and model assessment from prior rounds | Densify where the evidence says accuracy is missing |

`N` is not fixed. Each round produces a corpus increment that is benchmarked and folded into the training
set, the model is retrained from scratch, and §5.5 decides from measured accuracy whether another round is
warranted. A run that meets its target after round 0 has `N = 0` and is finished.

**Exploration floor.** Backfill guided solely by where the current model reports weakness entrenches blind spots: a region the model is confidently and uniformly wrong about looks healthy and is never revisited. Every backfill round MUST therefore allocate at least **20%** of its samples by unbiased stratified draw, independent of any assessment signal.

§5.6.3's evaluation slice covers every region from round 0, so a region-sized blind spot now shows as measured regret rather than as confident silence. The floor survives that at finer grain: the slice holds a few problems per region, so a sub-region between them can still be uniformly wrong with nothing to reveal it. Coverage supplies a signal everywhere; the floor supplies samples where the signal says nothing is wrong.

**Round 0 is the majority of the budget, and the only part committed in advance.** Backfill targeting is
only as good as the regret estimates driving it, and those need enough samples per region to be signal
rather than noise; under-sizing round 0 to reserve room for backfill produces confident targeting of the
wrong regions. Whether any of the reserve is spent is §5.5's decision, not an assumption.

### 5.2 Target Distribution, Where One Is Known

**The default is blind.** A new kernel arrives with a new UED and UHD and no usage history, so there is no
distribution to aim at. That is the normal case rather than the exception: the corpus is generated from
the operation's feasible dimensions alone (§4.3.2), sampled uniformly — log-uniform on size dimensions,
since performance regimes scale multiplicatively rather than additively.

Blind generation is also why §5.4 matters more than it first appears. With no prior on where behaviour
changes, every signal that locates a boundary is a *measured* one — boundary density over the corpus,
regret concentration over the evaluation slice — and nothing can be declared in advance.

**Weighting is a refinement for operations that have a usage record.** Where one exists it answers the
question uniform sampling cannot — "representative of *what*" — since uniform stratification weights a
prime-dimension corner case identically with a shape every customer runs.

For convolution the record exists outside these RFCs: the MIOpen performance database carries curated
shape collections keyed by model, dataset and client. Those are *used* shapes rather than *supported*
ones, so they are a weighting signal and a set of shapes known to matter, not the corpus itself. For GEMM,
SDPA and the remaining operations there is no equivalent source (§13, S5).

Where a record exists, operation metadata MAY declare per-regime weights:

```json
"regimes": {
  "llm_shapes": { "parameter": "shape_family", "buckets": [...], "weight": 4.0 },
  "primes":     { "parameter": "M",            "buckets": [...], "weight": 0.5 }
}
```

`weight` defaults to `1.0` and is a relative expected-traffic multiplier, not a sampling count.

Weights are used **twice, differently**:

- **Sampling** — round 0 allocates samples proportional to `weight^0.5`, not `weight`. Square-root damping keeps low-weight regimes populated enough to be learnable while still favouring common shapes; allocating proportional to raw weight starves the tail, and the tail is where regret concentrates.
- **Reporting** — §11.2 regret is reported unweighted, and additionally traffic-weighted when weights are
  declared. The unweighted number says how good the heuristic is across the space the engine supports; the
  weighted number estimates what a user will experience. They can diverge sharply, and for a blindly
  generated corpus only the first exists.

### 5.3 Round 0 — Broad Coverage

| Strategy | Behaviour |
|----------|-----------|
| `one_per_regime` | One representative per bucket of each regime, other parameters at their most common value. Smoke only. |
| `stratified_cross_product` | Cross-product of all regime buckets × categorical parameters, then samples drawn per bucket (allocation per §5.2), with free numeric dimensions drawn by the footprint-first method below. Default for `standard`. |
| `dense_log_grid` | Footprint-first draws on a deterministic log-spaced schedule rather than at random, × full cross-product of categoricals. `exhaustive` only. |

**Drawing the free numeric dimensions: footprint first, then shape.** §4.3.2 leaves most numeric
dimensions without an authored range, so there is no per-dimension interval to sample from. Sample the
quantity that is bounded instead:

1. Draw a total tensor footprint log-uniformly between a floor of one element and the device memory
   ceiling. This is the constraint §4.3.2 identifies, applied directly rather than as a rejection test.
2. Draw a shape that realizes that footprint — for a matmul, the aspect ratios that partition it across
   `M`, `N` and `K`; for a normalization, the split between row count and row width.
3. Round to integers, then apply any `range` the operation declares as a semantic bound, and any regime
   bucket this sample belongs to.

Two properties make this the right order. Feasibility holds by construction, so no sample is generated
only to be discarded, which matters because the rejection rate of an independent per-dimension draw grows
with dimensionality. And log-uniformity lands on footprint, which is the quantity performance regimes
scale with, rather than on each dimension separately — drawing three dimensions log-uniformly and
multiplying concentrates the product near the middle of its range and starves both ends.

The floor is one element, not something larger. Degenerate shapes are real workloads: `M = 1` is
single-token decode, and it is a regime in its own right (§12.1).

**The engine is the authority on its own bounds, so ask it.** The footprint draw above says what
fits in memory. It does not say what the engine accepts, and only two operations have a written
decomposition of footprint into a shape — matmul across `M`/`N`/`K`, normalization across row count
and row width. Convolution and attention have neither: padding, stride, dilation and groups are not
size at all, they decide whether a shape is degenerate, and no arithmetic on bytes yields them.

There is no declaration to fall back on, and the asymmetry is worth stating plainly because it is
what forces this. A kernel knob arrives with `min_value`, `max_value`, `step`, sometimes an explicit
value list — which is why §6.2 can enumerate the variant space by forming a product. An operation
parameter arrives with nothing. An engine advertises its id, its knobs, its behaviour notes and its
name; it says nothing about the tensor dimensions it will accept. The only thing that knows is
`is_applicable` (§7.1), and it answers one shape at a time.

So generation **SHOULD** treat the predicate as the authority rather than modelling the region:

1. **Propose** by the footprint-first draw. Feasible against memory by construction, log-uniform
   across scales.
2. **Accept or reject** by calling `is_applicable` on the built graph (§4.3.6). No execution, so a
   probe costs a graph build and a predicate call — cheap enough to spend thousands of them for the
   price of one benchmark.
3. **Bisect** to locate a boundary where one is wanted: hold every other parameter fixed, and binary
   search the one under study between an accepted and a rejected value.
4. **Sample the interior at random**, seeded, to find out how solid the located interval is. Steps
   2 and 3 move in powers of two, so both are blind to a region whose acceptance shares that stride
   — a kernel taking only multiples of 512, probed from 512, answers yes to every question either
   one asks. Uniform draws have no stride to collide with. The accepted share is then the rejection
   rate a uniform proposal over that interval will pay, which this section already requires a
   generator to report rather than absorb.

This replaces analysis with measurement, and it is what makes the unwritten operations tractable —
a twelve-parameter convolution needs no closed form if candidates can be tested.

Three properties of the answer, which the generator MUST NOT overstate:

- **It is a membership oracle, not a range.** The predicate answers about a shape, never about a
  dimension. Every quantitative statement costs a bisection, roughly a probe per halving per
  direction.
- **The region has holes.** Alignment, tile divisibility and LDS limits routinely make a kernel
  accept 1024 and 4096 while rejecting 2048. Bisection assumes monotonicity and that assumption is
  false, so a search returns *a* boundary rather than *the* extent. Step 4 is what measures how far
  off that is; without it a bound carries no evidence either way. Sampling the interior stays
  sound; concluding "`M` runs from A to B" does not, and a reported bound MUST carry the fact that
  it was probed rather than declared.
- **The bounds belong to the engine, not the operation.** Applicability is one engine's answer, so
  the region mapped is that engine's. For training its UHD that is exactly right — it is the region
  the model will be asked about — but two engines' corpora are not comparable and neither is
  portable.

**Where the footprint has no closed form.** An operation whose byte count is unavailable — the same set
§4.3.3 permits to have no cost fields — falls back to an independent draw per dimension over `[1, 2^k]`
a `k` above anything addressable, discarding samples that exceed the memory ceiling. Simpler, unbiased
within the feasible set, and wasteful in proportion to how much of the box is infeasible. The generator
MUST report the rejection rate so that waste is visible rather than absorbed into the run time. A
rejection rate high enough to dominate the run is the signal to bisect the offending dimension and
propose inside the located bound instead.

**Non-regime parameter handling.** Under `one_per_regime`, a parameter not being stratified takes
`common_values[0]` where declared, and otherwise the median of a footprint-first draw. It MUST NOT take a
range minimum: doing so collapses every sample onto one corner of the space.

**Reaching a target count.** Undershoot by reducing samples-per-bucket uniformly; overshoot by round-robin removal across buckets. A generator MUST NOT truncate the accumulated list, which drops whole regimes according to iteration order.

**Dedup.** Deduplicate on the tuple of `q.*` values after generation, then top up by re-sampling under-filled buckets, up to `max_attempts = 10 × target`. `metadata.count` records the actual post-dedup count, which MAY be below target; the shortfall MUST be reported.

**Where each number comes from.** Regret is computable only on the evaluation slice (§5.6.3), since a
partial configuration set makes its best member a lower bound, not the true best. Out-of-fold
predictions over the whole corpus measure prediction error, not regret. Loop decisions read the steering
portion of the evaluation slice; a reserved portion supplies the reported figure, and the manifest records
which produced which (§5.6.4).

### 5.4 Backfill Rounds — Evidence-Driven

After round 0 is benchmarked and a model trained, three signals identify where to densify. All are computed from data in hand; none requires knowing boundary locations in advance.

| Signal | Computed from | Identifies |
|--------|---------------|------------|
| **Boundary density** | All measurements | Among neighbouring measured problems, the fraction whose top-1 variant differs. High density = a decision boundary runs through the region. |
| **Regret concentration** | Evaluation slice only | Per-region mean top-1 regret (§11.2). High regret = the model is losing performance here. Computable only where every configuration was measured (§5.6.3), which round 0's even spread guarantees for every region. |
| **Prediction dispersion** | Model only | Variance of predicted score across CV folds. High dispersion with few samples = the model is guessing. |

**Regret concentration leads**, because §5.5 stops on accuracy and this is the signal that says where the accuracy is missing. Boundary density qualifies it: being model-independent, it distinguishes a region that is intrinsically hard to rank from one the current model merely got wrong, and the former is worth more samples than the latter. Dispersion says the corpus is too thin to tell. A region flagged by all three is the highest-value target.

Boundary density reads the whole corpus rather than the evaluation slice: the cell rule of §5.6.2 gives
neighbouring problems the same menu, so a change in the best measured configuration between them is a real
change and not an artifact of which configurations each was assigned. It needs a comparable winner, not an
exact one.

**Combining the signals.** The three are on incomparable scales — a 0–1 fraction, a 0–1 ratio, and an
unbounded variance — so each is divided by its own maximum across regions within the round, putting all
three in `[0, 1]`, and the weighted sum taken:

```
score(region) = 0.5 × regret/max(regret)
              + 0.3 × density/max(density)
              + 0.2 × dispersion/max(dispersion)
```

**Scaling, not ranking.** Budget is allocated proportional to this score, so it must preserve how much
worse one region is than another. Ranking would not: a region at 40% regret and one at 5% rank adjacent
and would draw near-equal budget, when the first is where the corpus is failing. Dividing by the maximum
keeps a region eight times worse eight times heavier.

The usual objection to max-scaling — one extreme region compresses the rest — is the intended behaviour
here, and the 40% single-region cap below is what bounds it.

The weights are defaults matching the ordering §5.5 implies, regret leading because it is what the
stopping rule measures. They MUST be recorded in the corpus metadata so a run's targeting can be
reproduced, or compared against one that weighted differently.

**Allocation within a backfill round:**

1. Reserve the 20% exploration floor (§5.1), drawn by unbiased stratified sampling.
2. Distribute the remaining 80% across regions proportional to `score(region)`.
3. Cap any single region at 40% of the round, so one pathological region cannot consume the budget.
4. Sample within a targeted region by **bisection between disagreeing neighbours**. Where two measured
   problems in the region are adjacent and their top-1 variants differ, the boundary lies between them, so
   draw the midpoint — interpolating each numeric dimension in log space, consistent with §5.3. This
   converges on the boundary rather than scattering around it, needs no per-dimension range, and cannot
   pile up on a single point the way "draw near a high-signal problem" can. Where a region has no
   disagreeing pair — it was flagged by dispersion alone — fall back to a footprint-first draw (§5.3)
   restricted to that region's buckets.

New samples MUST be tagged with their round and the signal that selected them, so a post-hoc analysis can tell whether backfill actually helped or merely spent budget.

### 5.5 Budget Allocation and Stopping

**The unit of benchmark cost is the (problem, variant) pair, not the problem.** A corpus of 5,000 shapes costs 2.5M timed configurations against a 500-variant catalog and 25M against a 5,000-variant catalog. A shape count is therefore meaningful only alongside the variant count it was measured against.

Tiers are defined by a **configuration budget**:

| Tier | Budget (configs) | Approx. wall-clock | Purpose |
|------|------------------|--------------------|---------|
| `smoke` | 10⁴ | minutes | Validate that generation, graph construction, filtering and benchmarking run end to end |
| `standard` | 2 × 10⁶ | ~8–15 GPU-hours | Production heuristic |
| `exhaustive` | 2 × 10⁷ | ~4–7 GPU-days | Research; maximum accuracy |

**Splitting the budget.** §5.6 fixes the criterion — fill the joint `(q.*, kernel.*)` space — and the
budget divides by purpose rather than between the two axes:

| Slice | Share | Purpose |
|-------|-------|---------|
| Training | bulk | Space-filling over the applicable joint space (§5.6.1) |
| Evaluation | a declared fraction of problems × every member of every applicable cell | Exact `v*(p)`, so regret is a measurement (§5.6.3) |
| Reserved | a portion of the evaluation slice | The reported number, insulated from stopping and backfill (§5.6.4) |

The evaluation slice's cost is its declared fraction of the problem count times the applicable
configuration count, which the tool projects before committing spend. The training slice takes what remains, and problem count and cell
count are the two sides of one division: `cells_allowed = budget / N_problems` (§5.6.2.1). A run declares
the budget; how it splits between covering more problems and resolving the configuration space more finely
is the one trade the tool exposes.

**Coverage floor.** Rather than a per-variant count, the floor is the cell rule of §5.6.2: every sampled
problem measures one configuration from every applicable cell. No region of kernel feature space is left
without a measurement, since a configuration in an unobserved region is extrapolated rather than
interpolated, and §7.3's argmax then seeks out whichever extrapolation was most optimistic. A configuration
that shares a cell with a measured one needs no sample of its own — that is what the cell asserts.
Applicability (§7.1) bounds the space before any budget is spent on it.

**Pruning configurations that cannot win.** A configuration that loses by a wide margin everywhere it has
been measured may be dropped from further training sampling, which on a typical engine is most of the
catalog and frees budget quickly. The margin must be wide rather than merely losing: a configuration that
is narrowly second may still win in a region not yet sampled, and dropping it removes the evidence that
would have shown so. Pruning MUST NOT touch the evaluation slice (§5.6.3) — it stays exhaustive, which is
what lets §11.3 measure what a pruned configuration would have contributed. A dropped configuration is
recorded as such, since it remains in the runtime candidate set and §7.3's invariant still covers it.

**If the coverage floor exceeds the budget**, the run cannot observe the kernel feature space and the tool
MUST say so rather than silently sampling a subset. This is likelier than it sounds for a large catalog,
and it is the rule working rather than failing: a configuration space that cannot be covered within a
reasonable budget is one too large to train against, which is a finding about the catalog and routes to
reducing it upstream in package creation (RFC 0019 §14) — or to raising the tier if the budget is
genuinely available.

| Applicable variants | `smoke` | `standard` | `exhaustive` |
|---------------------|---------|------------|--------------|
| 50 | 200 | 40,000 | (saturated) |
| 500 | 30 (floor) | 4,000 | 40,000 |
| 5,000 | 30 (floor) | 400 | 4,000 |

Problem counts above are indicative, computed before the evaluation slice is subtracted.

The **problem floor** (`30 × N_regime_buckets`) keeps stratification meaningful under a tight budget; if it
exceeds what remains after the evaluation slice, the budget is insufficient for both and the tool reports
that rather than under-sampling either.

Wall-clock is estimated as:

```
T ≈ N_configs × (t_setup + n_iter × t_kernel)
```

`t_setup` (plan build, kernel load, workspace allocation) typically dominates for small problems. `uhd_gen benchmark` MUST measure `t_setup` and `t_kernel` on a calibration sample of ~100 configs and print the projected total before starting the full run, so an infeasible sweep is caught in the first minute rather than on day three.

CK's published corpus (≈5,000 GEMM shapes × ≈500 kernels ≈ 2.5M configs) sits at the `standard` budget.

Corpus size is bounded by benchmark cost and by coverage, not by model capacity. A 4,000-problem corpus against 500 variants yields 2M training rows — orders of magnitude past what a leaf-population parameter such as LightGBM's `min_data_in_leaf` constrains.

**Per-round split — a planning estimate, not a commitment.**

| Round | Share of budget | Selection |
|-------|-----------------|-----------|
| 0 | 50% | Stratified over the feasible region (§5.3) |
| 1 | 25% | 20% exploration floor, 80% evidence-targeted (§5.4) |
| 2 | 25% | Same, using signals refreshed after round 1 |

Use this to size a run. **Only round 0 is committed spend.** Whether to iterate at all is decided from
measured predictive accuracy after round 0, not assumed before any measurement exists — which makes the
stopping criterion below the decision point rather than an exit condition. A model that is already
accurate enough after round 0 should release its remaining budget to another operation or architecture
rather than backfill a corpus that has converged.

`smoke` runs round 0 only — its purpose is pipeline validation, not accuracy, and there is nothing to assess.

**Stopping is decided on accuracy, and failing it drives where the next round samples.**

The run declares an accuracy target before it starts — a maximum acceptable top-1 regret on the evaluation slice (§5.6.3). This
RFC fixes no value: what is achievable differs by operation and by how much the candidates differ from one
another, so a number written here would be the same invented threshold the corpus ranges used to be. The
target is a required input, recorded in the manifest alongside the result.

After each round the model is refit from scratch (§5.6.4), regret is evaluated on the evaluation
slice, and the run stops when any of these holds (regret on the round-0 core, so the comparison is
against the same problems each round):

1. **The target is met.** The model is accurate enough; remaining budget SHOULD go to another operation or
   architecture rather than to a corpus that has done its job.
2. **Nothing is left to target.** No region exceeds the §5.4 thresholds, so there is nowhere the evidence
   says to sample next.
3. **Budget is exhausted.**

If the target is missed and regions remain, the next round samples **where the model is inaccurate** —
§5.4's regret-concentration signal is what localizes that, and it becomes the primary allocator rather
than one of three equals.

Cases 1 and 3 mean opposite things and MUST be reported differently. Meeting the target means the corpus
was sufficient. Exhausting the budget means the corpus was the binding constraint and the model is likely
still improvable, which is the single most useful thing to know when sizing the next campaign.

Retrain from scratch each round rather than continuing the previous model. On a corpus of this size
training is minutes against benchmarking's hours, so incremental fitting saves nothing and introduces a
path dependence that makes one round's result depend on the order the data arrived.

### 5.6 Scheduling the Sparse Matrix

The budget buys `N` observations of a `problems × configurations` matrix that cannot be filled. This
section decides which cells to observe.

#### 5.6.1 The target is the joint space, not the two margins

A heuristic exists only because performance is **not** separable into a problem term and a configuration
term. If it were, one configuration would win everywhere and a fixed order would do. The signal is the
interaction: which configuration wins changes as you move through problem space.

That fixes the design criterion. Treat a measurement as one point in the joint space of `$q.*` and
`$kernel.*` features, and choose points that **cover that space** — so that no region of the interaction
surface is unobserved and every runtime query sits near evidence rather than beyond it. §5.6.2 and §5.3
supply the two halves: one member of every applicable cell on the configuration side, a stratified draw on
the problem side. The joint coverage is their product, not a separate construction.

Criteria defined on either margin alone do not achieve this, and it is worth being explicit about why,
because they look reasonable. Requiring every configuration to appear a fixed number of times, spread
evenly across regimes, is satisfiable while measuring each one only where it behaves identically to its
neighbours: structurally balanced, informationally empty. Marginal balance describes the edges of a
distribution whose interior is the thing being learned.

**Configuration completeness relaxes correctly under this criterion.** A configuration never measured is
harmless if its `$kernel.*` features sit near ones that were, because the model then interpolates rather
than extrapolates — and interpolation is what §7.3's argmax argument needs, since the danger is an
unmeasured configuration drawing an optimistic prediction from a region with no evidence. Coverage of
kernel-feature space is the requirement; visiting every configuration was always a proxy for it, and a
loose one wherever configurations cluster.

Applicability still applies: a point whose configuration does not apply to its problem is not a candidate,
so the space being covered is the applicable subset rather than the full product.

#### 5.6.2 Per-problem coverage of the configuration space

Filling the joint space does not by itself constrain what is measured *at any one problem*. A schedule can
be well spread overall while giving each problem a handful of configurations that resemble each other,
which leaves every within-problem comparison uninformative: the best of three near-identical configs says
nothing about which region of the configuration space wins there.

So the schedule carries a per-problem floor, expressed on cells rather than counts.

**A cell is a group of configurations that perform alike.** Cells partition the configuration space on
`$kernel.*` features — the kernel-side analogue of the problem regimes of §4.3.4 — and one member
represents a cell only to the extent its members are interchangeable. That is what makes the count a
consequence rather than a choice: a space of thirty configurations that all behave differently refines to
thirty cells and is measured exhaustively, while a space of a million minor variations stops refining once
splitting no longer separates anything.

**Every sampled problem MUST measure one configuration from every cell applicable to it.** A cell is
applicable to a problem when at least one member applies there (§7.1). Cost follows:

```
N_configs ≈ N_problems × N_cells_applicable(problem)
```

`N_cells` is an outcome of refinement, not an input. The evaluation slice of §5.6.3 is the limit case
where every member of every cell is measured rather than one, not a different mechanism.

Which cell is fixed corpus-wide; which *member* of the cell is drawn rotates across problems by the run's
seed. So every problem spans the whole space, while the union across problems still reaches cell
interiors. This is also what makes §5.4's boundary-density signal readable: two neighbouring problems are
compared over the same cells, so a change in the winner is a real change rather than an artifact of
different menus.

##### 5.6.2.1 Deriving the partition

The partition is derived, not authored. Kernel developers supply nothing beyond what RFC 0017 already
requires of the KMD — the configuration set (an explicit list, or fields and ranges expanded through the
validity predicate), each configuration's `$kernel.*` values, and the applicability predicate.

**Round 0, before any measurement.** Nothing has been timed, so the partition can only come from the
declared structure:

```
levels(knob) = distinct values if few, else quantile bins over the KMD range
               (log-spaced where the knob scales multiplicatively — tiles, unroll, split counts)
rank knobs by level count, descending
cells := { all configurations }
for knob in ranked knobs:
    if |cells| × levels(knob) > cells_allowed: break
    cells := cells crossed with levels(knob)
drop empty cells; merge any cell below a minimum member count into its nearest neighbour
```

Knobs enter coarsest-first, so the axes carrying the most distinct values structure the partition before
near-binary ones do. `cells_allowed` is the budget divided by the problem count — the single quantity a
run declares (§5.5), not a separate parameter.

**Round 0 opens with a pilot, so the guess is measured rather than trusted.** The crossing above orders
knobs by how many values they take, which is a statement about the declaration and not about performance:
a knob with many levels that none of them separate structures the partition ahead of a binary knob that
splits it cleanly. Nothing in the declaration distinguishes those two, and round 0 would otherwise pay for
the whole corpus before finding out.

So round 0 runs in two parts. The first spends a small share of its budget measuring the coarse partition
on problems drawn by §5.3, at a cell count well below `cells_allowed`. The refinement rule below then
runs on that evidence, and the partition it produces is what the rest of round 0 samples against.

This costs a fraction of one round and answers the question the declared structure cannot: which knobs
actually separate performance. It also fails usefully — a pilot whose cells all split says the space is
finer than `cells_allowed` can resolve and the run is under-budgeted for its catalog (§5.5), which is
worth learning before the budget is spent rather than after.

**Later rounds, from measurements.** Performance is problem-dependent, so a cell must group configurations
that behave alike *across* problems, which requires normalising within each problem before pooling:

```
y[p, c]  := t[p, c] / best_measured_t[p]        # relative to the best seen on that problem
noise    := run-to-run reproducibility, from the repeat sample of §8.5.1 — NOT stddevMs,
            which is jitter within a single invocation and understates it

grow a regression tree on $kernel.* features predicting y:
    split on the knob and threshold that most reduces within-node spread of y
    stop when within-node spread <= noise        # members are indistinguishable
              or node members < minimum
              or leaf count reaches cells_allowed
cells := leaves
then merge adjacent leaves whose pooled spread stays under noise
```

The merge step lets the partition shrink where round 0 over-split, so the two directions are symmetric:
splitting where the space proved finer than the declared structure suggested, merging where it proved
coarser.

**Why this partition and the model are the same object.** The tree is grown on kernel features against
normalised performance, which is a projection of the heuristic itself. A cell that stops splitting holds
configurations the model cannot distinguish, so measuring more of them buys nothing — which is exactly the
property the per-problem floor needs.

**Two dependencies this creates.** The split rule terminates against measurement noise, and which noise
matters: the question is whether two configurations would still differ if both were re-run, so the
threshold is run-to-run reproducibility and not the within-invocation jitter `stddevMs` records. Using the
narrower number makes the tree split on differences that would not survive a re-run, producing more cells
and more measurements per problem, all resolving noise. §8.5.1 supplies the repeat sample this needs. And
round 0's `cells_allowed` fixes round 0's cost before any evidence exists that the partition is the right
coarseness — recorded as a gap in §13 rather than settled here.

The partition is recorded per round in the manifest, so a run can show where the configuration space
turned out finer or coarser than the declared structure implied.

#### 5.6.3 Training and evaluation want different shapes

The cell rule of §5.6.2 makes a problem's best measured configuration meaningful — it is the best across
the configuration space, one member per applicable cell. But it is still one member per cell. `v*(p)` — the
best configuration for `p` — is exact only where every member of every cell was measured, so regret
computed off the training slice is a lower bound: it cannot see a loss to a cell-mate that was never run,
which is precisely the interchangeability the partition assumes rather than proves.

So the budget splits by purpose rather than being one schedule asked to serve both:

**Training slice — problems by stratified draw, configurations by cell.** The bulk of `N`. Problem
coordinates come from the footprint-first draw of §5.3; configuration coordinates from one member of every
applicable cell (§5.6.2). The joint space is covered as the product of the two rather than by any separate
construction over it.

**Evaluation slice — a fraction of the problems, measured exhaustively.** Every applicable configuration is
measured on each, so `v*(p)` is the true best and regret is exact rather than a lower bound. The run
declares the fraction rather than a count, so the slice scales with the tier; its cost is that fraction of
the problem count times the applicable configuration count, which the tool projects before committing
spend.

Selecting the evaluation slice:

- **Drawn before measurement**, from each round's generated problems, using the run's seed. Choosing it
  from results would bias it.
- **Append-only across rounds.** The slice grows with the corpus — each backfill round draws its share
  from that round's new problems, before they are measured, at the same declared fraction — but every
  earlier member is kept. Growth adds precision; resampling would make successive regret figures
  incomparable, which is the one thing the loop needs them to be.

  Two regret figures follow, and both are reported: the round-0 core, an even spread over the same
  problems every round, which shows whether the model is improving; and the full slice, weighted toward
  complexity by construction, which is the better estimate of accuracy on the corpus as it ended up.
  Divergence between them is the corpus telling you the added regions are harder than the original draw —
  worth seeing rather than averaging away.
- **Even at round 0, complexity-following afterwards.** Round 0 has no evidence about where behaviour is
  complicated, so it spreads evaluation problems evenly across regions — a uniform prior, and a guarantee
  that no region lacks a regret signal for §5.4 to act on. Every later round draws its share from that
  round's new problems, which backfill has already concentrated in the regions that proved hard, so
  evaluation density comes to follow complexity without anything having to declare where it is.

  Within a region, problems are drawn by §5.3's method so a small set still spans the joint space.

  Neither figure is proportional to a real traffic distribution, so **regret is reported per region** and
  any aggregate states the weights that produced it (§5.2, §11.2). A raw mean over the slice would
  under-weight dense regions at round 0 and over-weight them later.
- **Exempt from pruning.** Dropping a configuration from the training schedule is a budget economy;
  dropping it from the evaluation slice removes it from the oracle, which is the corruption §5.5's prune
  is otherwise warned about. The evaluation slice stays exhaustive for the whole campaign, which is also
  what lets §11.3 measure directly what a pruned configuration would have contributed.
- **Sized visibly.** A small slice means the regret estimate has sampling error; the report carries the
  problem count so the precision is legible.

#### 5.6.4 Three instruments, three jobs

The corpus supports different measurements in different places, and conflating them is how a number that
cannot move ends up steering the loop.

| Instrument | Computed on | Answers |
|---|---|---|
| Out-of-fold prediction error | The whole corpus | How well the model predicts timing |
| Top-1 regret | Evaluation slice only | Whether the model picks the right configuration |
| Mechanical validity | Everything else | Whether the pick is applicable and its predicted time matches its measured one |

Out-of-fold, over everything, validates the body of data against itself: every row is scored by a model
trained without it, so accuracy is measured everywhere rather than on a corner. Regret is confined to the
evaluation slice, because knowing whether a pick was *best* requires knowing what the alternatives would
have done, and only there do we. On a problem covering a fraction of the cells the pick can still be
checked — that the configuration is applicable, that its predicted time matches its measured one — but not
verified, since the alternatives were never run.

**Folds are by problem.** §2.6's GroupKFold puts all of a problem's rows in one fold, so the model scoring
an evaluation problem never trained on that problem. Other evaluation problems remaining in training is
not a leak; scoring a problem with a model that saw it would be.

**Models MUST be refit from scratch each round.** Grouping only protects the current fit. A model
warm-started on an earlier round carries evaluation rows in its parameters that no later fold assignment
can remove, and the regret figure decays round over round with nothing in the numbers to show it. Fitting
costs minutes against benchmarking's hours, so incremental fitting buys nothing worth that exposure. Each
round records which model was scored, and whether it was refit or continued — a round that appends data
without refitting has invalidated its own regret figure and the manifest must be able to show it.

**A reserved portion supplies the reported number.** §5.5 stops when regret meets its target and §5.4 aims
backfill where regret is worst, so the regret the loop reads is being optimised against. That is selection
rather than leakage — the loop never trains on it — but it is enough to stop the number estimating what it
did. A portion of the evaluation slice, never consulted for stopping, backfill, feature selection or
hyperparameters, supplies the figure that is reported. The manifest records which portion produced which.

**Backfill drift.** Backfill targets regions where regret is worst, which are regions the evaluation slice
occupies. Adding problems near evaluation problems is not leakage under grouping, but it does make the
slice progressively easier. Recording the distance from backfilled problems to evaluation problems keeps
that drift visible rather than silent.

#### 5.6.5 Declared Quantities and Their Defaults

Five quantities parameterise the schedule. Each has a default, and each is overridable — the defaults are
starting points chosen to be defensible, not values this RFC claims are optimal. All are recorded in the
manifest, so a run that overrode one is legible later.

| Quantity | Default | Anchored to |
|---|---|---|
| Evaluation share | 10% of budget | Expressed as budget share rather than a problem count, because an evaluation problem costs every applicable configuration while a training problem costs one per cell — the ratio between them varies by catalog, so a fixed problem count would swing wildly in cost |
| Evaluation floor | 30 problems per region | §5.5's existing stratification floor, reused rather than a second invented number |
| Pilot share | 5% of round 0 | Large enough to refit a coarse partition, small enough that a wasted pilot is not a wasted round |
| Response normalisation | `t[p,c] / best_measured_t[p]` | Scale-free across problems, and proportional to regret — the quantity being minimised. Absolute or log-absolute time is the alternative, and weights large problems more heavily |
| Repeat-sample share | 1% of pairs, floor 200, cap 2000 | The noise floor is a median, whose precision improves with the square root of the sample; a few hundred stabilises it and more buys little |

**The problems-versus-cells trade has no default, and should not.** `cells_allowed = budget / N_problems`
is the one place a run states what it is buying, and the two sides fail differently: too few problems and
the model interpolates across gaps in problem space; too few cells and configurations that differ are
asserted to be interchangeable. §5.10's truncation counts report which way a run erred, and the pilot
above gives an early read before the budget is committed.

#### 5.6.6 What is not settled

The joint space is covered as a product — problems by stratified draw, configurations by cell — so there
is no separate design to construct over it. What remains open is whether the partition earns its cost.

**Unvalidated.** No evidence yet shows that one-member-per-cell beats the same number of configurations
drawn at random per problem. The partition is where all of this section's machinery went, so that is the
comparison that matters, and structural properties of a partition — cells that separate, spread below
noise — are proxies for model quality rather than measurements of it. The first campaign should run a
random-per-problem arm alongside — and §8.7 makes that cheaper than a second campaign, since both arms are
selections over one exhaustive collection rather than two sets of measurements. If random matches it, the
simpler construction wins and this section reduces to a count.

**Unmeasured.** The defaults above are anchored, not derived. Each is a candidate for tuning once a
campaign has run, and the manifest records them precisely so a later run can tell which value produced
which result.

### 5.7 Corpus Location

RFC 0019 Open Question 10 leaves open whether the shape corpus lives in a tool-side config or a descriptor field. **This RFC places it tool-side**, as the versioned JSON artifact of §5.9.

The corpus is a training input, not a runtime contract. Nothing at selection time reads it, so a descriptor field would ship sampling policy inside the engine and force a descriptor version bump on every corpus revision — including the backfill rounds of §5.4, which revise it by design. Reproducibility, which is what motivated the question, is met instead by the provenance the artifact carries (§5.9) and by the manifest reference from the training run (§10.5).

What remains descriptor-side is the *knob* grid, not the shape corpus: a validity constraint expresses which values are legal, not which to sample, so an irregular knob axis still needs an explicit sweep hint. That part of Open Question 10 is untouched here and belongs with the enumeration gap (§13, S1).

### 5.8 Determinism and Provenance

Corpus generation MUST be reproducible. Given identical `(operation, tier, seed, generator_version,
metadata_hash, config_set_hash, applicability_id, cells_allowed)`, generation produces identical output.

- `seed` is REQUIRED in corpus metadata; if not supplied on the command line, the tool generates one and records it.
- All sampling MUST draw from a seeded generator instance (`np.random.default_rng(seed)`). Module-level `np.random` MUST NOT be used.
- `metadata_hash` records the SHA-256 of the operation metadata file, so a corpus cannot be silently invalidated by an edit to the op definition.
- `config_set_hash` records the enumerated configuration set, canonically hashed (§8.7). It is a generation
  input rather than provenance alone: the configuration set determines the cells (§5.6.2), and the cells
  determine what is measured at every problem. Hashing the enumerated set rather than the KMD file means
  the value moves when the candidate set moves and not when an unrelated field is edited.
- `applicability_id` records the problem-dependent applicability predicate, whose changes do not show up
  in the configuration set (§8.7).
- `cells_allowed` is recorded because §5.5 lets a run trade problem count against partition resolution, so
  the tier alone does not fix it. Two runs at one tier can partition differently and both be correct.

Backfill rounds are reproducible only relative to their inputs: they depend on measurements and on the model trained from prior rounds. A backfill increment therefore records `input_model_hash` alongside its seed. Replaying a full campaign requires the round-0 seed plus the recorded per-round inputs; replaying round 0 alone requires only the seed.

The same holds for the partition from round 1 onward: it is refit from measured times (§5.6.2.1), so it is
reproducible given the same measurements and not from the seed alone. Round 0's partition, derived from
declared structure only, is reproducible from the tuple above.

2. `metadata.regimes` values sum to `metadata.count`.
3. `metadata.rounds[*].count` values sum to `metadata.count`.
4. All entries in `problems` have identical `q.*` key sets.
5. All `q.*` values are JSON primitives.
6. Every `q.*` key corresponds to a parameter declared in the operation metadata.
8. Every backfill round has `exploration_fraction >= 0.20`.

### 5.10 Coverage Reporting

The generator MUST emit `axis_occupancy` and per-regime counts, and MUST warn when any bucket on the declared stratification axis holds fewer than 30 problems. A corpus that silently collapsed into one roofline bucket, or that missed an entire regime, is otherwise indistinguishable from a good one until the model underperforms.

**The partition MUST be reported alongside the corpus.** It decides what was measured at every problem
(§5.6.2), so a corpus is not interpretable without it. Per round: the cell count, how the partition was
derived — round 0's knob crossing or a refit tree (§5.6.2.1) — the distribution of members per cell, and
two counts that separate a converged partition from a truncated one:

- **Cells that never split**, meaning the configuration space proved coarser than the declared structure
  implied. Measuring more of those configurations would have bought nothing, which is the good case.
- **Cells sitting at the minimum member count, or leaves cut off by `cells_allowed`**, meaning refinement
  stopped because it ran out of room rather than because the members stopped differing. Those cells are
  asserting an interchangeability the measurements do not support.

Both produce the same regret figure and need opposite responses — the second says raise the budget or
lower the problem count, the first says the run is already resolving everything it can.

**A probed bound MUST be reported as probed.** §5.3 locates bounds by bisecting the engine's
applicability predicate, which assumes a monotone region that alignment and divisibility rules make
non-monotone. The number is still useful and it is not the same kind of fact as a declared range, so
the report carries which dimensions were probed, the bound found, and the probe count behind it. A
reader who cannot tell a measured boundary from a declared one will eventually treat a hole as an
edge.

**The evaluation slice's composition MUST be reported per round.** Round 0 spreads it evenly across
regions; later rounds draw from their own new problems, so it drifts toward wherever backfill went
(§5.6.3). That drift is what explains a divergence between the round-0 core figure and the full-slice
figure, and without it the two numbers just disagree.

From round 1 onward the report MUST also carry, per round: boundary density by region, regret before and after the round, and the fraction of the round spent on exploration versus targeting. This is what makes backfill auditable — without it there is no way to distinguish targeting that found real boundaries from targeting that chased noise.

## 6. Kernel Variant Enumeration

### 6.1 What the Parent Fixes

Two things are settled by RFC 0019 and are not this RFC's to revisit.

**The variant space is the shipped kernels.** RFC 0019 §13.5: "The variant space is fixed: it is the
pack's existing child UKDs, so the generator does not enumerate or build variants but enrolls the shipped ones
and times them." Generation never invents a kernel. Deciding which variants should exist is the
package-creation stage of RFC 0019 §14, upstream of everything here.

**Addressing them is the unsolved part.** Autotune reaches a kernel only through exposed knob settings
(RFC 0019 §13.2), and knob ranges are reported per knob, independently. So the addressable set is the
Cartesian product of the axes, of which — for a sparse catalog — most combinations name no kernel. Cost
scales with the product rather than with the catalog, `add_engine_sweep()` caps the product at 10,000, and
nothing expresses which combinations are valid. RFC 0019 records this as **Open Question 12**, states that
it "requires an API improvement, tracked outside this RFC", and says the generation pipeline "depends on
it for the harder cases."

**The KMD declares the variant space** (§6.2). It carries either an explicit list of the configurations
the engine's kernels occupy, or the fields with their ranges plus a validation function that says which
combinations are real. Either form describes the shipped kernels; neither invents one, so RFC 0019 §13.5
holds.

Q12 is narrower than it first appears against that. It concerns a consumer holding only an engine id —
knob ranges reported per axis, nothing saying which combinations exist. The generation tool is not in that
position: it loads the descriptor set already, because §10.4 has it emit an updated UED. Q12 is owned with
the hipDNN API and **this RFC does not resolve it**, but it does not block generation.

### 6.2 How the Generator Obtains the Variant Set

**Preferred — read it from the KMD.** The declaration (§6.3) gives the variant set directly:

- *Explicit configurations.* The list is the variant set. Enrol it.
- *Fields, ranges and a validator.* Form the product of the declared ranges and keep what the validator
  accepts. The validator is what makes this tractable on a sparse space, where most of the product is not
  real.

**Fallback — read it from the catalog.** A KMD that does not yet carry a variant declaration still leaves
the information available: RFC 0019 §13.5 fixes the variant space as "the pack's existing child UKDs", and
each UKD's `metadata` is one valid configuration. Collecting those tuples yields the same set the explicit
form would have declared. This is the route taken against a KMD written before the declaration exists,
and it costs nothing extra, since the tool loads the descriptor set anyway.

**Enrol explicit tuples either way.** `add_engine_variants()` takes `(engineId, knobSettings)` pairs
directly. RFC 0019 §13.2 places the 10,000-combination cap on `add_engine_sweep()`, which enrols the
Cartesian product of knob axes — a path neither route above takes. Sweeping is what "turns an intractable
sweep into a rejected one"; enrolling a known set does not meet the cap at all.

**Report what was enrolled against what exists.** Under the validator form, record how much of the product
survived; under either form, record the enrolled count. A ratio that collapses says the declared ranges
are far wider than the real configuration set, which is worth knowing before it is mistaken for a coverage
problem in the corpus.

### 6.3 What the Generator Requires of the KMD

The KMD's schema is RFC 0017's, not this document's. What matters here is only the shape of the
information generation consumes, which takes one of two forms:

**An explicit set of configurations.** The KMD states the configurations its kernels occupy. The generator
enrols them as given. This is the cheaper form for a sparse or irregular space, where the set is small and
nothing about it is regular enough to compress.

**Per-axis values plus a validity predicate.** The KMD states the values each axis takes, and supplies a
predicate answering whether a given combination is real. The generator forms the product and keeps what
the predicate accepts. This is the cheaper form for a dense space, where enumerating every configuration
would be large but the axes are regular.

The predicate is necessary rather than incidental. Per-axis values alone cannot express a constraint
spanning axes — that `tile_m × tile_k` must fit LDS, that two knobs are mutually exclusive — and RFC 0019
RFC 0019 §13.5 makes the same observation about `[min, max, step]`, noting it leaves *cross-knob* validity
unaddressed. Without the predicate the second form cannot describe a real engine.

Two properties this document depends on, whatever spelling RFC 0017 gives them:

- **The predicate is problem-independent.** It answers whether a configuration exists, not whether it
  suits a graph, which is what separates it from `is_applicable_config` (§7.1). It is therefore evaluated
  once per configuration rather than once per pair.
- **Neither form invents a kernel.** Both describe configurations the engine already ships, so RFC 0019
  RFC 0019 §13.5's "the variant space is fixed" holds under either.

The generator reaches the predicate through the backend, on the same grounds as §7.1: tooling does not
load provider objects directly.

### 6.4 Alignment Regimes Depend on the Catalog

A regime declared with `"derived": "alignment"` (§4.3.5) cannot be resolved until the variant set is known — "aligned" means aligned with respect to *these* tile sizes. Variant enumeration therefore runs **before** final corpus generation, and the tile values discovered here feed the alignment buckets. Concretely, the pipeline order is: enumerate variants → derive alignment buckets → generate corpus → filter → benchmark.

## 7. Applicability Filtering

### 7.1 Where Filtering Happens

The UHD is owned by the engine, and the engine is already registered with the hipDNN backend through the plugin loader. Tooling therefore MUST invoke applicability **through the backend API**, using the `engine_id` from the engine descriptor.

`uhd_gen` MUST NOT `dlopen` provider shared objects or resolve provider symbols with `dlsym`. Doing so bypasses the backend's plugin lifecycle and would give tooling a second, divergent view of which engines exist.

The C entry points below are the **provider-side contract** — what a provider implements so the backend can route to it. They are not the interface tooling calls.

```cpp
// Provider implements in the KMD library; backend routes to it.
extern "C" bool <provider>_is_applicable(
    const uint8_t* graph_flatbuffer,  // serialized hipDNN graph
    size_t         graph_size,
    int64_t        engine_id,
    char*          error_msg,         // optional; may be NULL
    size_t         error_msg_capacity);
```

Returns `true` when the provider can execute this graph with this engine; `false` otherwise, with the reason written to `error_msg` when that buffer is non-NULL. The reason string is not decorative — §7.4 records it.

**Three predicates, distinguished by what they take.** They are easy to conflate because two of them
concern kernel configurations:

| Predicate | Takes | Answers | When |
|-----------|-------|---------|------|
| `is_applicable` | graph | Can this engine run this problem at all? | Once per problem (§7.1) |
| `is_valid_config` | variant | Is this kernel configuration real? | Once per configuration, at enumeration (§6.3) |
| `is_applicable_config` | graph + variant | Can this configuration run this problem? | Once per pair (§7.5) |

`is_valid_config` is problem-independent — it encodes constraints like "`tile_m × tile_k` must fit LDS",
which hold regardless of what is being computed. `is_applicable_config` is the per-variant sibling of
`is_applicable`, and is the only one of the three whose cost scales with the product of problems and
variants.

**Provider precedent.** rocKE pre-filters explicitly via `miopenConvolutionForwardGetSolutionCount() > 0` rather than discovering inapplicability by failure. hipDNN adopts explicit pre-filtering.

### 7.2 The Native Scorer Signature

RFC 0019 §7.1 permits a native scorer to work in either of two modes — consume the standard feature row, or featurize from the engine's bindings itself — but specifies neither signature. The only C ABI the parent writes down is `custom_library`'s (RFC 0019 §7.4). That omission is why the two existing implementations chose different signatures independently, and it is filled here.

**Mode 1 — feature row.** The scorer receives the row the extractor already produced from `features_signature`, in declared order. This is the same C ABI `custom_library` uses, so a single implementation can be reached either way — registered in-process as `native`, or exported from a `.so` as `custom_library` — without changing its signature.

```cpp
// Registered with the UHD scorer registry; also the custom_library export ABI.
extern "C" double <symbol>(const double* features, size_t num_features);
```

`features` is in `features_signature` order and `num_features` matches the UHD's declared feature count. Implementations MUST be thread-safe. Return value is in the units the UHD's `score` metadata declares.

**Mode 2 — bindings.** The scorer receives the match context and featurizes itself. This is the kernel ingestor's existing `ScoreFn`, and a scorer written for it participates in the ingestor's selection path rather than the UHD adapter path:

```cpp
using ScoreFn = double (*)(const MatchContext&, const BoundTokens&, const KernelDefinition&);
```

**Which mode to use.** Mode 2 is the escape hatch RFC 0019 §7.1 describes — a heuristic no model expresses, needing inputs the feature row does not carry. Mode 1 is required for the **baseline** role: RFC 0019 §9 defines the `tree_data` overhead target as within 2× of `native`, and RFC 0019 §9.4 requires feature extraction and scoring be wall-clocked separately. A mode-2 scorer featurizes inside its own call, so timing it against a `tree_data` that goes through the generic extractor measures two different things and the ratio is meaningless.

**Why they are separate registries.** The two signatures are not convertible, so one registry cannot serve both. Both are instantiations of the ingestor's `NativeRegistry<T>` template — mode 1 as `NativeRegistry<UhdScoreFn>`, mode 2 as the ingestor's own `ScoreRegistry` — so the mechanism is shared even though the contracts are not. A UHD declaring `adapter: NATIVE` names a mode-1 symbol; `HeuristicKind::NATIVE` in the ingestor's descriptor names a mode-2 symbol. A symbol registered in one is not visible to the other, and that is deliberate rather than an oversight.

### 7.3 The Candidate-Set Invariant

**Normative.** For any problem `p`, the set of variants scored by the UHD at runtime MUST be a subset of the variants **eligible** at training time — that is, the same `is_applicable` / `is_valid_config` predicates MUST gate both paths.

Two obligations follow:

1. **The same predicates run on both paths.** Whatever combination of `is_applicable`, `is_valid_config` and `is_applicable_config` filtered the training corpus MUST also gate the runtime candidate list before scoring. A provider that filters at training but not at runtime is asking the model to rank configurations its predicates declared impossible.
2. **Predicate changes invalidate the model.** If a provider tightens or loosens either predicate the eligible set shifts, and the model MUST be retrained. The training manifest records the predicate versions (§10.4) so this is detectable.

Problem-level applicability is exempt in one direction: if `is_applicable(p)` is false the UHD is never consulted for `p`, so dropping those problems from training is safe.

**Eligible is not the same as benchmarked.** The invariant constrains which variants are *scored*, not which were *measured*. Variant knobs are numeric, so a model interpolates across tile configurations it has not seen exactly as it interpolates across unseen problem shapes; subsampling the variant space is therefore sound, and for dense knob spaces it is unavoidable (§13, S1).

What subsampling requires is **measurement of the resulting error**, and here variants differ from problems in a way that matters:

- An unseen **problem** yields one prediction per candidate; ranking errors partly cancel.
- An unseen **variant** competes in an argmax. Selection preferentially returns whichever candidate received the most optimistic error — the optimizer's curse — so the quantity that governs runtime quality is the model's error at the *top* of the predicted distribution, and it worsens as the catalog grows.

Two consequences, both already required elsewhere. Variant sampling MUST cover the configuration space
evenly rather than densely in one corner, because a thinly-sampled corner is where an inflated score goes
unchallenged; §5.6.2's cell rule supplies that directly — every problem measures one variant per
applicable cell, so no corner is thin by construction, and an unmeasured variant is always represented by
a cell-mate the model has seen. And §11.3 MUST include a leave-variants-out split, so the regret
attributable to unmeasured variants is a reported number rather than an assumption.

That second obligation is where §5.10's truncation counts feed back: a cell cut off by `cells_allowed`
holds members whose interchangeability was assumed rather than measured, so it is exactly the population
the leave-variants-out split should be drawn from.

### 7.4 Recording Filtered Pairs

Pre-filtering saves benchmark time but destroys the record of what was filtered, which is the same record needed for coverage auditing (§5.10) and for diagnosing an over-narrow predicate.

Filtered pairs MUST therefore be recorded — but in the run's report, not as rows in the results. A pair
that was never a candidate is not a measurement, and a configuration the model will never be asked to
rank contributes nothing to training. Carrying it as a row costs a validity flag on every row, a reason
column that only a human reads, and a set of rules to keep the two consistent; and it makes two
collections appear to have had different candidate sets when they did not, because the tuple comparison
that guards a merge (§8.3) then sees pairs that were never measured.

The results file holds what was attempted. A pair that was attempted and failed keeps its row, with the
timings null and `error` populated, because that failure *is* information about a candidate. A pair that
was never eligible leaves the coverage record to the report.

```csv
q.M,q.N,q.K,kernel.tile_m,…,minTimeMs,avgTimeMs,tflops,error
1024,1024,1024,128,…,0.123456,0.124011,17.4,
1024,1024,1024,256,…,,,,HIP error 700: illegal address
```

Only the two problem-dependent predicates produce rows here. A configuration rejected by
`is_valid_config` — one that is not a real kernel on any problem, such as a tile pair exceeding LDS — is
filtered at enumeration (§6.2) and never enrolled, so it has no pair to record. If such a configuration
does reach benchmarking, the variant set was built wrong rather than the problem being unsuitable, and
that is worth failing on rather than logging.

### 7.5 Benchmark Execution Order

```
for problem in corpus:
    graph = build_graph(problem)                      # §4.3.6
    if not backend.is_applicable(graph, engine_id):   # §7.1
        record_skipped(problem, all_variants, "not_applicable: " + reason)
        continue
    for variant in variants:                          # §6
        if not backend.is_applicable_config(graph, engine_id, variant):
            record_skipped(problem, variant, "config_not_applicable: " + reason)
            continue
        record(benchmark(graph, engine_id, variant))
```

## 8. Benchmark Dataset Construction

### 8.1 Autotune Integration

Timing goes through the RFC 0013 autotune API (§2.2), not standalone per-kernel executables. Variants are enrolled with `add_engine_variants()` (explicit) or `add_engine_sweep()` (range), and timed with `autotune(mode=EXHAUSTIVE, strategy=RUN_UNTIL_STABLE)`.

Autotune itself is RFC 0013's and is out of scope here (RFC 0019 §2). This section specifies only what the generation tool does around it.

Long runs (hours to days at `standard` and above) require progress reporting and checkpointing: the benchmark step MUST write results incrementally and MUST be resumable from a partial CSV. This requirement is why collection is CSV and not the published Parquet (§8.3): a partial CSV is every row written so far, while a Parquet file killed before its footer is written is not readable at all.

### 8.2 The Kernel-Identity Contract

Per RFC 0019 §13.3, the candidate autotune timed MUST map 1:1 to the UKD it stands for in the emitted engine, so that the model's argmax over timed candidates is exactly argmax over UKDs at runtime. The join key is the knob tuple reported on each result; under full exposure (§2.2) that tuple is the kernel's metadata tuple, unique engine-wide.

Two obligations, both on the generation tool:

1. **Verify the round-trip.** The tool MUST confirm that the `knobSettings` reported back on a result select the same kernel they enrolled, rather than assuming it. An unverified join silently mislabels every row it touches.
2. **Treat a tuple collision as a dataset error.** If two enrolled candidates share a knob tuple, timings cannot be attributed to a kernel. Under full exposure this cannot happen, so a collision means the generation UED did not expose every KMD field. The tool MUST **fail loudly** rather than train on an ambiguous join.

The runtime case is different and benign: once the emitted UED exposes only the model's feature axes, two kernels differing solely in dispatch-only fields share a knob tuple, score identically, and are separated by the `priority`/`id` tie-break with a load-time warning (RFC 0019 §3.2).

### 8.3 Benchmark Result Schema

One schema, two encodings, because collection and consumption want opposite things.

**Collected as CSV.** UTF-8, RFC 4180, header row required. Columns are read by name; order is arbitrary. Null is the empty string. Booleans are `True`/`False` (case-sensitive). Floats carry ≥6 significant digits.

**Published as Parquet.** The aggregation step (§8.8) reads the collected CSVs, validates them against the rules below, and writes a single Parquet dataset. That dataset is what training consumes; the CSVs are the durable intermediate, not the artifact.

The split is not a preference. A run at `standard` or above lasts hours to days and MUST be resumable from a partial result, and shard outputs MUST merge cheaply. Parquet places its footer at the end, so a writer killed mid-run leaves an unreadable file where a truncated CSV is still every row it managed to write; and a Parquet file cannot be appended to, so a merge would be a full rewrite rather than a concatenation. Collecting as CSV keeps both properties. Publishing as Parquet gives training a typed, columnar dataset with the string columns dictionary-encoded rather than repeated per row — which matters at 10^4–10^6 rows.

Aggregation is also the only place the rules below are *enforced*. While the result was a CSV that training read directly, nothing sat between producer and consumer to check them.

**Required columns**

| Column | Type | Description |
|--------|------|-------------|
| `q.*` | varies | Problem parameters, namespace-qualified |
| `kernel.*` | varies | Kernel variant knob values |
| `device.*` | varies | Device properties (provenance; see §3.3 for their use as features) |
| `minTimeMs` | float | Minimum time across iterations. Null when the measurement failed |
| `avgTimeMs` | float | Mean time across iterations. Null when the measurement failed |
| `stddevMs` | float | Standard deviation across iterations. Null when the measurement failed |
| `iters` | int | Iterations actually timed. Null when the measurement failed |
| `tflops` | float | Achieved throughput, derived. Null for a memory-bound operation and where there is no measurement. RFC 0019 §11.3's calibrated cross-engine metric |
| `gbs` | float | Bytes moved per second, derived. Null where there is no measurement. The metric that ranks a memory-bound operation, where `tflops` is a small number that says nothing |
| `error` | string | Why a measurement was attempted and failed; empty otherwise |
| `problem_complete` | bool | Every applicable configuration for this problem was measured. Default `True` when absent |
| `shard_id` | int | Which shard produced the row; `0` unsharded. Collection only — see below |

**Null is the empty CSV field**, and it is the whole signal that a row has no measurement. There is no
separate validity flag: timings absent and `error` populated says the pair was attempted and broke;
timings present says it was measured. A flag would be a third thing to keep consistent with the two that
already carry the answer.

Null rather than zero, though a time of zero is equally impossible and equally recognisable. The
difference is which way each fails when a consumer forgets to check. Null drops out of sorts and
aggregations; zero sorts *first* in any ranking on time, and derived it is worse still, since dividing by
it yields an infinity that beats every real value in a ranking on throughput. An unhandled zero does not
merely leak through — it presents as the best row in the corpus.

**Rows exist only for pairs that were attempted.** A configuration filtered as inapplicable is not a
candidate and leaves no row; recording it would add nothing to a model that ranks only applicable
configurations, and would make two collections appear to have had different candidate sets when they did
not.

**`shard_id` is collection-only.** It distinguishes the CSV parts of a distributed gather and means
nothing once they are merged, so it is not carried into the published dataset.

**Derived, not collected.** `tflops` and `gbs` are computed during aggregation from a declared
quantity and the measured time: `tflops = flops / time`, `gbs = elements * width(dtype) / time`.
`flops` and `elements` are declared per operation in its `.opmeta.json`, closed-form over `$q.*`
and free of anything the runtime measures — `2*M*N*K` is the same count however a matmul is tiled.
A producer that already has the metrics may supply them and aggregation takes them as given;
one that has only a time gets them computed. Neither is asked for.

`flops` is declared only where a FLOP count is canonical — matmul, SDPA and convolution.
Layernorm is variously 4, 5 or 8 operations per element depending on what is counted, and those
operations are memory-bound in any case, so `tflops` is null for them and `gbs` is their metric.
`elements` is declared for every operation, because an element count is unambiguous where a FLOP
count is not.

**Validation rules**

Checked by aggregation, which is the only place they can be enforced: while training read the collected
CSV directly, nothing sat between producer and consumer to apply them.

- Every `q.*` key from the corpus, every `kernel.*` field from variant enumeration, and every `device.*`
  property queried appears as a column.
- For a row carrying a measurement: `minTimeMs ≤ avgTimeMs`, and `stddevMs ≥ 0`.
- A row has either a measurement or an `error`, never both and never neither. Timings, `iters`, `tflops`
  and `gbs` are null together; `error` is populated exactly when they are.
- `tflops` is non-null for a compute-bound operation with a measurement — it is the metric §11.3 compares
  across engines, and a corpus without it trains a model that can rank within its own engine and say
  nothing about how that engine compares to another. It is null throughout for an operation whose FLOP
  count is a convention rather than a fact; `gbs` is that operation's metric.
- `problem_complete` is identical across all rows sharing a `q.*` key, and false for any problem where an
  attempted configuration errored. A configuration that was a candidate and could not be measured means
  the space was not fully measured, and regret over it is a lower bound rather than exact — a hardware
  fault on one pair should downgrade that problem's completeness, not discard a multi-hour sweep.
- Rows sharing a `q.*` key and marked `problem_complete` carry the same set of `kernel.*` tuples. A merge
  spanning two different candidate sets is rejected rather than silently reinterpreted: added
  configurations mean the runtime offers candidates never trained on, and argmax seeks the most
  optimistic extrapolation. Compared as tuple sets rather than against a recorded hash, because the
  tuples are on the rows and can be checked, where a hash is a token whose correctness rests on the
  producer having set it honestly.

**Feature columns are produced by the shared extractor, not by this schema.** RFC 0019 §13.3 requires one generic extractor to run the `features_signature` on both sides — offline for training, the in-tree evaluator for inference — reading the same signature, so there is no reimplementation and no drift. The column list above therefore describes the *dataset envelope* (timings, errors, completeness); the feature columns within it MUST be emitted by running the signature through that extractor rather than assembled independently by the benchmark step. A training↔runtime parity test comparing the two evaluations on identical inputs is RFC 0019's Phase 4 deliverable and gates use of the generic extractor.

### 8.4 Target Metric

The target is derived from the operation's FLOP count (§4.3.3), not hardcoded per operation:

```
tflops = $<op>.flops / (minTimeMs * 1e9)
```

`$<op>.flops` is the precomputed binding field, read from the bound graph for that problem, with the
host-side interim of §4.3.3 applying until the field exists.

All column references MUST be namespace-qualified (`q.M`, not `M`) per §8.6.

Alternatives, all narrower: `tflops / theoretical_peak` for a 0–1 efficiency scale; bytes/sec for bandwidth-bound ops, computed from `$<op>.bytes`; and `minTimeMs` with `objective: min`, which ranks identically but forfeits cross-engine comparability (§2.5).

### 8.5 Measurement Noise

`stddevMs` is recorded so it can be used, not merely stored.

- Rows where `stddevMs / avgTimeMs > 0.10` SHOULD be flagged as high-variance and either re-timed or excluded from training; these targeted re-timings are a data-quality measure and are **not** the noise estimate of §8.5.1; the exclusion count MUST be reported.
- `minTimeMs` is the default target because it is the most noise-robust statistic available, but it is biased low under contention. Benchmarks SHOULD run with the GPU otherwise idle and with a fixed clock/power state where the platform permits; the training manifest records whether this was done.
- Two variants whose timing distributions overlap within noise are not meaningfully ordered. §11.2 accounts for this by scoring regret in throughput terms rather than rank position.

#### 8.5.1 The Repeat Sample

`stddevMs` measures iteration-to-iteration jitter inside one benchmark invocation. It does not measure
whether the invocation would produce the same answer again — cache state, clock ramp, allocation and node
contention all vary between invocations and not within one. The partition of §5.6.2.1 terminates its
splits against the second quantity, so the run must measure it.

**A declared percentage of `(problem, configuration)` pairs MUST be re-timed in a separate invocation**,
and the median relative difference between the two timings is the run's noise floor, recorded in the
manifest.

Two properties the sample needs:

- **Drawn at random, not selected.** §8.5 already re-times rows whose `stddevMs / avgTimeMs` exceeds 10%.
  Those re-timings MUST NOT be reused as the noise estimate: they were chosen for looking bad, so the
  spread among them is biased upward, and a noise floor set from them would stop the tree splitting on
  differences that are real.
- **Spread across regimes and cells.** Reproducibility is not uniform — a small problem dominated by setup
  cost and a large one dominated by kernel time do not vary the same way. A single pooled figure is the
  minimum; per-regime figures are better, and let the split rule use the threshold appropriate to where
  the cell's members were measured.

The repeat sample is a real cost against the benchmark budget (§5.5), paid on pairs already measured.

### 8.6 Feature Namespace Enforcement

Unqualified feature columns are rejected.

```bash
--features q.M q.N q.K kernel.tile_m kernel.tile_n
```

A bare `cu_count` becomes `$cu_count` in the signature, which the runtime cannot resolve — the failure mode is silent degradation to static ordering, so it is rejected at training time instead.


### 8.7 Collection Is Independent of Strategy

A schedule decides which measurements to take. Nothing requires the two to be decided together, and
binding them wastes the more expensive half: measurements outlive the strategy that requested them.

So collection is specified as a service the schedule calls, and the corpus it produces is a dataset a
schedule is a **view over**. Two modes, one schema:

| Mode | Request | Produces |
|------|---------|----------|
| `targeted` | The exact `(problem, configuration)` pairs a schedule asks for | Only those pairs |
| `exhaustive` | A set of problems | Every applicable configuration on each |

**Rows are keyed by `(q.*, kernel.*)`.** The full problem parameters and knob values identify a row, so a
schedule is reconstructed by filtering rather than by re-running, and a corpus assembled under one strategy
can be evaluated under another. That is what makes §5.6.5's open question answerable without a second
campaign: collect exhaustively once for a representative operation, then compare one-member-per-cell
against random-per-problem as two selections over the same measurements.

It also makes cells rebuildable offline. §5.6.2.1 derives the partition from `$kernel.*` features and
measured times, both of which are on the rows, so no KMD lookup is needed to re-derive a partition from an
old collection.

**`problem_complete` is the marker regret depends on.** After a merge, an exhaustively collected problem
and a targeted one are otherwise indistinguishable, and §11.1's regret would quietly become a lower bound
on problems the reader believes are exact. The flag MUST be set only where every applicable configuration
was measured. A configuration that was attempted and failed leaves the flag false for that problem: it
was a candidate, it has no measurement, and regret over the problem is therefore a lower bound rather
than exact.

**The candidate set is compared, not hashed.** After a merge, rows for one problem may come from two
collections taken against different kernel sets — configurations added, removed, or a validity predicate
changed. That matters: added configurations mean the runtime offers candidates never trained on, breaking
§7.3's invariant, and argmax specifically seeks the most optimistic extrapolation.

Rule 9 catches it by comparing the `kernel.*` tuple sets of rows sharing a `q.*` key, for problems marked
`problem_complete`. Earlier drafts recorded a `config_set_hash` and an `applicability_id` on every row and
compared those instead. Both are gone. When `problem_complete=True` the tuples on the rows *are* the
enumerated set, so a hash restates data already present; when it is `False` the hash cannot be checked
against anything. And an identity token is only as good as the producer that set it — a field that can
only be wrong silently reads as a guarantee while providing none, which is worse than its absence.

`collection_mode` is gone for the same reason. It recorded how a schedule *asked*; `problem_complete`
records what it *got*, which is what every consumer decision turns on. A targeted request that happened
to cover the space is complete, and an exhaustive one that hit an error is not.

**External sources.** A corpus may come from a producer that never ran this tooling. The minimum such a
CSV must carry is `q.*`, `kernel.*`, `device.*`, and a measurement. `problem_complete` defaults to `True`
when absent — a provider publishing tuning results is publishing a sweep, not hand-tuned partials — and
`shard_id` to `0` and `error` to empty, since an external producer simply omits the rows it did not
time. `tflops` and `gbs` are derived (§8.3) rather than required of them.

### 8.8 Sharding

Collection parallelises across a cluster by partitioning the work list, not by coordinating workers.

The request — targeted pairs or exhaustive problems — is expanded to an ordered work list, deterministic
under the run's seed. Shard `k` of `n` takes the entries where `index mod n == k`. Interleaving rather than
contiguous blocks keeps each shard's mix of problem sizes comparable, so shards finish at similar times
rather than one drawing all the large problems.

Requirements:

- **Shards are independent.** No shared state, no ordering constraint between them. A shard that fails is
  re-run alone, and re-running it under the same seed and `(k, n)` reproduces the same work list.
- **Outputs concatenate.** Shard CSVs merge by appending; `shard_id` on every row preserves provenance.
  Appending is why collection stays CSV (§8.3): the same merge against Parquet would be a full
  rewrite, since a Parquet file cannot be appended to.
- **Aggregation publishes once, and validates while it does.** After the shards merge, one step reads
  the CSVs, applies §8.3's rules, and writes the Parquet dataset training consumes. Rules 8 and 9 are
  the ones that earn their place here: a merge spanning inconsistent completeness or KMDs is rejected
  at this boundary rather than silently reinterpreted downstream, which is the failure a directly-read
  CSV had no opportunity to catch.
- **`problem_complete` is a property of the merge, not of a shard.** A problem's configurations may be
  split across shards, so no shard can assert completeness alone. It is set when the merged collection is
  validated against the requested work list, and a merge missing entries reports which rather than
  clearing the flag silently.
- **Sharding does not change what is measured.** The same request sharded any number of ways yields the
  same set of rows. Only `shard_id` differs, which makes a sharded run comparable against an unsharded
  one — and makes contention effects visible, since §8.5.1's repeat sample can be drawn across shards.

## 9. Feature Engineering

### 9.1 Auto-Derivable Features (RFC 0019 §13.6)

| Tier | Kind | Auto-derivable | Example |
|------|------|----------------|---------|
| 1 | Raw bindings | Yes | `$kernel.tile_m`, `$q.dims[2]`, `$device.cu_count` |
| 2 | Generic transforms | Partially | `{"log2": ["$q.dims[2]"]}`, `{"ceil_div": ["$q.dims[2]", "$kernel.tile_m"]}` |
| 3 | Physics | Yes, from the precomputed binding fields (§4.3.3) | `{"/": ["$sdpa_fwd.flops", "$sdpa_fwd.bytes"]}` |

**Tile quantization** requires author input: the tool cannot infer which problem dimension pairs with which tile field. The author supplies pairs, the tool emits the `ceil_div` expressions.

```python
dim_tile_pairs = [("seqlen_q", "tile_m"), ("head_dim", "tile_k")]
```

### 9.2 Physics Features

Physics features are ratios over the precomputed cost fields (§4.3.3), written inline in the signature exactly as RFC 0019 §6.4 requires:

```json
{"features_signature": [ {"/": ["$sdpa_fwd.flops", "$sdpa_fwd.bytes"]} ]}
```

**GAP:** the binding layer does not yet publish these fields (RFC 0020 §6). Until it does, the generator computes the quantities from its own per-op table (§4.3.3) and emits precomputed CSV columns.

### 9.3 Feature Selection

Gain-based importance ranks the features. Drop low-importance features and retrain; the emitted UED exposes only the survivors (RFC 0019 §3.2). Pruning a feature and dropping a knob are one action, and the emitted UED must carry the result (§10.4).

Selection MUST be evaluated with the §11 metrics, not with RMSE — a feature can reduce regression error while leaving top-1 selection unchanged, and such a feature costs runtime extraction work for no decision benefit.

**Prefer prefix features over per-candidate tail features.** RFC 0019 §9 splits the feature row into a shared prefix (`$q.*`, `$device.*`, computed invariants), evaluated once per selection, and a per-candidate `$kernel.*` suffix re-evaluated for every candidate — and names "keeping the kernel-dependent tail small" the main lever on selection cost. Two features of equal importance are therefore not equally cheap: the one in the tail costs `N_candidates` times more to extract. Feature selection SHOULD break near-ties toward the prefix, and MUST report the prefix/tail split alongside importances so the cost of the chosen set is visible.

This also bounds how far auto-derivation should be trusted: RFC 0019 §13.6 notes it yields a *superset* that "can hurt a small-data model," and every derived `$kernel.*` term it proposes lands in the tail.

## 10. Training Workflow

### 10.1 CLI

The workflow is five subcommands: `validate-metadata`, `generate-corpus`, `enumerate-variants`,
`benchmark`, `train`. Each is separately runnable, so a stage can be re-run without repeating the ones
before it — which is what lets §8.7's collection be requested independently of the schedule that consumes
it.

`train` takes the model-fitting flags:

```bash
python -m uhd_gen train \
    --input benchmark_results.csv \
    --features q.M q.N q.K kernel.tile_m kernel.tile_n kernel.tile_k \
    --target tflops --objective max \
    --group-by q.M q.N q.K \
    --output-dir ./uhd_output --name "GEMM UHD" \
    --num-boost-round 500 --early-stopping 50
```

### 10.2 Algorithm

1. Load the dataset, keeping rows that carry a measurement.
2. Split features/target; `y = log1p(target)`.
3. GroupKFold (5 splits) on `--group-by` columns (§2.6).
4. Train LightGBM with early stopping.
5. Evaluate against the §11 protocol and record the report.
6. Export LightGBM → FlatBuffer `GbdtModel`.
7. Write the UHD document with `features_signature`, `categorical_encoding` and `features_hash`.

### 10.3 Hyperparameter Defaults

```python
params = { "objective": "regression", "metric": "rmse",
           "num_leaves": 127, "learning_rate": 0.05,
           "feature_fraction": 0.8, "bagging_fraction": 0.8, "bagging_freq": 5 }
```

**GAP:** no per-operation or per-dataset-size tuning guidance. `num_leaves = 127` is aggressive for a small corpus; tune against §11.2 regret, not RMSE.

**Inference cost is a training constraint.** RFC 0019 §9 requires the model to be cheap to load and cheap to rank with — ranking may be triggered for an engine that then loses — and targets `tree_data` overhead within 2× the `native` adapter baseline. Model capacity is therefore bounded from above by selection-time cost, not only from below by accuracy. `num_leaves` and `num_boost_round` are reported alongside measured per-candidate scoring time so that a model whose accuracy was bought with selection latency is visible as such.

### 10.4 Output Artifacts — Stage P

Training feeds RFC 0019 §13.4's package stage, which emits or updates the engine's whole descriptor set. Producing only the UHD leaves the engine inconsistent with the model it names.

```
output_dir/
├── uhd.json             # sort_kernel_catalog UHD, adapter: tree_data (RFC 0019 §4)
├── model.bin            # tree_data artifact the UHD body points at, embedding features_hash
├── ued.json             # UPDATED engine descriptor — knobs = surviving $kernel.* axes
├── kmd.json             # emitted only if the engine does not already carry one
├── train_manifest.json  # provenance and coverage (§10.5)
└── eval_report.json     # §11 metrics vs. baselines
```

**Descriptor documents are JSON; model artifacts are not.** RFC 0019 §4 defines a UHD as a JSON document
tagged `hipdnn.uhd/v1`, and RFC 0020 §4.2 applies the same convention to the UED, so every descriptor this
stage emits is JSON. The FlatBuffer in RFC 0019 belongs to the `tree_data` **artifact** (§7.2) — the tree
table the UHD body's `artifact` path points at — not to the descriptor that names it. A stage emitting a
binary UHD would produce a set the descriptor family's loader cannot read.

The artifact format itself is RFC 0019 Open Question 3: a FlatBuffer tree schema is recommended over
parsing LightGBM `model.txt` at load, and is not settled. This RFC assumes the FlatBuffer and does not
resolve the question.

When the engine needs an estimate, Stage P additionally emits a **second UHD** under the
`predict_engine_tflops` role key, with its own `features_signature`, `features_hash` and model artifact
(§10.6). It is not required for v1 — with a single descriptor engine there is nothing to rank against, and
`sort_kernel_catalog`'s top score is RFC 0019 §11.1's documented stopgap.

The UMDs, UDD, and child UKDs are **not** regenerated. Only the heuristic side changes; that is the intent of the two-stage design.

**Emitting the UED is neither optional nor separable.** RFC 0019 §3.2 makes `UED.knobs` equal to the set of `$kernel.*` fields reachable from `features_signature` — including those nested inside computed entries — and enforces that equality at load. Pruning a feature and dropping a knob are one action. A run that writes a new UHD without the matching UED produces a descriptor set that fails its own load check.

Because any change to the knob set is a **major** UED version bump (RFC 0019 §8), a retrain that drops an axis is a breaking change for a caller setting that knob. The tool MUST report knob-set deltas against the previous UED rather than emitting them silently. Whether a "sticky" superset knob set should insulate callers from model churn is RFC 0019 Open Question 18 and is **not** resolved here.

### 10.5 Required Provenance and Coverage Metadata

`train_manifest.json` and the emitted UHD MUST carry:

| Record | Why | Source |
|--------|-----|--------|
| `trained_against: {ued, umd, kmd}` versions | All three can invalidate the heuristic; the load rule checks major equality and minor ≥ | RFC 0019 §8 |
| Trained **arch set** | Loader exact-matches device GFX name against it — a loader-side check, not a `features_signature` read | RFC 0019 §8, §12 |
| Per-feature **trained value ranges** | Drives the coverage warning when a scored candidate falls outside training | RFC 0019 §8, §12 |
| `categorical_encoding` and its ordering rule | Integer codes imply an order a tree will split on | RFC 0019 §6, Q17 |
| Content hash over the UHD document **and** the model artifact | `features_hash` fingerprints the input contract, not the weights — two models with identical features and different training hash identically, so it is **not** a model identity | RFC 0019 §9 |
| Corpus `seed`, `metadata_hash`, per-round provenance | Reproducibility | §5.6 |
| Predicate versions behind the candidate-set invariant | Detects when the eligible set shifted | §7.2 |
| Benchmark clock/power conditions and which timing statistic was used | Calibration comparability | §8.5, §11.2 |
| Model size and measured per-candidate scoring time | The 2× `native` overhead target | RFC 0019 §9 |

The UMD entry is the easiest to forget and the most dangerous to omit: a matcher change can alter which candidates exist *or* change what a `$graph.*` token means, and neither is visible to a feature-name check.

**`trained_against` is obtainable.** RFC 0019 §8 states that none of the three descriptors carries a
version field, which was true when written and has since been overtaken: RFC 0020 §4.2 makes a
`major.minor` `version` required on **every** descriptor type, gated at load by its §11 accept rule. The
generation tool therefore reads the UED, UMD and KMD versions from the descriptor set it is generating
against and records all three. No new field is needed, and §8's load rule can run as specified.

`categorical_encoding` is fully specified — RFC 0019 §4.1 requires it in the UHD header, RFC 0019 §6.5 defines its
content and the rules that make it correct — and is an outstanding item in the UHD implementation
currently being built. Until the UHD carries it, the encoding exists only in the training manifest, which
the loader does not read, so the §6.3 contract check that would catch a changed encoding has nothing to
check against.

**Out-of-distribution behaviour.** Tree models extrapolate badly — nearest-leaf yields a value with confidence and no basis for it (RFC 0019 §8).

RFC 0019 Open Question 16 offered two mitigations: versioning discipline with a cheap discrete arch check, or per-feature coverage metadata checked at runtime. **The first is decided and implemented.** `uhd_gen --training-arches` records the trained arch set into the model artifact (`gbdt_model.fbs`, `table_model.fbs`: `training_arches`); `TreeDataAdapter` and `TableAdapter` expose it and test device arch against it, treating an empty set as unrestricted; and `SelectionEngine` surfaces it on the selection trace.

Per-feature coverage metadata is the deferred half. The artifact format keeps it additive so it can land without a format break, and until it does, a candidate outside the trained value ranges is undetected at runtime.

**Categorical encoding (RFC 0019 Open Question 17).** RFC 0019 §6.5 permits two treatments per field — ordered
integer codes where a meaningful order exists, one-hot where none does — and rules out first-seen order.
What it leaves open is whether to standardize on one.

**Answer: per-field, declared, defaulting to one-hot.** Which treatment applies depends on whether the
field's values carry a magnitude, and only the author knows: `dtype` ordered by byte width is
interpretable, a scheduler or pipeline name ordered by anything is not. The tooling generates the encoding
but cannot infer the semantics, so the treatment is an author declaration rather than something to
standardize globally.

One-hot is the default because the failure modes are asymmetric. A wrongly ordered code is a silent
modelling error — the tree splits on a threshold that means nothing, and no contract check catches it.
One-hot is never wrong, only wider. That width is a real cost and lands in the per-candidate tail (§9.3,
§11.6), so ordered codes stay worth declaring where an order genuinely exists — as an opt-in that names
the ordering key, not a default to fall into.

Whichever is chosen is recorded in `categorical_encoding` and hashed into `features_hash`, so a later
change invalidates the contract rather than being silently absorbed.
### 10.6 The Engine Estimate

RFC 0019 §3.1 lets a UED name a second role-scoped UHD, `predict_engine_tflops`, which the quick
engine-selection policy uses to rank engines *before* any of them enumerates candidates. RFC 0019 §11.1 fixes its
signature as `f(graph) → expected perf` and notes that the "cheap, no catalog enumeration" property
"depends on `predict_engine_tflops` being trained on `f(graph)` alone, not `f(graph, candidates)`."

**Decision: a distinct trained model, not derived from the ranker.** RFC 0019 Open Question 6 leaves this
open, weighing "distinct is cheaper for the quick policy" against "derived is one fewer model to train."
Both halves look different from inside the training pipeline:

- **The derived option is systematically optimistic.** Deriving the estimate as the maximum *predicted*
  score over candidates takes a max over predictions, which selects for the largest positive prediction
  error — the same optimizer's curse §7.3 describes for variants. The bias grows with candidate count, so
  each engine's estimate is inflated by a different amount depending on how large its catalog is. That is
  precisely the bias that corrupts a cross-engine comparison, which is the estimate's only purpose. A
  model trained directly on measured best throughput carries no such term.
- **"One fewer model to train" overstates the saving.** A distinct estimate needs **no new benchmarking**.
  It is a projection of the dataset the ranker already produced.

#### 10.6.1 Who reads it, and why there is nothing to arbitrate

The estimate's consumer is engine selection — RFC 0007's policy layer, through one of the two policies
RFC 0019 §11.2 names. The quick policy ranks every applicable engine by the estimate and runs the ranker
only on the winner, so losing engines are never scored at kernel level. The thorough policy runs the
ranker everywhere and compares top scores, falling back to the estimate for engines that have no ranker.

**The engine does not choose between its UHDs.** RFC 0019 §11.2: "Both estimates are exposed through the
plugin API, and both are optional. The query surface must carry A and B separately — they have different
costs, and the quick policy's entire value is being able to ask for A *without* paying for B." The engine
offers whichever roles it has; the policy asks for one. RFC 0019 §11.2's four-case matrix covers what a policy does
when an engine has only one of them, or neither.

So a second UHD introduces no contention with the first. The UED's three role-scoped fields (RFC 0019
§3.1) are slots for distinct questions asked by distinct callers at distinct points in the pipeline —
`predict_engine_tflops` before any catalog exists, `sort_kernel_catalog` after applicability has narrowed
to one engine. Adding a role extends what the engine can answer; it does not create an ambiguity the
engine has to resolve. Whether more ranking strategies are worth adding later is a UED capacity question,
not a UHD one.

**This is also the second reason the model is distinct rather than derived.** RFC 0019 §11.1 notes that deriving the
estimate from the ranker means "every engine runs the ranker to produce it, collapsing the quick and
thorough policies into one operation" — the quick policy's whole purpose is to avoid enumeration, and a
derived estimate makes obtaining it require enumeration. The calibration argument above and this one are
independent, and point the same way.

#### 10.6.2 Corpus, features and target

**Corpus — a projection, not a new sweep.** Group the §8.3 dataset by problem and keep, for each, the best
measured throughput across that problem's valid rows. The result is one row per problem where the ranker
had one row per (problem, variant).

**Features — `$q.*` and `$device.*` only.** No `$kernel.*` reference may appear, in a raw entry or nested
inside a computed one. That exclusion is what makes the model `f(graph)` and preserves the no-enumeration
property the quick policy depends on; a single `$kernel.*` term silently turns the cheap estimate into the
expensive one. The prefix/tail distinction of §9.3 does not apply here, since every feature is prefix.

**Knobs are unaffected.** RFC 0019 §3.1 derives `UED.knobs` from `sort_kernel_catalog`'s `$kernel.*` axes
"and no other", so the §6.3 load check that knobs equal the model's kernel-side feature set is scoped to
the ranker alone. A second UHD does not widen it. Here the point is doubly moot: the estimate carries no
`$kernel.*` reference at all, so it has no kernel-side axes to contribute.

**Target — best achieved throughput for the problem**, in the same units and under the same transform as
the ranker, so the two are comparable. The estimate exists to be compared across engines, so it MUST
declare `score.calibrated: true`, which per §11.2 means training it on `avgTimeMs` rather than
`minTimeMs`.

#### 10.6.3 Evaluation

The §11.2 ranking metrics do not apply: there is no candidate set, so there is nothing to rank and no
regret to measure. What applies is the calibration half — relative absolute error and signed bias — and
those become the whole of the estimate's evaluation rather than a secondary axis.

One check is specific to having two models. On the same problem, the estimate and the ranker's top score
answer the same question by different routes, so they SHOULD agree within the estimate's error band. A
systematic disagreement means one of them is miscalibrated, and the comparison localizes which without
needing new measurements.

#### 10.6.4 What this costs the corpus

The two models want different budget shapes. The ranker needs variants per problem; the estimate needs
problems. §5.5's allocation assumes the ranker, and a run serving both should stay that way — but the
tension is worth stating because it is not one-sided.

Spending the same budget on more problems and fewer variants each would give the estimate more rows, and
would also make each row's *label* worse: "best over measured variants" approximates "best achievable"
less well when fewer variants were measured. Shifting budget toward the estimate therefore improves its
coverage and degrades its target at the same time. If the estimate ever becomes the priority, that
trade — not raw problem count — is what to optimize.

#### 10.6.5 Status of Open Question 6

RFC 0019 records the distinct-versus-derived choice as Open Question 6 and does not settle it. This RFC
takes the distinct-model position on the grounds above and specifies training against it. That resolution
belongs in RFC 0019 §11.1 and Q6 as well; until that document is updated, this section is where the
decision and its reasoning live.

## 11. Evaluation Protocol

**SPECIFIED HERE.** The training objective is pointwise regression on `log1p(tflops)`; the runtime decision is *pick the best kernel for this problem*. RMSE on the regression target can improve while top-1 selection gets worse, so RMSE alone does not tell an author whether a model is worth shipping.

### 11.1 Definitions

For problem `p` with measured candidate set `V(p)`:

- `t(p, v)` — measured value of the target metric for variant `v` on `p`
- `v*(p)` — best measured variant (the oracle): `argmax` when `objective` is `max`, `argmin` when it is `min`
- `v̂(p)` — variant the model ranks first, by the same direction

On the evaluation slice (§5.6.3), `V(p)` is every applicable configuration, so `v*(p)` is the true best and
regret is exact. Elsewhere `V(p)` is what the schedule happened to measure, so `v*(p)` is a lower bound on
the best and the regret computed against it is optimistic. Regret figures MUST state which set they were
computed on, and MUST carry the problem count behind them, since a slice of a few hundred problems leaves
visible sampling error in the estimate.

### 11.2 Metrics

| Metric | Definition | Reported as |
|--------|------------|-------------|
| **Top-1 regret** | fractional shortfall against the oracle — `1 − t(v̂)/t(v*)` under `objective: max`, `t(v̂)/t(v*) − 1` under `min`. Non-negative either way | mean, p50, p95, max |
| **Regret tail** | fraction of problems with regret > 5% | percentage |
| **Top-k recall** | fraction of problems where `v*(p)` ∈ model's top-k | k = 1, 3, 5 |
| **Per-regime regret** | mean top-1 regret grouped by corpus regime | table |

Regret is measured in the target metric, not rank position, because ranks are meaningless between variants whose timings overlap within noise (§8.5): choosing the second-best of two statistically indistinguishable kernels costs nothing and MUST NOT be scored as an error.

Per-regime breakdown is required because aggregate regret hides a model that is excellent on the dense middle of the corpus and useless on decode-shaped or prime-dimension problems — which are frequently the shapes the heuristic exists to get right.

**The evaluation slice is not a scale model of the corpus.** Regret is computed on it (§5.6.3), and its
composition is even across regions at round 0 and complexity-weighted afterwards — neither of which
matches how the corpus is distributed. So the per-regime table is the primary form, and every aggregate
states what it averaged over and with which weights. An unweighted mean across the slice is a statement
about the slice, not about the corpus.

**Weighting.** Every regret metric MUST be reported unweighted over the corpus, and — **when regime
weights are declared** (§5.2) — additionally weighted by them. A blindly generated corpus has no weights,
which is the normal case for a new kernel, and there the unweighted number is the whole report. These answer different questions — how good the heuristic is across the space the engine supports, versus what a user is likely to experience —. Backfill (§5.4) skews the corpus toward hard regions, so the unweighted number drifts pessimistic as rounds accumulate; the weighted number alone would hide a regime the heuristic handles badly.

**Calibration metrics — required when `score.calibrated` is true.**

Regret measures whether the model picks the right kernel *within* an engine. It says nothing about whether the score is right in absolute terms, and RFC 0019 §11.3 makes the absolute value load-bearing: engine selection compares predicted TFLOPS across engines, so "rocKE predicting 310 against MIOpen's 240 selects rocKE." A model with flawless ranking and a systematic absolute bias passes every metric above and then loses every cross-engine arbitration.

| Metric | Definition | Reported as |
|--------|------------|-------------|
| **Relative absolute error** | `\|ŷ(p,v) − t(p,v)\| / t(p,v)` | mean, p95 |
| **Signed bias** | `mean( ŷ(p,v) / t(p,v) − 1 )` | single value, per regime |
| **Selected-candidate calibration** | The two above restricted to `v̂(p)` | mean, p95 |

Signed bias matters more than symmetric error: RFC 0019 §11.3 notes "a miscalibrated absolute score is worse than a correct rank, because it produces confident but wrong cross-engine picks," and it is bias, not spread, that skews an argmax between engines. Selected-candidate calibration is called out separately because that score is what gets published as the engine's figure of merit.

**Timing statistic and calibration.** The `minTimeMs` default of §8.5 is the most noise-robust statistic and suits ranking, but minimum-over-iterations is optimistically biased: a score trained on it predicts a throughput the engine will not sustain, and two engines trained on different statistics are not comparable at all. A UHD declaring `calibrated: true` MUST train its score on `avgTimeMs`. The manifest records the statistic used (§10.5), and cross-engine comparison between models trained on different statistics MUST be refused.

### 11.3 Splits

Three evaluations, all required:

1. **Interpolation** — GroupKFold by problem (§2.6). Performance on unseen shapes drawn from the training distribution.
2. **Shape extrapolation** — leave-one-regime-out: withhold an entire regime, train on the rest, evaluate on the withheld regime; repeat per regime. The honest estimate of behaviour on a shape family nobody thought to benchmark, which is the situation the runtime will meet.
3. **Variant extrapolation** — leave-variants-out: withhold a stratified 20% of the kernel variants across the whole corpus, train on the rest, then evaluate with the withheld variants restored to the candidate set. This measures the cost of subsampling the knob space (§7.2), and is the check that says whether an unmeasured variant can be scored safely or will win the argmax on an inflated prediction.

All three fold by problem (§2.6), so no model scores a problem it trained on. Their regret figures are
computable only where a problem carries several measured configurations — the evaluation slice (§5.6.3);
elsewhere the same folds yield prediction error rather than regret. The loop reads the steering portion,
the reported figure comes from the reserved portion, and the report carries them separately rather than
collapsing them into one number (§5.6.4).

Extrapolation regret will be substantially worse than interpolation regret in both directions. Those two gaps are the numbers to track: the shape gap estimates the risk of a workload nobody sampled, the variant gap estimates the risk of the catalog containing kernels nobody measured.

### 11.4 Baselines and Interpretation

Every evaluation reports the model against three references:

| Reference | Definition |
|-----------|------------|
| **Oracle** | `v*(p)`; regret 0 by construction. Upper bound. |
| **Static order** | The `priority`/`id` ordering the engine ships with in Stage 1 (§2.1). This is what the model must beat to justify existing. |
| **Random** | Uniform choice from `V(p)`. Sanity floor. |

**These metrics do not gate emission.** RFC 0019's delivery model is two-stage: an engine ships functional with `static_order`, and a heuristic is layered on afterward as data. At runtime every failure path degrades to `static_order`, logs, and never fails the request. A training tool that refuses to emit a model is a different posture, and not the one the parent describes — a mediocre heuristic that loses to static ordering on one regime is still an artifact an author may legitimately ship, iterate on, or hold, and that judgement is theirs.

What this protocol produces is a report and a direction for the next round (§5.4). The obligations are on the tool, not on the model:

1. The tool MUST compute every §11.2 metric against all three references and write them to `eval_report.json`.
2. The tool MUST warn prominently when mean top-1 regret is not better than static order — a model that loses to the ordering it replaces is the one case where shipping is almost certainly wrong.
3. The tool MUST warn when any individual regime is worse than static order for that regime, since aggregate improvement can hide a regression confined to the workloads a heuristic was built for.
4. The tool MUST warn when a previous UHD exists for the same engine and arch and regret has worsened against it.
5. Reported, not judged: per-candidate scoring time against the `native` baseline of RFC 0019 §9, and — when `score.calibrated` is true — relative absolute error and signed bias.

Reference points for reading the report, not thresholds to pass: p95 top-1 regret under 10%, and for a calibrated score, mean relative absolute error under 15% with |signed bias| under 5%. An engine that wants hard thresholds in its own CI can impose them; this RFC supplies the numbers, not the policy.

Item 5's scoring-time comparison is blocked on the measurement, not on the adapter. `NativeAdapter` exists
(§13), so the reference it compares against is available in builds with `HIPDNN_ENABLE_KERNEL_INGESTOR`
enabled — which, being an experimental gate, means the comparison is reportable there and absent
elsewhere. What is missing is the harness of §11.6 (B5). Until that lands, the number is recorded without
a reference.

### 11.5 Objective: Absolute Score, With Ranking as the Documented Fallback

RFC 0019 §11.3 specifies the target: candidates are scored **cardinally, on an absolute metric (calibrated TFLOPS) rather than a within-group rank**, because that is what makes per-engine heuristics compose into a cross-engine comparison without a central ranker. Absolute scoring is acknowledged there as strictly harder than ranking — a per-engine model need only be monotonic to pick correctly among its own candidates — and the RFC accepts that cost deliberately.

Rank-ordering is the **documented fallback**, not the aspiration: if the absolute method underperforms, engine selection degrades to RFC 0007 static/rank ordering while each UHD keeps ranking within its engine without claiming a comparable absolute score. The design does not depend on calibration succeeding.

Accordingly, this RFC keeps pointwise regression on `log1p(tflops)` as the default objective, and reports the §11.2 calibration metrics alongside regret rather than treating them as secondary.

A listwise objective (LightGBM `lambdarank`, groups = problems) optimizes top-1 selection directly and would score better on regret alone, but it forecloses the calibrated cross-engine metric because its scores are only meaningful within a group. Two constraints bound its use:

- RFC 0019 §3.2 requires that a UHD score each kernel on its own metadata and the problem, **never relative to the rest of the catalog** — this is what makes filtering and ranking commute, and a scorer that normalizes across the candidate set is out of scope. A `lambdarank`-trained GBDT still evaluates per candidate at inference, so it satisfies the letter of this; a scorer that inspected the candidate set at scoring time would not.
- Choosing between regressor and ranker is RFC 0019 **Open Question 1**. The regressor is the path this RFC takes: LightGBM regression on `log1p(target)`, inverted with `expm1`, and the UHD header carries `score{units, calibrated, transform}` (RFC 0019 §4.1) so a consumer can
recover TFLOPS. That matches Q1's recommendation and this RFC specifies against it.

What stays open in Q1 is narrower: whether a ranking mode should ever be *offered* alongside, for engines that do not need cross-engine comparability. §11.2's metrics are objective-agnostic, so a regressor and a `lambdarank` model can be compared directly on both regret and calibration whenever that question is taken up. The manifest records which objective produced a given model.

### 11.6 Selection Cost

RFC 0019 §9.4 requires four numbers wall-clocked separately — descriptor load and model parse, feature
extraction split into shared prefix versus per-candidate tail, and scoring — with `native` as the baseline
and `tree_data` targeted within 2×. It fixes no budget: "the requirement is that the numbers exist and are
tracked." This section defines how they are obtained.

**Separate the prefix from the tail by varying candidate count, not by instrumenting the code.** A single
selection cannot attribute its own time, and instrumentation perturbs what it measures. Time one selection
at several catalog sizes and fit `total(N) = prefix + N × tail`. The intercept is the graph-invariant work
— shared feature extraction plus any per-call setup — and the slope is the per-candidate cost, which is
the number RFC 0019 §9 calls "the main lever on selection cost." The fit is also adapter-agnostic, so it
compares a compiled scorer against a tree walker without either being specially wired.

Requirements on the measurement:

1. **At least three catalog sizes, none of them 1.** RFC 0019 §9 short-circuits selection when a single
   UKD survives, so `N=1` measures the bypass rather than the scorer. Sizes should span the range an
   engine plausibly has — tens to low thousands.
2. **One fixture across every adapter compared.** Same graph, same catalog, same `features_signature`.
   Comparing adapters over different signatures measures feature work, not scoring, and the ratio against
   the `native` baseline becomes meaningless.
3. **Descriptor load and model parse are measured cold and once**, not per selection. They are a
   per-engine startup cost, not part of `total(N)`.
4. **Report the slope, the intercept, and their dispersion.** A model whose mean is acceptable but whose
   tail cost is erratic across repeats is a different problem from one that is uniformly slow, and the 2×
   target should be read against the slope.

**Left open, and needed before the numbers are compared across runs.** Three details are not fixed here
because a first implementation can pick any reasonable value, but none of them can stay arbitrary once a
series is being read for regressions: how many repeats each measurement point takes and how outliers are
rejected; what CPU state the run requires, since frequency scaling moves these numbers between runs on the
same machine; and where the series is stored, which is what makes "tracked" mean something other than
printed once. Whoever builds the harness should settle all three and record them alongside the results, so
a later comparison can tell whether it is comparing like with like.

The per-candidate slope is what §10.3 bounds model capacity against and what §10.5 records alongside
`num_leaves` and `num_boost_round`, so a model whose accuracy was bought with selection latency is visible
in its own manifest. Tracking over time is the point of recording it: a single number says whether a model
is shippable, a series says whether the adapter is regressing.

## 12. Per-Operation Reference

Regime structure per operation class — which axes stratify an operation, and what kinds of value sit on them.

**The numbers below are illustrative, not authoritative.** They were assembled from general knowledge of
common model architectures, not from measurement or from any hipDNN source, and they do not bound the
operation: §4.3.2 makes the feasible region a computed ceiling pruned by applicability, so nothing here
constrains what a generator may sample. Read this section for the *shape* of an operation's stratification,
and take concrete values, where they matter, from the usage record §5.2 describes.

Nor are these a second source of truth for corpus size — tiers are budget-driven and global (§5.5).

Every operation belongs to a class, and the class fixes the stratification axis (§4.3.4).

| Class | Operations | Stratification axis |
|-------|-----------|---------------------|
| 1. Dense linear algebra | MatMul, MoE grouped MatMul | `arithmetic_intensity` |
| 2. Spatial convolution | Conv fwd/bwd/wrw, Resample | `arithmetic_intensity` |
| 3. Attention | SDPA fwd/bwd | `arithmetic_intensity` |
| 4. Normalization | LayerNorm, RMSNorm, BatchNorm (± backward) | `working_set` |
| 5. Elementwise | Pointwise (47 modes) | `working_set` |
| 6. Reduction | Reduction (9 modes) | `reduction_ratio` |
| 7. Quantization | BlockScale quantize/dequantize | `working_set` |

### 12.1 Class 1 — MatMul

**Parameters:** `M`, `N`, `K`, `batch`, `transA`, `transB`, `dtype` (fp32, fp16, bf16, fp8, int8).

| Regime | M | N | K | Use case |
|--------|---|---|---|----------|
| Single token | 1 | 512–28672 | 256–8192 | Batch-1 decode |
| Small | 32–512 | 32–512 | 32–512 | Small NLP, batch-1 inference |
| Medium | 512–4096 | 512–4096 | 512–4096 | Training, mid-size models |
| Large | 4096–16384 | 4096–16384 | 4096–16384 | Large LLM training |
| Tall-skinny | 8192–32768 | 128–512 | 4096–8192 | Token generation |
| Short-fat | 128–512 | 8192–32768 | 4096–8192 | Projection layers |
| Deep K | 16–256 | 16–256 | 4096–32768 | Compute-bound |
| Shallow K | 4096–16384 | 4096–16384 | 32–256 | Memory-bound |
| Primes | 17, 31, 37, 127, 251, 509, 1021, 2039, 4093 | — | — | Worst-case tiling |
| LLM shapes | LLaMA MLP (1×4096×11008), DeepSeek V3 configs | | | Real workloads |

Roofline: `$matmul.flops / $matmul.bytes`, thresholded against the device ridge point. The byte term sums each tensor's own dtype size, which for an fp8-in/fp16-out GEMM differs materially from a single-dtype form — one reason the count belongs in the binding layer rather than in per-op metadata (§4.3.3). Compute-bound above the device ridge point (`peak_flops / peak_bandwidth`), not a fixed constant — the threshold is device-dependent and MUST be computed from the queried device properties.

Alignment regimes: aligned (`M % tile_m == 0` for all three dims), partial remainder (one dim), full remainder (all three). Tile values come from variant enumeration (§6.4).

**MoE grouped MatMul** adds `num_experts` (4, 8, 16, 32, 64), `expert_capacity`, and routing skew (uniform vs. imbalanced), with capacity factors 1.0 / 1.25 / 1.5 / 2.0.

**Parameters:** `N`, `C`, `K`, `H`, `W`, `R`, `S`, `pad_*`, `stride_*`, `dilation_*`, `groups`, `dtype`.

| Layer archetype | N | C | H×W | K | R×S | Notes |
|-----------------|---|---|-----|---|-----|-------|
| ResNet50 conv1 | 64–256 | 3 | 224 | 64 | 7×7 | Large spatial, few channels |
| ResNet50 layer3 | 64–256 | 512 | 28 | 512 | 3×3 | Balanced |

| U-Net encoder | 4–16 | 64–512 | 128–512 | 128–1024 | 3×3 | Medical imaging |
| Dilated (segmentation) | 4–32 | 256–1024 | 64–128 | 256–1024 | 3×3 | `dilation = 2` |

Roofline: compute-bound for large filters, many channels, large batch; memory-bound for 1×1 convolutions, small batch, large spatial.
Alignment: `H % tile_h`, `W % tile_w`, `C % tile_c`, `K % tile_k`.

**Resample** shares the class: `window` (2×2, 3×3, 4×4, 8×8), `stride` (1, 2), padding per dimension, `resample_mode` (MAX, AVG), `padding_mode` (ZERO, EDGE, REFLECT).

### 12.3 Class 3 — SDPA

**Parameters:** `batch`, `heads`, `seqlen_q`, `seqlen_k`, `head_dim` (64, 128, 256), `is_causal`, `attn_scale`, `dropout_probability`, `dtype` (fp16, bf16, fp8).

| Regime | batch | heads | seqlen_q | seqlen_k | head_dim |
|--------|-------|-------|----------|----------|----------|
| Prefill / training | 1–64 | 32–96 | 512–8192 | = seqlen_q | 64–128 |
| Decode | 1–256 | 32–96 | 1 | 512–32768 | 64–128 |
| Short context | 4–128 | 8–32 | 128–512 | 128–512 | 64–128 |
| Long context | 1–16 | 32–96 | 8192–32768 | = seqlen_q | 64–128 |
| Edge cases | 1 | 1 | — | — | 256 |

Model configs to include: LLaMA-2 7B/13B/70B (32/32/40 heads, head_dim 128), GPT-3 175B (96 heads), BERT-base (16 heads, head_dim 64), DeepSeek V3 (128 query heads, 8 KV heads — exercises GQA ratio).

Key relationships: training and prefill have `seqlen_q ≈ seqlen_k`; decode has `seqlen_q = 1, seqlen_k >> 1` (KV cache) and is always causal.
Alignment: `seqlen_q % tile_m`, `seqlen_k % tile_n`, `head_dim % tile_k`.

### 12.4 Class 4 — Normalization

**LayerNorm / RMSNorm parameters:** `batch`, `seq_len`, `hidden_dim`, `epsilon`, `dtype`, `forward_phase`.

| Model | batch | seq_len | hidden_dim |
|-------|-------|---------|------------|
| BERT-base | 1–512 | 128–512 | 768 |
| BERT-large | 1–512 | 128–512 | 1024 |
| LLaMA-2 7B | 1–128 | 512–4096 | 4096 |
| LLaMA-2 70B | 1–64 | 512–8192 | 8192 |
| GPT-3 175B | 1–2048 | 1024–2048 | 12288 |
| ViT-Base / Large / Huge | 1–256 | 196–256 | 768 / 1024 / 1280 |

**BatchNorm parameters:** `N`, `C`, `H`, `W`, `epsilon`, `momentum`, `dtype` — CNN-shaped rather than transformer-shaped: N 1–256, C 32–1024, H×W 14–224.

Stratification is by `working_set` — the per-row normalized footprint bucketed against L1/L2/LLC capacity. Arithmetic intensity is constant for this class (§4.3.4) and MUST NOT be used.

Alignment: `hidden_dim` (or `C`) against the reduction tile width; row lengths that are not a multiple of the wavefront size are the interesting cases.

### 12.5 Class 5 — Elementwise

**Parameters:** `operation` (47 `PointwiseMode` values), input shape(s), broadcast pattern, `dtype`, plus mode-specific scalars (`swish_beta`, `elu_alpha`, `softplus_beta`, `relu_*_clip`).

Stratification by total element count against cache hierarchy: 1K–10K (L1), 100K–1M (L2), 10M–100M (HBM streaming), 1B+ (multi-pass). Additional axes: broadcast pattern (none, scalar, 1D, channel, spatial), tensor rank (1D–5D), aspect ratio (square vs. tall-skinny, which changes access coalescing).

The 47 modes do not each need full coverage. Group them by cost profile — cheap unary (`ABS`, `NEG`, `IDENTITY`), transcendental (`EXP`, `LOG`, `TANH`, `ERF`, `GELU_*`), binary (`ADD`, `MUL`, `SUB`, `DIV`), comparison/select — and sample shapes densely per *group*, with a thin sweep across modes within a group. Arithmetic intensity here is below 1 FLOP/byte for every mode, which is why mode identity matters far less than footprint.

### 12.6 Class 6 — Reduction

**Parameters:** `mode` (ADD, MUL, MIN, MAX, AMAX, AVG, NORM1, NORM2, MUL_NO_ZEROS), input shape, reduction axes, `dtype`, `is_deterministic`.

Stratification by `reduction_ratio = input_elements / output_elements`:

| Pattern | Ratio | Example |
|---------|-------|---------|
| Full reduction | 10⁶–10⁹ | `(N,C,H,W) → scalar` |
| Batch reduction | 10–10³ | `(N,C,H,W) → (C,H,W)` |
| Channel reduction | 10–10³ | `(N,C,H,W) → (N,H,W)` |
| Spatial reduction | 10²–10⁴ | `(N,C,H,W) → (N,C)` |
| Near-identity | 1–10 | Reducing a length-2 axis |

`is_deterministic` materially changes the algorithm (tree vs. atomic accumulation) and MUST be sampled on both settings.

### 12.7 Class 7 — Quantization

**Parameters:** `block_size` (16, 32, 64, 128, 256), input dtype → output dtype pair, `scale_dtype` (float32, float16), tensor shape.

Stratification by `working_set` with a dedicated alignment axis: whether the tensor's fastest-varying dimension is a multiple of `block_size`. Ragged final blocks are the interesting case and are trivially missed by power-of-two-only sampling.

**On items B6 and B7.** These are the two that bound what this RFC can deliver, and neither is a training problem.

B6 is the sharper one. `UhdBuiltIn` runs the full selection path — extract features, score every candidate, sort, tie-break — and then drops the result, because the heuristic plugin ABI returns engine ids and has no field for a per-engine kernel ranking. The code says so directly and carries a `TODO(RFC-0017)`. Until that ABI grows a return path, a trained UHD changes nothing at runtime, which means the corpus, the benchmark, the model and the evaluation in this document all terminate in an artifact that cannot yet be acted on. Training work is still worth doing ahead of the ABI, but no measured end-to-end improvement can be claimed until it lands.

B7 is the structural one. Two trees implement RFC 0019 with inverted coverage: the kernel ingestor has `HeuristicDescriptor`, `HeuristicKind::NATIVE` and `NativeKernelHeuristic`, loading `.uhd.json` through `DescriptorLoader`, with `MODEL` explicitly unimplemented; the backend has the `tree_data`, `table`, `onnx` and `custom_library` adapters, the `features_signature` extractor, `features_hash`, score transforms and arch-keyed resolution, loading a binary `.uhd.fb` through `UhdLoader` — which is a third divergence, since RFC 0019 §4 defines
the UHD as a JSON document tagged `hipdnn.uhd/v1` and reserves the FlatBuffer for the `tree_data`
artifact. The descriptors are not interconvertible — the ingestor's is four fields and an opaque payload, which cannot express a feature contract, an objective, score units, or a model artifact — and the ingestor is compiled only under an off-by-default flag. This RFC is written against the backend path, because that is the one carrying the feature contract it depends on. Deciding whether the two converge, and in which direction, is RFC 0017's to make; it is recorded here because a corpus and a model are only useful to whichever path survives.

**On item B5.** RFC 0019 §9.4 states the requirement and leaves the method open. §11.6 supplies it: fit
`total(N) = prefix + N × tail` over several catalog sizes rather than instrumenting the call, which
separates the two feature-extraction terms without perturbing them and compares adapters without wiring
each one specially. What remains is building it.

The adapter itself now exists: a `NATIVE` value in the `UhdAdapter` enum, `native_symbol` in `uhd.fbs`, a `NativeAdapter` resolving a compiled scorer in-process, and loader dispatch. What is still absent is the benchmark that turns it into a baseline — the four separately wall-clocked numbers RFC 0019 §9.4 asks for (descriptor load and model parse, feature extraction split prefix versus per-candidate tail, and scoring), measured for `native` and `tree_data` over one fixture and tracked over time.

The kernel ingestor carries a parallel mechanism — `NativeRegistry.hpp`'s `ScoreRegistry` over `ScoreFn = double (*)(const MatchContext&, const BoundTokens&, const KernelDefinition&)`, consumed by `NativeKernelHeuristic` under `HeuristicKind::NATIVE`. The UHD path does not reuse it, for two reasons that are worth stating rather than rediscovering: the ingestor is compiled only under `HIPDNN_ENABLE_KERNEL_INGESTOR`, which defaults off, so a shared registry would make the baseline unavailable in exactly the builds that need to measure it; and the two scorer signatures are not convertible, since an ingestor scorer receives the match context and featurizes itself while a UHD scorer receives the extracted feature row. §13's note on the two descriptor paths covers the broader question.

**On S2.** The cap bounds how many variants autotune enrolls in one sweep. An engine whose knob space exceeds it enrolls in batches or measures a subsample; neither the problem space nor the variant space is ever measured exhaustively (§7.2).

What the cap constrains is how *evenly* a dense knob space can be covered within a given budget, which is what the optimizer's curse makes expensive. The variant budget therefore goes to uniform coverage of the knob space rather than to dense enumeration of one corner of it, and the leave-variants-out regret of §11.3 reports what the subsample cost. The runtime candidate set stays whole: narrowing it to the measured subset would discard working kernels to protect an assumption that §11.3 already tests.

## 14. Implementation Roadmap

**This document is RFC 0019's Phase 5.** RFC 0019 §15 schedules the generation tool as Phase 5 — a standalone tool wrapping hipDNN that drives autotune over a shape corpus and the knob space, logs results, trains, and emits an updated UED/UHD plus model. It depends on Phases 3 and 4 (the `tree_data` adapter, and the `features_signature` generic extractor with its training↔runtime parity test), and RFC 0019 records it as **gated on Open Question 12**, the catalog-enumeration API gap, for engines with large sparse knob spaces. Phases 9 (AOT selection) and 10 (knob reduction) depend on it in turn.

The phases below subdivide that Phase 5. They are not a parallel numbering of RFC 0019's.

**Phase 1 — make one operation work end to end.**

1. `validate-metadata` plus the metadata file for `matmul` (§4).
2. `generate-corpus` round 0 — `stratified_cross_product`, seeded (§5.3), then draw and pin the
   evaluation slice before any measurement (§5.6.3).
3. Graph construction from `graph_builder` (§4.3.6).
4. `enumerate-variants` — read the variant set from the KMD declaration, or collect UKD tuples from the
   catalog where the KMD does not yet carry one (§6.2).
5. The round-0 cell partition and one-member-per-cell assignment (§5.6.2.1), plus exhaustive measurement
   of the evaluation slice (§5.6.3).
6. `benchmark` against the backend applicability API, honouring the coverage floor (§5.5) and recording skipped
   pairs (§5.5, §7, §8).
7. Evaluation protocol against a static-order baseline (§11): out-of-fold prediction error over the
   corpus, regret on the evaluation slice, reported from the reserved portion (§5.6.4).
8. A random-per-problem arm over the same budget, so the cell partition is measured against the
   alternative it claims to beat (§5.6.5, gap S6). Phase 1 does not exit without it.

Phase 1 is open-loop: round 0 plus evaluation. It is the smallest increment that yields a shippable UHD, and it produces the first measurements of boundary density and regret — the inputs Phase 2's targeting consumes.

**Phase 2 — close the loop.**

9. Boundary-density, regret-concentration and dispersion signals over round-0 results (§5.4).
10. Backfill rounds with the exploration floor and per-region caps (§5.1, §5.4).
11. Stopping against the declared accuracy target, distinguishing target-met from budget-exhausted (§5.5).
12. Budget calibration (`t_setup` / `t_kernel` measurement and projection) (§5.5).

**Phase 3 — generalize across operations.**

13. Metadata files for the remaining Tier-1 ops (`sdpa_fwd`, `conv_fwd`), then normalization and elementwise.
14. Regime weights and traffic-weighted regret reporting (§5.2, §11.2).
15. Coverage reporting and axis-occupancy warnings (§5.10).
16. The engine estimate as a second projection of the same corpus (§10.6) — no new benchmarking, so it lands whenever a second descriptor engine makes it useful.

**Phase 4 — close the schema and tooling gaps.**

17. Whatever RFC 0017 settles on for the KMD's variant declaration and its validity predicate (§6.3), and whatever Open Question 12 separately settles on for the public enumeration API (S1).
18. Leave-variants-out evaluation, covering variants dropped by the §5.5 prune (§11.3, §7.3).
19. `$<op>.flops` / `$<op>.bytes` in the binding layer (B2).
20. `lambdarank`, only if a pack opts out of cross-engine comparability; §2.5 prefers `max` on TFLOPS and §11.5 records why (§11.5).
21. Feature-importance and tree-inspection tooling (B4).

### 15.1 `objective` — What `min` Means

RFC 0019 §4.1 requires `objective` on any adapter that scores, values it `max | min`, and then suspends
it: "*Deferred in implementation* — the current layout fixes higher-wins; adapters normalize until this
lands." An implementer cannot act on that. It does not say whether to honour `min`, reject it, or accept
and ignore it, and "adapters normalize" places an obligation on adapter authors without defining it.

**Answer: honour it at selection, prefer `max` on TFLOPS, and bind `min` to an uncalibrated score.**

*Selection.* §5 step 4 already reads "`max` (or `min`) over the scores." The runtime honours the declared
direction — `argmin` rather than `argmax` — which is one comparison flip and needs no normalization by
adapters. "Adapters normalize" is then unnecessary and should be dropped rather than defined.

*The constraint that makes it coherent.* RFC 0019 §11.3 requires a cross-engine score to be "an absolute metric
(calibrated TFLOPS)… on a scale that means the same thing across engines." Two engines cannot be compared
if one reports throughput ascending and the other latency descending. So `objective: min` is legal only
where `score.calibrated` is `false` — a UHD ranking within its own engine and declining to participate in
cross-engine comparison. A calibrated score is TFLOPS and is necessarily `max`. A UHD declaring both
`calibrated: true` and `objective: min` is a load error, not a preference.

*What this document does with it.* §8.4 offers `minTimeMs` with `objective: min` as an alternative target;
that choice therefore forfeits cross-engine comparability, which is the same trade §11.2's calibration
rules already describe for the timing statistic. §11.1 and §11.2 now define the oracle and regret by the
declared direction rather than assuming higher-is-better, so a cost-target model is evaluated correctly
instead of scoring inverted.

### 15.2 What Selection Returns

RFC 0019 §5 fixes the contract and leaves the binding open. It states that "the output is the ranked
catalog, not just a winner", that "the winner is simply its first element", that "the winner is a single
UKD", and that callers need the ordering because "a knob query reports the top-ranked value as the
default, autotune walks the ranked list, and engine selection reads the top score as the engine's figure
of merit". RFC 0019 §11.1 gives `sort_kernel_catalog` the signature `f(graph) → best kernel + perf`. What no
section gives is the concrete type.

**Answer: an ordered sequence of `(UKD id, score)`, winner first.**

*Identity by id, not object or reference.* The result crosses a plugin boundary. An object commits the ABI
to a kernel-definition layout; a reference couples the caller's lifetime to the catalog. RFC 0017 already
makes a UKD's id unique engine-wide and validates it at load, so it is a stable handle the engine resolves
locally.

*The score travels with it.* An id alone satisfies kernel selection and breaks engine selection, because
RFC 0019 §11.3 compares engines on the top candidate's predicted throughput. Dropping the score at the boundary
would leave nothing to compare and force the estimate of §10.6 to be consulted separately even where a
ranker had already computed the number.

*The sequence, not the winner.* §5 names three callers that need the ordering, and a fourth case matters
in practice: a winner that fails to build should fall to the runner-up rather than trigger a fresh
selection pass.

**Who asks, and why no new ABI is needed to start.** The engine consults its own UHD during plan build.
That call is in-process and the `(id, score)` sequence never crosses the host boundary, so the delivery
gap is narrower than it looks: only the single cross-engine figure of merit needs a channel the plugin API
lacks, and RFC 0019 §11.3 already scopes that as deferred plugin-SDK work.

A ranking that is computed and discarded is a symptom of being computed in the wrong place — in a
host-level heuristic *policy* plugin, whose ABI returns engine ids because engine ordering is what that
interface is for. Kernel selection is not engine ordering. Moving the call into plan build puts the result
where its consumer already is, and needs no interface that does not exist: the engine holds its own
catalog, resolves an id locally, and hands the winner to dispatch. The policy plugin keeps doing what it
is shaped for. RFC 0019 §11.2's policies still decide whether the ranker runs at all for a given engine, and
A-versus-B remains a policy question above the engine (§10.6.1).
