# RFC 0019.13: UHD Training Methodology

- **Parent:** [RFC 0019 Universal Heuristic Descriptor](0019_UniversalHeuristicDescriptor.md) §13 Model Generation Pipeline
- **Status:** Draft — formalizes the methodology for training UHDs across arbitrary operations
- **Contributors:** Chris Erb, Jason Campbell
- **Tooling:** `projects/hipdnn/tools/uhd_gen/`

---

## Abstract

RFC 0019 §13 specifies the high-level training workflow (two-stage delivery, autotune substrate, feature contract enforcement) but leaves the **per-operation parameter space exploration** and **corpus generation methodology** unspecified. This companion RFC formalizes:

1. **Parameter space exploration** — how to construct the benchmark sweep for arbitrary operations
2. **Stratified sampling strategies** — regime-based corpus generation (roofline, tile alignment, use-case stratification)
3. **Per-operation methodology** — concrete sampling strategies for GEMM, SDPA, Convolution, Normalization ops
4. **Tooling roadmap** — what's implemented (`uhd_gen train`), what's missing (corpus generation, autotune integration), and priority gaps

**Key architectural principle**: Corpus generation must synthesize **operation-aware sampling** (the full potential parameter space of the operation) with **provider applicability filtering** (what the engine's kernels can actually handle). The provider supplies an applicability predicate but **not** an exhaustive problem list — tooling generates a representative corpus from the operation space and relies on applicability to prune infeasible problems.

This RFC is **descriptive** (documents what CK/rocKE do, what hipDNN has implemented) and **prescriptive** (defines the missing pieces and how to fill them).

## 2. What RFC 0019 Already Specifies

### 2.1 Two-Stage Workflow (RFC §13.1)

**IMPLEMENTED**: Ships working pack first, adds heuristic later.

1. **Stage 1**: Ship a functional pack with `static_order` (or no UHD). The catalog returns in deterministic `priority`/`id` order. No benchmarking required.
2. **Stage 2**: Generate data-driven heuristic from on-hardware timings. Update the UED/UHD in place.

### 2.2 Benchmarking Substrate (RFC §13.2)

**IMPLEMENTED**: Uses hipDNN autotune (RFC 0013) to time kernels.

```python
# Enumerate applicable engines and their knobs
configs = handle.get_engine_configs(graph)

# Enroll explicit variants OR Cartesian sweep
handle.add_engine_variants(engine_id, [(knob1, knob2, ...), ...])
handle.add_engine_sweep(engine_id, knob_ranges, fixed_settings)

# Time until convergence
results = handle.autotune(mode=EXHAUSTIVE, strategy=RUN_UNTIL_STABLE)
# → [{engineId, knobSettings, minTimeMs, avgTimeMs, stddevMs, ...}]
```

**Key constraint**: Autotune addresses kernels via **exposed knobs only**. A kernel the tool cannot name cannot be timed.

**Requirement**: Generation runs against a **fully-exposed UED** (every KMD field exposed as a knob) so every catalog entry is individually addressable. The emitted UED then exposes only the features the model kept.

### 2.3 Feature Extraction (RFC §6)

**IMPLEMENTED**: Features drawn from three sources, all available at plan time:

| Source | Namespace | Examples | Bindable at Training Time |
|--------|-----------|----------|---------------------------|
| **Device properties** | `$device.*` | `cu_count`, `lds_size`, `vgpr_count` | ✅ Yes — known per GPU |
| **Kernel metadata (KMD)** | `$kernel.*` | `tile_m`, `split_k`, `warp_n` | ✅ Yes — from UKD metadata |
| **Query/problem shape** | `$q.*` | `dims[0]`, `dims[2]`, `dtype` | ✅ Yes — sweep parameter |

**Computed features** (RFC §6.4): Expressions over the three sources, written as `{"op": [args]}` trees:
```json
{"ceil_div": ["$q.dims[2]", "$kernel.tile_m"]}  // tile count
{"/": ["$sdpa_fwd.flops", "$sdpa_fwd.bytes"]}   // arithmetic intensity
```

### 2.4 Feature Contract Enforcement (RFC §6.3)

**IMPLEMENTED**: `features_hash` pins the feature signature.

- Training emits `features_signature` + `categorical_encoding` → `sha256:...` hash
- Runtime extractor validates hash before scoring
- Hash mismatch → refuse to load (fail closed) or degrade to static ordering (fail open)

### 2.5 Training Target and Transform (RFC §11.3)

**IMPLEMENTED** in `uhd_gen/train_uhd.py`:

```python
y = np.log1p(df[target_col].values)  # log1p(TFLOPS) for scale-invariant training
```

**Objective**: `max` (higher score = better kernel) or `min` (lower score = better, e.g., latency)

**Score metadata** (RFC §11.3):
```json
"score": {
  "units": "tflops",
  "calibrated": false,  // cross-engine comparable if true
  "transform": "log1p"
}
```

Runtime inverts the transform: `score = expm1(model.predict(features))`

### 2.6 Cross-Validation (RFC §13.2 implicit)

**IMPLEMENTED**: GroupKFold to prevent problem leakage.

```python
groups = df.groupby(group_cols).ngroup().values  # e.g., (M, N, K)
folds = GroupKFold(n_splits=5).split(X, y, groups)
```

Ensures the same problem shape never appears in both train and validation.

## 3. Parameter Space Exploration

**STATUS**: Partially specified in RFC §13.5; **GAP** in tooling automation.

### 3.1 What to Sweep

The training benchmark sweep is **two-dimensional**:

1. **Problem-shape corpus** (`$q.*` bindings): batch, seqlen, heads, dims, dtype, layout
   - **Source**: Operation-specific methodology (Section 9)
   - **Responsibility**: Training tooling generates per Section 9 corpus generation
   
2. **Kernel variants** (`$kernel.*` bindings): tile sizes, split factors, wavefront config
   - **Source**: KMD schema declares fields and ranges; catalog contains actual values
   - **Responsibility**: Training tooling enumerates/explores this space

**Key insight**: The training tooling's **primary responsibility is to train models** (evaluate benchmarks, train, assess accuracy, iterate). To do this, it must **generate benchmark corpora** by handling both sweeps:
- Generate representative problem shapes (operation-aware)
- Enumerate kernel variants (KMD-aware)

**Three-space responsibility matrix**:

```
                  Device Space ($device.*)          Problem Space ($q.*)              Kernel Space ($kernel.*)
                  ────────────────────────          ────────────────────              ────────────────────────
Declares:         GPU hardware                      Operation semantics               KMD schema
                  (queried at runtime)              (implicit, from op type)          (fields, types, ranges)

Explores:         NOT explored                      Training tooling                  Training tooling
                  (single fixed point               (Section 9 per-op generator)      (KMD reader + catalog
                   per training run)                                                   enumerator)

Input to:         Device properties JSON            Corpus JSON                       Variant tuples / ranges
                  {cu_count:304, lds_size:...}      [{batch:32, seqlen:2048, ...}]    [(tile_m:128, ...), ...]

Source:           HIP runtime query OR              Training tooling generates        Training tooling reads
                  manual JSON config                per Section 9 methodology         KMD + enumerates catalog

Autotune API:     Implicit (on device)              Graph construction                add_engine_variants() or
                                                    (problem params → node attrs)     add_engine_sweep()
```

**Key distinctions**:

1. **Device space** — Fixed point, not explored:
   - Single GPU target per training run (e.g., one MI300X node)
   - Properties queried via HIP runtime: `hipDeviceGetAttribute()`, `hipGetDeviceProperties()`
   - For multi-arch training: run **separate training sessions** on different hardware, produce arch-keyed UHDs
   - Alternative: manual device config JSON (for testing without hardware access)

2. **Problem space** — Explored via corpus generation:
   - Operation-specific sampling (Section 9)
   - Generates representative shapes across roofline regimes

3. **Kernel space** — Explored via catalog enumeration:
   - KMD-driven, catalog-bounded
   - Strategy chosen based on catalog density

**Workflow** (the core UHD training tooling responsibility):

The tooling must **generate and traverse all three configuration spaces** to produce the training corpus:

```
Device properties queried:   Training tooling generates:    Training tooling enumerates:
  (HIP runtime)                  Problem corpus                   Kernel variants
      ↓                                 ↓                                   ↓
  ┌─────────────┐               ┌─────────────┐               ┌─────────────────┐
  │ Device      │               │ Problem     │               │ Kernel          │
  │ (query GPU) │               │ (generate)  │               │ (enumerate)     │
  │             │               │             │               │                 │
  │ {cu_count:  │               │ corpus =    │               │ variants =      │
  │  304, ...}  │               │  gen_sdpa_  │               │  enum_kmd_      │
  │             │               │  corpus()   │               │  variants()     │
  └─────────────┘               └─────────────┘               └─────────────────┘
         ↓                              ↓                              ↓
         │                    ┌─────────▼────────────┐       ┌─────────▼────────┐
         │                    │ Applicability filter │       │ Config validator │
         │                    │ (provider predicate) │       │ (provider pred.) │
         │                    └─────────┬────────────┘       └─────────┬────────┘
         │                              ↓                              ↓
         │                      applicable_corpus             valid_variants
         │                              │                              │
         └──────────────────────────────┴──────────────────────────────┘
                                        ↓
                          Autotune benchmark loop (on device):
                          for problem in applicable_corpus:
                            for variant in valid_variants:
                              features = merge(device, problem, variant)
                              time_ms = benchmark(problem, variant)
                              → {device.*, q.*, kernel.*, tflops, minTimeMs}
                                        ↓
                                benchmark_results.csv
                                (device.* + q.* + kernel.* columns)
```

**Tooling responsibilities** (what `uhd_gen` must do):

**Primary: Training and Model Evaluation**
1. ✅ **Train model** — LightGBM + log1p + GroupKFold (implemented in `uhd_gen train`)
2. ❌ **GAP: Model validation** — hold-out test set, baseline comparison, regression detection
3. ❌ **GAP: Iterative refinement** — feature selection feedback loop, hyperparameter tuning

**Supporting: Benchmark Corpus Generation**
4. ✅ **Query device space** — HIP runtime API, emit `device.*` features (constant per run)
5. ❌ **GAP: Generate problem space** — operation-aware stratified sampling (§3.2)
6. ❌ **GAP: Enumerate kernel space** — read KMD declaration, extract/validate variants (§3.3)
7. ❌ **GAP: Filter via predicates** — invoke applicability + config validation before benchmarking
8. ❌ **GAP: Benchmark Cartesian product** — autotune integration (§8.2)

The **central gap** is items 5-8: the tooling to **generate, filter, and traverse** the three spaces to produce benchmark corpora. But the **primary purpose** remains training: items 1-3.

### 3.2 Problem-Shape Corpus Construction: Synthesis of Operation Space and Provider Applicability

**GAP**: No formalized method for generating representative shape sets.

**Architectural principle** — Tooling generates, provider filters:

**Tooling responsibility**: Generate a representative problem corpus from the **full potential parameter space of the operation**. The tooling knows the operation's semantics and typical use cases (e.g., SDPA: prefill/decode regimes, LLM configs; GEMM: batch-1 inference, training batches, tall-skinny projections).

**Provider responsibility**: Supply an **applicability predicate** that returns true/false for each problem. This declares what the engine's kernels can handle (e.g., "requires `head_dim % 64 == 0`", "only supports `batch <= 256`").

**NOT the provider's responsibility**: Enumerate an exhaustive list of problems their kernels support.

**Why this division**:
1. **Providers don't know the full operation space** — they know their kernel's constraints, not every use case hipDNN must cover.
2. **Applicability is declarative** — a predicate is cheaper to author and maintain than an exhaustive problem list.
3. **Tooling has operation knowledge** — it understands SDPA regimes (prefill vs decode), GEMM regimes (batch-1, training, tall-skinny), etc.
4. **Synthesis is automatic** — tooling generates broad coverage, applicability prunes infeasible problems, training sees only what the engine can handle.

**Workflow**:
```python
# 1. Tooling generates operation-aware corpus
corpus = generate_sdpa_corpus(tier="standard")
# → 500 problems covering prefill/decode, small/medium/large seqlen, model configs

# 2. Build graph per problem and query applicability
applicable_corpus = []
for problem in corpus:
    graph = build_sdpa_graph(problem)
    if engine.is_applicable(graph):
        applicable_corpus.append(problem)
# → 320 problems (provider doesn't support head_dim=96, dropped those)

# 3. Benchmark only applicable problems
benchmark(engine_id, applicable_corpus)
```

**Current practice** (per RFC §13.5):
- Author supplies representative shapes (ad-hoc, no operation-aware stratification)
- Or use a per-op default (undefined)

**Open questions**:
- **Coverage criteria**: How to ensure the corpus spans the performance-critical region?
- **Sampling strategy**: Uniform? Log-spaced? Stratified by roofline bound (compute vs memory)?
- **Size**: How many shapes? (Trade-off: coverage vs. benchmark time)

**Proposed tiers** (to be formalized):

| Tier | Size | Use Case | Sampling Strategy |
|------|------|----------|-------------------|
| **Smoke** | 10-20 | Quick validation | Hand-picked canonical cases |
| **Standard** | 100-500 | Production heuristic | Stratified by dimension ranges + roofline regime |
| **Exhaustive** | 1000+ | Multi-arch sweep | Dense grid over key dimensions |

**Stratification axes** (operation-aware sampling):
1. **Problem size regime**: Small (fits L2), medium (DRAM-bound), large (multi-wave)
2. **Tile efficiency**: Well-aligned vs. remainder tiles (tests provider's padding/masking)
3. **Arithmetic intensity**: Memory-bound vs. compute-bound (roofline x-axis)
4. **Use-case regimes**: Operation-specific (SDPA: prefill/decode; GEMM: batch-1/training/tall-skinny)

### 3.3 Kernel Variant Enumeration: KMD Declaration + Validation Predicate

**Architectural principle** — Same as problem space: KMD declares space, provider validates:

**KMD responsibility**: Declare the kernel configuration space via **one of two modes**:

1. **Explicit enumeration** (sparse/irregular catalog):
   ```json
   {
     "variants": [
       {"tile_m": 128, "tile_n": 128, "tile_k": 8, "use_lds": true},
       {"tile_m": 256, "tile_n": 128, "tile_k": 8, "use_lds": true},
       {"tile_m": 128, "tile_n": 256, "tile_k": 16, "use_lds": false}
     ]
   }
   ```
   Provider supplies the **complete list** of valid configurations. Training enumerates this list directly.

2. **Range declaration + validation predicate** (dense/regular catalog with constraints):
   ```json
   {
     "fields": [
       {"name": "tile_m", "type": "int64", "values": [64, 128, 256]},
       {"name": "tile_n", "type": "int64", "values": [64, 128, 256]},
       {"name": "tile_k", "type": "int64", "values": [8, 16, 32]},
       {"name": "use_lds", "type": "bool"}
     ],
     "has_config_validator": true
   }
   ```
   Provider declares independent ranges for each field **plus** a validation function:
   ```cpp
   bool is_valid_config(const KernelConfig& cfg) {
       // Example constraint: tile_m * tile_k must fit in LDS
       if (cfg.use_lds && cfg.tile_m * cfg.tile_k > 8192) return false;
       // Example constraint: tile_n must be <= tile_m
       if (cfg.tile_n > cfg.tile_m) return false;
       return true;
   }
   ```

**Provider responsibility**:
- **Mode 1**: Enumerate all valid configs (when sparse or irregular)
- **Mode 2**: Declare ranges + supply validator (when dense with constraints)
- **NOT**: Require tooling to guess constraints from UKD inspection

**Tooling workflow**:
```python
# Read KMD declaration
kmd = read_kmd_schema(engine_id)

if kmd.has_explicit_variants():
    # Mode 1: Explicit enumeration
    variants = kmd.get_variants()
    handle.add_engine_variants(engine_id, variants)
    
elif kmd.has_config_validator():
    # Mode 2: Generate from ranges, validate each
    ranges = kmd.get_field_ranges()
    cartesian = generate_cartesian_product(ranges)
    
    valid_variants = []
    for cfg in cartesian:
        if engine.is_valid_config(cfg):
            valid_variants.append(cfg)
    
    handle.add_engine_variants(engine_id, valid_variants)
    
else:
    # Fallback: Cartesian sweep (assumes all combinations valid)
    ranges = kmd.get_field_ranges()
    handle.add_engine_sweep(engine_id, ranges, fixed={})
```

**Why this matters**:
- **Sparse catalogs** (e.g., hand-tuned tile configs): Explicit enumeration avoids benchmarking invalid configs
- **Dense catalogs with constraints** (e.g., "tile_m × tile_k must fit LDS"): Validation predicate prunes infeasible configs before benchmarking
- **Fallback to Cartesian** (unconstrained): Works for simple cases but wastes benchmark time on invalid configs

**Current gap** (RFC §13.2, Open Question 12):
- KMD schema supports range declaration but **not** explicit variant enumeration or validation predicates
- No API to query "is this config valid?" before benchmarking
- Tooling must infer strategy by inspecting the catalog (fragile)

**Training tooling responsibilities**:
1. ✅ Read KMD schema to discover kernel feature space
2. ❌ **GAP**: Extract explicit variant list (KMD doesn't support this yet)
3. ❌ **GAP**: Query validation predicate (no API for this yet)
4. ✅ Choose enumeration strategy based on KMD mode
5. ❌ **GAP**: Validate that enumeration covered the full catalog

### 3.4 Multi-Architecture Coverage

**PARTIALLY SPECIFIED** (RFC §8.3): Arch-keyed UHD selection.

Each architecture gets its own UHD:
```json
{
  "gfx942": "sdpa_fwd_gfx942.uhd.fb",
  "gfx950": "sdpa_fwd_gfx950.uhd.fb",
  "default": "sdpa_fwd_default.uhd.fb"
}
```

**GAP**: No guidance on:
- Whether to train separate models per arch, or one arch-aware model with `$device.*` features
- When to use `$device.*` features vs. arch-keyed models
- How to handle arch families (gfx942 vs. gfx942:mi300x vs. gfx942:mi325x)

**Current practice**: Separate model per arch, no `$device.arch` feature (it's a KDP property for UHD resolution, not a runtime feature per RFC §6.1).

## 4. Benchmark Dataset Construction

**STATUS**: Specified in RFC §13.2; **IMPLEMENTED** in autotune integration.

### 4.1 Dataset Schema

Each row is one (problem shape, kernel variant, device) → timing:

| Column Group | Example Columns | Source |
|--------------|-----------------|--------|
| **Problem shape** (`q.*`) | `M`, `N`, `K`, `batch`, `seqlen_q`, `dtype` | Sweep parameter |
| **Kernel metadata** (`kernel.*`) | `tile_m`, `tile_n`, `tile_k`, `split_k` | UKD metadata |
| **Device properties** (`device.*`) | `cu_count`, `lds_size`, `vgpr_count` | GPU query |
| **Timing** | `minTimeMs`, `avgTimeMs`, `stddevMs`, `iters` | Autotune result |
| **Derived** | `tflops`, `gbs`, `efficiency` | Post-processing |

### 4.2 Target Metric Construction

**IMPLEMENTED**: Throughput in TFLOPS.

```python
df["tflops"] = (2 * df["M"] * df["N"] * df["K"]) / (df["minTimeMs"] * 1e9)
```

**Alternative targets**:
- **Latency**: `minTimeMs` (objective: `min`)
- **Efficiency**: `tflops / theoretical_peak` (0-1 scale)
- **Bytes/sec**: For memory-bound ops

### 4.3 Feature Namespace Enforcement

**IMPLEMENTED** (commit aa2be93): `uhd_gen` rejects unqualified columns.

All feature columns must be prefixed:
```bash
--features q.M q.N q.K kernel.tile_m kernel.tile_n device.cu_count
```

Bare `cu_count` → `$cu_count` in signature → runtime cannot resolve → silent degradation to static ordering.

## 5. Feature Engineering

**STATUS**: Partially specified in RFC §6.4 and §13.6; **GAP** in tooling automation.

### 5.1 Auto-Derivable Features (RFC §13.6)

**Three tiers**:

| Tier | Feature Kind | Auto-Derivable? | Example |
|------|--------------|-----------------|---------|
| **1. Raw fields** | Direct KMD/device/query bindings | ✅ Yes | `$kernel.tile_m`, `$q.dims[2]`, `$device.cu_count` |
| **2. Generic transforms** | Logs, ratios, tile quantization | ⚠️ Partially | `{"log2": ["$q.dims[2]"]}`, `{"ceil_div": ["$q.dims[2]", "$kernel.tile_m"]}` |
| **3. Physics** | Arithmetic intensity, roofline | ✅ Yes (via precomputed fields) | `{"/": ["$op.flops", "$op.bytes"]}` |

**Tile quantization** (Tier 2): Requires author input.

The tool cannot infer which problem dim pairs with which tile field. Author supplies:
```python
dim_tile_pairs = [
    ("seqlen_q", "tile_m"),  # q.dims[2] / kernel.tile_m
    ("head_dim", "tile_k"),  # q.dims[3] / kernel.tile_k
]
```

Tool generates:
```json
{"ceil_div": ["$q.dims[2]", "$kernel.tile_m"]},
{"ceil_div": ["$q.dims[3]", "$kernel.tile_k"]}
```

### 5.2 Precomputed Op Fields (RFC §13.6)

**SPECIFIED** but not yet implemented in hipDNN schema.

Physics features (FLOP count, byte count) are **op-specific** closed-form functions:
```python
# SDPA forward
flops = 4 * batch * heads * seqlen_q * seqlen_k * head_dim
bytes = (batch * heads * seqlen_q * head_dim +  # Q
         batch * heads * seqlen_k * head_dim +  # K
         batch * heads * seqlen_k * head_dim +  # V
         batch * heads * seqlen_q * head_dim)   # O
```

These should be **published by the binding layer** (RFC 0020 §6 symbol binding):
```json
"precomputed_fields": {
  "$sdpa_fwd.flops": "4 * $q.batch * $q.heads * $q.seqlen_q * $q.seqlen_k * $q.head_dim",
  "$sdpa_fwd.bytes": "..."
}
```

Then usable in `features_signature`:
```json
{"features_signature": [
  {"/": ["$sdpa_fwd.flops", "$sdpa_fwd.bytes"]}  // arithmetic intensity
]}
```

**GAP**: Not yet implemented. Workaround: Pre-compute in input CSV.

### 5.3 Feature Selection

**IMPLEMENTED**: LightGBM's built-in importance scoring.

After training, inspect feature importance:
```python
importance = model.feature_importance(importance_type='gain')
for feat, score in zip(feature_cols, importance):
    print(f"{feat}: {score}")
```

Drop low-importance features and retrain. The emitted UED's `knobs` expose only the survivors (RFC §3.2).

## 6. Training Workflow

```bash

    --input benchmark_results.csv \
    --features q.M q.N q.K kernel.tile_m kernel.tile_n kernel.tile_k device.cu_count \

### 6.2 Training Algorithm

**IMPLEMENTED** (`train_uhd.py`):

1. **Load data**: Read CSV/JSON
2. **Feature/target split**: `X = df[feature_cols]`, `y = log1p(df[target_col])`
3. **Cross-validation**: GroupKFold (5 splits) on `--group-by` columns
4. **Train**: LightGBM with early stopping
5. **Export**: LightGBM → FlatBuffer GbdtModel
6. **Generate UHD**: Write `uhd.fb` + `uhd.json` with `features_signature` and `features_hash`

## 7. Implementation Patterns (Extracted from CK/rocKE)

**Note**: Full code examples live in `UHD_TRAINING_TUTORIAL.md` and `CORPUS_GENERATION_GAP_ANALYSIS.md`. This section documents only the architectural patterns.

This section provides **actionable code patterns** extracted from working CK and rocKE implementations. These are the "copy this" instructions for implementing the missing tooling gaps.

### 7.1 Problem Corpus Generation

#### 7.1.1 GEMM Corpus (CK Pattern)

**Source:** `projects/composablekernel/dispatcher/heuristics/generate_benchmark_data.py`

**Pattern:** Stratified discrete sampling via 13 regimes, combinatorial within each, set-based dedup.

**CK's 13 regimes:**
1. M=1 (single token inference)
2. Tiny M (2-16), Small M (32-128), Medium M (256-2048), Large M (4096-20480)
3. Square shapes (powers of 2: 64, 256, 1024, 4096, 8192)
4. Skinny M/tall N (M << N), Tall M/skinny N (M >> N)
5. Deep K (K >> M, N) — compute-bound
6. Shallow K (K << M, N) — memory-bound
7. Prime dimensions (17, 31, 127, 251, ...) — worst-case tiling
8. LLM-specific (LLaMA MLP: 1×4096×11008, DeepSeek configs)
9. Non-power-of-2 common sizes

**hipDNN adoption:** Inherit CK's regimes as `standard` tier default, add tier control (`smoke`: 10-20 shapes, `standard`: 100-500, `exhaustive`: 1000+), YAML config overrides.

#### 7.1.2 SDPA Corpus (LLM-Specific)

**Parameter space:** `(batch, heads, seqlen_q, seqlen_k, head_dim, is_causal)`

**Regime stratification:**
1. **Decode** — `seqlen_q=1`, varying `seqlen_k` (128, 512, 2048, 8192)
2. **Prefill** — `seqlen_q = seqlen_k`, square attention, causal mask
3. **LLM configs** — LLaMA-2 (7B/13B/70B), DeepSeek V3 (128 q_heads, 8 kv_heads)
4. **Edge cases** — small heads (1), large head_dim (256), non-causal decode

**Density:** ~200-400 shapes for `standard` tier.

#### 7.1.3 Convolution Corpus (ResNet/VGG/MobileNet)

**Parameter space:** `(N, C, H, W, K, R, S, pad, stride, dilation, group)`

**Regime stratification:**
1. **ResNet-50 layers** — conv1 (7×7), bottleneck blocks (1×1, 3×3)
2. **Batch sweep** — training batches (8, 16, 32, 64)
3. **Depthwise** — MobileNet (group = C)
4. **Dilated** — segmentation (dilation=2)
5. **Large spatial** — 512×512 input

**Density:** ~150-300 shapes for `standard` tier.

### 7.2 Kernel Variant Enumeration

**CK pattern:** Parse pre-generated catalog (`gemm_universal_kernel_list.txt`) where kernel names encode configs (`tile_m`, `tile_n`, `tile_k`, `warp_*`, `scheduler`, `epilogue`, etc.).

**hipDNN approach (two modes):**

**Mode 1 — Explicit enumeration:** KMD declares full variant list in metadata.  
**Mode 2 — Range + validator:** KMD declares field ranges (e.g., `tile_m: [64, 128, 256]`), tooling generates Cartesian product, optionally filters via provider-supplied validation predicate.

**Requirement:** KMD schema extension to declare ranges and optional `has_config_validator` flag.

---

### 7.3 Applicability Filtering

**rocKE pattern:** Explicit pre-filter via `miopenConvolutionForwardGetSolutionCount()` — check BEFORE benchmarking, not implicitly via failure.

**Generic interface (provider-agnostic):**
class KernelProvider(ABC):
    @abstractmethod
    def is_applicable(self, graph: Graph) -> bool:
        """
        Return True if this provider can execute the given problem graph.
        
        Called BEFORE enumerating variants.
        
        Implementation examples:
        - MIOpen Conv: miopenGetSolutionCount(graph_params) > 0
        - Custom GEMM: check tensor dims/dtypes/layouts are supported
        - SDPA: check head_dim in [64, 128, 256], is_causal supported
        """
        pass
    
    def is_valid_config(self, graph: Graph, variant: Dict) -> bool:
        """
        Optional: Return True if this specific kernel variant applies.
        
        Called AFTER is_applicable(), FOR EACH variant.
        
        Implementation examples:
        - Tile size fits LDS: tile_m * tile_k * sizeof(T) <= 65536
        - Wave constraint: tile_m / warp_m <= device.max_waves
        - Alignment: M % tile_m == 0 for this specific kernel
        
        Default: return True (all variants apply if is_applicable() passed)
        """
        return True
```

**Key difference from CK:**

| Aspect | CK | rocKE | hipDNN UHD Should |
|--------|-------|-------|-------------------|
| **Applicability** | Implicit (run exe, mark failure) | **Explicit** (`miopenGetSolutionCount()`) | **Explicit** (generic interface) |
| **When checked** | During benchmarking | **Before** benchmarking | **Before** benchmarking |
| **Filtering** | Post-hoc (`is_valid` flag) | Pre-emptive (skip pairs) | Pre-emptive (skip pairs) |

**Adoption for hipDNN UHD:**
- Define `is_applicable()` as REQUIRED provider interface
- Define `is_valid_config()` as OPTIONAL optimization
- Pre-filter before benchmarking (saves time vs. CK's try-everything approach)

### 7.4 Benchmark Execution Workflow

**Pattern:** Pre-filter via applicability, then benchmark only applicable pairs.

```python
def benchmark_corpus(
    provider: KernelProvider,
    corpus: List[Dict],
    variants: List[Dict]
) -> List[Dict]:
    """Benchmark applicable (problem, variant) pairs."""
    results = []
    
    for problem in corpus:
        # Build graph for this problem
        graph = build_graph(problem)
        
        # STEP 1: Problem-level filtering (REQUIRED interface)
        if not provider.is_applicable(graph):
            # Provider cannot handle this problem — skip all variants
            continue
        
        # STEP 2: Variant-level filtering and benchmarking
        for variant in variants:
            # Optional: per-variant applicability check
            if not provider.is_valid_config(graph, variant):
                continue  # Skip this variant for this problem
            
            # STEP 3: Benchmark only applicable pairs
            try:
                timing = benchmark_single_variant(graph, provider, variant)
                
                results.append({
                    # Problem features (from graph)
                    **extract_problem_features(graph),
                    # Kernel features (from variant)
                    **extract_kernel_features(variant),
                    # Target variable
                    "minTimeMs": timing.min_time_ms,
                    "tflops": compute_tflops(problem, timing.min_time_ms),
                    "is_valid": True,
                })
            except Exception as e:
                # Benchmark failed (unexpected — should have been filtered)
                results.append({
                    **extract_problem_features(graph),
                    **extract_kernel_features(variant),
                    "minTimeMs": 0,
                    "tflops": 0,
                    "is_valid": False,
                    "error": str(e),
                })
    
    return results
```

**CK precedent:** Runs every kernel against every problem, marks failures as `is_valid=False`.

**rocKE precedent:** Checks `miopenGetSolutionCount()` before benchmarking.

**hipDNN approach:** Adopt rocKE's explicit pre-filtering via generic interface.

## 10. Per-Operation Parameter Space Methodology

**Note:** This section provides reference parameter ranges. Concrete sampling code lives in `UHD_TRAINING_TUTORIAL.md` and `uhd_gen/corpus/` implementations.

This section formalizes the parameter space exploration strategy for each operation type currently supported in hipDNN.

### 9.1 Three-Space Decomposition

For every operation, the feature space decomposes into three sources (RFC §6.1):

1. **Device space (`$device.*`)** - ~10-15 features, constrained and known per GPU
2. **Kernel space (`$kernel.*`)** - Developer-controlled via KMD schema, varies by engine
3. **Problem space (`$q.*`, `$<node>.*`)** - Operation-specific, potentially unbounded

The **device space** is fixed per target arch. The **kernel space** is enumerable from the compiled catalog. The **problem space** is where operation-specific methodology is required.

### 9.2 GEMM / MatMul

**Problem dimensions**:
- `M`, `N`, `K` - matrix dimensions
- `batch` - batch size (for batched GEMM)
- `transA`, `transB` - transpose flags (boolean)
- `dtype` - data type (fp32, fp16, bf16, fp8, int8)

**Dimension ranges** (typical workloads):

| Regime | M | N | K | Use Case |
|--------|---|---|---|----------|
| **Small** | 32-512 | 32-512 | 32-512 | Small NLP models, batch-1 inference |
| **Medium** | 512-4096 | 512-4096 | 512-4096 | Training, medium models |
| **Large** | 4096-16384 | 4096-16384 | 4096-16384 | Large LLM training |
| **Tall-skinny** | 8192-32768 | 128-512 | 4096-8192 | Token generation (seqlen >> vocab subset) |
| **Short-fat** | 128-512 | 8192-32768 | 4096-8192 | Projection layers |

**Roofline regimes**:
- **Compute-bound**: `M*N*K / (M*K + K*N + M*N)` > 100 FLOP/byte
- **Memory-bound**: Arithmetic intensity < 100 FLOP/byte

**Tile alignment cases**:
- Well-aligned: `M % tile_m == 0`, `N % tile_n == 0`, `K % tile_k == 0`
- Partial remainder: One dimension has remainder
- Full remainder: All dimensions have remainder

**Recommended corpus tiers**:

| Tier | Size | Sampling Strategy |
|------|------|-------------------|
| **Smoke** | 20 | Hand-picked: powers of 2, common LLM dims (4096, 8192), mixed alignment |
| **Standard** | 200 | Stratified: 5 regimes × 4 alignment cases × 2 dtypes × 5 samples per bucket |
| **Exhaustive** | 2000+ | Dense grid: log-spaced M/N/K in [32, 16384], all dtype/transpose combos |

**Example standard corpus generation**:
```python
import numpy as np

def generate_gemm_corpus(tier='standard'):
    corpus = []
    
    # Dimension ranges per regime
    regimes = {
        'small': (32, 512),
        'medium': (512, 4096),
        'large': (4096, 16384),
        'tall_skinny': (8192, 32768, 'M'),
        'short_fat': (8192, 32768, 'N'),
    }
    
    # Tile sizes to test alignment against
    tiles = [64, 128, 256]
    
    for regime_name, bounds in regimes.items():
        for _ in range(40):  # 40 samples per regime
            if regime_name == 'tall_skinny':
                M = np.random.randint(bounds[0], bounds[1])
                N = np.random.randint(128, 512)
                K = np.random.randint(4096, 8192)
            elif regime_name == 'short_fat':
                M = np.random.randint(128, 512)
                N = np.random.randint(bounds[0], bounds[1])
                K = np.random.randint(4096, 8192)
            else:
                M = np.random.randint(bounds[0], bounds[1])
                N = np.random.randint(bounds[0], bounds[1])
                K = np.random.randint(bounds[0], bounds[1])
            
            # Mix alignment: 50% well-aligned, 50% remainder
            if np.random.rand() < 0.5:
                tile = np.random.choice(tiles)
                M = (M // tile) * tile
                N = (N // tile) * tile
                K = (K // tile) * tile
            
            corpus.append({
                'q.M': M, 'q.N': N, 'q.K': K,
                'q.batch': np.random.choice([1, 4, 16, 32]),
                'q.transA': np.random.choice([0, 1]),
                'q.transB': np.random.choice([0, 1]),
            })
    
    return corpus
```

### 9.3 Convolution (Forward/Backward Data/Backward Weights)

**Problem dimensions**:
- `N` - batch size
- `C`, `K` - input/output channels
- `H`, `W` - spatial dimensions (height, width)
- `R`, `S` - filter size
- `pad_h`, `pad_w`, `stride_h`, `stride_w`, `dilation_h`, `dilation_w`
- `groups` - grouped convolution factor
- `dtype` - data type

**Dimension ranges** (CNN workloads):

| Network Layer | N | C | H×W | K | R×S | Notes |
|---------------|---|---|-----|---|-----|-------|
| **ResNet50 conv1** | 64-256 | 3 | 224 | 64 | 7×7 | Large spatial, few channels |
| **ResNet50 layer3** | 64-256 | 512 | 28 | 512 | 3×3 | Balanced |
| **MobileNet depthwise** | 64-256 | 32-512 | 56-112 | 1 | 3×3 | groups=C |
| **U-Net encoder** | 4-16 | 64-512 | 128-512 | 128-1024 | 3×3 | Medical imaging |

**Roofline regimes**:
- **Compute-bound**: Large filters (R×S ≥ 5×5), many channels, large batch
- **Memory-bound**: 1×1 conv, small batch, large spatial

**Tile alignment**:
- Input tile alignment: `H % tile_h`, `W % tile_w`
- Channel alignment: `C % tile_c`, `K % tile_k`
- Filter alignment: Usually well-aligned (3×3, 5×5, 7×7)

**Recommended corpus tiers**:

| Tier | Size | Sampling Strategy |
|------|------|-------------------|
| **Smoke** | 15 | ResNet50 layers, MobileNetV2 first/last, 1×1 + 3×3 + 7×7 filters |
| **Standard** | 150 | Stratified: 5 network types × 3 layers × 2 batch sizes × 5 channel configs |
| **Exhaustive** | 1500+ | Full sweep of real-world CNN architectures + synthetic edge cases |

### 9.4 Scaled Dot-Product Attention (SDPA) Forward/Backward

**Problem dimensions**:
- `batch` - batch size
- `heads` - number of attention heads
- `seqlen_q` - query sequence length
- `seqlen_k` - key/value sequence length
- `head_dim` - dimension per head (typically 64, 128, 256)
- `is_causal` - causal masking flag
- `attn_scale` - attention scale factor
- `dropout_probability` - dropout rate
- `dtype` - data type (fp16, bf16, fp8)

**Dimension ranges** (LLM workloads):

| Regime | batch | heads | seqlen_q | seqlen_k | head_dim | Use Case |
|--------|-------|-------|----------|----------|----------|----------|
| **Prefill (training)** | 1-64 | 32-96 | 512-8192 | 512-8192 | 64-128 | Training, long context |
| **Decode (generation)** | 1-256 | 32-96 | 1 | 512-32768 | 64-128 | Token generation |
| **Short context** | 4-128 | 8-32 | 128-512 | 128-512 | 64-128 | Small models |
| **Long context** | 1-16 | 32-96 | 8192-32768 | 8192-32768 | 64-128 | 100k+ context |

**Key relationships**:
- **Training**: `seqlen_q ≈ seqlen_k` (bidirectional)
- **Inference prefill**: `seqlen_q ≈ seqlen_k`
- **Inference decode**: `seqlen_q = 1`, `seqlen_k >> 1` (KV cache)

**Roofline regimes**:
- **Compute-bound**: Large seqlen × seqlen matmuls (O(seqlen²))
- **Memory-bound**: Small batch, short sequences, decode (seqlen_q=1)

**Tile alignment**:
- Sequence tile: `seqlen_q % tile_m`, `seqlen_k % tile_n`
- Head tile: `head_dim % tile_k`
- Common tiles: 64, 128, 256

**Recommended corpus tiers**:

| Tier | Size | Sampling Strategy |
|------|------|-------------------|
| **Smoke** | 20 | GPT3/Llama2 canonical configs, decode vs. prefill, causal vs. non-causal |
| **Standard** | 200 | Stratified: 4 regimes × 5 head counts × 2 causal modes × 5 seqlen pairs |
| **Exhaustive** | 2000+ | Dense seqlen sweep [128, 32768], all head_dim {64,128,256}, mixed dtypes |

**Example SDPA corpus generation**:
```python
def generate_sdpa_corpus(tier='standard'):
    corpus = []
    
    # Common model configs
    configs = [
        # (heads, head_dim, name)
        (32, 128, 'llama2_7b'),
        (32, 128, 'llama2_13b'),
        (40, 128, 'llama2_70b'),
        (96, 128, 'gpt3_175b'),
        (16, 64, 'bert_base'),
    ]
    
    # Sequence length regimes
    seqlen_ranges = {
        'short': (128, 512),
        'medium': (512, 2048),
        'long': (2048, 8192),
        'very_long': (8192, 32768),
    }
    
    for heads, head_dim, model in configs:
        for regime, (min_seq, max_seq) in seqlen_ranges.items():
            # Training/prefill: seqlen_q ≈ seqlen_k
            for _ in range(5):
                seqlen = np.random.randint(min_seq, max_seq)
                corpus.append({
                    'q.batch': np.random.choice([1, 4, 16, 32]),
                    'q.heads': heads,
                    'q.seqlen_q': seqlen,
                    'q.seqlen_k': seqlen,
                    'q.head_dim': head_dim,
                    'q.is_causal': np.random.choice([0, 1]),
                })
            
            # Decode: seqlen_q = 1, seqlen_k >> 1
            for _ in range(5):
                seqlen_k = np.random.randint(min_seq, max_seq)
                corpus.append({
                    'q.batch': np.random.choice([1, 16, 64, 256]),
                    'q.heads': heads,
                    'q.seqlen_q': 1,
                    'q.seqlen_k': seqlen_k,
                    'q.head_dim': head_dim,
                    'q.is_causal': 1,  # Decode is always causal
                })
    
    return corpus
```

### 9.5 Batch Normalization (Training/Inference)

**Problem dimensions**:
- `N` - batch size
- `C` - channels
- `H`, `W` - spatial dimensions
- `epsilon` - numerical stability term
- `momentum` - running stats momentum (training only)
- `dtype` - data type

**Dimension ranges**:

| Regime | N | C | H×W | Notes |
|--------|---|---|-----|-------|
| **Small** | 1-16 | 32-128 | 28-56 | Small models |
| **Medium** | 16-64 | 128-512 | 28-56 | ResNet-style |
| **Large batch** | 64-256 | 256-1024 | 14-28 | Distributed training |
| **Large spatial** | 4-32 | 64-256 | 112-224 | Early layers |

**Roofline**: Almost always **memory-bound** (simple elementwise ops + reductions)

**Recommended corpus**:
- **Smoke**: 10 shapes from ResNet50/MobileNetV2
- **Standard**: 50 shapes stratified by batch/channel/spatial regime
- **Exhaustive**: 500+ covering all CNN normalization layers

### 9.6 Layer Normalization / RMSNorm

**Problem dimensions**:
- `batch` - batch size (or sequence length)
- `hidden_dim` - normalized dimension
- `epsilon` - numerical stability
- `dtype` - data type

**Dimension ranges** (Transformer models):

| Model | batch | hidden_dim | Notes |
|-------|-------|------------|-------|
| **BERT-base** | 1-512 | 768 | |
| **BERT-large** | 1-512 | 1024 | |
| **GPT-3** | 1-2048 | 12288 | |
| **Llama2-70B** | 1-4096 | 8192 | |

**Roofline**: **Memory-bound** (reduction + elementwise)

**Recommended corpus**:
- **Smoke**: 10 shapes from BERT/GPT/Llama configs
- **Standard**: 50 shapes, batch × hidden_dim sweep
- **Exhaustive**: 500+ covering {batch: 1-4096} × {hidden: 256-16384}

### 9.7 Reduction Operations

**Problem dimensions**:
- Input shape: `[N, C, H, W]` or arbitrary rank
- Reduction axes: which dimensions to reduce over
- Reduction op: sum, mean, max, min, etc.
- `dtype` - data type

**Recommended corpus**: Operation-agnostic, stratified by:
- Rank: 2D, 3D, 4D, 5D
- Reduction pattern: full, channel-wise, spatial-only, batch-only
- Size regime: small (100s), medium (1000s), large (10k+)

### 9.8 Pointwise Operations (Unary/Binary)

**Problem dimensions**:
- Input shape(s): arbitrary rank tensors
- Operation type: add, mul, relu, gelu, silu, etc.
- Broadcasting: which dimensions broadcast
- `dtype` - data type

**Roofline**: **Extreme memory-bound** (FLOP/byte < 1)

**Recommended corpus**: Shape-agnostic, focus on:
- Broadcasting patterns: scalar, 1D, channel, spatial
- Tensor ranks: 1D through 5D
- Sizes: small/medium/large per dimension
