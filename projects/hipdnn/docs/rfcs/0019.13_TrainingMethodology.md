# RFC 0019.13: UHD Training Methodology

- **Parent:** [RFC 0019 Universal Heuristic Descriptor](0019_UniversalHeuristicDescriptor.md) §13 Model Generation Pipeline
- **Status:** Draft — formalizes the methodology for training UHDs across arbitrary operations
- **Contributors:** Chris Erb, Jason Campbell
- **Tooling:** `projects/hipdnn/tools/uhd_gen/`

---

## Abstract

RFC 0019 §13 specifies the high-level training workflow (two-stage delivery, autotune substrate, feature contract enforcement) but leaves **per-operation parameter space exploration**, **corpus generation**, and **model evaluation** unspecified. This companion RFC fills those gaps so that a UHD can be trained for an arbitrary operation without per-operation tooling changes.

It specifies:

1. **An operation metadata schema** — a machine-readable description of an operation's parameter space, cost formulas, stratification axes, and graph construction, sufficient to drive corpus generation mechanically (§4).
2. **Staged corpus generation** — broad exploration first, then evidence-driven backfill, under a budget denominated in benchmark cost rather than shape count (§5).
3. **Kernel variant enumeration and applicability filtering** — including the train/serve candidate-set invariant that makes the trained model valid at runtime (§6, §7).
4. **An evaluation protocol** — ranking and calibration metrics tied to the decision the UHD actually makes, with baselines, for judging a model and directing the next round of refinement (§11).

**Key architectural principle:** corpus generation synthesizes **operation-aware sampling** (the operation's full potential parameter space) with **provider applicability filtering** (what the engine's kernels can handle). The provider supplies predicates, not an exhaustive problem list.

This RFC is **descriptive** (documents what CK/rocKE do and what `uhd_gen` implements) and **prescriptive** (defines the missing pieces).

## 2. What RFC 0019 Already Specifies

### 2.1 Two-Stage Workflow (RFC 0019 §13.1)

**IMPLEMENTED.** Ship a working pack first, add the heuristic later.

1. **Stage 1** — ship a functional pack with `static_order` (or no UHD). The catalog returns in deterministic `priority`/`id` order. No benchmarking required.
2. **Stage 2** — generate a data-driven heuristic from on-hardware timings. Update the UED/UHD in place.

### 2.2 Benchmarking Substrate (RFC 0019 §13.2)

**IMPLEMENTED.** Uses hipDNN autotune (RFC 0013) to time kernels.

```python
configs = handle.get_engine_configs(graph)
handle.add_engine_variants(engine_id, [(knob1, knob2, ...), ...])
handle.add_engine_sweep(engine_id, knob_ranges, fixed_settings)
results = handle.autotune(mode=EXHAUSTIVE, strategy=RUN_UNTIL_STABLE)
# → [{engineId, knobSettings, minTimeMs, avgTimeMs, stddevMs, ...}]
```

**Key constraint:** autotune addresses kernels via **exposed knobs only**. A kernel the tool cannot name cannot be timed.

**Requirement:** generation runs against a **fully-exposed UED** (every KMD field exposed as a knob) so every catalog entry is individually addressable. The emitted UED then exposes only the features the model kept.

### 2.3 Feature Extraction (RFC 0019 §6)

**IMPLEMENTED.** Features are drawn from three sources, all available at plan time:

| Source | Namespace | Examples | Bindable at training time |
|--------|-----------|----------|---------------------------|
| Device properties | `$device.*` | `cu_count`, `lds_size`, `vgpr_count` | Yes — known per GPU |
| Kernel metadata (KMD) | `$kernel.*` | `tile_m`, `split_k`, `warp_n` | Yes — from UKD metadata |
| Query/problem shape | `$q.*` | `dims[0]`, `dims[2]`, `dtype` | Yes — sweep parameter |

**Computed features** (RFC 0019 §6.4) are expression trees of the form `{"op": [args]}` with bare `$`-prefixed variable references:

```json
{"ceil_div": ["$q.dims[2]", "$kernel.tile_m"]}
{"/": ["$sdpa_fwd.flops", "$sdpa_fwd.bytes"]}
```

This RFC uses the same syntax throughout (§4.3.3).

### 2.4 Feature Contract Enforcement (RFC 0019 §6.3)

**IMPLEMENTED.** `features_hash` pins the feature signature. Training emits `features_signature` + `categorical_encoding` → `sha256:…`. The runtime extractor validates the hash before scoring; a mismatch means refuse to load (fail closed) or degrade to static ordering (fail open).

### 2.5 Training Target and Transform (RFC 0019 §11.3)

**IMPLEMENTED** in `uhd_gen/train_uhd.py`:

```python
y = np.log1p(df[target_col].values)   # scale-invariant regression target
```

**Objective:** `max` (higher score = better kernel) or `min` (lower = better, e.g. latency).

```json
"score": { "units": "tflops", "calibrated": false, "transform": "log1p" }
```

Runtime inverts the transform: `score = expm1(model.predict(features))`.

Note that this is a **pointwise regression** target while the runtime decision is a **ranking** decision. §11 defines the evaluation metrics that make that gap measurable, and §11.5 discusses replacing the objective outright.

### 2.6 Cross-Validation (RFC 0019 §13.2, implicit)

**IMPLEMENTED.** GroupKFold prevents problem leakage — the same problem shape never appears in both train and validation folds.

```python
groups = df.groupby(group_cols).ngroup().values   # e.g. (q.M, q.N, q.K)
folds  = GroupKFold(n_splits=5).split(X, y, groups)
```

Grouping MUST be by problem, so that all kernel variants measured for one problem stay in the same fold. §11.3 adds a second, stricter split.

## 3. The Three Spaces

### 3.1 Decomposition

For every operation the feature space decomposes into three sources (RFC 0019 §6.1):

```
                  Device ($device.*)          Problem ($q.*)                Kernel ($kernel.*)
                  ──────────────────          ──────────────                ──────────────────
Declared by:      GPU hardware                Operation metadata (§4)       KMD schema (§6)
Explored by:      NOT explored                Corpus generator (§5)         Variant enumerator (§6)
                  (one fixed point
                   per training run)
Filtered by:      —                           is_applicable (§7)            is_valid_config (§7)
Obtained from:    HIP runtime query           Generated corpus JSON         KMD + catalog
```

The **device space** is a single fixed point per training run. The **kernel space** is enumerable from the compiled catalog. The **problem space** is unbounded and is where operation-specific methodology is required.

### 3.2 Division of Responsibility: Tooling Generates, Provider Filters

**Tooling responsibility.** Generate a representative problem corpus spanning the **operation's full potential parameter space**. Tooling holds the operation-level knowledge — that SDPA has prefill and decode regimes, that GEMM has batch-1 inference and tall-skinny projection shapes.

**Provider responsibility.** Supply **predicates** that answer "can this engine handle this problem?" and "is this variant valid?".

**Explicitly NOT the provider's responsibility.** Enumerating an exhaustive list of supported problems.

Why this split:

1. Providers know their kernel's constraints, not every use case hipDNN must cover.
2. A predicate is cheaper to author and maintain than an exhaustive list, and cannot silently go stale.
3. Synthesis is automatic — tooling generates broad coverage, predicates prune what the engine cannot run, training sees exactly the feasible set.

### 3.3 Device Space Handling

Device properties are queried once per training run via `hipGetDeviceProperties()` / `hipDeviceGetAttribute()`, or loaded from a JSON config when running without hardware.

The field set is the one RFC 0019 §6.1 specifies, extended additively as predictive need is demonstrated: `cu_count`, `lds_size`, `warp_size`, `sgpr_count`, `vgpr_count`, `max_waves_per_cu`, `memory_clock_mhz`, `memory_bus_width`, `peak_bandwidth_gbps`.

**Normative rule — device columns are recorded but are not features in single-arch runs.**

- Every benchmark CSV MUST carry the `device.*` columns (§8.3). They are provenance: they identify what hardware produced the timings.
- For a **single-arch training run**, `device.*` columns are constant across all rows. A zero-variance column can never be split on by a tree model; including it in `--features` adds nothing to accuracy while enlarging `features_signature` and changing `features_hash`. Single-arch runs therefore MUST NOT pass `device.*` columns as features.
- For a **pooled multi-arch training run** (§3.4), `device.*` columns vary and SHOULD be features.

`uhd_gen` SHOULD reject a `--features` list containing a column with zero variance, naming the column, rather than training a model with a dead feature.

### 3.4 Multi-Architecture Coverage

**PARTIALLY SPECIFIED** (RFC 0019 §8.3): arch-keyed UHD selection. The UED maps each architecture to a
UHD **id**, resolved exact-first then `default` (RFC 0019 §3.1); the values are descriptor identities, not
paths.

```json
"sort_kernel_catalog": {
  "gfx942":  "ae896b07-80cd-473c-b3f4-6a8892998519",
  "gfx950":  "7b1e9c40-1f2d-4a55-9c31-0b7e6d2ac418",
  "default": "c93e17aa-5b60-4f0e-8a72-3d1c9f4e2b06"
}
```

**Two strategies, and when to use each:**

| Strategy | Training data | `device.*` as features | Use when |
|----------|---------------|------------------------|----------|
| **Per-arch models** | One run per arch | No (§3.3) | Default. Arch behaviour differs qualitatively; each model stays small. |
| **Pooled arch-aware model** | Runs from ≥3 archs concatenated | Yes | Covering SKU variation within a family (CU-count differences on the same `gfx`) where behaviour differs quantitatively, not qualitatively. |

`$device.arch` itself MUST NOT be a feature — it is a KDP property used for UHD resolution, not a runtime feature (RFC 0019 §6.1). SKU variation is expressed through numeric properties (`cu_count`, `lds_size`, `peak_bandwidth_gbps`) which the model can actually interpolate over. Arch enters the training artifact only as loader-checked coverage metadata (§10.5).

Where an architecture needs materially different behaviour, RFC 0019 §3.3 gives it a **separate engine** rather than a folded-in model. Arch-keyed maps split where arches diverge; they are not a substitute for that decision.

The **mechanism** is decided and implemented: RFC 0019 §3.1's three role-scoped, arch-keyed UHD maps exist, with exact `gcnArchName` resolution falling back to `default`.

What RFC 0019 Open Question 2 still asks is which of the two strategies above should be the *default*, and that turns on cross-arch accuracy data nobody has yet. §11 is the protocol that would produce it; this RFC takes no position on the outcome.

### 3.5 Engine Scope, Not Pack Scope

A UHD belongs to the **UED — the engine** — and is shared by every pack that joins it (RFC 0019 §3.3: "Engine-scoped, never per-pack"). A UHD is never inlined per kernel or per pack.

Two consequences for training:

1. **The corpus must cover the union of every pack on the engine.** A UHD trained against pack A alone will rank A ∪ B once pack B joins, and nothing in the load-time contract check catches it — the model silently extrapolates. RFC 0019 Open Question 5 records this; its v1 recommendation is to retrain over the union and emit a coverage warning. Training that scopes its corpus to one pack violates the intent even though it passes every mechanical check.
2. **The engine, not the pack, is the unit of a training run.** A pack is a shipped kernel collection contributing UKDs; the engine is what owns the heuristic trained over them.

## 4. Operation Metadata Schema

**SPECIFIED HERE.** This is the canonical, machine-readable description of an operation. It is the single input that makes corpus generation mechanical rather than per-operation code.

### 4.1 File Location and Identity

```
projects/hipdnn/tools/uhd_gen/metadata/<operation>.json
```

`<operation>` MUST match the FlatBuffers `NodeAttributes` union member for the op, lowercased with an explicit direction suffix where the schema distinguishes one — e.g. `matmul`, `layernorm_fwd`, `layernorm_bwd`, `sdpa_fwd`, `conv_fwd`.

### 4.2 Schema

```json
{
  "schema_version": "1.0",
  "operation": "layernorm_fwd",
  "display_name": "LayerNorm Forward",
  "description": "Layer normalization over the trailing normalized dimensions.",

  "parameters": {
    "batch":       { "type": "int64", "range": [1, 4096],
                     "common_values": [1, 4, 8, 16, 32, 64, 128, 512] },
    "seq_len":     { "type": "int64", "range": [1, 32768],
                     "common_values": [128, 512, 1024, 2048, 4096, 8192, 16384] },
    "hidden_dim":  { "type": "int64", "range": [128, 16384],
                     "common_values": [768, 1024, 1536, 4096, 5120, 6656, 8192, 12288] },
    "dtype":       { "type": "enum", "values": ["float32", "float16", "bfloat16"] },
    "forward_phase": { "type": "enum", "values": ["INFERENCE", "TRAINING"] }
  },

  "stratification_axis": "working_set",

  "regimes": {
    "hidden_dim":  { "parameter": "hidden_dim",
                     "buckets": [768, 1024, 1536, 4096, 5120, 6656, 8192, 12288] },
    "batch":       { "parameter": "batch",  "buckets": [1, 4, 16, 32, 64, 128, 512] },
    "seq_len":     { "parameter": "seq_len","buckets": [128, 512, 2048, 8192, 16384] },
    "alignment":   { "parameter": "hidden_dim", "derived": "alignment",
                     "buckets": ["aligned", "partial_remainder", "full_remainder"] }
  },

  "graph_builder": {
    "function": "createValidLayernormFpropGraph",
    "source": "hipdnn_test_sdk/utilities/FlatbufferGraphTestUtils.hpp",
    "arguments": [
      { "name": "dims",    "kind": "expr",
        "value": ["$q.batch", "$q.seq_len", "$q.hidden_dim"] },
      { "name": "strides", "kind": "strides_of", "of": "dims" },
      { "name": "inputDataType",   "kind": "dtype_of", "source": "$q.dtype" },
      { "name": "computeDataType", "kind": "dtype_of", "source": "$q.dtype" }
    ]
  }
}
```

### 4.3 Field Definitions

#### 4.3.1 Top level

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `schema_version` | string | Yes | Metadata schema version (current `"1.0"`) |
| `operation` | string | Yes | Operation identifier (§4.1) |
| `display_name` | string | No | Human-readable name |
| `description` | string | No | Operation semantics |
| `parameters` | object | Yes | Parameter space (§4.3.2) |
| `stratification_axis` | string | Yes | `arithmetic_intensity` \| `working_set` \| `reduction_ratio` (§4.3.4) |
| `regimes` | object | Yes | Stratification buckets (§4.3.5) |
| `graph_builder` | object | Yes | Graph construction mapping (§4.3.6) |

There is no `tier_sampling` field. Tiers are budget-derived and global (§5.5); an operation does not get to declare its own corpus size.

#### 4.3.2 Parameters

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `type` | string | Yes | `int64` \| `float64` \| `enum` \| `bool` |
| `range` | `[min, max]` | No | A **semantic** bound only — a limit inherent to the operation, such as one dimension that cannot exceed another. Not a judgement about typical sizes. |
| `values` | array | For enum | Permitted values |
| `common_values` | array | No | Representative values, where a usage source exists (§5.2) |
| `description` | string | No | — |

`values` is REQUIRED for `enum`; `bool` has implicit `[true, false]`.

**Numeric dimensions are not bounded by authored ranges.** Two things bound the region a generator draws
from, and neither requires anyone to guess a typical size:

- **Benchmarkability.** A problem whose tensors do not fit in device memory cannot be timed, so it cannot
  enter a training corpus at any budget. That ceiling is computed, not declared: tensor bytes from shape
  and dtype, against the device's memory size. It is the limit that actually binds, and it is sharper than
  any statement about what the hardware can express.
- **Applicability.** Everything below that ceiling is a candidate; the provider's predicate prunes what the
  engine cannot run (§7.5). The feasible region is the intersection, and it is discovered by sampling
  rather than declared up front.

A `range` entry is therefore reserved for bounds intrinsic to the operation itself. Authoring one to
express "sizes we expect to see" is a metadata bug: it silently truncates the space the engine claims to
support, and expected sizes belong in §5.2's weighting instead.

#### 4.3.3 Cost Quantities

Stratification and the throughput target both need an operation's FLOP and byte counts. **Operation
metadata does not define them.** RFC 0019 §13.6 places them in the binding layer as precomputed fields,
published for every op that has them:

```
$<op>.flops        // e.g. $sdpa_fwd.flops — 4·B·H·Sq·Sk·D for SDPA forward
$<op>.bytes        // sum over each tensor of element_count × that tensor's own dtype size
```

The parent is explicit that these are **not** authored as expressions: they are op-intrinsic, identical
for every engine implementing the op, and "what needs a rebuild to change belongs in code, as a
precomputed binding field." Re-declaring them per operation-metadata file would create the second
definition site that rule exists to prevent, and would put the mixed-dtype byte rule — each tensor
contributing its own dtype size — in a place where each author could get it wrong independently.

Consequently this RFC defines no cost expressions, and needs no `sizeof` operator. RFC 0019 §6.2 fixes the
expression operator set and states that no extension is needed; `sizeof` is not in it, and the byte count
that would have required it is the binding layer's to compute.

**Where the generator gets them.** The corpus generator builds a graph per candidate problem (§4.3.6) and
reads the bound fields. Stratification therefore happens after graph construction rather than before it:
candidates are generated, bound, classified by the resulting axis value, then kept or dropped to meet
bucket targets (§5.3).

**Interim, while the binding fields do not exist.** RFC 0019 §13.6 specifies these fields; RFC 0019 Open
Question 4 leaves which counts to publish, and the mixed-dtype byte convention, unsettled, and no
operation publishes them today. Until they land the generator MAY compute the quantities host-side. That
fallback lives in the generator's own per-op table, **not** in the operation metadata file, so there is
one place to delete when the binding fields arrive and no descriptor carries a definition that has to be
migrated. A host-side value MUST match the definition RFC 0019 §13.6 states for that op.

**Ops without a closed form.** Ragged or data-dependent shapes can make an exact count impossible. RFC 0019
§13.6 directs that the field then expose a documented upper bound or be absent rather than be silently
wrong. An operation with no cost fields cannot use the `arithmetic_intensity` stratification axis and MUST
declare `working_set` or `reduction_ratio`.

**A proposed addition.** The `working_set` axis (§4.3.4) needs a per-group footprint — the bytes one
normalization row, tile or reduction group touches — which is op-intrinsic in exactly the way FLOPs and
bytes are, and which the parent's set does not currently include. RFC 0019 §13.6 notes that the op
vocabulary "should carry a *set* of useful precomputed fields — some universal across ops, some per-op",
and assigns the question of what belongs in that set to the UMD. This RFC therefore **proposes**
`$<op>.working_set_bytes` as an addition to that set rather than defining it here. Until it exists, the
same host-side interim applies.

#### 4.3.4 Stratification Axis

Arithmetic intensity is **not** a universal stratification axis. For a bandwidth-bound elementwise or normalization op it is shape-invariant: LayerNorm moves a fixed number of bytes per element and does a fixed amount of arithmetic on each, so `flops / bytes` reduces to a constant independent of batch, sequence length and hidden size. Stratifying such an op by AI produces exactly one bucket and no coverage.

Each operation therefore declares which axis is informative:

| Axis | Definition | Use for |
|------|------------|---------|
| `arithmetic_intensity` | `$<op>.flops / $<op>.bytes`, thresholded against `peak_flops / peak_bandwidth` | Ops that can be compute-bound: GEMM, Conv, SDPA, MoE |
| `working_set` | `$<op>.working_set_bytes` (§4.3.3, proposed) bucketed against L1 / L2 / LLC / HBM capacity | Bandwidth-bound ops: Norm, Pointwise, Quantize |
| `reduction_ratio` | `input_elements / output_elements` | Reductions, where cost is driven by fan-in, not footprint |

The corpus generator MUST report bucket occupancy for the declared axis (§5.9), so a corpus that collapsed into one bucket is visible rather than silent.

#### 4.3.5 Regimes

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `parameter` | string | Yes | Parameter this regime stratifies |
| `buckets` | array | Yes | Discrete values, or labels when `derived` is set |
| `derived` | string | No | `alignment` — buckets are `aligned`/`partial_remainder`/`full_remainder` relative to the kernel tile sizes discovered in §6 |
| `description` | string | No | — |

Regimes are the axes of the stratified cross-product in §5.3. All declared regimes participate; there is no "primary" regime.

#### 4.3.6 Graph Builder Mapping

Corpus entries are parameter dictionaries; benchmarking needs a serialized FlatBuffers graph. `graph_builder` closes that gap declaratively.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `function` | string | Yes | Builder function name |
| `source` | string | Yes | Header providing it |
| `arguments` | array | Yes | Ordered argument mapping |

Each argument has a `kind`:

| `kind` | Fields | Behaviour |
|--------|--------|-----------|
| `direct` | `source` | Copy the named `$q.*` value |
| `expr` | `value` | Evaluate a §4.3.3 expression (arrays yield dims lists) |
| `strides_of` | `of` | Row-major contiguous strides for a previously-named argument |
| `dtype_of` | `source` | Map a dtype string to the FlatBuffers `DataType` enumerator |
| `constant` | `value` | Literal |

Arguments are resolved in declaration order, so `strides_of` may reference an argument declared earlier.

Every argument named in `arguments` MUST reference only parameters declared in `parameters`. A validator MUST reject metadata that references an undeclared parameter — this is the check that catches a `graph_builder` written against a different parameterization than the op declares.

Builders live in `hipdnn_test_sdk/utilities/FlatbufferGraphTestUtils.hpp`; all 22 ops with FlatBuffers schemas have one. Dispatch is by `graph_builder.function`, so adding an operation requires no change to the generator.

### 4.4 Metadata Validation

`uhd_gen validate-metadata` MUST check:

1. Conformance to the §4.3 field tables.
2. Every `$q.*` reference in `graph_builder` resolves to a declared parameter.
3. Every `regimes[*].parameter` is a declared parameter, and non-derived buckets fall inside that parameter's `range`.
4. `stratification_axis` is one of the three permitted values, and the cost fields that axis reads are available for the operation (§4.3.3).
5. `graph_builder.function` resolves in the declared source header.
6. Expressions parse and evaluate to a positive number on the parameter midpoint.

## 5. Problem Corpus Generation

### 5.1 Sampling Is an Exploration Problem

What makes a corpus effective is coverage of the regions where **which kernel wins changes** — the decision boundaries. Elsewhere the ranking is stable and extra samples buy little.

Those boundaries cannot be targeted up front. Knowing where they lie means already knowing the answer the model is being trained to produce. Boundary location is an *output* of benchmarking, not an input to it, so any single-pass generator is choosing every sample while blind to the thing that determines whether the sample was worth taking.

Corpus generation is therefore staged:

| Round | Informed by | Purpose |
|-------|-------------|---------|
| **0 — exploration** | Nothing. Declared regimes only. | Broad, unbiased coverage of the whole declared space |
| **1..N — backfill** | Measurements and model assessment from prior rounds | Densify where the evidence says coverage is insufficient |

Default `N = 2`. Each round produces a corpus increment that is benchmarked and folded into the training set; the model is retrained between rounds.

**Exploration floor.** Backfill guided solely by where the current model reports weakness entrenches blind spots: a region the model is confidently and uniformly wrong about looks healthy and is never revisited. Every backfill round MUST therefore allocate at least **20%** of its samples by unbiased stratified draw, independent of any assessment signal.

**Round 0 is the majority of the budget.** Backfill targeting is only as good as the regret estimates driving it, and those estimates need enough samples per region to be signal rather than noise. Under-sizing round 0 to leave room for backfill produces confident targeting of the wrong regions.

### 5.2 Target Distribution, Where One Is Known

**The default is blind.** A new kernel arrives with a new UED and UHD and no usage history, so there is no
distribution to aim at. That is the normal case rather than the exception: the corpus is generated from
the operation's feasible dimensions alone (§4.3.2), sampled uniformly — log-uniform on size dimensions,
since performance regimes scale multiplicatively rather than additively.

Blind generation is also why §5.4 matters more than it first appears. With no prior on where behaviour
changes, measured boundary density is the *only* signal available for a new kernel; nothing can be
declared in advance.

**Weighting is a refinement for operations that have a usage record.** Where one exists it answers the
question uniform sampling cannot — "representative of *what*" — since uniform stratification weights a
prime-dimension corner case identically with a shape every customer runs.

For convolution the record exists outside these RFCs: the MIOpen performance database carries curated
shape collections keyed by model, dataset and client. Those are *used* shapes rather than *supported*
ones, so they are a weighting signal and a set of shapes known to matter, not the corpus itself. For GEMM,
SDPA and the remaining operations there is no equivalent source (§13, Gap 13).

Where a record exists, operation metadata MAY declare per-regime weights:

```json
"regimes": {
  "llm_shapes": { "parameter": "shape_family", "buckets": [...], "weight": 4.0 },
  "primes":     { "parameter": "M",            "buckets": [...], "weight": 0.5 }
}
```

`weight` defaults to `1.0` and is a relative expected-traffic multiplier, not a sampling count.

Weights are used **twice, differently**:

- **Sampling** — round 0 allocates samples proportional to `weight^0.5`, not `weight`. Square-root damping keeps low-weight regimes populated enough to be learnable while still favouring common shapes; allocating proportional to raw weight starves the tail, and the tail is where regret concentrates.
- **Reporting** — §11.2 regret is reported unweighted, and additionally traffic-weighted when weights are
  declared. The unweighted number says how good the heuristic is across the space the engine supports; the
  weighted number estimates what a user will experience. They can diverge sharply, and for a blindly
  generated corpus only the first exists.

### 5.3 Round 0 — Broad Coverage

| Strategy | Behaviour |
|----------|-----------|
| `one_per_regime` | One representative per bucket of each regime, other parameters at their most common value. Smoke only. |
| `stratified_cross_product` | Cross-product of all regime buckets × categorical parameters, then samples drawn per bucket (allocation per §5.2) with free numeric parameters sampled log-uniformly within range. Default for `standard`. |
| `dense_log_grid` | Log-spaced grid over every numeric parameter × full cross-product of categoricals. `exhaustive` only. |

**Non-regime parameter handling.** Under `one_per_regime`, a parameter not being stratified takes `common_values[0]` where `common_values` is declared, and the geometric midpoint of `range` otherwise. It MUST NOT take the range minimum: doing so collapses every sample onto one corner of the space.

**Reaching a target count.** Undershoot by reducing samples-per-bucket uniformly; overshoot by round-robin removal across buckets. A generator MUST NOT truncate the accumulated list, which drops whole regimes according to iteration order.

**Dedup.** Deduplicate on the tuple of `q.*` values after generation, then top up by re-sampling under-filled buckets, up to `max_attempts = 10 × target`. `metadata.count` records the actual post-dedup count, which MAY be below target; the shortfall MUST be reported.

**Frozen holdout.** Before any backfill, a random **10%** stratified slice of round 0 MUST be marked `holdout: true` and excluded from training in every subsequent round. Backfill deliberately skews the corpus toward hard regions, so a holdout drawn after backfill is no longer representative and cannot be compared across rounds. The frozen round-0 holdout is the only evaluation set whose distribution is stable for the whole campaign (§11.3).

### 5.4 Backfill Rounds — Evidence-Driven

After round 0 is benchmarked and a model trained, three signals identify where to densify. All are computed from data in hand; none requires knowing boundary locations in advance.

| Signal | Computed from | Identifies |
|--------|---------------|------------|
| **Boundary density** | Measurements only | Among neighbouring measured problems, the fraction whose top-1 variant differs. High density = a decision boundary runs through the region. |
| **Regret concentration** | Model + measurements | Per-region mean top-1 regret (§11.2). High regret = the model is losing performance here. |
| **Prediction dispersion** | Model only | Variance of predicted score across CV folds. High dispersion with few samples = the model is guessing. |

Boundary density is the strongest signal because it is model-independent: it says the region is *intrinsically* hard to rank, whether or not the current model has noticed. Regret concentration says the current model is failing. Dispersion says the corpus is too thin to tell. A region flagged by all three is the highest-value backfill target.

**Allocation within a backfill round:**

1. Reserve the 20% exploration floor (§5.1), drawn by unbiased stratified sampling.
2. Distribute the remaining 80% across regions proportional to a combined score, with boundary density weighted most heavily.
3. Cap any single region at 40% of the round, so one pathological region cannot consume the budget.
4. Sample within a targeted region by local refinement — draw near existing high-signal problems rather than re-drawing from the region's full range.

New samples MUST be tagged with their round and the signal that selected them, so a post-hoc analysis can tell whether backfill actually helped or merely spent budget.

### 5.5 Budget Allocation and Stopping

**The unit of benchmark cost is the (problem, variant) pair, not the problem.** A corpus of 5,000 shapes costs 2.5M timed configurations against a 500-variant catalog and 25M against a 5,000-variant catalog. A shape count is therefore meaningful only alongside the variant count it was measured against.

Tiers are defined by a **configuration budget**:

| Tier | Budget (configs) | Approx. wall-clock | Purpose |
|------|------------------|--------------------|---------|
| `smoke` | 10⁴ | minutes | Validate that generation, graph construction, filtering and benchmarking run end to end |
| `standard` | 2 × 10⁶ | ~8–15 GPU-hours | Production heuristic |
| `exhaustive` | 2 × 10⁷ | ~4–7 GPU-days | Research; maximum accuracy |

Problem count follows from the measured variant count:

```
N_problems = clamp( budget_configs / N_applicable_variants,
                    min = 30 × N_regime_buckets,
                    max = parameter-space saturation )
```

| Applicable variants | `smoke` | `standard` | `exhaustive` |
|---------------------|---------|------------|--------------|
| 50 | 200 | 40,000 | (saturated) |
| 500 | 30 (floor) | 4,000 | 40,000 |
| 5,000 | 30 (floor) | 400 | 4,000 |

The **floor** (`30 × N_regime_buckets`) guarantees stratification remains meaningful even under a tight budget; if the floor exceeds the budget, the tool MUST report that the budget is insufficient rather than silently under-sampling. The **saturation cap** stops adding problems once new samples no longer occupy unfilled buckets on the declared stratification axis.

Wall-clock is estimated as:

```
T ≈ N_configs × (t_setup + n_iter × t_kernel)
```

`t_setup` (plan build, kernel load, workspace allocation) typically dominates for small problems. `uhd_gen benchmark` MUST measure `t_setup` and `t_kernel` on a calibration sample of ~100 configs and print the projected total before starting the full run, so an infeasible sweep is caught in the first minute rather than on day three.

CK's published corpus (≈5,000 GEMM shapes × ≈500 kernels ≈ 2.5M configs) sits at the `standard` budget.

Corpus size is bounded by benchmark cost and by coverage, not by model capacity. A 4,000-problem corpus against 500 variants yields 2M training rows — orders of magnitude past what a leaf-population parameter such as LightGBM's `min_data_in_leaf` constrains.

**Per-round split — a planning estimate, not a commitment.**

| Round | Share of budget | Selection |
|-------|-----------------|-----------|
| 0 | 50% | Stratified over the feasible region (§5.3) |
| 1 | 25% | 20% exploration floor, 80% evidence-targeted (§5.4) |
| 2 | 25% | Same, using signals refreshed after round 1 |

Use this to size a run. **Only round 0 is committed spend.** Whether to iterate at all is decided from
measured predictive accuracy after round 0, not assumed before any measurement exists — which makes the
stopping criterion below the decision point rather than an exit condition. A model that is already
accurate enough after round 0 should release its remaining budget to another operation or architecture
rather than backfill a corpus that has converged.

`smoke` runs round 0 only — its purpose is pipeline validation, not accuracy, and there is nothing to assess.

**Stopping.** Rounds stop early when any of these holds:

1. Traffic-weighted mean top-1 regret on the frozen holdout improves by **< 1 percentage point** over the previous round. The learning curve has flattened; further shapes buy nothing and the remaining budget SHOULD go to another operation or architecture.
2. No region exceeds the backfill-targeting thresholds — the evidence says coverage is already adequate everywhere.
3. Budget is exhausted.

Case 1 and case 3 mean different things and MUST be reported differently. Stopping on a flat curve means the corpus is sufficient. Stopping on budget means the corpus was the binding constraint and the model is likely still improvable — the training manifest MUST record which occurred, because shipping a budget-limited model without recording that fact loses the single most useful piece of information for the next training campaign.

### 5.6 Corpus Location

RFC 0019 Open Question 10 leaves open whether the shape corpus lives in a tool-side config or a descriptor field. **This RFC places it tool-side**, as the versioned JSON artifact of §5.8.

The corpus is a training input, not a runtime contract. Nothing at selection time reads it, so a descriptor field would ship sampling policy inside the engine and force a descriptor version bump on every corpus revision — including the backfill rounds of §5.4, which revise it by design. Reproducibility, which is what motivated the question, is met instead by the provenance the artifact carries (§5.8) and by the manifest reference from the training run (§10.5).

What remains descriptor-side is the *knob* grid, not the shape corpus: a validity constraint expresses which values are legal, not which to sample, so an irregular knob axis still needs an explicit sweep hint. That part of Open Question 10 is untouched here and belongs with the enumeration gap (§13, Gap 2).

### 5.7 Determinism and Provenance

Corpus generation MUST be reproducible. Given identical `(operation, tier, seed, generator_version, metadata content hash)`, round 0 MUST be byte-identical.

- `seed` is REQUIRED in corpus metadata; if not supplied on the command line, the tool generates one and records it.
- All sampling MUST draw from a seeded generator instance (`np.random.default_rng(seed)`). Module-level `np.random` MUST NOT be used.
- `metadata_hash` records the SHA-256 of the operation metadata file, so a corpus cannot be silently invalidated by an edit to the op definition.

Backfill rounds are reproducible only relative to their inputs: they depend on measurements and on the model trained from prior rounds. A backfill increment therefore records `input_model_hash` alongside its seed. Replaying a full campaign requires the round-0 seed plus the recorded per-round inputs; replaying round 0 alone requires only the seed.

1. `metadata.count == len(problems)`.
2. `metadata.regimes` values sum to `metadata.count`.
3. `metadata.rounds[*].count` values sum to `metadata.count`.
4. All entries in `problems` have identical `q.*` key sets.
5. All `q.*` values are JSON primitives.
6. Every `q.*` key corresponds to a parameter declared in the operation metadata.
7. Every problem with `holdout: true` has `round: 0`.
8. Every backfill round has `exploration_fraction >= 0.20`.

### 5.9 Coverage Reporting

The generator MUST emit `axis_occupancy` and per-regime counts, and MUST warn when any bucket on the declared stratification axis holds fewer than 30 problems. A corpus that silently collapsed into one roofline bucket, or that missed an entire regime, is otherwise indistinguishable from a good one until the model underperforms.

From round 1 onward the report MUST also carry, per round: boundary density by region, regret before and after the round on the frozen holdout, and the fraction of the round spent on exploration versus targeting. This is what makes backfill auditable — without it there is no way to distinguish targeting that found real boundaries from targeting that chased noise.

## 6. Kernel Variant Enumeration

### 6.1 What the Parent Fixes

Two things are settled by RFC 0019 and are not this RFC's to revisit.

**The variant space is the shipped kernels.** RFC 0019 §13.5: "The variant space is fixed: it is the
pack's existing child UKDs, so the tool does not enumerate or build variants but enrolls the shipped ones
and times them." Generation never invents a kernel. Deciding which variants should exist is the
package-creation stage of RFC 0019 §14, upstream of everything here.

**Addressing them is the unsolved part.** Autotune reaches a kernel only through exposed knob settings
(RFC 0019 §13.2), and knob ranges are reported per knob, independently. So the addressable set is the
Cartesian product of the axes, of which — for a sparse catalog — most combinations name no kernel. Cost
scales with the product rather than with the catalog, `add_engine_sweep()` caps the product at 10,000, and
nothing expresses which combinations are valid. RFC 0019 records this as **Open Question 12**, states that
it "requires an API improvement, tracked outside this RFC", and says the generation pipeline "depends on
it for the harder cases."

Q12 is therefore blocking and is owned with the hipDNN API. **This RFC does not resolve it.**

### 6.2 What the Generator Does Until Q12 Lands

Enrol the shipped variants it can address, and be honest about the rest:

1. Read the engine's knob axes and form the product.
2. If the product exceeds the `add_engine_sweep()` cap, do not silently truncate — report the count and
   the cap, and stop. RFC 0019 §13.2 notes the cap "bounds the damage but does not solve the problem — it
   just turns an intractable sweep into a rejected one," and a rejected sweep the operator can see beats a
   sampled one they cannot.
3. Enrol the product, time what binds, and record combinations that named no kernel as skipped rows with a
   `skip_reason` (§7.4), so the ratio of addressable to real is measurable rather than folded into the
   noise.
4. Report that ratio. It is the number that says how much Q12 is costing this engine, and it is what would
   justify prioritising one resolution over another.

This is workable for engines with small or dense knob spaces, which is exactly the boundary RFC 0019 §13.2
draws. For large sparse spaces it is not, and no amount of tooling changes that.

### 6.3 A Proposal Against Open Question 12

Offered as input to whoever owns Q12, **not as settled schema**. Q12 asks four sub-questions — knob tuples
versus opaque handles, whether enumeration is bounded or paged, public API versus generation-tool-only, and
where a `[min, max, step]` triple lives. What follows addresses the first and touches the fourth; it leaves
the others open.

RFC 0019 §13.5 already floats part of the descriptor-side answer: a `[min, max, step]` triple "makes a
regular axis enumerable without guessing the increment, which covers most numeric knobs; an irregular axis
still needs an explicit `sweep_values` list." It then notes that neither addresses **cross-knob** validity,
which is the harder half. The proposal below is a way to express both.

A `variant_enumeration` block on the KMD, in one of two modes:

**Mode `explicit`** — the provider supplies the valid tuples directly. This is Q12's "enumerate the valid
knob-tuple set" branch, answered by the descriptor rather than by an API call.

```json
{ "variant_enumeration": {
    "mode": "explicit",
    "variants": [
      {"tile_m": 64,  "tile_n": 64,  "tile_k": 8,  "use_lds": true},
      {"tile_m": 128, "tile_n": 128, "tile_k": 16, "use_lds": true},
      {"tile_m": 256, "tile_n": 128, "tile_k": 8,  "use_lds": false}
    ] } }
```

**Mode `range`** — per-axis values plus a provider predicate that prunes the product. This keeps the
descriptor small for a dense space while still expressing cross-knob validity, which `[min, max, step]`
alone cannot.

```json
{ "variant_enumeration": {
    "mode": "range",
    "fields": [
      {"name": "tile_m",  "type": "int64", "values": [64, 128, 256]},
      {"name": "tile_n",  "type": "int64", "values": [64, 128, 256]},
      {"name": "tile_k",  "type": "int64", "values": [8, 16, 32]},
      {"name": "use_lds", "type": "bool",  "values": [true, false]}
    ],
    "has_validator": true } }
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `mode` | string | Yes | `explicit` \| `range` |
| `variants` | array | Mode=explicit | Valid tuples |
| `fields` | array | Mode=range | Per-axis values for product generation |
| `fields[i].name` | string | Yes | MUST match a KMD knob name |
| `fields[i].type` | string | Yes | `int64` \| `float64` \| `bool` \| `string` |
| `fields[i].values` | array | Yes | Discrete values |
| `has_validator` | bool | Mode=range | Provider supplies a config predicate |

Two properties worth preserving in whatever Q12 settles on, independent of this particular shape:

- **The sparse case needs an enumeration, not a filter.** A predicate over a product that is mostly invalid
  still costs the product to walk. Mode `explicit` exists because for a sparse catalog the only affordable
  answer is being handed the valid set.
- **Cross-knob validity has to be expressible somewhere.** Per-axis ranges cannot state "tile_m × tile_k
  must fit LDS". Whether that lives in a predicate, in an enumerated set, or in an API that returns tuples
  is open — that it must live somewhere is not.

Under mode `range` the predicate would be a provider-side entry point, invoked through the backend
(§7.1) rather than by loading the provider directly:

```cpp
// Provider implements in the KMD library; backend routes to it.
extern "C" bool <provider>_is_valid_config(
    const char* variant_json,   // JSON object of knob values
    size_t      json_len);
```

It expresses the constraints tooling cannot infer: LDS capacity for a tile pair, wavefront limits, mutual
exclusivity between knobs.

### 6.4 Alignment Regimes Depend on the Catalog

A regime declared with `"derived": "alignment"` (§4.3.5) cannot be resolved until the variant set is known — "aligned" means aligned with respect to *these* tile sizes. Variant enumeration therefore runs **before** final corpus generation, and the tile values discovered here feed the alignment buckets. Concretely, the pipeline order is: enumerate variants → derive alignment buckets → generate corpus → filter → benchmark.

## 7. Applicability Filtering

### 7.1 Where Filtering Happens

The UHD is owned by the engine, and the engine is already registered with the hipDNN backend through the plugin loader. Tooling therefore MUST invoke applicability **through the backend API**, using the `engine_id` from the engine descriptor.

`uhd_gen` MUST NOT `dlopen` provider shared objects or resolve provider symbols with `dlsym`. Doing so bypasses the backend's plugin lifecycle and would give tooling a second, divergent view of which engines exist.

The C entry points below are the **provider-side contract** — what a provider implements so the backend can route to it. They are not the interface tooling calls.

```cpp
// Provider implements in the KMD library; backend routes to it.
extern "C" bool <provider>_is_applicable(
    const uint8_t* graph_flatbuffer,  // serialized hipDNN graph
    size_t         graph_size,
    int64_t        engine_id,
    char*          error_msg,         // optional; may be NULL
    size_t         error_msg_capacity);
```

Returns `true` when the provider can execute this graph with this engine; `false` otherwise, with the reason written to `error_msg` when that buffer is non-NULL. The reason string is not decorative — §7.4 records it.

**Provider precedent.** rocKE pre-filters explicitly via `miopenConvolutionForwardGetSolutionCount() > 0` rather than discovering inapplicability by failure. hipDNN adopts explicit pre-filtering.

### 7.2 The Native Scorer Signature

RFC 0019 §7.1 permits a native scorer to work in either of two modes — consume the standard feature row, or featurize from the engine's bindings itself — but specifies neither signature. The only C ABI the parent writes down is `custom_library`'s (RFC 0019 §7.4). That omission is why the two existing implementations chose different signatures independently, and it is filled here.

**Mode 1 — feature row.** The scorer receives the row the extractor already produced from `features_signature`, in declared order. This is the same C ABI `custom_library` uses, so a single implementation can be reached either way — registered in-process as `native`, or exported from a `.so` as `custom_library` — without changing its signature.

```cpp
// Registered with the UHD scorer registry; also the custom_library export ABI.
extern "C" double <symbol>(const double* features, size_t num_features);
```

`features` is in `features_signature` order and `num_features` matches the UHD's declared feature count. Implementations MUST be thread-safe. Return value is in the units the UHD's `score` metadata declares.

**Mode 2 — bindings.** The scorer receives the match context and featurizes itself. This is the kernel ingestor's existing `ScoreFn`, and a scorer written for it participates in the ingestor's selection path rather than the UHD adapter path:

```cpp
using ScoreFn = double (*)(const MatchContext&, const BoundTokens&, const KernelDefinition&);
```

**Which mode to use.** Mode 2 is the escape hatch RFC 0019 §7.1 describes — a heuristic no model expresses, needing inputs the feature row does not carry. Mode 1 is required for the **baseline** role: RFC 0019 §9 defines the `tree_data` overhead target as within 2× of `native`, and RFC 0019 §9.4 requires feature extraction and scoring be wall-clocked separately. A mode-2 scorer featurizes inside its own call, so timing it against a `tree_data` that goes through the generic extractor measures two different things and the ratio is meaningless.

**Why they are separate registries.** The two signatures are not convertible, so one registry cannot serve both. Both are instantiations of the ingestor's `NativeRegistry<T>` template — mode 1 as `NativeRegistry<UhdScoreFn>`, mode 2 as the ingestor's own `ScoreRegistry` — so the mechanism is shared even though the contracts are not. A UHD declaring `adapter: NATIVE` names a mode-1 symbol; `HeuristicKind::NATIVE` in the ingestor's descriptor names a mode-2 symbol. A symbol registered in one is not visible to the other, and that is deliberate rather than an oversight.

### 7.3 The Candidate-Set Invariant

**Normative.** For any problem `p`, the set of variants scored by the UHD at runtime MUST be a subset of the variants **eligible** at training time — that is, the same `is_applicable` / `is_valid_config` predicates MUST gate both paths.

Two obligations follow:

1. **The same predicates run on both paths.** Whatever pair filtered the training corpus MUST also gate the runtime candidate list before scoring. A provider that filters at training but not at runtime is asking the model to rank configurations its predicates declared impossible.
2. **Predicate changes invalidate the model.** If a provider tightens or loosens either predicate the eligible set shifts, and the model MUST be retrained. The training manifest records the predicate versions (§10.4) so this is detectable.

Problem-level applicability is exempt in one direction: if `is_applicable(p)` is false the UHD is never consulted for `p`, so dropping those problems from training is safe.

**Eligible is not the same as benchmarked.** The invariant constrains which variants are *scored*, not which were *measured*. Variant knobs are numeric, so a model interpolates across tile configurations it has not seen exactly as it interpolates across unseen problem shapes; subsampling the variant space is therefore sound, and for dense knob spaces it is unavoidable (§13, Gap 4).

What subsampling requires is **measurement of the resulting error**, and here variants differ from problems in a way that matters:

- An unseen **problem** yields one prediction per candidate; ranking errors partly cancel.
- An unseen **variant** competes in an argmax. Selection preferentially returns whichever candidate received the most optimistic error — the optimizer's curse — so the quantity that governs runtime quality is the model's error at the *top* of the predicted distribution, and it worsens as the catalog grows.

Two consequences, both already required elsewhere: variant sampling MUST cover the knob space evenly rather than densely in one corner (§6.2), because a thinly-sampled corner is where an inflated score goes unchallenged; and §11.3 MUST include a leave-variants-out split, so the regret attributable to unmeasured variants is a reported number rather than an assumption.

### 7.4 Recording Filtered Pairs

Pre-filtering saves benchmark time but destroys the record of what was filtered, which is the same record needed for coverage auditing (§5.9) and for diagnosing an over-narrow predicate.

Filtered pairs MUST therefore be written to the benchmark CSV with `is_valid=False` and a populated `skip_reason`, and MUST NOT be timed. Training excludes them by filtering on `is_valid`; auditing reads them to answer "which variants were never eligible, and why".

```csv
q.M,q.N,q.K,kernel.tile_m,…,minTimeMs,is_valid,skip_reason,error
1024,1024,1024,128,…,0.123456,True,,
1024,1024,1024,256,…,,False,invalid_config: tile_m*tile_k exceeds LDS,
17,17,17,256,…,,False,not_applicable: M below minimum tile,
```

### 7.5 Benchmark Execution Order

```
for problem in corpus:
    graph = build_graph(problem)                      # §4.3.6
    if not backend.is_applicable(graph, engine_id):   # §7.1
        record_skipped(problem, all_variants, "not_applicable: " + reason)
        continue
    for variant in variants:                          # §6
        if not backend.is_valid_config(graph, engine_id, variant):
            record_skipped(problem, variant, "invalid_config: " + reason)
            continue
        record(benchmark(graph, engine_id, variant))
```

## 8. Benchmark Dataset Construction

### 8.1 Autotune Integration

Timing goes through the RFC 0013 autotune API (§2.2), not standalone per-kernel executables. Variants are enrolled with `add_engine_variants()` (explicit) or `add_engine_sweep()` (range), and timed with `autotune(mode=EXHAUSTIVE, strategy=RUN_UNTIL_STABLE)`.

Autotune itself is RFC 0013's and is out of scope here (RFC 0019 §2). This section specifies only what the generation tool does around it.

Long runs (hours to days at `standard` and above) require progress reporting and checkpointing: the benchmark step MUST write results incrementally and MUST be resumable from a partial CSV.

### 8.2 The Kernel-Identity Contract

Per RFC 0019 §13.3, the candidate autotune timed MUST map 1:1 to the UKD it stands for in the emitted engine, so that the model's argmax over timed candidates is exactly argmax over UKDs at runtime. The join key is the knob tuple reported on each result; under full exposure (§2.2) that tuple is the kernel's metadata tuple, unique engine-wide.

Two obligations, both on the generation tool:

1. **Verify the round-trip.** The tool MUST confirm that the `knobSettings` reported back on a result select the same kernel they enrolled, rather than assuming it. An unverified join silently mislabels every row it touches.
2. **Treat a tuple collision as a dataset error.** If two enrolled candidates share a knob tuple, timings cannot be attributed to a kernel. Under full exposure this cannot happen, so a collision means the generation UED did not expose every KMD field. The tool MUST **fail loudly** rather than train on an ambiguous join.

The runtime case is different and benign: once the emitted UED exposes only the model's feature axes, two kernels differing solely in dispatch-only fields share a knob tuple, score identically, and are separated by the `priority`/`id` tie-break with a load-time warning (RFC 0019 §3.2).

### 8.3 Benchmark CSV Schema

UTF-8, RFC 4180, header row required. Columns are read by name; order is arbitrary. Null is the empty string. Booleans are `True`/`False` (case-sensitive). Floats carry ≥6 significant digits.

**Required columns**

| Column | Type | Description |
|--------|------|-------------|
| `q.*` | varies | Problem parameters, namespace-qualified |
| `kernel.*` | varies | Kernel variant knob values |
| `device.*` | varies | Device properties (provenance; see §3.3 for their use as features) |
| `minTimeMs` | float | Minimum time across iterations |
| `avgTimeMs` | float | Mean time across iterations |
| `stddevMs` | float | Standard deviation across iterations |
| `iters` | int | Iterations actually timed |
| `is_valid` | bool | Row carries a real measurement |
| `skip_reason` | string | Why the pair was not timed; empty when `is_valid=True` |

**Optional columns:** `tflops`, `gbs`, `error`.

**Validation rules**

1. Every `q.*` key from the corpus appears as a column.
2. Every `kernel.*` field from variant enumeration appears as a column.
3. Every `device.*` property queried appears as a column.
4. `minTimeMs ≤ avgTimeMs` for rows with `is_valid=True`.
5. `stddevMs ≥ 0`.
6. When `is_valid=False`, timing columns are empty and `skip_reason` is non-empty.
7. When `is_valid=True`, `skip_reason` and `error` are empty.

**Feature columns are produced by the shared extractor, not by this schema.** RFC 0019 §13.3 requires one generic extractor to run the `features_signature` on both sides — offline for training, the in-tree evaluator for inference — reading the same signature, so there is no reimplementation and no drift. The column list above therefore describes the *dataset envelope* (timings, validity, provenance); the feature columns within it MUST be emitted by running the signature through that extractor rather than assembled independently by the benchmark step. A training↔runtime parity test comparing the two evaluations on identical inputs is RFC 0019's Phase 4 deliverable and gates use of the generic extractor.

### 8.4 Target Metric

The target is derived from the operation's FLOP count (§4.3.3), not hardcoded per operation:

```
tflops = $<op>.flops / (minTimeMs * 1e9)
```

`$<op>.flops` is the precomputed binding field, read from the bound graph for that problem, with the
host-side interim of §4.3.3 applying until the field exists.

All column references MUST be namespace-qualified (`q.M`, not `M`) per §8.6.

Alternative targets: `minTimeMs` with objective `min`; `tflops / theoretical_peak` for a 0–1 efficiency scale; bytes/sec for bandwidth-bound ops, computed from `$<op>.bytes`.

### 8.5 Measurement Noise

`stddevMs` is recorded so it can be used, not merely stored.

- Rows where `stddevMs / avgTimeMs > 0.10` SHOULD be flagged as high-variance and either re-timed or excluded from training; the exclusion count MUST be reported.
- `minTimeMs` is the default target because it is the most noise-robust statistic available, but it is biased low under contention. Benchmarks SHOULD run with the GPU otherwise idle and with a fixed clock/power state where the platform permits; the training manifest records whether this was done.
- Two variants whose timing distributions overlap within noise are not meaningfully ordered. §11.2 accounts for this by scoring regret in throughput terms rather than rank position.

### 8.6 Feature Namespace Enforcement

**IMPLEMENTED** (commit `aa2be93`). `uhd_gen` rejects unqualified feature columns.

```bash
--features q.M q.N q.K kernel.tile_m kernel.tile_n
```

A bare `cu_count` becomes `$cu_count` in the signature, which the runtime cannot resolve — the failure mode is silent degradation to static ordering, so it is rejected at training time instead.

## 9. Feature Engineering

### 9.1 Auto-Derivable Features (RFC 0019 §13.6)

| Tier | Kind | Auto-derivable | Example |
|------|------|----------------|---------|
| 1 | Raw bindings | Yes | `$kernel.tile_m`, `$q.dims[2]`, `$device.cu_count` |
| 2 | Generic transforms | Partially | `{"log2": ["$q.dims[2]"]}`, `{"ceil_div": ["$q.dims[2]", "$kernel.tile_m"]}` |
| 3 | Physics | Yes, via cost model | `{"/": ["$op.flops", "$op.bytes"]}` |

**Tile quantization** requires author input: the tool cannot infer which problem dimension pairs with which tile field. The author supplies pairs, the tool emits the `ceil_div` expressions.

```python
dim_tile_pairs = [("seqlen_q", "tile_m"), ("head_dim", "tile_k")]
```

### 9.2 Cost-Model Features

Physics features are ratios over the precomputed cost fields (§4.3.3), written inline in the signature exactly as RFC 0019 §6.4 requires:

```json
{"features_signature": [ {"/": ["$op.flops", "$op.bytes"]} ]}
```

**GAP:** the binding layer does not yet publish `$op.flops` / `$op.bytes` (RFC 0020 §6). Until it does, `uhd_gen` evaluates the cost model host-side and emits precomputed CSV columns.

### 9.3 Feature Selection

**IMPLEMENTED.** LightGBM gain-based importance. Drop low-importance features and retrain; the emitted UED exposes only the survivors (RFC 0019 §3.2). Pruning a feature and dropping a knob are one action, and the emitted UED must carry the result (§10.4).

Selection MUST be evaluated with the §11 metrics, not with RMSE — a feature can reduce regression error while leaving top-1 selection unchanged, and such a feature costs runtime extraction work for no decision benefit.

**Prefer prefix features over per-candidate tail features.** RFC 0019 §9 splits the feature row into a shared prefix (`$q.*`, `$device.*`, computed invariants), evaluated once per selection, and a per-candidate `$kernel.*` suffix re-evaluated for every candidate — and names "keeping the kernel-dependent tail small" the main lever on selection cost. Two features of equal importance are therefore not equally cheap: the one in the tail costs `N_candidates` times more to extract. Feature selection SHOULD break near-ties toward the prefix, and MUST report the prefix/tail split alongside importances so the cost of the chosen set is visible.

This also bounds how far auto-derivation should be trusted: RFC 0019 §13.6 notes it yields a *superset* that "can hurt a small-data model," and every derived `$kernel.*` term it proposes lands in the tail.

## 10. Training Workflow

**IMPLEMENTED** in `uhd_gen`.

### 10.1 CLI

The current tool is a single flat command:

```bash
python -m uhd_gen \
    --input benchmark_results.csv \
    --features q.M q.N q.K kernel.tile_m kernel.tile_n kernel.tile_k \
    --target tflops --objective max \
    --group-by q.M q.N q.K \
    --output-dir ./uhd_output --name "GEMM UHD" \
    --num-boost-round 500 --early-stopping 50
```

The workflow in this RFC requires five commands: `validate-metadata`, `generate-corpus`, `enumerate-variants`, `benchmark`, `train`. Adopting them means restructuring `uhd_gen` around subcommands, which is a **breaking CLI change**: today's invocation is the training path with no subcommand. The migration is to move the existing flags under `train` and keep the bare form working with a deprecation warning for one release.

### 10.2 Algorithm

1. Load CSV, filter to `is_valid == True`.
2. Split features/target; `y = log1p(target)`.
3. GroupKFold (5 splits) on `--group-by` columns (§2.6).
4. Train LightGBM with early stopping.
5. Evaluate against the §11 protocol and record the report.
6. Export LightGBM → FlatBuffer `GbdtModel`.
7. Write the UHD document with `features_signature`, `categorical_encoding` and `features_hash`.

### 10.3 Hyperparameter Defaults

```python
params = { "objective": "regression", "metric": "rmse",
           "num_leaves": 127, "learning_rate": 0.05,
           "feature_fraction": 0.8, "bagging_fraction": 0.8, "bagging_freq": 5 }
```

**GAP:** no per-operation or per-dataset-size tuning guidance. `num_leaves = 127` is aggressive for a small corpus; tune against §11.2 regret, not RMSE.

**Inference cost is a training constraint.** RFC 0019 §9 requires the model to be cheap to load and cheap to rank with — ranking may be triggered for an engine that then loses — and targets `tree_data` overhead within 2× the `native` adapter baseline. Model capacity is therefore bounded from above by selection-time cost, not only from below by accuracy. `num_leaves` and `num_boost_round` are reported alongside measured per-candidate scoring time so that a model whose accuracy was bought with selection latency is visible as such.

### 10.4 Output Artifacts — Stage P

Training feeds RFC 0019 §13.4's package stage, which emits or updates the engine's whole descriptor set. Producing only the UHD leaves the engine inconsistent with the model it names.

```
output_dir/
├── uhd.json             # sort_kernel_catalog UHD, adapter: tree_data (RFC 0019 §4)
├── model.bin            # tree_data artifact the UHD body points at, embedding features_hash
├── ued.json             # UPDATED engine descriptor — knobs = surviving $kernel.* axes
├── kmd.json             # emitted only if the engine does not already carry one
├── train_manifest.json  # provenance and coverage (§10.5)
└── eval_report.json     # §11 metrics vs. baselines
```

**Descriptor documents are JSON; model artifacts are not.** RFC 0019 §4 defines a UHD as a JSON document
tagged `hipdnn.uhd/v1`, and RFC 0020 §4.2 applies the same convention to the UED, so every descriptor this
stage emits is JSON. The FlatBuffer in RFC 0019 belongs to the `tree_data` **artifact** (§7.2) — the tree
table the UHD body's `artifact` path points at — not to the descriptor that names it. A stage emitting a
binary UHD would produce a set the descriptor family's loader cannot read.

The artifact format itself is RFC 0019 Open Question 3: a FlatBuffer tree schema is recommended over
parsing LightGBM `model.txt` at load, and is not settled. This RFC assumes the FlatBuffer and does not
resolve the question.

When the engine needs an estimate, Stage P additionally emits a **second UHD** under the
`predict_engine_tflops` role key, with its own `features_signature`, `features_hash` and model artifact
(§10.6). It is not required for v1 — with a single descriptor engine there is nothing to rank against, and
`sort_kernel_catalog`'s top score is RFC 0019 §11.1's documented stopgap.

The UMDs, UDD, and child UKDs are **not** regenerated. Only the heuristic side changes; that is the intent of the two-stage design.

**Emitting the UED is neither optional nor separable.** RFC 0019 §3.2 makes `UED.knobs` equal to the set of `$kernel.*` fields reachable from `features_signature` — including those nested inside computed entries — and enforces that equality at load. Pruning a feature and dropping a knob are one action. A run that writes a new UHD without the matching UED produces a descriptor set that fails its own load check.

Because any change to the knob set is a **major** UED version bump (RFC 0019 §8), a retrain that drops an axis is a breaking change for a caller setting that knob. The tool MUST report knob-set deltas against the previous UED rather than emitting them silently. Whether a "sticky" superset knob set should insulate callers from model churn is RFC 0019 Open Question 18 and is **not** resolved here.

### 10.5 Required Provenance and Coverage Metadata

`train_manifest.json` and the emitted UHD MUST carry:

| Record | Why | Source |
|--------|-----|--------|
| `trained_against: {ued, umd, kmd}` versions | All three can invalidate the heuristic; the load rule checks major equality and minor ≥ | RFC 0019 §8 |
| Trained **arch set** | Loader exact-matches device GFX name against it — a loader-side check, not a `features_signature` read | RFC 0019 §8, §12 |
| Per-feature **trained value ranges** | Drives the coverage warning when a scored candidate falls outside training | RFC 0019 §8, §12 |
| `categorical_encoding` and its ordering rule | Integer codes imply an order a tree will split on | RFC 0019 §6, Q17 |
| Content hash over the UHD document **and** the model artifact | `features_hash` fingerprints the input contract, not the weights — two models with identical features and different training hash identically, so it is **not** a model identity | RFC 0019 §9 |
| Corpus `seed`, `metadata_hash`, per-round provenance | Reproducibility | §5.6 |
| Predicate versions behind the candidate-set invariant | Detects when the eligible set shifted | §7.2 |
| Benchmark clock/power conditions and which timing statistic was used | Calibration comparability | §8.5, §11.2 |
| Model size and measured per-candidate scoring time | The 2× `native` overhead target | RFC 0019 §9 |

The UMD entry is the easiest to forget and the most dangerous to omit: a matcher change can alter which candidates exist *or* change what a `$graph.*` token means, and neither is visible to a feature-name check.

Two of these records have nowhere to go yet. RFC 0019 §4.1 makes `trained_against` and
`categorical_encoding` required header fields, but §8 notes that none of the three descriptors carries a
version field for `trained_against` to reference, and no shipped UHD carries either field. Until those fields land, the manifest is the only carrier and the corresponding load-time checks cannot run — the requirement above is on the artifact, and it is unmet, not satisfied by writing the values somewhere the loader does not read.

**Out-of-distribution behaviour.** Tree models extrapolate badly — nearest-leaf yields a value with confidence and no basis for it (RFC 0019 §8).

RFC 0019 Open Question 16 offered two mitigations: versioning discipline with a cheap discrete arch check, or per-feature coverage metadata checked at runtime. **The first is decided and implemented.** `uhd_gen --training-arches` records the trained arch set into the model artifact (`gbdt_model.fbs`, `table_model.fbs`: `training_arches`); `TreeDataAdapter` and `TableAdapter` expose it and test device arch against it, treating an empty set as unrestricted; and `SelectionEngine` surfaces it on the selection trace.

Per-feature coverage metadata is the deferred half. The artifact format keeps it additive so it can land without a format break, and until it does, a candidate outside the trained value ranges is undetected at runtime.

**Categorical encoding.** RFC 0019 Open Question 17 requires the ordering semantics — meaningful order, one-hot, or author-declared — to be settled *before the first real model*, because changing it later forces a retrain. It is still open, and the tooling reflects that: the LightGBM exporter folds categorical `==` splits into `<=`, which is only sound for a field whose integer codes carry a real order.

This RFC does not choose the semantics. It requires that whatever is chosen be recorded in `categorical_encoding` and hashed into `features_hash`, so a later change is detected rather than silently absorbed — which, per the note above, needs the schema field first.

### 10.6 The Engine Estimate

RFC 0019 §3.1 lets a UED name a second role-scoped UHD, `predict_engine_tflops`, which the quick
engine-selection policy uses to rank engines *before* any of them enumerates candidates. §11.1 fixes its
signature as `f(graph) → expected perf` and notes that the "cheap, no catalog enumeration" property
"depends on `predict_engine_tflops` being trained on `f(graph)` alone, not `f(graph, candidates)`."

**Decision: a distinct trained model, not derived from the ranker.** RFC 0019 Open Question 6 leaves this
open, weighing "distinct is cheaper for the quick policy" against "derived is one fewer model to train."
Both halves look different from inside the training pipeline:

- **The derived option is systematically optimistic.** Deriving the estimate as the maximum *predicted*
  score over candidates takes a max over predictions, which selects for the largest positive prediction
  error — the same optimizer's curse §7.3 describes for variants. The bias grows with candidate count, so
  each engine's estimate is inflated by a different amount depending on how large its catalog is. That is
  precisely the bias that corrupts a cross-engine comparison, which is the estimate's only purpose. A
  model trained directly on measured best throughput carries no such term.
- **"One fewer model to train" overstates the saving.** A distinct estimate needs **no new benchmarking**.
  It is a projection of the dataset the ranker already produced.

#### 10.6.1 Who reads it, and why there is nothing to arbitrate

The estimate's consumer is engine selection — RFC 0007's policy layer, through one of the two policies
RFC 0019 §11.2 names. The quick policy ranks every applicable engine by the estimate and runs the ranker
only on the winner, so losing engines are never scored at kernel level. The thorough policy runs the
ranker everywhere and compares top scores, falling back to the estimate for engines that have no ranker.

**The engine does not choose between its UHDs.** RFC 0019 §11.2: "Both estimates are exposed through the
plugin API, and both are optional. The query surface must carry A and B separately — they have different
costs, and the quick policy's entire value is being able to ask for A *without* paying for B." The engine
offers whichever roles it has; the policy asks for one. §11.2's four-case matrix covers what a policy does
when an engine has only one of them, or neither.

So a second UHD introduces no contention with the first. The UED's three role-scoped fields (RFC 0019
§3.1) are slots for distinct questions asked by distinct callers at distinct points in the pipeline —
`predict_engine_tflops` before any catalog exists, `sort_kernel_catalog` after applicability has narrowed
to one engine. Adding a role extends what the engine can answer; it does not create an ambiguity the
engine has to resolve. Whether more ranking strategies are worth adding later is a UED capacity question,
not a UHD one.

**This is also the second reason the model is distinct rather than derived.** §11.1 notes that deriving the
estimate from the ranker means "every engine runs the ranker to produce it, collapsing the quick and
thorough policies into one operation" — the quick policy's whole purpose is to avoid enumeration, and a
derived estimate makes obtaining it require enumeration. The calibration argument above and this one are
independent, and point the same way.

#### 10.6.2 Corpus, features and target

**Corpus — a projection, not a new sweep.** Group the §8.3 dataset by problem and keep, for each, the best
measured throughput across that problem's valid rows. The result is one row per problem where the ranker
had one row per (problem, variant).

**Features — `$q.*` and `$device.*` only.** No `$kernel.*` reference may appear, in a raw entry or nested
inside a computed one. That exclusion is what makes the model `f(graph)` and preserves the no-enumeration
property the quick policy depends on; a single `$kernel.*` term silently turns the cheap estimate into the
expensive one. The prefix/tail distinction of §9.3 does not apply here, since every feature is prefix.

**Knobs are unaffected.** RFC 0019 §3.1 derives `UED.knobs` from `sort_kernel_catalog`'s `$kernel.*` axes
"and no other", so the §6.3 load check that knobs equal the model's kernel-side feature set is scoped to
the ranker alone. A second UHD does not widen it. Here the point is doubly moot: the estimate carries no
`$kernel.*` reference at all, so it has no kernel-side axes to contribute.

**Target — best achieved throughput for the problem**, in the same units and under the same transform as
the ranker, so the two are comparable. The estimate exists to be compared across engines, so it MUST
declare `score.calibrated: true`, which per §11.2 means training it on `avgTimeMs` rather than
`minTimeMs`.

#### 10.6.3 Evaluation

The §11.2 ranking metrics do not apply: there is no candidate set, so there is nothing to rank and no
regret to measure. What applies is the calibration half — relative absolute error and signed bias — and
those become the whole of the estimate's evaluation rather than a secondary axis.

One check is specific to having two models. On the same problem, the estimate and the ranker's top score
answer the same question by different routes, so they SHOULD agree within the estimate's error band. A
systematic disagreement means one of them is miscalibrated, and the comparison localizes which without
needing new measurements.

#### 10.6.4 What this costs the corpus

The two models want different budget shapes. The ranker needs variants per problem; the estimate needs
problems. §5.5's allocation assumes the ranker, and a run serving both should stay that way — but the
tension is worth stating because it is not one-sided.

Spending the same budget on more problems and fewer variants each would give the estimate more rows, and
would also make each row's *label* worse: "best over measured variants" approximates "best achievable"
less well when fewer variants were measured. Shifting budget toward the estimate therefore improves its
coverage and degrades its target at the same time. If the estimate ever becomes the priority, that
trade — not raw problem count — is what to optimize.

#### 10.6.5 Status of Open Question 6

RFC 0019 records the distinct-versus-derived choice as Open Question 6 and does not settle it. This RFC
takes the distinct-model position on the grounds above and specifies training against it. That resolution
belongs in RFC 0019 §11.1 and Q6 as well; until that document is updated, this section is where the
decision and its reasoning live.

## 11. Evaluation Protocol

**SPECIFIED HERE.** The training objective is pointwise regression on `log1p(tflops)`; the runtime decision is *pick the best kernel for this problem*. RMSE on the regression target can improve while top-1 selection gets worse, so RMSE alone does not tell an author whether a model is worth shipping.

### 11.1 Definitions

For problem `p` with measured candidate set `V(p)`:

- `t(p, v)` — measured throughput of variant `v` on `p`
- `v*(p) = argmax_v t(p, v)` — best measured variant (the oracle)
- `v̂(p)` — variant the model ranks first

### 11.2 Metrics

| Metric | Definition | Reported as |
|--------|------------|-------------|
| **Top-1 regret** | `1 − t(p, v̂(p)) / t(p, v*(p))` | mean, p50, p95, max |
| **Regret tail** | fraction of problems with regret > 5% | percentage |
| **Top-k recall** | fraction of problems where `v*(p)` ∈ model's top-k | k = 1, 3, 5 |
| **Per-regime regret** | mean top-1 regret grouped by corpus regime | table |

Regret is measured in throughput, not rank position, because ranks are meaningless between variants whose timings overlap within noise (§8.5): choosing the second-best of two statistically indistinguishable kernels costs nothing and MUST NOT be scored as an error.

Per-regime breakdown is required because aggregate regret hides a model that is excellent on the dense middle of the corpus and useless on decode-shaped or prime-dimension problems — which are frequently the shapes the heuristic exists to get right.

**Weighting.** Every regret metric MUST be reported unweighted over the corpus, and — **when regime
weights are declared** (§5.2) — additionally weighted by them. A blindly generated corpus has no weights,
which is the normal case for a new kernel, and there the unweighted number is the whole report. These answer different questions — how good the heuristic is across the declared space, versus what a user is likely to experience —. Backfill (§5.4) skews the corpus toward hard regions, so the unweighted number drifts pessimistic as rounds accumulate; the weighted number alone would hide a regime the heuristic handles badly.

**Calibration metrics — required when `score.calibrated` is true.**

Regret measures whether the model picks the right kernel *within* an engine. It says nothing about whether the score is right in absolute terms, and RFC 0019 §11.3 makes the absolute value load-bearing: engine selection compares predicted TFLOPS across engines, so "rocKE predicting 310 against MIOpen's 240 selects rocKE." A model with flawless ranking and a systematic absolute bias passes every metric above and then loses every cross-engine arbitration.

| Metric | Definition | Reported as |
|--------|------------|-------------|
| **Relative absolute error** | `\|ŷ(p,v) − t(p,v)\| / t(p,v)` | mean, p95 |
| **Signed bias** | `mean( ŷ(p,v) / t(p,v) − 1 )` | single value, per regime |
| **Selected-candidate calibration** | The two above restricted to `v̂(p)` | mean, p95 |

Signed bias matters more than symmetric error: RFC 0019 §11.3 notes "a miscalibrated absolute score is worse than a correct rank, because it produces confident but wrong cross-engine picks," and it is bias, not spread, that skews an argmax between engines. Selected-candidate calibration is called out separately because that score is what gets published as the engine's figure of merit.

**Timing statistic and calibration.** The `minTimeMs` default of §8.5 is the most noise-robust statistic and suits ranking, but minimum-over-iterations is optimistically biased: a score trained on it predicts a throughput the engine will not sustain, and two engines trained on different statistics are not comparable at all. A UHD declaring `calibrated: true` MUST train its score on `avgTimeMs`. The manifest records the statistic used (§10.5), and cross-engine comparison between models trained on different statistics MUST be refused.

### 11.3 Splits

Three evaluations, all required:

1. **Interpolation** — GroupKFold by problem (§2.6). Performance on unseen shapes drawn from the training distribution.
2. **Shape extrapolation** — leave-one-regime-out: withhold an entire regime, train on the rest, evaluate on the withheld regime; repeat per regime. The honest estimate of behaviour on a shape family nobody thought to benchmark, which is the situation the runtime will meet.
3. **Variant extrapolation** — leave-variants-out: withhold a stratified 20% of the kernel variants across the whole corpus, train on the rest, then evaluate with the withheld variants restored to the candidate set. This measures the cost of subsampling the knob space (§7.2), and is the check that says whether an unmeasured variant can be scored safely or will win the argmax on an inflated prediction.

All three are additionally reported against the **frozen round-0 holdout** (§5.3), which is the only evaluation slice whose distribution does not move as backfill proceeds. Cross-round comparisons — did round 1 help? — MUST use the frozen holdout; comparing against a set that grew between rounds measures the change in the set, not the change in the model.

Extrapolation regret will be substantially worse than interpolation regret in both directions. Those two gaps are the numbers to track: the shape gap estimates the risk of a workload nobody sampled, the variant gap estimates the risk of the catalog containing kernels nobody measured.

### 11.4 Baselines and Interpretation

Every evaluation reports the model against three references:

| Reference | Definition |
|-----------|------------|
| **Oracle** | `v*(p)`; regret 0 by construction. Upper bound. |
| **Static order** | The `priority`/`id` ordering the engine ships with in Stage 1 (§2.1). This is what the model must beat to justify existing. |
| **Random** | Uniform choice from `V(p)`. Sanity floor. |

**These metrics do not gate emission.** RFC 0019's delivery model is two-stage: an engine ships functional with `static_order`, and a heuristic is layered on afterward as data. At runtime every failure path degrades to `static_order`, logs, and never fails the request. A training tool that refuses to emit a model is a different posture, and not the one the parent describes — a mediocre heuristic that loses to static ordering on one regime is still an artifact an author may legitimately ship, iterate on, or hold, and that judgement is theirs.

What this protocol produces is a report and a direction for the next round (§5.4). The obligations are on the tool, not on the model:

1. The tool MUST compute every §11.2 metric against all three references and write them to `eval_report.json`.
2. The tool MUST warn prominently when mean top-1 regret is not better than static order — a model that loses to the ordering it replaces is the one case where shipping is almost certainly wrong.
3. The tool MUST warn when any individual regime is worse than static order for that regime, since aggregate improvement can hide a regression confined to the workloads a heuristic was built for.
4. The tool MUST warn when a previous UHD exists for the same engine and arch and regret has worsened against it.
5. Reported, not judged: per-candidate scoring time against the `native` baseline of RFC 0019 §9, and — when `score.calibrated` is true — relative absolute error and signed bias.

Reference points for reading the report, not thresholds to pass: p95 top-1 regret under 10%, and for a calibrated score, mean relative absolute error under 15% with |signed bias| under 5%. An engine that wants hard thresholds in its own CI can impose them; this RFC supplies the numbers, not the policy.

Item 5's scoring-time comparison needs the `native` adapter, which RFC 0019 schedules as Phase 2 and which is not yet implemented (§13, Gap 9). Until it lands, the number is recorded without a reference.

### 11.5 Objective: Absolute Score, With Ranking as the Documented Fallback

RFC 0019 §11.3 specifies the target: candidates are scored **cardinally, on an absolute metric (calibrated TFLOPS) rather than a within-group rank**, because that is what makes per-engine heuristics compose into a cross-engine comparison without a central ranker. Absolute scoring is acknowledged there as strictly harder than ranking — a per-engine model need only be monotonic to pick correctly among its own candidates — and the RFC accepts that cost deliberately.

Rank-ordering is the **documented fallback**, not the aspiration: if the absolute method underperforms, engine selection degrades to RFC 0007 static/rank ordering while each UHD keeps ranking within its engine without claiming a comparable absolute score. The design does not depend on calibration succeeding.

Accordingly, this RFC keeps pointwise regression on `log1p(tflops)` as the default objective, and reports the §11.2 calibration metrics alongside regret rather than treating them as secondary.

A listwise objective (LightGBM `lambdarank`, groups = problems) optimizes top-1 selection directly and would score better on regret alone, but it forecloses the calibrated cross-engine metric because its scores are only meaningful within a group. Two constraints bound its use:

- RFC 0019 §3.2 requires that a UHD score each kernel on its own metadata and the problem, **never relative to the rest of the catalog** — this is what makes filtering and ranking commute, and a scorer that normalizes across the candidate set is out of scope. A `lambdarank`-trained GBDT still evaluates per candidate at inference, so it satisfies the letter of this; a scorer that inspected the candidate set at scoring time would not.
- Choosing between regressor and ranker is RFC 0019 **Open Question 1**. The regressor is the path taken: `uhd_gen` trains LightGBM regression on `log1p(target)` and inverts with `expm1`, and the UHD header carries `score{units, calibrated, transform}` (RFC 0019 §4.1) so a consumer can
recover TFLOPS. That matches Q1's recommendation and this RFC specifies against it.

What stays open in Q1 is narrower: whether a ranking mode should ever be *offered* alongside, for engines that do not need cross-engine comparability. §11.2's metrics are objective-agnostic, so a regressor and a `lambdarank` model can be compared directly on both regret and calibration whenever that question is taken up. The manifest records which objective produced a given model.

## 12. Per-Operation Reference

Regime structure per operation class — which axes stratify an operation, and what kinds of value sit on them.

**The numbers below are illustrative, not authoritative.** They were assembled from general knowledge of
common model architectures, not from measurement or from any hipDNN source, and they do not bound the
operation: §4.3.2 makes the feasible region a computed ceiling pruned by applicability, so nothing here
constrains what a generator may sample. Read this section for the *shape* of an operation's stratification,
and take concrete values, where they matter, from the usage record §5.2 describes.

Nor are these a second source of truth for corpus size — tiers are budget-driven and global (§5.5).

Every operation belongs to a class, and the class fixes the stratification axis (§4.3.4).

| Class | Operations | Stratification axis |
|-------|-----------|---------------------|
| 1. Dense linear algebra | MatMul, MoE grouped MatMul | `arithmetic_intensity` |
| 2. Spatial convolution | Conv fwd/bwd/wrw, Resample | `arithmetic_intensity` |
| 3. Attention | SDPA fwd/bwd | `arithmetic_intensity` |
| 4. Normalization | LayerNorm, RMSNorm, BatchNorm (± backward) | `working_set` |
| 5. Elementwise | Pointwise (47 modes) | `working_set` |
| 6. Reduction | Reduction (9 modes) | `reduction_ratio` |
| 7. Quantization | BlockScale quantize/dequantize | `working_set` |

### 12.1 Class 1 — MatMul

**Parameters:** `M`, `N`, `K`, `batch`, `transA`, `transB`, `dtype` (fp32, fp16, bf16, fp8, int8).

| Regime | M | N | K | Use case |
|--------|---|---|---|----------|
| Single token | 1 | 512–28672 | 256–8192 | Batch-1 decode |
| Small | 32–512 | 32–512 | 32–512 | Small NLP, batch-1 inference |
| Medium | 512–4096 | 512–4096 | 512–4096 | Training, mid-size models |
| Large | 4096–16384 | 4096–16384 | 4096–16384 | Large LLM training |
| Tall-skinny | 8192–32768 | 128–512 | 4096–8192 | Token generation |
| Short-fat | 128–512 | 8192–32768 | 4096–8192 | Projection layers |
| Deep K | 16–256 | 16–256 | 4096–32768 | Compute-bound |
| Shallow K | 4096–16384 | 4096–16384 | 32–256 | Memory-bound |
| Primes | 17, 31, 37, 127, 251, 509, 1021, 2039, 4093 | — | — | Worst-case tiling |
| LLM shapes | LLaMA MLP (1×4096×11008), DeepSeek V3 configs | | | Real workloads |

Roofline: `$matmul.flops / $matmul.bytes`, thresholded against the device ridge point. The byte term sums each tensor's own dtype size, which for an fp8-in/fp16-out GEMM differs materially from a single-dtype form — one reason the count belongs in the binding layer rather than in per-op metadata (§4.3.3). Compute-bound above the device ridge point (`peak_flops / peak_bandwidth`), not a fixed constant — the threshold is device-dependent and MUST be computed from the queried device properties.

Alignment regimes: aligned (`M % tile_m == 0` for all three dims), partial remainder (one dim), full remainder (all three). Tile values come from variant enumeration (§6.4).

**MoE grouped MatMul** adds `num_experts` (4, 8, 16, 32, 64), `expert_capacity`, and routing skew (uniform vs. imbalanced), with capacity factors 1.0 / 1.25 / 1.5 / 2.0.

### 12.2 Class 2 — Convolution and Resample

**Parameters:** `N`, `C`, `K`, `H`, `W`, `R`, `S`, `pad_*`, `stride_*`, `dilation_*`, `groups`, `dtype`.

| Layer archetype | N | C | H×W | K | R×S | Notes |
|-----------------|---|---|-----|---|-----|-------|
| ResNet50 conv1 | 64–256 | 3 | 224 | 64 | 7×7 | Large spatial, few channels |
| ResNet50 layer3 | 64–256 | 512 | 28 | 512 | 3×3 | Balanced |
| MobileNet depthwise | 64–256 | 32–512 | 56–112 | 1 | 3×3 | `groups = C` |
| U-Net encoder | 4–16 | 64–512 | 128–512 | 128–1024 | 3×3 | Medical imaging |
| Dilated (segmentation) | 4–32 | 256–1024 | 64–128 | 256–1024 | 3×3 | `dilation = 2` |

Roofline: compute-bound for large filters, many channels, large batch; memory-bound for 1×1 convolutions, small batch, large spatial.
Alignment: `H % tile_h`, `W % tile_w`, `C % tile_c`, `K % tile_k`.

**Resample** shares the class: `window` (2×2, 3×3, 4×4, 8×8), `stride` (1, 2), padding per dimension, `resample_mode` (MAX, AVG), `padding_mode` (ZERO, EDGE, REFLECT).

### 12.3 Class 3 — SDPA

**Parameters:** `batch`, `heads`, `seqlen_q`, `seqlen_k`, `head_dim` (64, 128, 256), `is_causal`, `attn_scale`, `dropout_probability`, `dtype` (fp16, bf16, fp8).

| Regime | batch | heads | seqlen_q | seqlen_k | head_dim |
|--------|-------|-------|----------|----------|----------|
| Prefill / training | 1–64 | 32–96 | 512–8192 | = seqlen_q | 64–128 |
| Decode | 1–256 | 32–96 | 1 | 512–32768 | 64–128 |
| Short context | 4–128 | 8–32 | 128–512 | 128–512 | 64–128 |
| Long context | 1–16 | 32–96 | 8192–32768 | = seqlen_q | 64–128 |
| Edge cases | 1 | 1 | — | — | 256 |

Model configs to include: LLaMA-2 7B/13B/70B (32/32/40 heads, head_dim 128), GPT-3 175B (96 heads), BERT-base (16 heads, head_dim 64), DeepSeek V3 (128 query heads, 8 KV heads — exercises GQA ratio).

Key relationships: training and prefill have `seqlen_q ≈ seqlen_k`; decode has `seqlen_q = 1, seqlen_k >> 1` (KV cache) and is always causal.
Alignment: `seqlen_q % tile_m`, `seqlen_k % tile_n`, `head_dim % tile_k`.

### 12.4 Class 4 — Normalization

**LayerNorm / RMSNorm parameters:** `batch`, `seq_len`, `hidden_dim`, `epsilon`, `dtype`, `forward_phase`.

| Model | batch | seq_len | hidden_dim |
|-------|-------|---------|------------|
| BERT-base | 1–512 | 128–512 | 768 |
| BERT-large | 1–512 | 128–512 | 1024 |
| LLaMA-2 7B | 1–128 | 512–4096 | 4096 |
| LLaMA-2 70B | 1–64 | 512–8192 | 8192 |
| GPT-3 175B | 1–2048 | 1024–2048 | 12288 |
| ViT-Base / Large / Huge | 1–256 | 196–256 | 768 / 1024 / 1280 |

**BatchNorm parameters:** `N`, `C`, `H`, `W`, `epsilon`, `momentum`, `dtype` — CNN-shaped rather than transformer-shaped: N 1–256, C 32–1024, H×W 14–224.

Stratification is by `working_set` — the per-row normalized footprint bucketed against L1/L2/LLC capacity. Arithmetic intensity is constant for this class (§4.3.4) and MUST NOT be used.

Alignment: `hidden_dim` (or `C`) against the reduction tile width; row lengths that are not a multiple of the wavefront size are the interesting cases.

### 12.5 Class 5 — Elementwise

**Parameters:** `operation` (47 `PointwiseMode` values), input shape(s), broadcast pattern, `dtype`, plus mode-specific scalars (`swish_beta`, `elu_alpha`, `softplus_beta`, `relu_*_clip`).

Stratification by total element count against cache hierarchy: 1K–10K (L1), 100K–1M (L2), 10M–100M (HBM streaming), 1B+ (multi-pass). Additional axes: broadcast pattern (none, scalar, 1D, channel, spatial), tensor rank (1D–5D), aspect ratio (square vs. tall-skinny, which changes access coalescing).

The 47 modes do not each need full coverage. Group them by cost profile — cheap unary (`ABS`, `NEG`, `IDENTITY`), transcendental (`EXP`, `LOG`, `TANH`, `ERF`, `GELU_*`), binary (`ADD`, `MUL`, `SUB`, `DIV`), comparison/select — and sample shapes densely per *group*, with a thin sweep across modes within a group. Arithmetic intensity here is below 1 FLOP/byte for every mode, which is why mode identity matters far less than footprint.

### 12.6 Class 6 — Reduction

**Parameters:** `mode` (ADD, MUL, MIN, MAX, AMAX, AVG, NORM1, NORM2, MUL_NO_ZEROS), input shape, reduction axes, `dtype`, `is_deterministic`.

Stratification by `reduction_ratio = input_elements / output_elements`:

| Pattern | Ratio | Example |
|---------|-------|---------|
| Full reduction | 10⁶–10⁹ | `(N,C,H,W) → scalar` |
| Batch reduction | 10–10³ | `(N,C,H,W) → (C,H,W)` |
| Channel reduction | 10–10³ | `(N,C,H,W) → (N,H,W)` |
| Spatial reduction | 10²–10⁴ | `(N,C,H,W) → (N,C)` |
| Near-identity | 1–10 | Reducing a length-2 axis |

`is_deterministic` materially changes the algorithm (tree vs. atomic accumulation) and MUST be sampled on both settings.

### 12.7 Class 7 — Quantization

**Parameters:** `block_size` (16, 32, 64, 128, 256), input dtype → output dtype pair, `scale_dtype` (float32, float16), tensor shape.

Stratification by `working_set` with a dedicated alignment axis: whether the tensor's fastest-varying dimension is a multiple of `block_size`. Ragged final blocks are the interesting case and are trivially missed by power-of-two-only sampling.

## 13. Open Gaps

| # | Gap | Impact | Where |
|---|-----|--------|-------|
| 1 | Corpus generation, variant enumeration, and benchmarking tooling do not exist | Every engine author reinvents them; the methodology here is unenforced | §5, §6, §8 |
| 2 | RFC 0019 Open Question 12 is unresolved — no way to enumerate the valid knob-tuple set | The generator can only address a Cartesian product of knob axes, most of which names no kernel on a sparse catalog. Blocks Phase 5 for those engines | §6.1, §6.2 |
| 3 | Binding layer does not publish `$op.flops` / `$op.bytes` | Cost-model features must be precomputed host-side | §9.2 |
| 4 | `add_engine_sweep()` caps the product at 10,000 combinations | The consequence of Gap 2 rather than a separate limit: it bounds the damage of an unenumerable space by rejecting the sweep. Sets a floor on how coarsely the knob space can be covered | §6.1, §6.2, §7.3 |
| 5 | No empirical guidance on per-arch vs. pooled multi-arch models | §3.4 strategy choice is unvalidated | §3.4 |
| 6 | Operation metadata files do not exist for any of the 22 ops with graph builders | Nothing to feed the generator | §4 |
| 7 | Tile-quantization dim↔tile correspondence must be authored by hand | Blocks fully mechanical feature derivation | §9.1 |
| 8 | No feature-importance or tree-inspection tooling | Model behaviour is opaque when regret is bad | §9.3 |
| 9 | The `native` adapter exists but its benchmark does not | The `tree_data` 2× overhead target has no measured reference | §10.3, §11.4 |
| 10 | A trained UHD's kernel ranking cannot currently be delivered | `UhdBuiltIn` computes the ranking and discards it — "the heuristic plugin ABI carries engine IDs only", `TODO(RFC-0017)`. Everything this RFC specifies produces an artifact that cannot yet affect selection | RFC 0017 plugin ABI |
| 11 | Two disconnected implementations of the descriptor family | The ingestor implements `HeuristicKind::NATIVE` over JSON descriptors; the backend implements the model adapters over FlatBuffers. Neither can consume the other's artifacts | §13 note below |
| 12 | The engine estimate is specified but has no consumer yet | §10.6 defines its training; the quick engine-selection policy that would read it is RFC 0007's, and RFC 0019 §11.3 defers the plugin-query surface that carries it | §10.6 |
| 13 | No usage-shape record exists for non-convolution operations | Convolution has curated collections in the MIOpen performance database, keyed by model, dataset and client. GEMM, SDPA and the rest have no equivalent, so §5.2 weighting is unavailable and their corpora stay blind | §5.2, §12 |

**On Gaps 10 and 11.** These are the two that bound what this RFC can deliver, and neither is a training problem.

Gap 10 is the sharper one. `UhdBuiltIn` runs the full selection path — extract features, score every candidate, sort, tie-break — and then drops the result, because the heuristic plugin ABI returns engine ids and has no field for a per-engine kernel ranking. The code says so directly and carries a `TODO(RFC-0017)`. Until that ABI grows a return path, a trained UHD changes nothing at runtime, which means the corpus, the benchmark, the model and the evaluation in this document all terminate in an artifact that cannot yet be acted on. Training work is still worth doing ahead of the ABI, but no measured end-to-end improvement can be claimed until it lands.

Gap 11 is the structural one. Two trees implement RFC 0019 with inverted coverage: the kernel ingestor has `HeuristicDescriptor`, `HeuristicKind::NATIVE` and `NativeKernelHeuristic`, loading `.uhd.json` through `DescriptorLoader`, with `MODEL` explicitly unimplemented; the backend has the `tree_data`, `table`, `onnx` and `custom_library` adapters, the `features_signature` extractor, `features_hash`, score transforms and arch-keyed resolution, loading a binary `.uhd.fb` through `UhdLoader` — which is a third divergence, since RFC 0019 §4 defines
the UHD as a JSON document tagged `hipdnn.uhd/v1` and reserves the FlatBuffer for the `tree_data`
artifact. The descriptors are not interconvertible — the ingestor's is four fields and an opaque payload, which cannot express a feature contract, an objective, score units, or a model artifact — and the ingestor is compiled only under an off-by-default flag. This RFC is written against the backend path, because that is the one carrying the feature contract it depends on. Deciding whether the two converge, and in which direction, is RFC 0017's to make; it is recorded here because a corpus and a model are only useful to whichever path survives.

**On Gap 9.** RFC 0019 §15 orders `native` before `tree_data`, but implementation landed Phases 3, 4 and 6 and skipped Phase 2. The consequence is narrow but real: RFC 0019 §9 defines the `tree_data` performance target as "within 2× of the `native` baseline," and with no `native` adapter there is nothing to divide by. Scoring time can still be measured in absolute terms and is (§11.4 item 5); what is missing is the reference that makes it a pass or a fail.

The adapter itself now exists: a `NATIVE` value in the `UhdAdapter` enum, `native_symbol` in `uhd.fbs`, a `NativeAdapter` resolving a compiled scorer in-process, and loader dispatch. What is still absent is the benchmark that turns it into a baseline — the four separately wall-clocked numbers RFC 0019 §9.4 asks for (descriptor load and model parse, feature extraction split prefix versus per-candidate tail, and scoring), measured for `native` and `tree_data` over one fixture and tracked over time.

The kernel ingestor carries a parallel mechanism — `NativeRegistry.hpp`'s `ScoreRegistry` over `ScoreFn = double (*)(const MatchContext&, const BoundTokens&, const KernelDefinition&)`, consumed by `NativeKernelHeuristic` under `HeuristicKind::NATIVE`. The UHD path does not reuse it, for two reasons that are worth stating rather than rediscovering: the ingestor is compiled only under `HIPDNN_ENABLE_KERNEL_INGESTOR`, which defaults off, so a shared registry would make the baseline unavailable in exactly the builds that need to measure it; and the two scorer signatures are not convertible, since an ingestor scorer receives the match context and featurizes itself while a UHD scorer receives the extracted feature row. §13's note on the two descriptor paths covers the broader question.

**On Gap 4.** The cap bounds how many variants autotune enrolls in one sweep. An engine whose knob space exceeds it enrolls in batches or measures a subsample; neither the problem space nor the variant space is ever measured exhaustively (§7.2).

What the cap constrains is how *evenly* a dense knob space can be covered within a given budget, which is what the optimizer's curse makes expensive. The variant budget therefore goes to uniform coverage of the knob space rather than to dense enumeration of one corner of it, and the leave-variants-out regret of §11.3 reports what the subsample cost. The runtime candidate set stays whole: narrowing it to the measured subset would discard working kernels to protect an assumption that §11.3 already tests.

## 14. Implementation Roadmap

**This document is RFC 0019's Phase 5.** RFC 0019 §15 schedules the generation tool as Phase 5 — a standalone tool wrapping hipDNN that drives autotune over a shape corpus and the knob space, logs results, trains, and emits an updated UED/UHD plus model. It depends on Phases 3 and 4 (the `tree_data` adapter, and the `features_signature` generic extractor with its training↔runtime parity test), and RFC 0019 records it as **gated on Open Question 12**, the catalog-enumeration API gap, for engines with large sparse knob spaces. Phases 9 (AOT selection) and 10 (knob reduction) depend on it in turn.

The phases below subdivide that Phase 5. They are not a parallel numbering of RFC 0019's.

**Phase 1 — make one operation work end to end.**

1. `validate-metadata` plus the metadata file for `matmul` (§4).
2. `generate-corpus` round 0 — `stratified_cross_product`, seeded, with the frozen holdout (§5.3).
3. Graph construction from `graph_builder` (§4.3.6).
4. `benchmark` against the backend applicability API, recording skipped pairs (§7, §8).
5. Evaluation protocol against the frozen holdout with a static-order baseline, reported (§11).

Phase 1 is open-loop: round 0 plus evaluation. It is the smallest increment that yields a shippable UHD, and it produces the first measurements of boundary density and regret — the inputs Phase 2's targeting consumes.

**Phase 2 — close the loop.**

6. Boundary-density, regret-concentration and dispersion signals over round-0 results (§5.4).
7. Backfill rounds with the exploration floor and per-region caps (§5.1, §5.4).
8. Stopping criterion on the frozen-holdout regret curve, distinguishing convergence from budget exhaustion (§5.5).
9. Budget calibration (`t_setup` / `t_kernel` measurement and projection) (§5.5).

**Phase 3 — generalize across operations.**

10. Metadata files for the remaining Tier-1 ops (`sdpa_fwd`, `conv_fwd`), then normalization and elementwise.
11. Regime weights and traffic-weighted regret reporting (§5.2, §11.2).
12. Coverage reporting and axis-occupancy warnings (§5.9).
13. Subcommand CLI migration with deprecation shim (§10.1).
14. The engine estimate as a second projection of the same corpus (§10.6) — no new benchmarking, so it lands whenever a second descriptor engine makes it useful.

**Phase 4 — close the schema and tooling gaps.**

15. Whatever RFC 0019 Open Question 12 settles on for enumerating the valid knob-tuple set; §6.3 is this RFC's proposal into that decision, not a commitment to build it (Gap 2).
16. Leave-variants-out evaluation and variant-space coverage metrics (§11.3, Gap 4).
17. `$op.flops` / `$op.bytes` in the binding layer (Gap 3).
18. `lambdarank` objective evaluation (§11.5).
19. Feature-importance and tree-inspection tooling (Gap 8).

### 15.1 The `table` Adapter Names Two Mechanisms

RFC 0019 attaches two unrelated mechanisms to a single adapter value, and the resulting ambiguity is why
`table` has no body schema anywhere in the document.

**Mechanism one — a lookup.** §4.2 describes "a CSV/lookup keyed by coarse problem buckets" shipping "with
engine"; §7 lists it as a standalone drop-in with no runtime dependency; §15 schedules it as Phase 6,
"cheap bucketed heuristics for ops that don't warrant a model." This is a downscale of `tree_data`: an
artifact of pre-computed answers, hand-authorable and human-readable where a tree table is neither.

**Mechanism two — a rule.** §13.6 describes something with no artifact at all:

> Tiers 1–2 alone (no benchmarking) already support a real model-free heuristic better than
> `static_order`: prefer the kernel whose tile best divides the problem (minimize quantization waste),
> tie-break on an occupancy proxy. That is a legitimate `table`/rule UHD computable from the KMD, the
> engine's bound symbols, and device facts, and it is the zero-benchmark starting point before the
> autotune-trained `tree_data` model replaces it.

That is a scoring expression, not a lookup. It ships nothing, needs no benchmarking, and is computable
from data the engine already publishes.

**Three symptoms of the conflation.**

*§4.2's row disagrees with itself.* It reads "keyed by coarse problem buckets" and "table lookup, then
tie-break" in adjacent columns. A problem-keyed lookup returns one value per problem, which cannot rank
candidates against each other — yet §5's flow scores each candidate and takes an argmax. The two halves
are describing the two mechanisms: bucket-keyed lookup is the first, score-then-tie-break-on-occupancy is
the second.

*The artifact question has two answers.* §4.2 and §7 both say the adapter ships an artifact with the
engine. §13.6 says its content is "computable from the KMD, the engine's bound symbols, and device facts."
Both are correct about their own mechanism.

*No body schema exists because one body cannot serve both.* A lookup body needs an artifact path, bin
edges, a key subset — a `features_signature` sized for a GBDT is far too wide to key a coarse table — and
a CSV column layout, plus a rule for a key that misses every bucket. A rule body needs none of those; it
needs a scoring expression, which the `features_signature` machinery already provides.

**Recommendation: split them, and specify the rule first.**

The rule is the more valuable of the two and is the one with no home. The adapter ladder runs
`static_order` (computes nothing), `native` (compiled into the engine), and `tree_data` / `onnx` /
`custom_library` (all requiring a trained model). There is no rung for *computed, data-driven, but not
trained*. The rule cannot borrow `native`'s, because that means recompiling the engine and forfeits the
drop-in delivery §7.1 gives as the reason `native` is a bootstrap rather than a destination.

Its payoff is also immediate in a way the lookup's is not. Producing any trained adapter costs the corpus
this document specifies, measured in GPU-hours to GPU-days, behind tooling that does not yet exist. A rule
gives an engine a real heuristic on day zero. The lookup, by contrast, mostly buys hand-authorability over
a small `tree_data` model that the same pipeline would produce anyway.

**Consequence if the split lands.** §11.4 evaluates a trained model against `static_order`, on the
grounds that it is what the engine ships in Stage 1. A rule adapter would displace `static_order` in that
role, and the baseline would have to move with it — a model that beats `priority`/`id` but loses to the
rule the engine would otherwise have shipped has not earned its place. No change is warranted before the
split is decided; the point is recorded here so the baseline is revisited at the same time.
