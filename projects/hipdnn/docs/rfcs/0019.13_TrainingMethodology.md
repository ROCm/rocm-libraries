# RFC 0019.13: UHD Training Methodology

- **Parent:** [RFC 0019 Universal Heuristic Descriptor](0019_UniversalHeuristicDescriptor.md) §13 Model Generation Pipeline
- **Status:** Draft — formalizes the methodology for training UHDs across arbitrary operations
- **Contributors:** Chris Erb, Jason Campbell
- **Tooling:** `projects/hipdnn/tools/uhd_gen/`

---

## Abstract

RFC 0019 §13 specifies the high-level training workflow (two-stage delivery, autotune substrate, feature contract enforcement) but leaves **per-operation parameter space exploration**, **corpus generation**, and **model evaluation** unspecified. This companion RFC fills those gaps so that a UHD can be trained for an arbitrary operation without per-operation tooling changes.

It specifies:

1. **An operation metadata schema** — a machine-readable description of an operation's parameter space, cost formulas, stratification axes, and graph construction, sufficient to drive corpus generation mechanically (§4).
2. **Staged corpus generation** — broad exploration first, then evidence-driven backfill, under a budget denominated in benchmark cost rather than shape count (§5).
3. **Kernel variant enumeration and applicability filtering** — including the train/serve candidate-set invariant that makes the trained model valid at runtime (§6, §7).
4. **An evaluation protocol** — ranking metrics tied to the decision the UHD actually makes, with baselines and acceptance gates (§11).

**Key architectural principle:** corpus generation synthesizes **operation-aware sampling** (the operation's full potential parameter space) with **provider applicability filtering** (what the engine's kernels can handle). The provider supplies predicates, not an exhaustive problem list.

This RFC is **descriptive** (documents what CK/rocKE do and what `uhd_gen` implements) and **prescriptive** (defines the missing pieces).

## 2. What RFC 0019 Already Specifies

### 2.1 Two-Stage Workflow (RFC §13.1)

**IMPLEMENTED.** Ship a working pack first, add the heuristic later.

1. **Stage 1** — ship a functional pack with `static_order` (or no UHD). The catalog returns in deterministic `priority`/`id` order. No benchmarking required.
2. **Stage 2** — generate a data-driven heuristic from on-hardware timings. Update the UED/UHD in place.

### 2.2 Benchmarking Substrate (RFC §13.2)

**IMPLEMENTED.** Uses hipDNN autotune (RFC 0013) to time kernels.

```python
configs = handle.get_engine_configs(graph)
handle.add_engine_variants(engine_id, [(knob1, knob2, ...), ...])
handle.add_engine_sweep(engine_id, knob_ranges, fixed_settings)
results = handle.autotune(mode=EXHAUSTIVE, strategy=RUN_UNTIL_STABLE)
# → [{engineId, knobSettings, minTimeMs, avgTimeMs, stddevMs, ...}]
```

**Key constraint:** autotune addresses kernels via **exposed knobs only**. A kernel the tool cannot name cannot be timed.

**Requirement:** generation runs against a **fully-exposed UED** (every KMD field exposed as a knob) so every catalog entry is individually addressable. The emitted UED then exposes only the features the model kept.

### 2.3 Feature Extraction (RFC §6)

**IMPLEMENTED.** Features are drawn from three sources, all available at plan time:

| Source | Namespace | Examples | Bindable at training time |
|--------|-----------|----------|---------------------------|
| Device properties | `$device.*` | `cu_count`, `lds_size`, `vgpr_count` | Yes — known per GPU |
| Kernel metadata (KMD) | `$kernel.*` | `tile_m`, `split_k`, `warp_n` | Yes — from UKD metadata |
| Query/problem shape | `$q.*` | `dims[0]`, `dims[2]`, `dtype` | Yes — sweep parameter |

**Computed features** (RFC §6.4) are expression trees of the form `{"op": [args]}` with bare `$`-prefixed variable references:

```json
{"ceil_div": ["$q.dims[2]", "$kernel.tile_m"]}
{"/": ["$sdpa_fwd.flops", "$sdpa_fwd.bytes"]}
```

RFC 0019 §6.4 is explicit that references are `$`-prefixed strings **and not** JsonLogic's `{"var": …}` form. This RFC uses the same syntax throughout (§4.3).

### 2.4 Feature Contract Enforcement (RFC §6.3)

**IMPLEMENTED.** `features_hash` pins the feature signature. Training emits `features_signature` + `categorical_encoding` → `sha256:…`. The runtime extractor validates the hash before scoring; a mismatch means refuse to load (fail closed) or degrade to static ordering (fail open).

### 2.5 Training Target and Transform (RFC §11.3)

**IMPLEMENTED** in `uhd_gen/train_uhd.py`:

```python
y = np.log1p(df[target_col].values)   # scale-invariant regression target
```

**Objective:** `max` (higher score = better kernel) or `min` (lower = better, e.g. latency).

```json
"score": { "units": "tflops", "calibrated": false, "transform": "log1p" }
```

Runtime inverts the transform: `score = expm1(model.predict(features))`.

Note that this is a **pointwise regression** target while the runtime decision is a **ranking** decision. §11 defines the evaluation metrics that make that gap measurable, and §11.5 discusses replacing the objective outright.

### 2.6 Cross-Validation (RFC §13.2, implicit)

**IMPLEMENTED.** GroupKFold prevents problem leakage — the same problem shape never appears in both train and validation folds.

```python
groups = df.groupby(group_cols).ngroup().values   # e.g. (q.M, q.N, q.K)
folds  = GroupKFold(n_splits=5).split(X, y, groups)
```

Grouping MUST be by problem, so that all kernel variants measured for one problem stay in the same fold. §11.3 adds a second, stricter split.

## 3. The Three Spaces

### 3.1 Decomposition

For every operation the feature space decomposes into three sources (RFC §6.1):

```
                  Device ($device.*)          Problem ($q.*)                Kernel ($kernel.*)
                  ──────────────────          ──────────────                ──────────────────
Declared by:      GPU hardware                Operation metadata (§4)       KMD schema (§6)
Explored by:      NOT explored                Corpus generator (§5)         Variant enumerator (§6)
                  (one fixed point
                   per training run)
Filtered by:      —                           is_applicable (§7)            is_valid_config (§7)
Obtained from:    HIP runtime query           Generated corpus JSON         KMD + catalog
```

The **device space** is a single fixed point per training run. The **kernel space** is enumerable from the compiled catalog. The **problem space** is unbounded and is where operation-specific methodology is required.

### 3.2 Division of Responsibility: Tooling Generates, Provider Filters

**Tooling responsibility.** Generate a representative problem corpus spanning the **operation's full potential parameter space**. Tooling holds the operation-level knowledge — that SDPA has prefill and decode regimes, that GEMM has batch-1 inference and tall-skinny projection shapes.

**Provider responsibility.** Supply **predicates** that answer "can this engine handle this problem?" and "is this variant valid?".

**Explicitly NOT the provider's responsibility.** Enumerating an exhaustive list of supported problems.

Why this split:

1. Providers know their kernel's constraints, not every use case hipDNN must cover.
2. A predicate is cheaper to author and maintain than an exhaustive list, and cannot silently go stale.
3. Synthesis is automatic — tooling generates broad coverage, predicates prune what the engine cannot run, training sees exactly the feasible set.

### 3.3 Device Space Handling

Device properties are queried once per training run via `hipGetDeviceProperties()` / `hipDeviceGetAttribute()`, or loaded from a JSON config when running without hardware.

**Normative rule — device columns are recorded but are not features in single-arch runs.**

- Every benchmark CSV MUST carry the `device.*` columns (§8.2). They are provenance: they identify what hardware produced the timings.
- For a **single-arch training run**, `device.*` columns are constant across all rows. A zero-variance column can never be split on by a tree model; including it in `--features` adds nothing to accuracy while enlarging `features_signature` and changing `features_hash`. Single-arch runs therefore MUST NOT pass `device.*` columns as features.
- For a **pooled multi-arch training run** (§3.4), `device.*` columns vary and SHOULD be features.

`uhd_gen` SHOULD reject a `--features` list containing a column with zero variance, naming the column, rather than training a model with a dead feature.

### 3.4 Multi-Architecture Coverage

**PARTIALLY SPECIFIED** (RFC §8.3): arch-keyed UHD selection.

```json
{ "gfx942": "sdpa_fwd_gfx942.uhd.fb",
  "gfx950": "sdpa_fwd_gfx950.uhd.fb",
  "default": "sdpa_fwd_default.uhd.fb" }
```

**Two strategies, and when to use each:**

| Strategy | Training data | `device.*` as features | Use when |
|----------|---------------|------------------------|----------|
| **Per-arch models** | One run per arch | No (§3.3) | Default. Arch behaviour differs qualitatively; each model stays small. |
| **Pooled arch-aware model** | Runs from ≥3 archs concatenated | Yes | Covering SKU variation within a family (CU-count differences on the same `gfx`) where behaviour differs quantitatively, not qualitatively. |

`$device.arch` itself MUST NOT be a feature — it is a KDP property used for UHD resolution, not a runtime feature (RFC §6.1). SKU variation is expressed through numeric properties (`cu_count`, `lds_size`, `peak_bandwidth_gbps`) which the model can actually interpolate over.

**GAP:** no empirical guidance yet on how many archs a pooled model needs before it beats per-arch models. Resolve by measuring with the §11 protocol.

## 4. Operation Metadata Schema

**SPECIFIED HERE.** This is the canonical, machine-readable description of an operation. It is the single input that makes corpus generation mechanical rather than per-operation code.

### 4.1 File Location and Identity

```
projects/hipdnn/tools/uhd_gen/metadata/<operation>.json
```

`<operation>` MUST match the FlatBuffers `NodeAttributes` union member for the op, lowercased with an explicit direction suffix where the schema distinguishes one — e.g. `matmul`, `layernorm_fwd`, `layernorm_bwd`, `sdpa_fwd`, `conv_fwd`.

### 4.2 Schema

```json
{
  "schema_version": "1.0",
  "operation": "layernorm_fwd",
  "display_name": "LayerNorm Forward",
  "description": "Layer normalization over the trailing normalized dimensions.",

  "parameters": {
    "batch":       { "type": "int64", "range": [1, 4096],
                     "common_values": [1, 4, 8, 16, 32, 64, 128, 512] },
    "seq_len":     { "type": "int64", "range": [1, 32768],
                     "common_values": [128, 512, 1024, 2048, 4096, 8192, 16384] },
    "hidden_dim":  { "type": "int64", "range": [128, 16384],
                     "common_values": [768, 1024, 1536, 4096, 5120, 6656, 8192, 12288] },
    "dtype":       { "type": "enum", "values": ["float32", "float16", "bfloat16"] },
    "forward_phase": { "type": "enum", "values": ["INFERENCE", "TRAINING"] }
  },

  "cost_model": {
    "flops": {"*": [8, "$q.batch", "$q.seq_len", "$q.hidden_dim"]},
    "bytes": {"+": [
      {"*": [2, "$q.batch", "$q.seq_len", "$q.hidden_dim", {"sizeof": ["$q.dtype"]}]},
      {"*": [2, "$q.hidden_dim", {"sizeof": ["$q.dtype"]}]}
    ]},
    "working_set_bytes": {"*": [2, "$q.hidden_dim", {"sizeof": ["$q.dtype"]}]}
  },

  "stratification_axis": "working_set",

  "regimes": {
    "hidden_dim":  { "parameter": "hidden_dim",
                     "buckets": [768, 1024, 1536, 4096, 5120, 6656, 8192, 12288] },
    "batch":       { "parameter": "batch",  "buckets": [1, 4, 16, 32, 64, 128, 512] },
    "seq_len":     { "parameter": "seq_len","buckets": [128, 512, 2048, 8192, 16384] },
    "alignment":   { "parameter": "hidden_dim", "derived": "alignment",
                     "buckets": ["aligned", "partial_remainder", "full_remainder"] }
  },

  "graph_builder": {
    "function": "createValidLayernormFpropGraph",
    "source": "hipdnn_test_sdk/utilities/FlatbufferGraphTestUtils.hpp",
    "arguments": [
      { "name": "dims",    "kind": "expr",
        "value": ["$q.batch", "$q.seq_len", "$q.hidden_dim"] },
      { "name": "strides", "kind": "strides_of", "of": "dims" },
      { "name": "inputDataType",   "kind": "dtype_of", "source": "$q.dtype" },
      { "name": "computeDataType", "kind": "dtype_of", "source": "$q.dtype" }
    ]
  }
}
```

### 4.3 Field Definitions

#### 4.3.1 Top level

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `schema_version` | string | Yes | Metadata schema version (current `"1.0"`) |
| `operation` | string | Yes | Operation identifier (§4.1) |
| `display_name` | string | No | Human-readable name |
| `description` | string | No | Operation semantics |
| `parameters` | object | Yes | Parameter space (§4.3.2) |
| `cost_model` | object | Yes | `flops`, `bytes`, and optionally `working_set_bytes` (§4.3.3) |
| `stratification_axis` | string | Yes | `arithmetic_intensity` \| `working_set` \| `reduction_ratio` (§4.3.4) |
| `regimes` | object | Yes | Stratification buckets (§4.3.5) |
| `graph_builder` | object | Yes | Graph construction mapping (§4.3.6) |

There is no `tier_sampling` field. Tiers are budget-derived and global (§5.5); an operation does not get to declare its own corpus size.

#### 4.3.2 Parameters

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `type` | string | Yes | `int64` \| `float64` \| `enum` \| `bool` |
| `range` | `[min, max]` | For numeric | Inclusive bounds |
| `values` | array | For enum | Permitted values |
| `common_values` | array | No | Representative values preferred by stratified sampling |
| `description` | string | No | — |

`range` is REQUIRED for `int64`/`float64`; `values` is REQUIRED for `enum`; `bool` has implicit `[true, false]`.

Ranges MUST cover the workloads the operation's reference table (§12) cites. A range that excludes a model listed as a target is a metadata bug.

#### 4.3.3 Cost Model — Expression Syntax

Expressions use RFC 0019 §6.4 syntax: `{"op": [args]}` trees with bare `$`-prefixed variable references. **Not** JsonLogic `{"var": …}` — RFC 0019 §6.4 rejects that form explicitly, and using it here would produce expressions that cannot be moved into a `features_signature`.

Operators: `+ - * / %`, `min`, `max`, `pow`, `log2`, `ceil_div`, comparison operators, `if`, plus two extensions defined by this RFC:

| Extension | Form | Result |
|-----------|------|--------|
| `sizeof` | `{"sizeof": ["$q.dtype"]}` | Byte width of the named dtype |
| array literal | `["$q.batch", "$q.seq_len"]` | Elementwise-evaluated list (for dims) |

`sizeof` resolves against a fixed table: `float32`/`int32` → 4, `float16`/`bfloat16` → 2, `float8_*`/`int8` → 1. An unknown dtype MUST raise, not default.

`cost_model.flops` and `cost_model.bytes` feed roofline classification and the `tflops` target (§8.3). `working_set_bytes` is the per-normalization-group (or per-tile) footprint used by the `working_set` stratification axis.

FLOP counts for bandwidth-bound ops are estimates; their only use is relative ordering and reporting. Do not read precision into the constant `8` above.

#### 4.3.4 Stratification Axis

Arithmetic intensity is **not** a universal stratification axis. For a bandwidth-bound elementwise or normalization op, AI is shape-invariant: for LayerNorm, `flops/bytes = 8·B·S·H / (2·B·S·H·sizeof) = 4/sizeof` — a constant. Stratifying such an op by AI produces exactly one bucket and no coverage.

Each operation therefore declares which axis is informative:

| Axis | Definition | Use for |
|------|------------|---------|
| `arithmetic_intensity` | `flops / bytes`, thresholded against `peak_flops / peak_bandwidth` | Ops that can be compute-bound: GEMM, Conv, SDPA, MoE |
| `working_set` | `working_set_bytes` bucketed against L1 / L2 / LLC / HBM capacity | Bandwidth-bound ops: Norm, Pointwise, Quantize |
| `reduction_ratio` | `input_elements / output_elements` | Reductions, where cost is driven by fan-in, not footprint |

The corpus generator MUST report bucket occupancy for the declared axis (§5.8), so a corpus that collapsed into one bucket is visible rather than silent.

#### 4.3.5 Regimes

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `parameter` | string | Yes | Parameter this regime stratifies |
| `buckets` | array | Yes | Discrete values, or labels when `derived` is set |
| `derived` | string | No | `alignment` — buckets are `aligned`/`partial_remainder`/`full_remainder` relative to the kernel tile sizes discovered in §6 |
| `description` | string | No | — |

Regimes are the axes of the stratified cross-product in §5.3. All declared regimes participate; there is no "primary" regime.

#### 4.3.6 Graph Builder Mapping

Corpus entries are parameter dictionaries; benchmarking needs a serialized FlatBuffers graph. `graph_builder` closes that gap declaratively.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `function` | string | Yes | Builder function name |
| `source` | string | Yes | Header providing it |
| `arguments` | array | Yes | Ordered argument mapping |

Each argument has a `kind`:

| `kind` | Fields | Behaviour |
|--------|--------|-----------|
| `direct` | `source` | Copy the named `$q.*` value |
| `expr` | `value` | Evaluate a §4.3.3 expression (arrays yield dims lists) |
| `strides_of` | `of` | Row-major contiguous strides for a previously-named argument |
| `dtype_of` | `source` | Map a dtype string to the FlatBuffers `DataType` enumerator |
| `constant` | `value` | Literal |

Arguments are resolved in declaration order, so `strides_of` may reference an argument declared earlier.

Every argument named in `arguments` MUST reference only parameters declared in `parameters`. A validator MUST reject metadata that references an undeclared parameter — this is the check that catches a `graph_builder` written against a different parameterization than the op declares.

Builders live in `hipdnn_test_sdk/utilities/FlatbufferGraphTestUtils.hpp`; all 22 ops with FlatBuffers schemas have one. Dispatch is by `graph_builder.function`, so adding an operation requires no change to the generator.

### 4.4 Metadata Validation

`uhd_gen validate-metadata` MUST check:

1. Conformance to the §4.3 field tables.
2. Every `$q.*` reference in `cost_model` and `graph_builder` resolves to a declared parameter.
3. Every `regimes[*].parameter` is a declared parameter, and non-derived buckets fall inside that parameter's `range`.
4. `stratification_axis` is one of the three permitted values, and `working_set` implies `cost_model.working_set_bytes` is present.
5. `graph_builder.function` resolves in the declared source header.
6. Expressions parse and evaluate to a positive number on the parameter midpoint.

## 5. Problem Corpus Generation

### 5.1 Sampling Is an Exploration Problem

What makes a corpus effective is coverage of the regions where **which kernel wins changes** — the decision boundaries. Elsewhere the ranking is stable and extra samples buy little.

Those boundaries cannot be targeted up front. Knowing where they lie means already knowing the answer the model is being trained to produce. Boundary location is an *output* of benchmarking, not an input to it, so any single-pass generator is choosing every sample while blind to the thing that determines whether the sample was worth taking.

Corpus generation is therefore staged:

| Round | Informed by | Purpose |
|-------|-------------|---------|
| **0 — exploration** | Nothing. Declared regimes only. | Broad, unbiased coverage of the whole declared space |
| **1..N — backfill** | Measurements and model assessment from prior rounds | Densify where the evidence says coverage is insufficient |

Default `N = 2`. Each round produces a corpus increment that is benchmarked and folded into the training set; the model is retrained between rounds.

**Exploration floor.** Backfill guided solely by where the current model reports weakness entrenches blind spots: a region the model is confidently and uniformly wrong about looks healthy and is never revisited. Every backfill round MUST therefore allocate at least **20%** of its samples by unbiased stratified draw, independent of any assessment signal. This is the explore half of explore/exploit and it is not optional.

**Round 0 is the majority of the budget.** Backfill targeting is only as good as the regret estimates driving it, and those estimates need enough samples per region to be signal rather than noise. Under-sizing round 0 to leave room for backfill produces confident targeting of the wrong regions.

### 5.2 Target Distribution

"Representative" is undefined without saying representative *of what*. Uniform stratification weights a prime-dimension corner case identically with a LLaMA MLP shape, which is rarely the intent.

Operation metadata MAY declare per-regime weights:

```json
"regimes": {
  "llm_shapes": { "parameter": "shape_family", "buckets": [...], "weight": 4.0 },
  "primes":     { "parameter": "M",            "buckets": [...], "weight": 0.5 }
}
```

`weight` defaults to `1.0` and is a relative expected-traffic multiplier, not a sampling count.

Weights are used **twice, differently**:

- **Sampling** — round 0 allocates samples proportional to `weight^0.5`, not `weight`. Square-root damping keeps low-weight regimes populated enough to be learnable while still favouring common shapes; allocating proportional to raw weight starves the tail, and the tail is where regret concentrates.
- **Reporting** — §11.2 regret is reported both unweighted and traffic-weighted. The unweighted number says how good the heuristic is across the declared space; the weighted number estimates what a user will actually experience. Both matter, and they can diverge sharply.

### 5.3 Round 0 — Broad Coverage

| Strategy | Behaviour |
|----------|-----------|
| `one_per_regime` | One representative per bucket of each regime, other parameters at their most common value. Smoke only. |
| `stratified_cross_product` | Cross-product of all regime buckets × categorical parameters, then samples drawn per bucket (allocation per §5.2) with free numeric parameters sampled log-uniformly within range. Default for `standard`. |
| `dense_log_grid` | Log-spaced grid over every numeric parameter × full cross-product of categoricals. `exhaustive` only. |

**Non-regime parameter handling.** Under `one_per_regime`, parameters not being stratified MUST be set to `common_values[0]` **only if** `common_values` is present and its first entry is representative; otherwise to the geometric midpoint of `range`. Pinning every free parameter to its range minimum produces a degenerate corpus (every sample at `batch=1, seq_len=128`) and MUST NOT be done.

**Truncation.** A generator MUST NOT satisfy a target count by truncating the accumulated list, which drops whole regimes depending on iteration order. Undershoot by reducing samples-per-bucket uniformly; overshoot by round-robin removal across buckets.

**Dedup.** Deduplicate on the tuple of `q.*` values after generation, then top up by re-sampling under-filled buckets, up to `max_attempts = 10 × target`. `metadata.count` records the actual post-dedup count, which MAY be below target; the shortfall MUST be reported.

**Frozen holdout.** Before any backfill, a random **10%** stratified slice of round 0 MUST be marked `holdout: true` and excluded from training in every subsequent round. Backfill deliberately skews the corpus toward hard regions, so a holdout drawn after backfill is no longer representative and cannot be compared across rounds. The frozen round-0 holdout is the only evaluation set whose distribution is stable for the whole campaign (§11.3).

### 5.4 Backfill Rounds — Evidence-Driven

After round 0 is benchmarked and a model trained, three signals identify where to densify. All are computed from data in hand; none requires knowing boundary locations in advance.

| Signal | Computed from | Identifies |
|--------|---------------|------------|
| **Boundary density** | Measurements only | Among neighbouring measured problems, the fraction whose top-1 variant differs. High density = a decision boundary runs through the region. |
| **Regret concentration** | Model + measurements | Per-region mean top-1 regret (§11.2). High regret = the model is losing performance here. |
| **Prediction dispersion** | Model only | Variance of predicted score across CV folds. High dispersion with few samples = the model is guessing. |

Boundary density is the strongest signal because it is model-independent: it says the region is *intrinsically* hard to rank, whether or not the current model has noticed. Regret concentration says the current model is failing. Dispersion says the corpus is too thin to tell. A region flagged by all three is the highest-value backfill target.

**Allocation within a backfill round:**

1. Reserve the 20% exploration floor (§5.1), drawn by unbiased stratified sampling.
2. Distribute the remaining 80% across regions proportional to a combined score, with boundary density weighted most heavily.
3. Cap any single region at 40% of the round, so one pathological region cannot consume the budget.
4. Sample within a targeted region by local refinement — draw near existing high-signal problems rather than re-drawing from the region's full range.

New samples MUST be tagged with their round and the signal that selected them, so a post-hoc analysis can tell whether backfill actually helped or merely spent budget.

### 5.5 Budget Allocation and Stopping

**The unit of benchmark cost is the (problem, variant) pair, not the problem.** A corpus of 5,000 shapes costs 2.5M timed configurations against a 500-variant catalog and 25M against a 5,000-variant catalog. Specifying tiers as fixed shape counts is therefore meaningless in isolation, and it is why the shape counts quoted in CK's tooling do not transfer.

Tiers are defined by a **configuration budget**:

**The unit of benchmark cost is the (problem, variant) pair, not the problem.** A corpus of 5,000 shapes costs 2.5M timed configurations against a 500-variant catalog and 25M against a 5,000-variant catalog. Specifying tiers as fixed shape counts is therefore meaningless in isolation, and it is why the shape counts quoted in CK's tooling do not transfer.

Tiers are defined by a **configuration budget**:

| Tier | Budget (configs) | Approx. wall-clock | Purpose |
|------|------------------|--------------------|---------|
| `smoke` | 10⁴ | minutes | Validate that generation, graph construction, filtering and benchmarking run end to end |
| `standard` | 2 × 10⁶ | ~8–15 GPU-hours | Production heuristic |
| `exhaustive` | 2 × 10⁷ | ~4–7 GPU-days | Research; maximum accuracy |

Problem count follows from the measured variant count:

```
N_problems = clamp( budget_configs / N_applicable_variants,
                    min = 30 × N_regime_buckets,
                    max = parameter-space saturation )
```

| Applicable variants | `smoke` | `standard` | `exhaustive` |
|---------------------|---------|------------|--------------|
| 50 | 200 | 40,000 | (saturated) |
| 500 | 30 (floor) | 4,000 | 40,000 |
| 5,000 | 30 (floor) | 400 | 4,000 |

The **floor** (`30 × N_regime_buckets`) guarantees stratification remains meaningful even under a tight budget; if the floor exceeds the budget, the tool MUST report that the budget is insufficient rather than silently under-sampling. The **saturation cap** stops adding problems once new samples no longer occupy unfilled buckets on the declared stratification axis.

Wall-clock is estimated as:

```
T ≈ N_configs × (t_setup + n_iter × t_kernel)
```

`t_setup` (plan build, kernel load, workspace allocation) typically dominates for small problems. `uhd_gen benchmark` MUST measure `t_setup` and `t_kernel` on a calibration sample of ~100 configs and print the projected total before starting the full run, so an infeasible sweep is caught in the first minute rather than on day three.

CK's published corpus (≈5,000 GEMM shapes × ≈500 kernels ≈ 2.5M configs) sits at the `standard` budget, which is a useful sanity check on these numbers rather than their derivation.

**Note on model capacity.** Corpus size is bounded by benchmark cost and coverage, not by the learner. A 4,000-problem corpus against 500 variants yields 2M training rows, which is far past anything LightGBM's `min_data_in_leaf` constrains. Arguments that derive corpus size from leaf-population defaults conflate problems with rows and are unsound.

**Per-round split.** The tier budget is divided across rounds:

| Round | Share of budget | Selection |
|-------|-----------------|-----------|
| 0 | 50% | Stratified over declared regimes (§5.3) |
| 1 | 25% | 20% exploration floor, 80% evidence-targeted (§5.4) |
| 2 | 25% | Same, using signals refreshed after round 1 |

`smoke` runs round 0 only — its purpose is pipeline validation, not accuracy, and there is nothing to assess.

**Stopping.** Rounds stop early when any of these holds:

1. Traffic-weighted mean top-1 regret on the frozen holdout improves by **< 1 percentage point** over the previous round. The learning curve has flattened; further shapes buy nothing and the remaining budget SHOULD go to another operation or architecture.
2. No region exceeds the backfill-targeting thresholds — the evidence says coverage is already adequate everywhere.
3. Budget is exhausted.

Case 1 and case 3 mean different things and MUST be reported differently. Stopping on a flat curve means the corpus is sufficient. Stopping on budget means the corpus was the binding constraint and the model is likely still improvable — the training manifest MUST record which occurred, because shipping a budget-limited model without recording that fact loses the single most useful piece of information for the next training campaign.

### 5.6 Determinism and Provenance

Corpus generation MUST be reproducible. Given identical `(operation, tier, seed, generator_version, metadata content hash)`, round 0 MUST be byte-identical.

- `seed` is REQUIRED in corpus metadata; if not supplied on the command line, the tool generates one and records it.
- All sampling MUST draw from a seeded generator instance (`np.random.default_rng(seed)`). Module-level `np.random` MUST NOT be used.
- `metadata_hash` records the SHA-256 of the operation metadata file, so a corpus cannot be silently invalidated by an edit to the op definition.

Backfill rounds are reproducible only relative to their inputs: they depend on measurements and on the model trained from prior rounds. A backfill increment therefore records `input_model_hash` alongside its seed. Replaying a full campaign requires the round-0 seed plus the recorded per-round inputs; replaying round 0 alone requires only the seed.

This is what makes backfill auditable — without it there is no way to distinguish targeting that found real boundaries from targeting that chased noise.

## 6. Kernel Variant Enumeration

**Architectural principle** — as with the problem space: the KMD declares the space, the provider validates points in it.

### 6.1 KMD Declaration — Two Modes

The KMD JSON schema gains a `variant_enumeration` block.

**Mode `explicit`** — sparse or irregular catalogs. The provider supplies the complete list; tooling enumerates it directly.

```json
{ "variant_enumeration": {
    "mode": "explicit",
    "variants": [
      {"tile_m": 64,  "tile_n": 64,  "tile_k": 8,  "use_lds": true},
      {"tile_m": 128, "tile_n": 128, "tile_k": 16, "use_lds": true},
      {"tile_m": 256, "tile_n": 128, "tile_k": 8,  "use_lds": false}
    ] } }
```

**Mode `range`** — dense catalogs with constraints. Tooling forms the Cartesian product and filters through the provider's validator.

```json
{ "variant_enumeration": {
    "mode": "range",
    "fields": [
      {"name": "tile_m",  "type": "int64", "values": [64, 128, 256]},
      {"name": "tile_n",  "type": "int64", "values": [64, 128, 256]},
      {"name": "tile_k",  "type": "int64", "values": [8, 16, 32]},
      {"name": "use_lds", "type": "bool",  "values": [true, false]}
    ],
    "has_validator": true } }
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `mode` | string | Yes | `explicit` \| `range` |
| `variants` | array | Mode=explicit | Complete variant list |
| `fields` | array | Mode=range | Field metadata for Cartesian generation |
| `fields[i].name` | string | Yes | MUST match a KMD knob name |
| `fields[i].type` | string | Yes | `int64` \| `float64` \| `bool` \| `string` |
| `fields[i].values` | array | Yes | Discrete values |
| `has_validator` | bool | Mode=range | Provider exports `is_valid_config` |

With no validator, tooling falls back to the unfiltered Cartesian sweep and MUST report the count so an obviously oversized space is visible before benchmarking (see the 10,000-combination autotune cap, §13).

### 6.2 Validator Contract

Invoked through the backend (§7.1), not by loading the provider directly. The provider-side entry point is:

```cpp
// Provider implements in the KMD library
extern "C" bool <provider>_is_valid_config(
    const char* variant_json,   // JSON object of knob values
    size_t      json_len);
```

Constraints expressed here are the ones tooling cannot infer: LDS capacity for a tile pair, wavefront limits, mutual exclusivity between knobs.

### 6.3 Alignment Regimes Depend on the Catalog

A regime declared with `"derived": "alignment"` (§4.3.5) cannot be resolved until the variant set is known — "aligned" means aligned with respect to *these* tile sizes. Variant enumeration therefore runs **before** final corpus generation, and the tile values discovered here feed the alignment buckets. Concretely, the pipeline order is: enumerate variants → derive alignment buckets → generate corpus → filter → benchmark.

## 7. Applicability Filtering

### 7.1 Where Filtering Happens

The UHD is owned by the engine, and the engine is already registered with the hipDNN backend through the plugin loader. Tooling therefore MUST invoke applicability **through the backend API**, using the `engine_id` from the engine descriptor.

`uhd_gen` MUST NOT `dlopen` provider shared objects or resolve provider symbols with `dlsym`. Doing so bypasses the backend's plugin lifecycle and would give tooling a second, divergent view of which engines exist.

The C entry points below are the **provider-side contract** — what a provider implements so the backend can route to it. They are not the interface tooling calls.

```cpp
// Provider implements in the KMD library; backend routes to it.
extern "C" bool <provider>_is_applicable(
    const uint8_t* graph_flatbuffer,  // serialized hipDNN graph
    size_t         graph_size,
    int64_t        engine_id,
    char*          error_msg,         // optional; may be NULL
    size_t         error_msg_capacity);
```

Returns `true` when the provider can execute this graph with this engine; `false` otherwise, with the reason written to `error_msg` when that buffer is non-NULL. The reason string is not decorative — §7.3 records it.

**Provider precedent.** rocKE pre-filters explicitly via `miopenConvolutionForwardGetSolutionCount() > 0` rather than discovering inapplicability by failure. hipDNN adopts explicit pre-filtering.

### 7.2 The Candidate-Set Invariant

**Normative.** For any problem `p`, the set of variants scored by the UHD at runtime MUST be a subset of the variants **eligible** at training time — that is, the same `is_applicable` / `is_valid_config` predicates MUST gate both paths.

Two obligations follow:

1. **The same predicates run on both paths.** Whatever pair filtered the training corpus MUST also gate the runtime candidate list before scoring. A provider that filters at training but not at runtime is asking the model to rank configurations its predicates declared impossible.
2. **Predicate changes invalidate the model.** If a provider tightens or loosens either predicate the eligible set shifts, and the model MUST be retrained. The training manifest records the predicate versions (§10.4) so this is detectable.

Problem-level applicability is exempt in one direction: if `is_applicable(p)` is false the UHD is never consulted for `p`, so dropping those problems from training is safe.

**Eligible is not the same as benchmarked.** Requiring every eligible variant to be *measured* would be a much stronger claim, and a wrong one. Variant knobs are numeric, so a model can interpolate across tile configurations it has not seen, exactly as it interpolates across unseen problem shapes. Subsampling the variant space is legitimate and, for dense knob spaces, unavoidable (§13, Gap 4).

What subsampling requires is **measurement of the resulting error**, and here variants differ from problems in a way that matters:

- An unseen **problem** yields one prediction per candidate; ranking errors partly cancel.
- An unseen **variant** competes in an argmax. Selection preferentially returns whichever candidate received the most optimistic error — the optimizer's curse — so the quantity that governs runtime quality is the model's error at the *top* of the predicted distribution, and it worsens as the catalog grows.

Two consequences, both already required elsewhere: variant sampling MUST cover the knob space evenly rather than densely in one corner (§6.1), because a thinly-sampled corner is where an inflated score goes unchallenged; and §11.3 MUST include a leave-variants-out split, so the regret attributable to unmeasured variants is a reported number rather than an assumption.

### 7.3 Recording Filtered Pairs

Pre-filtering saves benchmark time but destroys the record of what was filtered, which is the same record needed for coverage auditing (§5.8) and for diagnosing an over-narrow predicate.

Filtered pairs MUST therefore be written to the benchmark CSV with `is_valid=False` and a populated `skip_reason`, and MUST NOT be timed. Training excludes them by filtering on `is_valid`; auditing reads them to answer "which variants were never eligible, and why".

```csv
q.M,q.N,q.K,kernel.tile_m,…,minTimeMs,is_valid,skip_reason,error
1024,1024,1024,128,…,0.123456,True,,
1024,1024,1024,256,…,,False,invalid_config: tile_m*tile_k exceeds LDS,
17,17,17,256,…,,False,not_applicable: M below minimum tile,
```

### 7.4 Benchmark Execution Order

```
for problem in corpus:
    graph = build_graph(problem)                      # §4.3.6
    if not backend.is_applicable(graph, engine_id):   # §7.1
        record_skipped(problem, all_variants, "not_applicable: " + reason)
        continue
    for variant in variants:                          # §6
        if not backend.is_valid_config(graph, engine_id, variant):
            record_skipped(problem, variant, "invalid_config: " + reason)
            continue
        record(benchmark(graph, engine_id, variant))
```

## 8. Benchmark Dataset Construction

### 8.1 Autotune Integration

Timing goes through the RFC 0013 autotune API (§2.2), not standalone per-kernel executables. Variants are enrolled with `add_engine_variants()` (explicit) or `add_engine_sweep()` (range), and timed with `autotune(mode=EXHAUSTIVE, strategy=RUN_UNTIL_STABLE)`.

Long runs (hours to days at `standard` and above) require progress reporting and checkpointing: the benchmark step MUST write results incrementally and MUST be resumable from a partial CSV.

### 8.2 Benchmark CSV Schema

UTF-8, RFC 4180, header row required. Columns are read by name; order is arbitrary. Null is the empty string. Booleans are `True`/`False` (case-sensitive). Floats carry ≥6 significant digits.

**Required columns**

| Column | Type | Description |
|--------|------|-------------|
| `q.*` | varies | Problem parameters, namespace-qualified |
| `kernel.*` | varies | Kernel variant knob values |
| `device.*` | varies | Device properties (provenance; see §3.3 for their use as features) |
| `minTimeMs` | float | Minimum time across iterations |
| `avgTimeMs` | float | Mean time across iterations |
| `stddevMs` | float | Standard deviation across iterations |
| `iters` | int | Iterations actually timed |
| `is_valid` | bool | Row carries a real measurement |
| `skip_reason` | string | Why the pair was not timed; empty when `is_valid=True` |

**Optional columns:** `tflops`, `gbs`, `error`.

**Validation rules**

1. Every `q.*` key from the corpus appears as a column.
2. Every `kernel.*` field from variant enumeration appears as a column.
3. Every `device.*` property queried appears as a column.
4. `minTimeMs ≤ avgTimeMs` for rows with `is_valid=True`.
5. `stddevMs ≥ 0`.
6. When `is_valid=False`, timing columns are empty and `skip_reason` is non-empty.
7. When `is_valid=True`, `skip_reason` and `error` are empty.

### 8.3 Target Metric

The target is derived from the operation's declared cost model (§4.3.3), not hardcoded per operation:

```python
flops = evaluate(op_metadata["cost_model"]["flops"], row)   # $q.* resolved from the row
df["tflops"] = flops / (df["minTimeMs"] * 1e9)
```

All column references MUST be namespace-qualified (`q.M`, not `M`) per §8.5.

Alternative targets: `minTimeMs` with objective `min`; `tflops / theoretical_peak` for a 0–1 efficiency scale; bytes/sec for bandwidth-bound ops, computed from `cost_model.bytes`.

### 8.4 Measurement Noise

`stddevMs` is recorded so it can be used, not merely stored.

- Rows where `stddevMs / avgTimeMs > 0.10` SHOULD be flagged as high-variance and either re-timed or excluded from training; the exclusion count MUST be reported.
- `minTimeMs` is the default target because it is the most noise-robust statistic available, but it is biased low under contention. Benchmarks SHOULD run with the GPU otherwise idle and with a fixed clock/power state where the platform permits; the training manifest records whether this was done.
- Two variants whose timing distributions overlap within noise are not meaningfully ordered. §11.2 accounts for this by scoring regret in throughput terms rather than rank position.

### 8.5 Feature Namespace Enforcement

**IMPLEMENTED** (commit `aa2be93`). `uhd_gen` rejects unqualified feature columns.

```bash
--features q.M q.N q.K kernel.tile_m kernel.tile_n
```

A bare `cu_count` becomes `$cu_count` in the signature, which the runtime cannot resolve — the failure mode is silent degradation to static ordering, so it is rejected at training time instead.

Adopting them means restructuring `uhd_gen` around subcommands, which is a **breaking CLI change**: today's invocation is the training path with no subcommand. The migration is to move the existing flags under `train` and keep the bare form working with a deprecation warning for one release.

### 10.2 Algorithm

1. Load CSV, filter to `is_valid == True`.
2. Split features/target; `y = log1p(target)`.
3. GroupKFold (5 splits) on `--group-by` columns (§2.6).
4. Train LightGBM with early stopping.
5. Evaluate against §11 protocol; refuse to emit on gate failure.
6. Export LightGBM → FlatBuffer `GbdtModel`.
7. Write `uhd.fb` / `uhd.json` with `features_signature` and `features_hash`.

## 11. Evaluation Protocol

**SPECIFIED HERE.** The training objective is pointwise regression on `log1p(tflops)`; the runtime decision is *pick the best kernel for this problem*. RMSE on the regression target can improve while top-1 selection gets worse, so RMSE MUST NOT be the acceptance criterion.

### 11.1 Definitions

For problem `p` with measured candidate set `V(p)`:

- `t(p, v)` — measured throughput of variant `v` on `p`
- `v*(p) = argmax_v t(p, v)` — best measured variant (the oracle)
- `v̂(p)` — variant the model ranks first

### 11.2 Metrics

| Metric | Definition | Reported as |
|--------|------------|-------------|
| **Top-1 regret** | `1 − t(p, v̂(p)) / t(p, v*(p))` | mean, p50, p95, max |
| **Regret tail** | fraction of problems with regret > 5% | percentage |
| **Top-k recall** | fraction of problems where `v*(p)` ∈ model's top-k | k = 1, 3, 5 |
| **Per-regime regret** | mean top-1 regret grouped by corpus regime | table |

Regret is measured in throughput, not rank position, because ranks are meaningless between variants whose timings overlap within noise (§8.4): choosing the second-best of two statistically indistinguishable kernels costs nothing and MUST NOT be scored as an error.

Per-regime breakdown is required because aggregate regret hides a model that is excellent on the dense middle of the corpus and useless on decode-shaped or prime-dimension problems — which are frequently the shapes the heuristic exists to get right.

**Weighting.** Every regret metric MUST be reported twice: unweighted over the corpus, and weighted by the declared regime weights (§5.2). These answer different questions — how good the heuristic is across the declared space, versus what a user is likely to experience — and backfill (§5.4) deliberately skews the corpus toward hard regions, so the unweighted number drifts pessimistic as rounds accumulate. Reporting only one of the two makes the model look either better or worse than it is, depending on which is omitted.

### 11.3 Splits

Three evaluations, all required:

1. **Interpolation** — GroupKFold by problem (§2.6). Performance on unseen shapes drawn from the training distribution.
2. **Shape extrapolation** — leave-one-regime-out: withhold an entire regime, train on the rest, evaluate on the withheld regime; repeat per regime. The honest estimate of behaviour on a shape family nobody thought to benchmark, which is the situation the runtime will meet.
3. **Variant extrapolation** — leave-variants-out: withhold a stratified 20% of the kernel variants across the whole corpus, train on the rest, then evaluate with the withheld variants restored to the candidate set. This measures the cost of subsampling the knob space (§7.2), and is the check that says whether an unmeasured variant can be scored safely or will win the argmax on an inflated prediction.

All three are additionally reported against the **frozen round-0 holdout** (§5.3), which is the only evaluation slice whose distribution does not move as backfill proceeds. Cross-round comparisons — did round 1 help? — MUST use the frozen holdout; comparing against a set that grew between rounds measures the change in the set, not the change in the model.

Extrapolation regret will be substantially worse than interpolation regret in both directions. Those two gaps are the numbers to track: the shape gap estimates the risk of a workload nobody sampled, the variant gap estimates the risk of the catalog containing kernels nobody measured.

### 11.4 Baselines and Acceptance Gates

Every evaluation reports the model against three references:

| Reference | Definition |
|-----------|------------|
| **Oracle** | `v*(p)`; regret 0 by construction. Upper bound. |
| **Static order** | The `priority`/`id` ordering the pack ships with in Stage 1 (§2.1). This is what the model must beat to justify existing. |
| **Random** | Uniform choice from `V(p)`. Sanity floor. |

A UHD MUST NOT be emitted unless:

1. Mean top-1 regret (interpolation) is **strictly better than static order**, and
2. p95 top-1 regret (interpolation) ≤ 10%, and
3. No regime's mean regret is worse than static order's regret for that regime — a model that improves the average by trading away a whole regime is a regression for the workloads in it, and
4. When a previous UHD exists for the same operation and arch, neither mean nor p95 regret has worsened against it.

Gate thresholds are defaults; a pack MAY tighten them, and MUST record any relaxation with a rationale in `train_manifest.json`.

### 11.5 On the Regression Objective

Pointwise regression on `log1p(tflops)` is a proxy for ranking. It spends model capacity on predicting absolute throughput accurately in regions where the ranking is never in doubt.

A ranking objective (LightGBM `lambdarank`, groups = problems, relevance graded by measured throughput) optimizes top-1 selection directly and is the more natural fit. It is not the current default because the UHD score is also consumed as a **calibrated cross-engine comparable value** when `score.calibrated` is true (RFC §11.3) — a pure ranking model produces scores that are only meaningful within a group, which breaks cross-engine comparison.

**Recommendation:** keep regression as the default while `calibrated` remains a goal; evaluate `lambdarank` under §11.2 for packs that do not need cross-engine comparability, and record which objective was used in the manifest. The metrics in §11.2 are objective-agnostic, so the comparison is direct.

## 12. Per-Operation Reference

Parameter ranges and regime definitions per operation class. These are reference values for authoring the metadata files of §4; they are not a second source of truth for corpus size — tiers are budget-driven and global (§5.2).

Every operation belongs to a class, and the class fixes the stratification axis (§4.3.4).

| Class | Operations | Stratification axis |
|-------|-----------|---------------------|
| 1. Dense linear algebra | MatMul, MoE grouped MatMul | `arithmetic_intensity` |
| 2. Spatial convolution | Conv fwd/bwd/wrw, Resample | `arithmetic_intensity` |
| 3. Attention | SDPA fwd/bwd | `arithmetic_intensity` |
| 4. Normalization | LayerNorm, RMSNorm, BatchNorm (± backward) | `working_set` |
| 5. Elementwise | Pointwise (47 modes) | `working_set` |
| 6. Reduction | Reduction (9 modes) | `reduction_ratio` |
| 7. Quantization | BlockScale quantize/dequantize | `working_set` |

### 12.1 Class 1 — MatMul

**Parameters:** `M`, `N`, `K`, `batch`, `transA`, `transB`, `dtype` (fp32, fp16, bf16, fp8, int8).

| Regime | M | N | K | Use case |
|--------|---|---|---|----------|
| Single token | 1 | 512–28672 | 256–8192 | Batch-1 decode |
| Small | 32–512 | 32–512 | 32–512 | Small NLP, batch-1 inference |
| Medium | 512–4096 | 512–4096 | 512–4096 | Training, mid-size models |
| Large | 4096–16384 | 4096–16384 | 4096–16384 | Large LLM training |
| Tall-skinny | 8192–32768 | 128–512 | 4096–8192 | Token generation |
| Short-fat | 128–512 | 8192–32768 | 4096–8192 | Projection layers |
| Deep K | 16–256 | 16–256 | 4096–32768 | Compute-bound |
| Shallow K | 4096–16384 | 4096–16384 | 32–256 | Memory-bound |
| Primes | 17, 31, 37, 127, 251, 509, 1021, 2039, 4093 | — | — | Worst-case tiling |
| LLM shapes | LLaMA MLP (1×4096×11008), DeepSeek V3 configs | | | Real workloads |

Roofline: `AI = 2·M·N·K / (sizeof · (M·K + K·N + M·N))`. Compute-bound above the device ridge point (`peak_flops / peak_bandwidth`), not a fixed constant — the threshold is device-dependent and MUST be computed from the queried device properties.

Alignment regimes: aligned (`M % tile_m == 0` for all three dims), partial remainder (one dim), full remainder (all three). Tile values come from variant enumeration (§6.3).

**MoE grouped MatMul** adds `num_experts` (4, 8, 16, 32, 64), `expert_capacity`, and routing skew (uniform vs. imbalanced), with capacity factors 1.0 / 1.25 / 1.5 / 2.0.

### 12.2 Class 2 — Convolution and Resample

**Parameters:** `N`, `C`, `K`, `H`, `W`, `R`, `S`, `pad_*`, `stride_*`, `dilation_*`, `groups`, `dtype`.

| Layer archetype | N | C | H×W | K | R×S | Notes |
|-----------------|---|---|-----|---|-----|-------|
| ResNet50 conv1 | 64–256 | 3 | 224 | 64 | 7×7 | Large spatial, few channels |
| ResNet50 layer3 | 64–256 | 512 | 28 | 512 | 3×3 | Balanced |
| MobileNet depthwise | 64–256 | 32–512 | 56–112 | 1 | 3×3 | `groups = C` |
| U-Net encoder | 4–16 | 64–512 | 128–512 | 128–1024 | 3×3 | Medical imaging |
| Dilated (segmentation) | 4–32 | 256–1024 | 64–128 | 256–1024 | 3×3 | `dilation = 2` |

Roofline: compute-bound for large filters, many channels, large batch; memory-bound for 1×1 convolutions, small batch, large spatial.
Alignment: `H % tile_h`, `W % tile_w`, `C % tile_c`, `K % tile_k`.

**Resample** shares the class: `window` (2×2, 3×3, 4×4, 8×8), `stride` (1, 2), padding per dimension, `resample_mode` (MAX, AVG), `padding_mode` (ZERO, EDGE, REFLECT).

### 12.3 Class 3 — SDPA

**Parameters:** `batch`, `heads`, `seqlen_q`, `seqlen_k`, `head_dim` (64, 128, 256), `is_causal`, `attn_scale`, `dropout_probability`, `dtype` (fp16, bf16, fp8).

| Regime | batch | heads | seqlen_q | seqlen_k | head_dim |
|--------|-------|-------|----------|----------|----------|
| Prefill / training | 1–64 | 32–96 | 512–8192 | = seqlen_q | 64–128 |
| Decode | 1–256 | 32–96 | 1 | 512–32768 | 64–128 |
| Short context | 4–128 | 8–32 | 128–512 | 128–512 | 64–128 |
| Long context | 1–16 | 32–96 | 8192–32768 | = seqlen_q | 64–128 |
| Edge cases | 1 | 1 | — | — | 256 |

Model configs to include: LLaMA-2 7B/13B/70B (32/32/40 heads, head_dim 128), GPT-3 175B (96 heads), BERT-base (16 heads, head_dim 64), DeepSeek V3 (128 query heads, 8 KV heads — exercises GQA ratio).

Key relationships: training and prefill have `seqlen_q ≈ seqlen_k`; decode has `seqlen_q = 1, seqlen_k >> 1` (KV cache) and is always causal.
Alignment: `seqlen_q % tile_m`, `seqlen_k % tile_n`, `head_dim % tile_k`.

### 12.4 Class 4 — Normalization

**LayerNorm / RMSNorm parameters:** `batch`, `seq_len`, `hidden_dim`, `epsilon`, `dtype`, `forward_phase`.

| Model | batch | seq_len | hidden_dim |
|-------|-------|---------|------------|
| BERT-base | 1–512 | 128–512 | 768 |
| BERT-large | 1–512 | 128–512 | 1024 |
| LLaMA-2 7B | 1–128 | 512–4096 | 4096 |
| LLaMA-2 70B | 1–64 | 512–8192 | 8192 |
| GPT-3 175B | 1–2048 | 1024–2048 | 12288 |
| ViT-Base / Large / Huge | 1–256 | 196–256 | 768 / 1024 / 1280 |

**BatchNorm parameters:** `N`, `C`, `H`, `W`, `epsilon`, `momentum`, `dtype` — CNN-shaped rather than transformer-shaped: N 1–256, C 32–1024, H×W 14–224.

Stratification is by `working_set` — the per-row normalized footprint (`hidden_dim × sizeof`, or `C × sizeof`) bucketed against L1/L2/LLC capacity. Arithmetic intensity is constant for this class (§4.3.4) and MUST NOT be used.

Alignment: `hidden_dim` (or `C`) against the reduction tile width; row lengths that are not a multiple of the wavefront size are the interesting cases.

### 12.5 Class 5 — Elementwise

**Parameters:** `operation` (47 `PointwiseMode` values), input shape(s), broadcast pattern, `dtype`, plus mode-specific scalars (`swish_beta`, `elu_alpha`, `softplus_beta`, `relu_*_clip`).

Stratification by total element count against cache hierarchy: 1K–10K (L1), 100K–1M (L2), 10M–100M (HBM streaming), 1B+ (multi-pass). Additional axes: broadcast pattern (none, scalar, 1D, channel, spatial), tensor rank (1D–5D), aspect ratio (square vs. tall-skinny, which changes access coalescing).

The 47 modes do not each need full coverage. Group them by cost profile — cheap unary (`ABS`, `NEG`, `IDENTITY`), transcendental (`EXP`, `LOG`, `TANH`, `ERF`, `GELU_*`), binary (`ADD`, `MUL`, `SUB`, `DIV`), comparison/select — and sample shapes densely per *group*, with a thin sweep across modes within a group. Arithmetic intensity here is below 1 FLOP/byte for every mode, which is why mode identity matters far less than footprint.

### 12.6 Class 6 — Reduction

**Parameters:** `mode` (ADD, MUL, MIN, MAX, AMAX, AVG, NORM1, NORM2, MUL_NO_ZEROS), input shape, reduction axes, `dtype`, `is_deterministic`.

Stratification by `reduction_ratio = input_elements / output_elements`:

| Pattern | Ratio | Example |
|---------|-------|---------|
| Full reduction | 10⁶–10⁹ | `(N,C,H,W) → scalar` |
| Batch reduction | 10–10³ | `(N,C,H,W) → (C,H,W)` |
| Channel reduction | 10–10³ | `(N,C,H,W) → (N,H,W)` |
| Spatial reduction | 10²–10⁴ | `(N,C,H,W) → (N,C)` |
| Near-identity | 1–10 | Reducing a length-2 axis |

`is_deterministic` materially changes the algorithm (tree vs. atomic accumulation) and MUST be sampled on both settings.

### 12.7 Class 7 — Quantization

**Parameters:** `block_size` (16, 32, 64, 128, 256), input dtype → output dtype pair, `scale_dtype` (float32, float16), tensor shape.

Stratification by `working_set` with a dedicated alignment axis: whether the tensor's fastest-varying dimension is a multiple of `block_size`. Ragged final blocks are the interesting case and are trivially missed by power-of-two-only sampling.

## 13. Open Gaps

| # | Gap | Impact | Where |
|---|-----|--------|-------|
| 1 | Corpus generation, variant enumeration, and benchmarking tooling do not exist | Every pack author reinvents them; the methodology here is unenforced | §5, §6, §8 |
| 2 | KMD schema lacks `variant_enumeration`; no backend API for `is_valid_config` | Mode-explicit and validator paths cannot be implemented | §6.1, §6.2 |
| 3 | Binding layer does not publish `$op.flops` / `$op.bytes` | Cost-model features must be precomputed host-side | §9.2 |
| 4 | Autotune caps variant enrollment at 10,000 combinations per sweep | Dense knob spaces must be enrolled in batches or subsampled; sets a floor on how coarsely the knob space can be covered | §6.1, §7.2 |
| 5 | No empirical guidance on per-arch vs. pooled multi-arch models | §3.4 strategy choice is unvalidated | §3.4 |
| 6 | Operation metadata files do not exist for any of the 22 ops with graph builders | Nothing to feed the generator | §4 |
| 7 | Tile-quantization dim↔tile correspondence must be authored by hand | Blocks fully mechanical feature derivation | §9.1 |
| 8 | No feature-importance or tree-inspection tooling | Model behaviour is opaque when regret is bad | §9.3 |

**On Gap 4.** The 10,000-combination cap is a throughput limit on how many variants autotune can enroll in one sweep, not a correctness cliff. An engine whose knob space exceeds it enrolls in batches, or measures a subsample — and subsampling the variant space is legitimate for the same reason subsampling the problem space is (§7.2): the model interpolates across numeric knobs. Neither space is ever exhaustively measured, and neither needs to be.

What the cap does constrain is how *evenly* a dense knob space can be covered within a given budget, which is what the optimizer's curse makes expensive. The mitigation is therefore to spend the variant budget on uniform coverage of the knob space rather than on exhaustively enumerating one corner of it, and to report the leave-variants-out regret from §11.3 so the cost of the subsample is a measured number. Restricting the runtime candidate set to the measured subset is **not** the mitigation — it discards working kernels to protect a modeling assumption, and the assumption is one the evaluation can test directly.

## 14. Implementation Roadmap

**Phase 1 — make one operation work end to end.**

1. `validate-metadata` plus the metadata file for `matmul` (§4).
2. `generate-corpus` round 0 — `stratified_cross_product`, seeded, with the frozen holdout (§5.3).
3. Graph construction from `graph_builder` (§4.3.6).
4. `benchmark` against the backend applicability API, recording skipped pairs (§7, §8).
5. Evaluation protocol against the frozen holdout with a static-order baseline; gate on it (§11).

Phase 1 is deliberately open-loop: round 0 plus evaluation. It is the smallest thing that produces a shippable UHD and, more importantly, it produces the first real measurements of boundary density and regret — the inputs Phase 2 needs. Building backfill before there is anything to assess would be targeting without evidence, which is the failure this design exists to avoid.

**Phase 2 — close the loop.**

6. Boundary-density, regret-concentration and dispersion signals over round-0 results (§5.4).
7. Backfill rounds with the exploration floor and per-region caps (§5.1, §5.4).
8. Stopping criterion on the frozen-holdout regret curve, distinguishing convergence from budget exhaustion (§5.5).
9. Budget calibration (`t_setup` / `t_kernel` measurement and projection) (§5.5).

**Phase 3 — generalize across operations.**

10. Metadata files for the remaining Tier-1 ops (`sdpa_fwd`, `conv_fwd`), then normalization and elementwise.
11. Regime weights and traffic-weighted regret reporting (§5.2, §11.2).
12. Coverage reporting and axis-occupancy warnings (§5.8).
13. Subcommand CLI migration with deprecation shim (§10.1).

**Phase 4 — close the schema and tooling gaps.**

14. KMD `variant_enumeration` and the `is_valid_config` backend route (Gap 2).
15. Leave-variants-out evaluation and variant-space coverage metrics (§11.3, Gap 4).
16. `$op.flops` / `$op.bytes` in the binding layer (Gap 3).
17. `lambdarank` objective evaluation (§11.5).
18. Feature-importance and tree-inspection tooling (Gap 8).
