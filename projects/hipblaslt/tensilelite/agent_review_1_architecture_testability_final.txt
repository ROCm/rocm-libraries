Agent 1 architecture/testability review - final

Scope reviewed:
- Branch: users/alvasile/ring_buffer
- Diff: git diff origin/develop...HEAD -- .
- Focus: architecture, design cleanliness, and testability of the current branch changes.

Findings:

1. High - The new copy-engine path preserves and tests a bad source-pointer behavior instead of isolating/fixing it.

client/src/DataInitialization.cpp:821-824 builds srcBytes from dst, ignores the src argument, and documents that this intentionally mirrors CopyTensorVoid's current behavior. That means the second phase of copyBadInputBuffers() can copy from the destination region back to itself rather than from the valid source buffer. In the NaN/bad-bounds path this defeats the intended "fill padding with sentinel, then overwrite the valid tensor region" design.

The test added around this seam then codifies the defect: tests/DataInitializationCopyPlan_test.cpp:309-315 treats call.dst == call.src as the marker for the valid-region copy and expects it. That is the wrong architectural direction. The CopyEngine seam should make this easier to correct and test, not lock the bug in under a "mirror existing behavior" comment.

Recommended shape:
- Fix copyTensorVoidThroughEngine() to compute srcBytes from src, not dst.
- Add a small content-level test for a non-contiguous or padded descriptor that proves the sentinel area remains sentinel and the valid area comes from the valid source.
- Do not assert call.dst == call.src as a success condition; assert semantic copy inputs instead.

2. Medium - The branch silently removes CuCount_test.cpp from the default tensilelite-tests target.

tests/CMakeLists.txt:20-35 comments out "${CMAKE_CURRENT_SOURCE_DIR}/CuCount_test.cpp" while adding the new policy/layout tests. That is a direct coverage regression from origin/develop and is not explained in the branch. If CuCount_test is flaky, GPU-dependent, or obsolete, it should be moved/guarded with an explicit reason and replacement coverage. As written, an unrelated ring-buffer PR weakens the pre-existing test target.

Recommended shape:
- Restore CuCount_test.cpp to tensilelite-tests, or split it behind an explicit option/condition with a comment explaining the dependency and a tracked follow-up.
- If the test was disabled because it blocks this branch's build, document the failure mode in the PR and add the narrowest replacement coverage.

3. Medium - DataInitialization's ring fast path still relies on call-site discipline and debug-only checks instead of release-mode self-validation.

client/include/DataInitialization.hpp:223-237 consumes a prepared ring slot when m_ringPolicy.allowed && m_ring.hasAvailableSlot(), and only asserts ringEligible(). The stronger predicate is defined at client/include/DataInitialization.hpp:1331-1340, but it is not part of the release-mode gate at the consumption point. The production scheduler does call resetPreparedSlotsForProblem() before preparing a new problem (client/src/ClientRunScheduler.cpp:119-127), so the main path is disciplined. The DataInitialization API itself, however, still exposes prepareGPUInputs() and primeNextInputSlot(); a caller that primes for one problem and then prepares another without reset can consume stale slot state.

This is exactly the kind of lifecycle invariant that tends to regress because it is spread across comments, scheduler order, and test subclasses. The branch already introduced PreparedProblemSignature and batch-pointer signatures; the ring fast path should use that machinery before advancing.

Recommended shape:
- Change the fast-path gate to require ringEligible() and a current prepared-problem signature for the requested problem before advanceBuffer().
- If the signature does not match, fall back to the typed prepare path or reset the prepared slots instead of consuming the ring.
- Add a regression test that primes a ring slot for p1, then calls prepareGPUInputs(p2) without scheduler reset and proves p2 does not receive p1's cached ring input.

4. Low - The plan/executor seams improve things, but too much "plan" behavior is still trapped inside a HIP-allocating DataInitialization object.

The tests expose protected internals through subclasses such as CopyPlanDataInitialization in tests/DataInitializationCopyPlan_test.cpp:33-49, then most of those tests still skip without a HIP device via tests/DataInitializationCopyPlan_test.cpp:95-109. That is a testability smell: the branch added pure-looking concepts like TensorCopyPlan, OutputResetPlan, BatchPointerLayout, InputLayoutPolicy, RingPolicy, and RingSlotController, but some of the most important planning behavior still requires constructing DataInitialization, which allocates GPU state in client/src/DataInitialization.cpp:1517-1519 and calls allocNewCPUInputs()/allocNewGPUInputs() at client/src/DataInitialization.cpp:1928-1930.

Recommended shape:
- Continue extracting planner objects that operate on descriptor/config/view metadata without owning HIP allocations.
- Keep DataInitialization as the executor and resource owner.
- Move the "what should be copied/reset/which slot is legal" decisions into HIP-free units where possible, then leave only stream/event/memory effects in GPU-backed tests.

Overall verdict:
- The branch is directionally better than the original monolithic flow: ClientRunScheduler, RingPolicy, RingSlotController, BatchPointerLayout, InputLayoutPolicy, and CopyEngine are all useful seams.
- The highest-risk issue is that one new seam reproduces and tests bad copy semantics. Fix that before treating the copy-plan layer as a stable testing surface.
- The second most important cleanup is restoring or explicitly accounting for the removed CuCount_test.cpp coverage.

Validation caveat:
- I performed static review of the current checkout and diff only. I did not run the C++ test binaries in this pass, and I did not inspect GPU runtime behavior beyond the code/tests shown above.
