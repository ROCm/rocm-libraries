Findings in progress:
- Finding A (production-path integration gap): `ClientRunScheduler` is well covered with fakes, but the branch has no test that composes the real `main.cpp` adapter path with `MetaRunListener`, `DataInitialization`, `ReferenceValidator`, and `BenchmarkTimer`. Production construction happens through `SchedulerDataCoordinatorAdapter`, `SchedulerSolutionSourceAdapter`, `SchedulerKernelLauncherAdapter`, and `ClientRunScheduler` in `client/main.cpp:1253-1286`. The scheduler tests instead use `RecordingDataCoordinator` and a fake listener stack in `tests/ClientRunScheduler_test.cpp:287-326` and `tests/ClientRunScheduler_test.cpp:501-548`. That proves scheduler ordering, but not that parsed client args select the expected ring policy, listener counts, data-init state, and reset behavior together. This is most relevant to the no-benchmark validation path asserted in `tests/ClientRunScheduler_test.cpp:562-609`, which does not instantiate real `DataInitialization` or the production listener stack.
- Finding B (grouped-GEMM ring fast path gap): the new ring fast path explicitly claims to work for grouped GEMM and bypasses typed dispatch once a prepared slot is available (`client/include/DataInitialization.hpp:223-238`). Grouped preparation delegates to `problem.gemms[0]` after only an element-type invariant assertion (`client/include/DataInitialization.hpp:351-364` and `client/include/DataInitialization.hpp:1291-1316`), and async priming/reset similarly funnels grouped problems through `gemms[0]` (`client/src/DataInitialization.cpp:4395-4407` and `client/src/DataInitialization.cpp:4476-4481`). I did not find any grouped-GEMM test exercising this ring path; the test helper has a `groupedGemm` knob (`tests/include/DataInitializationTestUtils.hpp:48-50`, `tests/include/DataInitializationTestUtils.hpp:163-165`), but current test references only touch grouped offsets/planning helpers, not a grouped problem through warm slot prepare/advance/validation.
- Finding C (scheduler `use-user-args` branch untested): `ClientRunScheduler` has a separate production branch for user-argument kernels: it calls `solveTensileGPU()` instead of `solve()` and then releases device user args (`client/src/ClientRunScheduler.cpp:186-196`, `client/src/ClientRunScheduler.cpp:322-325`). The test fake implements both hooks (`tests/ClientRunScheduler_test.cpp:357-387`), but I found no scheduler test setting `ClientRunSchedulerConfig::useUserArgs = true`; all scheduler scenarios exercise the ordinary `solve()` path. That leaves the extracted scheduler's user-args path, release ordering, and exception behavior uncovered.
- Finding D (solution-dependent MX refresh path only predicate-tested): `DataInitialization::beginSolution()` now performs solution-dependent MX FP4/FP8 regeneration and GPU recopy after `prepareGPUInputs()` (`client/include/DataInitialization.hpp:262-318`). The tests I found stop at predicate/freshness checks: `tests/BatchPointerReset_test.cpp:451-473` verifies `shouldRefreshMXForSolution()` after GPU preparation, but no test calls `beginSolution()`/`preSolution()` and verifies that `initializeMXData()`, `copyValidToGPUBuffer()`, the D2D `copyInputs()`, and CPU-current synchronization happen together. This is a production ordering/lifecycle gap because `ReferenceValidator::preSolution()` relies on that refresh having already updated CPU current buffers before it reruns the CPU reference.
- Finding E (scheduler loop shape lacks multi-problem/multi-pass coverage): production scheduling iterates benchmark runs, icache-flush modes, and `problemIdx = firstProblemIdx..lastProblemIdx`, resetting prepared slots before each problem (`client/src/ClientRunScheduler.cpp:91-123`). The harness supports only one default problem (`tests/ClientRunScheduler_test.cpp:501-548` sets `problems = makeProblems(1)`), and a search of `tests/ClientRunScheduler_test.cpp` did not find any test overriding the problem count or exercising a non-zero `firstProblemIdx`. That leaves off-by-one progress, per-problem reset/cancel behavior, and ring state cleanup across scheduler-driven problem changes covered only indirectly by lower-level manual `DataInitialization` tests, not by the extracted scheduler loop.
