# TensileLite: Creating a Library for hipBLASLt

This guide covers three angles: the standard GEMM YAML pipeline, custom/non-GEMM ops,
and the internal mechanism end-to-end. All claims include file references.

**Prerequisites:** Python >= 3.10 (declared in `pyproject.toml:63`). Install rocisa once
with `invoke rocisa` before any Python-level work. `ROCM_PATH` defaults to `/opt/rocm`.

---

## Quickstart: YAML → device library

Use `epilogues/scripts/build_library.sh` to go from a benchmark YAML to a compiled
device library in one step:

```bash
bash epilogues/scripts/build_library.sh \
    --yaml epilogues/yaml/gemm_partial_rms_k1_rowmajor.yaml \
    --chip gfx950 \
    --out-dir /tmp/partialrms_lib \
    --group-by PartialRMSResidualAdd
```

Internally the script calls `python -m Tensile.Tensile` to benchmark and emit
LibraryLogic YAMLs, then `python -m Tensile.TensileCreateLibrary` to compile them.

## 1. Standard Path: YAML Config + GEMM

**Reference:** `epilogues/docs/TUNING_PIPELINE.md` — the most complete existing walkthrough.

### Entry point

```bash
Tensile/bin/Tensile config.yaml output_dir [--gpu-targets gfx942]
```

`Tensile/Tensile.py:741` defines `main()`, which calls `Tensile()` at line 483.
`Tensile()` calls `executeStepsInConfig()` defined at line 72. The three phases run
from that function depending on which top-level YAML keys are present.

### Required YAML structure

Unknown keys are fatal (`ConfigTypeError`). Validation runs in
`_assertGlobalParametersAreValid()` at `Tensile/Common/GlobalParameters.py:753`,
called from `assignGlobalParameters()` at line 829.

```yaml
GlobalParameters:
  MinimumRequiredVersion: "4.2.0"
  ISA: [9, 4, 2]            # or set via --gpu-targets
  NumElementsToValidate: -1  # -1 = full; default 128
  KernelTime: True

BenchmarkProblems:           # triggers Phase 1
  - - OperationType: GEMM    # element [0] = ProblemType
      DataType: b            # s=f32, b=bf16, h=f16
      TransposeA: False
      TransposeB: True
      UseBeta: True
      Batched: False

    - BenchmarkCommonParameters:  # element [1+] = size group
        - KernelLanguage: ["Assembly"]
      ForkParameters:             # Cartesian product sweep
        - MatrixInstruction: [[32, 32, 8, 1, 2, 1, 1, 1, 2]]
        - DepthU: [16, 32, 64]
      BenchmarkFinalParameters:
        - ProblemSizes:
            - Exact: [4096, 4096, 1, 4096]

LibraryLogic:                # triggers Phase 2 (uses Phase 1 output)
  ScheduleName: "Tensile"

LibraryClient:               # triggers Phase 3 (uses Phase 2 output)
  - {}
```

A minimal working example is at `Tensile/Tests/common/benchmark_runs/fp32_tn.yaml`.
`ForkParameters` permutations are generated by `itertools.product` in
`BenchmarkStructs.py:339`. Combos rejected by `Solution.__init__` set `state["Valid"] = False`
and print a rejection reason when `printSolutionRejectionReason=True`.

### Three phases

| Phase | Module | Input | Output |
|-------|--------|-------|--------|
| 1 BenchmarkProblems | `Tensile/BenchmarkProblems.py` | YAML | `1_BenchmarkProblems/` (`.co`, `cache.yaml`), `2_BenchmarkData/` (CSVs + solution YAMLs) |
| 2 LibraryLogic | `Tensile/LibraryLogic.py` | `2_BenchmarkData/` | `3_LibraryLogic/<Schedule>_<ProblemType>.yaml` |
| 3 ClientWriter | `Tensile/ClientWriter.py` | `3_LibraryLogic/*.yaml` | `4_LibraryClient/` (`.co`, msgpack `.dat`, `ClientParameters*.ini`) |

Phase 2 runs `analyzeProblemType()` (`LibraryLogic.py:48`) to prune dominated solutions
and build a nested range decision tree. The `3_LibraryLogic/` YAMLs are the artifacts
committed to `library/src/amd_detail/rocblaslt/src/Tensile/Logic/`.

## 2. Custom Ops (Non-GEMM, e.g. Softmax / RMS Norm)

Two mechanisms exist.

### Mechanism A: Hand-written assembly (`CustomKernelName`)

Any LibraryLogic solution can set `CustomKernelName: <name>`. TensileLite then reads
`Tensile/CustomKernels/<name>.s` verbatim instead of code-generating it.
`CustomKernels.py:48` (`getCustomKernelConfigAndAssembly`) parses the embedded metadata;
`getCustomKernelContents()` at line 41 reads the `.s` file.

The `.s` file **must** embed its configuration in a `.amdgpu_metadata` YAML block:

```asm
.amdgpu_metadata
---
custom.config:
  ProblemType:
    OperationType: GEMM
    DataType: b
    ...
  InternalSupportParams:
    KernArgsVersion: 2
  MatrixInstruction: [32, 32, 8, 1]
  DepthU: 16
...
.end_amdgpu_metadata
```

119 production `.s` files exist in `Tensile/CustomKernels/` (flat directory; arch is
encoded in the filename, e.g. `..._gfx942_...s`).

### Mechanism B: Fused epilogue parameter (PartialRMS pattern)

For a new fused op, changes are required at eight layers. See
`epilogues/yaml/gemm_partial_rms_k1_rowmajor.yaml` for a complete example of a
benchmark YAML that drives the native Tensile pipeline to generate a LibraryLogic
YAML for a fused-epilogue kernel.

**Layer summary (with references):**

1. **Declare parameter** in `Tensile/Common/ValidParameters.py` (~line 450) and add a
   default in `Tensile/Common/GlobalParameters.py` (~line 500). Add to
   `Tensile/Common/RequiredParameters.py` (~line 169) so it enters the kernel name.

2. **Validate** — add a validator method in `Tensile/SolutionStructs/Solution.py`
   (see `_validatePartialRMS()`), called from `Solution.__init__`. Enforce ISA,
   data type, and mutual exclusions.

3. **Register ProblemType fields** — add to `Tensile/Contractions.py:StateKeys` (~line 70)
   and read from YAML (~lines 249–251).

4. **Write epilogue emitter** — e.g. `Tensile/Components/Subtile/SubtilePartialRMSEmit.py`.
   Implement `emit(accVgprBase: int) -> Module` returning rocisa instructions.

5. **Invoke from KernelWriter** at the global-write path (`KernelWriter.py:5200`):
   ```python
   if kernel["PartialRMS"]:
       module.add(pRmsEmitter.emit(dtile_agpr_base))
   ```

6. **Extend kernel signature** in `Tensile/Components/Signature.py` (~line 334) — add new
   kernel arguments for the new buffers.

7. **Add C++ runtime fields:**
   - `include/Tensile/ContractionProblem.hpp:354` — new tensor slot (e.g. `PARTIALBUF = 19`)
   - `include/Tensile/ContractionSolution.hpp:648` — SizeMapping flag (e.g. `partialRMS`)
   - `include/Tensile/Serialization/ContractionSolution.hpp` — deserialization
   - `src/ContractionSolution.cpp` — append buffer to kernel args

8. **Wire benchmark client** — `client/main.cpp`, `ClientProblemFactory.cpp`,
   `Reference.cpp`, `Tensile/ClientWriter.py`.

The Tensile pipeline (via `python -m Tensile.Tensile`) automatically places outputs in
`3_LibraryLogic/<ScheduleName>_<ProblemType>.yaml`; all variants with distinct
`ProblemType.__str__()` coexist in one merged library dispatched by predicates.

## 3. Internal Mechanism

### Call path: YAML → loaded `.co`

Entry: `Tensile/bin/TensileCreateLibrary` → `Tensile/TensileCreateLibrary/Run.py:run()`:

1. **Load logic** (`generateLogicDataAndSolutions`, line 814) — parses all `.yaml` via
   `LibraryIO.parseLibraryLogicFile`, builds `MasterSolutionLibrary` per arch.
2. **Deduplicate kernels** (`generateKernelObjectsFromSolutions`, line 702).
3. **Code generation** (`writeSolutionsAndKernelsTCL`, line 574) — for each assembly
   kernel, `processKernelSource():220` either runs rocisa codegen or loads the custom `.s`.
4. **Assemble** (`Tensile/Toolchain/Component.py`, `Assembler.__call__` ~line 162):
   ```
   amdclang++ -x assembler --target=amdgcn-amd-amdhsa -mcode-object-version=N \
              -mcpu=gfxNNN -c -o <name>.o <name>.s
   ```
5. **Link** (`Tensile/Toolchain/Assembly.py`, link call ~line 100):
   ```
   amdclang++ --target=amdgcn-amd-amdhsa -Xlinker --build-id=sha1 *.o -o <name>.co.raw
   ```
6. **Bundle/compress** (`Tensile/Toolchain/Assembly.py`, bundler ~line 103):
   ```
   clang-offload-bundler --compress --type=o --bundle-align=4096 ... -o <name>.co
   ```
7. **Write msgpack** — `LibraryIO.writeMsgPack()` at line 262 (dispatcher `write()` at
   line 231) — emits `TensileLibrary_lazy_<arch>.dat`.

### Output directory structure

```
<OutputPath>/
└── library/
    └── gfx942/
        ├── TensileLibrary_lazy_gfx942.dat       # master msgpack (lazy mode)
        ├── <lazyLibName>_gfx942.dat             # per-group sub-library
        ├── TensileLibrary_gfx942.co             # main code object
        ├── <lazyLibName>.co                     # per-lazy-library code object
        └── Kernels.so-000-gfx942.hsaco          # HIP helper kernels

# Temp (deleted unless --keep-build-tmp):
<OutputPath>/build_tmp/<stem>/assembly/<name>.s, <name>.o
```

### C++ runtime — selection and dispatch

`tensile_host.cpp:TensileHost::initialize():2765` is called once as a lazy static:
- Probes `HIPBLASLT_TENSILE_LIBPATH` env or locates the lib next to `librocblaslt.so`.
- Calls `TensileLite::LoadLibraryFilePreload<ContractionProblemGemm>(path)` at line 2922 —
  deserializes msgpack into `MasterSolutionLibrary`.
- Calls `adapter.initializeLazyLoading()` at line 2954 — `hipModuleLoad`s helper kernels.

Per-call dispatch:
1. `library->findBestSolution(problem, hardware)` — traverses the predicate tree
   (`MatchingLibrary.hpp`, `PlaceholderLibrary.hpp`).
2. Returns `KernelInvocation` with `kernelName` and `codeObjectFile`.
3. `SolutionAdapter::launchKernel():517` (`HipSolutionAdapter.cpp`):
   - `FindCodeObject()` at line 279 → `hipModuleLoad(&module, path)`.
   - `hipModuleGetFunction(&fn, module, kernelName.c_str())` at line 356.
   - `hipModuleLaunchKernel(fn, ...)`.

## Specific Questions

### Can I pass a raw `.s` / `.hsaco` and skip code generation?

**Partially yes, partially no.**

You can supply a hand-written `.s` file via the `CustomKernelName` mechanism —
TensileLite reads it verbatim and runs the normal assemble/link/bundle pipeline
(`CustomKernels.py:48`, `getCustomKernelContents():41`).

You **cannot** inject a pre-built `.co` or `.hsaco` directly. `TensileCreateLibrary`
always assembles from `.s` source. No `--prebuilt` or `--custom-object` CLI flag exists
in `Tensile/TensileCreateLibrary/ParseArguments.py`.

### Are there kernel naming conventions that must be respected?

**Yes.** The name is produced by `getKernelNameMin()` in `Tensile/SolutionStructs/Naming.py:242`,
which calls `_getName()` at line 148:

```
<ProblemType>_MT<M>x<N>x<DepthU>_MI<m>x<n>x<b>_SN_<abbrev><val>...
```

Example: `Cijk_Ailk_Bljk_HHS_BH_Bias_GG_AS_SAV_UserArgs_MT64x64x16_MI32x32x8x1_SN_...`

Any parameter listed in `Tensile/Common/RequiredParameters.py` is concatenated into the
name. The `.globl` and `.amdhsa_kernel` directives in assembly must match this name
exactly. These are emitted by `SignatureKernelDescriptor::toString()` in
`rocisa/rocisa/include/code.hpp` (~line 1414), using `writer.states.kernelName` set from
`getKernelNameMin()`.

For custom kernels, `_getName()` returns the `CustomKernelName` string verbatim
(`Naming.py:151`). The `.s` filename (without extension), the YAML field value, and
the assembly symbol must all match exactly.

**Maximum name length:** `MAX_FILENAME_LENGTH = 64` (`Tensile/Common/Constants.py:19`).
When exceeded, `shortenFileBase()` at `Naming.py:220` keeps the first 48 characters (pivot
= `MAX_FILENAME_LENGTH * 3 // 4`) and appends a 44-character base64-encoded SHA-256 hash
of the remainder, yielding a 92-character name.

### Can I skip the benchmark phase?

Yes. Use `TensileCreateLibrary` directly with pre-authored logic YAMLs (as
`epilogues/scripts/build_library.sh` does after the Tensile benchmark phase). This skips
re-running benchmarks and goes straight to assembly + msgpack generation from existing
`3_LibraryLogic/` outputs.
