## 1. TL;DR

- rms costs +24.9 us (+18.8%) of wall time over `none`; beta costs +12.0 us (+9.1%). The rms/beta epilogue cost ratio is 2.07 on wall time, 2.31 on PMC-regime time and 2.51 on GRBM cycles.
- The MFMA work is identical (8,388,608 bf16 + 15 i8 prologue MFMAs x 512 x 4 in every variant), so MFMA utilisation (61.2% none, 53.3% beta, 44.6% rms) drops only because the denominator grows.
- About 60% of rms's extra wave-cycles are dependency waits (`s_waitcnt`); for beta about 75% are issue waits. The two epilogues stall in different places.
- Operand loads are ideal for `none` only (exactly 8 L2 read requests per `buffer_load_dwordx4`; see the section 5 caveat for rms and beta). beta's C reads reach L2 at 128 B per request; rms's residual reads (baseline) at about 64 B per request.
- rms reads about twice the expected extra bytes over the fabric: +133.9 MB against 67.1 MB of logical residual. Fabric write bytes are close to compulsory: 136.9 MB against 134.7 MB, where 134.7 MB = D (2048 x 16384 x 2 B = 67.1 MB) + ResidualOut (67.1 MB) + a 0.52 MB partial-sum buffer. The doubling is in the write-request count: `TCC_WRITEBACK_sum` is 2,094,150 for rms against 524,400 for none (4.0x none, and about 2x the 1.05 M compulsory 128 B lines). L2 hit rate falls from 77.9% (none) to 59.7%. Root cause (the pair order is confirmed by the fix in section 3.6): each 64 B residual load covers half of a 128 B line, and the column-fastest pair order requested the partner half 16 pairs later, after the line had been evicted (inferred from the 6 MB vs 4 MB estimate, not measured), so every 64 B request cost a 128 B fabric read.
- Fix result (post-fix, section 3.6): interleaving the mp-pairs per column cut `TCC_EA0_RDREQ_128B_sum` from 2.62 M to 2.10 M (parity with beta), `TCC_WRITEBACK_sum` from 2.09 M to 1.06 M (the compulsory count), raised L2 hit rate from 59.7% to 71.7% and lowered the wall median from 157.5 to 148.6 us (-8.9 us, about 5.6%). beta and none are unchanged within noise. The fix applies only to T_M % 4 == 0; T_M = 2, 6 and 10 keep the old order and the 2x amplification.
- Occupancy is not a variable: 1 WG/CU, 4 waves/CU, 1 wave/SIMD in all three variants (limiter: VGPR; LDS also gives 1).
- icache is not a driver (hit rate 99.77-99.79%). LDS bank conflicts exist only in beta and none (from static `ds_bpermute_b32`), not in rms.
- ATT traces (one post-warmup dispatch per variant) were collected and decoded by rocprofv3's default decoder, but were not analysed for this document (section 6).

## 3. Where the epilogue cost comes from

### 3.1 Instruction widths (from disassembly)

Disassembled with `/opt/rocm/llvm/bin/llvm-objdump -d --mcpu=gfx950` from the code objects named in `variants.json`; label ranges were read from the emitted `.s` files under `tensile/1_BenchmarkProblems/<problem>/00_Final/caches/<hash>/source/build_tmp/SOURCE/assembly/`. Static opcode counts per kernel:

| Opcode | rms | beta | none |
|---|---:|---:|---:|
| `buffer_load_dwordx4` | 96 | 64 | 64 |
| `buffer_load_dwordx2` | 0 | 128 | 0 |
| `buffer_load_dword` | 1 | 0 | 0 |
| `buffer_load_short_d16` | 257 | 256 | 0 |
| `buffer_store_dwordx4` | 64 | 64 | 32 |
| `buffer_store_dwordx2` | 0 | 192 | 96 |
| `buffer_store_dword` | 32 | 0 | 0 |
| `buffer_store_short` | 512 | 512 | 256 |
| `ds_bpermute_b32` | 0 | 256 | 128 |

Where the static counts sit:

- rms: 64 of the 96 `buffer_load_dwordx4` are the GEMM prologue and 32 are the residual loads. The epilogue has a wide arm (rowExtent % 8 == 0, taken here since M = 2048) and a `label_rms_narrow` arm. The wide arm holds the 32 residual loads, the 1 `buffer_load_dword` (the gamma load into LDS), all 64 `buffer_store_dwordx4` and 16 of the 32 `buffer_store_dword`. The narrow arm holds all 257 `buffer_load_short_d16`, all 512 `buffer_store_short` and the other 16 `buffer_store_dword`. The narrow arm is a fallback that is not executed: the per-wave read count (1,090 VMEM reads = 1,024 + 2 x 33, i.e. 2 tiles x (32 residual + 1 gamma) loads) rules out the narrow arm, whose 257 `buffer_load_short_d16` would add far more read instructions.
- beta: the epilogue is emitted as separate beta == 0 and beta != 0 arms, each with a full-vector and an edge/fallback variant. `label_GW_B0_FD0_VW4_GSU1_NonEdge` (beta == 0) and `label_GW_B1_FD0_VW4_NonEdge_Deferred` (beta != 0) each hold 128 `ds_bpermute_b32`, 32 `buffer_store_dwordx4` and 32 `buffer_store_dwordx2`. The B1 arm additionally holds 64 `buffer_load_dwordx2`. The VW1 labels (`label_GW_B1_FD0_VW1_Then_Deferred`, `label_GW_B0_FD0_VW1_Then_Deferred`) hold the `_short` loads and stores, and the `Then_Deferred` VW4 labels hold the remaining 64 `buffer_load_dwordx2` (B1) and `buffer_store_dwordx2` (B1 and B0); by label name these are edge and fallback paths, and the counters show only one set of 64 C loads per wave-tile executing.
- none: one beta == 0 path, with the same 128 `ds_bpermute_b32`, 32 `buffer_store_dwordx4` and 32 `buffer_store_dwordx2` as beta's B0 NonEdge arm, plus its own `_short` and `Then_Deferred` fallbacks.

Notes:

- rms residual loads are `buffer_load_dwordx4` (16 B per lane, 1 KiB per instruction, 32 per wave-tile). beta C loads are `buffer_load_dwordx2` (8 B per lane, 64 per wave-tile, issued in a back-to-back batch of 36 then a decreasing `vmcnt` drain).
- rms D and ResidualOut stores are both `buffer_store_dwordx4`, with no `ds_bpermute_b32`. The counters agree: VMEM write instructions (163,840) are 2 x 65,536 + 32,768, and each D or ResidualOut instruction produces 16 L2 write requests, the same as `none`.
- rms's partial-sum buffer is written with 32,768 `buffer_store_dword` instructions (the extra 32,768 write instructions). I did not tie these to bytes per instruction.
- The rms residual-load address pattern is 16 columns x 64 B per instruction at a 4096 B column pitch (D is column-major, M contiguous). This is verified from the asm address arithmetic, not from a counter: the lane decode gives c = lane & 15 (column) and g = lane >> 4, each lane loads 16 B (8 bf16 rows) at row offset (g & 1) x 16 + (g >> 1) x 8, so the 4 row-groups cover 32 contiguous rows = 64 B per column, and the address is (column x rowExtent + row) x 2 B, a 4096 B pitch for rowExtent = 2048. That is why one instruction produces 16 requests of 64 B, where an operand `dwordx4` load produces 8 requests of 128 B.
- beta's static C loads, all in the beta != 0 arm: 128 `buffer_load_dwordx2` (2x the wave-tile area of 64), of which 64 are in the executed `label_GW_B1_FD0_VW4_NonEdge_Deferred` (the 36-load batch is its first part) and 64 are in `label_GW_B1_FD0_VW4_Then_Deferred`; plus 256 `buffer_load_short_d16` in `label_GW_B1_FD0_VW1_Then_Deferred` (the VW1 edge fallback). Counting every C-load form gives 64 + 64 + 256 = 384 = 6 x the wave-tile area (MIWaveTile 4x16 = 64). Only 64 C loads execute per wave-tile (counter delta of 128 loads per wave over two tiles), all in the `NonEdge_Deferred` arm.
- beta's static `ds_bpermute_b32` count (256) likewise splits 128 in `label_GW_B0_FD0_VW4_GSU1_NonEdge` (beta == 0 path, not executed in this run) and 128 in `label_GW_B1_FD0_VW4_NonEdge_Deferred` (executed). The executed bpermute path is therefore the same 128-instruction path that `none` runs, which is why beta's `SQ_LDS_BANK_CONFLICT` (524,288) equals none's.

### 3.2 Request granularity and fabric traffic

- beta: 524,288 extra L2 read requests x 128 B = 67.1 MB, matching the logical C volume. Nothing is amplified.
- rms: 1,050,624 extra requests x 64.1 B = 67.4 MB at the TCP, yet the fabric delivers 133.9 MB of excess reads (66.8 MB beyond the logical residual) and L2 loses about 0.42 M hits (6.97 M vs 7.40 M for none).
- rms writes: `TCC_WRITEBACK_sum` is 2.094 M against about 1.05 M for 134.7 MB of compulsory output at 128 B lines (none: 0.524 M for 67.1 MB), and each writeback produces about one 64 B EA write (2.139 M / 2.094 M). The write bytes are near compulsory (136.9 MB); only the request count doubles. That pattern is what half-dirty lines evicted twice would look like. Post-fix, `TCC_WRITEBACK_sum` fell to 1.056 M, the compulsory count (section 3.6).
- Root cause (pair order confirmed, eviction inferred; section 3.6): `_loadRawWide` makes each residual `buffer_load_dwordx4` cover 64 B per column (32 contiguous rows), half of a 128 B line. The other half (rows +32..63) belongs to pair mp+1 of the same column. The baseline traversal was column-fastest (`n = t % T_N`, `mp = t // T_N`); for this config T_M = 4 gives 2 pairs and T_N = 16, so the partner half was requested 16 pairs later. That the line had been evicted by then is inferred, not measured, and every 64 B request cost a 128 B fabric read. Supporting estimate (not measured): the per-XCD traffic between the two halves is about 6 MB (128 waves x 32 KB read, plus 64 KB written, per tile, halved), larger than the 4 MB L2 per XCD. The 4 MB per-XCD figure is the MI300-series value (rocminfo reports 4096 KB L2 and a 128 B cacheline for the agent); the pipeline did not measure it, and the fix result does not measure it either. Operand-tile pollution of L2 is not excluded. A supporting counter relation: L2 misses (`TCC_MISS_sum`) exceed EA 128 B reads (`TCC_EA0_RDREQ_128B_sum`) by an amount that tracks `TCC_WRITEBACK_sum` in all three variants: rms 4.70 M - 2.62 M = 2.083 M against 2.094 M writebacks, none 2.10 M - 1.57 M = 0.526 M against 0.524 M, beta 2.62 M - 2.10 M = 0.526 M against 0.524 M. This is consistent with misses that are served without a 128 B fabric read (for example partial-line write allocations) being about four times more frequent in rms, but the counters do not identify the mechanism. The relation still holds post-fix: rms 3.152 M - 2.098 M = 1.054 M against 1.056 M writebacks, while none and beta are unchanged (0.526 M against 0.524 M). In rms the gap is now about twice none's, in line with the doubled output (D plus ResidualOut), not four times.
- The reorder experiment was run; see section 3.6 for the fix and the post-fix counters.

### 3.3 Stalls and dependency waits

- Extra wave-cycles per wave over `none`: rms +59,140, beta +28,768. From the wait pass: rms's extra is about 60% dependency wait (`SQ_WAIT_ANY` +10.2 M of +17.0 M), 17% issue wait and 21% active; beta's extra is about 75% issue wait, 19% active and 6% dependency wait.
- Per-access address math in the rms epilogue (`v_mul_lo_u32`, `v_cmp`, `v_cndmask`) is present in the asm, but the counters do not isolate its cost, and no share is derived here. The extra `SQ_ACTIVE_INST_VALU` (+4.74 M, 27.9% of the +17.0 M extra wave-cycles) exceeds the extra `SQ_ACTIVE_INST_ANY` (+3.55 M, 20.9%), so these counters are not subsets of one another in the obvious sense (VALU active time can overlap what other categories account for), and the 28% figure is neither a bound nor an additive share of the wave-cycle breakdown. It only says that a large part of the extra work is VALU instructions.
- Contributing factors consistent with the data: rms keeps only 4 loads in flight per wave (RMSEpiloguePrefetchDepth 4, about 4 KB) against beta's 36 (about 18 KB), and `s_waitcnt vmcnt(0)` drains the GEMM loads before the epilogue starts (the "drain GEMM loads before epilogue" `s_waitcnt vmcnt(0)` at the start of the "Global Write Elements" block of the rms `.s` file, `Cijk_Alik_Bljk_BBS_H_RMSE_UserArgs_MT256x256x64_8qoBy1j8g4RysoLsLeuGpzH-mBJ5oJsMA7ETIl1codk=.s`, line 2595).
- At 1 wave/SIMD no second wave hides a wait, so every wait lands on the critical path.

### 3.4 MFMA dilution and occupancy

- `SQ_VALU_MFMA_BUSY_CYCLES` is 135,200,768 in all variants. MFMA utilisation is that numerator over `4 x GRBM_GUI_ACTIVE x CU`, so the 61.2 to 44.6 drop is entirely cycle dilution (cycles +37.2% for rms, +14.8% for beta).
- Occupancy is identical across variants (VGPR 120 + 384 = 504 allocated, LDS 128 KiB, 1 WG/CU). The epilogue cost is not an occupancy effect.

### 3.5 Burst-bandwidth sanity check

All 256 WGs enter each epilogue round together, so average HBM bandwidth (37.5% of peak for rms) hides the burst. If the extra fabric bytes were moved at the 8 TB/s peak, rms would need 203.7 MB / 8 TB/s = 25.5 us against 24.9 us observed (ratio 0.98), and beta 67.2 MB / 8 TB/s = 8.4 us against 12.0 us (ratio 1.43). The rms match with a literal peak-rate burst is not physically plausible as sustained HBM bandwidth, so this does not establish a bandwidth bound.

### 3.6 Fix: interleaved pair order (post-fix validation)

All figures in this section are post-fix unless marked baseline. Post-fix values come from `/home/fmoracor/epilogue-profile-fix/` (`metrics_wide.csv`, `metrics_long.csv`), baseline values from `/home/fmoracor/epilogue-profile/`. After the profile run, the emitter received comment- and docstring-only edits, which is why its mtime is later than `run_metadata.json`. A reviewer confirmed the edits were comment-only, and the profiled assembly in `/home/fmoracor/epilogue-profile-fix/` shows the interleaved order (t=1 is mp=1, n=0; t=2 is mp=0, n=1) and 8 `ds_read_b64`.

**What changed and why**

- `_loadRawWide` makes each residual load cover 64 B per column, half of a 128 B line; the partner half belongs to pair mp+1 of the same column. The fix makes the emitter visit the pairs so that both halves are requested in adjacent instructions.
- New `_pairOrder()` in `Components/Subtile/RMSEpilogueEmit.py`, with an `interleavePairs` flag. When `(T_M // 2) % 2 == 0` (T_M a multiple of 4), pairs (2q, n) and (2q+1, n) are visited back to back. Measured: the partner half no longer generates its own L2 request or fabric fetch (section 3.6). Inferred: it is served in the TCP, as a hit or a merge.
- The earlier suggestion in this document was "n-outer, mp-inner". The implemented order is equivalent for the pinned config, where T_M / 2 = 2 pairs per column.
- The per-column ssq summation order is unchanged (mp ascending per n), so the order of the floating-point accumulation is the same as before.
- Gamma uses one bank per mp parity, so the LDS gamma read is still once per mp and the `ds_read_b64` count stays at 8. VGPR, SGPR and occupancy are unchanged for the pinned kernel: 120 + 384 = 504 VGPRs, 96 SGPRs, 1 WG/CU (`resources.*` and `occupancy.*` are identical in both runs).

**Interpretation**

- The drop in `TCC_EA0_RDREQ_128B_sum` is 520,794, against the residual's 524,288 lines (67.1 MB / 128 B): the residual is now read from the fabric once. rms is within 826 requests of beta (2,097,978 against 2,097,152), and excess fabric reads against none fell from 133.9 MB to 67.3 MB, against 67.1 MB logical.
- `TCP_TCC_READ_REQ_sum` also fell, by exactly 524,288 (and `TCC_REQ_sum` by 524,272). The second half therefore no longer reaches L2: it is served in the TCP (inferred: a vL1D hit or a merge into the in-flight line; the counters here do not separate the two). vL1D hit rate rose from 60.7% to 62.4%. The remaining 2,048 TCP-to-L2 requests above beta equal the baseline's excess over twice beta's (1,050,624 - 2 x 524,288 = 2,048); by the per-wave read count I attribute them to the gamma loads, which I did not verify with a counter.
- `TCC_WRITEBACK_sum` dropped by 1,038,367 (-49.6%) to 1,055,784, which is the compulsory count (about 0.524 M for D plus about 0.524 M for ResidualOut). It is 2.01x none's 524,400 because rms writes two output streams. Each writeback now carries about two 64 B EA writes (2,108,474 / 1,055,784 = 2.0, the same ratio as none and beta), where in the baseline it carried about one (2.139 M / 2.094 M). The doubled write-request count described in section 3.2 is therefore gone. That the same half-line mechanism caused it is inferred from the two moving together under the same code change; no counter isolates the write-side mechanism. Fabric write bytes were already near compulsory and still are (134.9 MB against 134.7 MB).
- The `TCC_MISS_sum - TCC_EA0_RDREQ_128B_sum` relation still tracks `TCC_WRITEBACK_sum`: 1.054 M against 1.056 M for rms (baseline 2.083 M against 2.094 M), and unchanged for beta and none. The miss drop of 1.550 M is about the sum of the read drop (0.521 M) and the writeback drop (1.038 M), 1.559 M.
- What remains between rms and beta: wall +3.8 us (baseline +12.9), PMC-regime +10.4 us (baseline +20.1), GRBM cycles +25,150 (baseline +48,263), wave-cycles per wave +16,369 (baseline +30,372). Against none the wall cost is +18.5 us (baseline +24.9), PMC +25.8 us, cycles +64,392 (baseline +80,202); the wall figure uses none's own post-fix median, which moved by -2.5 us (see Timing noise below). Memory-side differences that remain: L2 hit rate 71.7% against beta's 73.9%, `TCC_MISS_sum` +0.53 M and `TCC_WRITEBACK_sum` +0.53 M (both from the second output stream), 67.8 MB more fabric writes (the compulsory ResidualOut), and rms `SQ_WAIT_ANY` of 13.5 M against 6.1 M for beta (baseline 15.9 M). Reads are at parity, so the remaining gap is not read amplification. I did not isolate its cause; the section 3.3 factors (prefetch depth 4, `vmcnt(0)` drain, the extra write stream) are still hypotheses.
- Dependency waits fell with the fix: `SQ_WAIT_ANY` 15.92 M -> 13.52 M, the dependency share 24.9% -> 22.6%, while `SQ_ACTIVE_INST_ANY` (22.69 M) is unchanged. They are still the largest rms-over-none difference (+8.0 M against +10.2 M in the baseline).

**Scope**

- Applies only when T_M % 4 == 0. T_M = 2, 6 and 10 keep the old order and the 2x amplification, because the partner half then belongs to the neighbouring wave.
- The VGPR, SGPR and occupancy statements above are measured on the pinned kernel only. The other tile shapes were correctness-tested but not profiled.

**Correctness and validation**

- The correctness harness passed 20/20: bf16 with T_M = 12, 10, 6 and 4 (including narrow-arm sizes) and mxfp8 with T_M = 8 and 6. The bf16 T_M = 8 config in `correctness_bf16.yaml` is rejected by an unrelated pre-existing solution check ("UseCustomMainLoopSchedule=1 is incompatible with UseSubtileImpl"), so T_M = 8 is covered only by mxfp8.
- `validation.csv` post-fix: PASS=186, INFO=12, WARN=0, FAIL=0 (the baseline has the same counts).
- 28 unit tests passed, including the new `Tests/unit/test_rms_epilogue_pair_order.py`.
- The pinned MI config `[16,16,32,1,1,4,16,4,1]` was added to `epilogues/YAMLs/correctness_bf16.yaml`.

**Timing noise**

- Run-to-run spread is large: the wall min-to-max range for rms is 152.1-166.7 us (baseline) and 139.5-159.9 us (post-fix), 14.6 and 20.4 us wide; beta is 135.2-154.6 -> 132.7-152.7 us, and none 115.6-138.9 -> 117.6-139.2 us (19-23 us wide).
- The rms shift is nevertheless consistent across statistics: wall median -8.9 us, wall mean -9.3 us (158.08 -> 148.75), PMC-regime median -9.5 us (the PMC regime has far lower spread: for rms, the std over 660 dispatches is 1.94 us post-fix and 2.81 us baseline). beta and none PMC medians moved by +0.2 us each, and their GRBM cycles by +1.6% and -1.5%. The wall medians of beta (+0.3 us) and none (-2.5 us) are within their run-to-run spread, but the none movement means the rms-over-none wall delta is less stable than the rms absolute numbers.
- The cause of the rms shift is supported by the counters (read requests, misses and writebacks fell by the amounts predicted), not only by timing.

## 5. Measurement caveats

- The PMC regime differs from the timing regime: PMC-regime duration over timing-regime duration is 0.919 (rms), 0.862 (beta) and 0.824 (none). Wall-time microseconds come from the timing regime only.
- The cost ratios differ by basis (rms/beta 2.07 wall, 2.31 PMC time, 2.51 GRBM cycles). The implied per-variant clocks (check V16, `implied_sclk_mhz`) are rms 2050, beta 1935 and none 1971 MHz (5.8% spread of the mean), all below the rocm-smi probe clocks (2169, 2134.5, 2103 MHz). `grbm_coverage_of_pmc_duration` (0.945 rms, 0.906 beta, 0.937 none) is algebraically `implied_sclk_mhz / sclk_probe_mhz` (check V19), so it is not independent evidence, and a value below 1 can equally mean that the clock was below the probe or that `GRBM_GUI_ACTIVE` does not span the full kernel-trace interval. The difference between the cycle-basis and PMC-time-basis ratios comes from this per-variant implied-clock spread; the data cannot distinguish a real clock difference from `GRBM_GUI_ACTIVE` not spanning the trace interval. Run-to-run wall time varies by a few us, so differences of 1-2 us (for example the +0.3% match with the YAML header) are not meaningful.
- `ideal_operand_over_total_l2_read_req` is 1.000 only for `none` (rms 0.889, beta 0.941), so the statement that operand loads are ideal applies to `none` alone. The sub-1 values are fully explained by the added epilogue requests (rms: 8,388,608 / (8,388,608 + 1,050,624) = 8,388,608 / 9,439,232 = 0.889; beta: 8,388,608 / (8,388,608 + 524,288) = 8,388,608 / 8,912,896 = 0.941) and do not indicate worse operand coalescing. Operand ideality for rms and beta cannot be checked independently, because their epilogue requests are derived as total minus `none`'s.
- Each counter group is a separate pass, so cross-pass ratios (for example VALU active against wave-cycles) carry a few percent of pass-to-pass noise.
- The rocprof-compute "Coalescing" metric is 25% for full-exec wave64 and is not an efficiency metric. vL1D hit rate is at least 50% by construction.
- On gfx9 `vmcnt` counts loads and stores. `SQ_WAIT_ANY` therefore cannot separate waits on residual loads from waits on store drain.
- The 4 MB per-XCD L2 interpretation, the `TCC_WRITEBACK` definition and any Little's-law latency estimate are unverified.
