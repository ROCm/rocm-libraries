Agent 2 overdesign/simplification review - final

Scope:
- Branch: users/alvasile/ring_buffer
- Diff reviewed: git diff origin/develop...HEAD -- .
- Focus: overcomplication, over-design, and opportunities to preserve behavior with less code and fewer concepts.

Verdict:
The branch contains useful seams for testability, but several of them have turned into durable abstractions rather than narrowly scoped helpers. The main simplification opportunity is to collapse ring-slot state, tensor copy/reset planning, and scheduler collaborator indirection back toward the actual behavior they support.

Findings:

1. Medium - `DataInitialization` now keeps two mutable representations of the same ring-slot state.

`MemoryInput` owns `current`, `batch`, and per-slot `buffers[]`/`batchBufs[]` in `client/include/DataInitialization.hpp:916-979`. The new `GpuInputSlotSet` separately owns per-slot `ptrs`, `batchPtrs`, and `cachedInputs` in `client/include/GpuInputSlotSet.hpp:16-33` and `client/include/GpuInputSlotSet.hpp:35-74`. `DataInitialization` then has to reconcile the two representations in `activateRingSlot()` by walking every pristine tensor and also replacing `m_gpuPtrs`, `m_gpuBatchPtrs`, and `m_cachedGPUInputs` (`client/src/DataInitialization.cpp:4338-4350`).

That creates a standing invariant that two containers must agree on the active slot and on which vector state describes that slot. This is the kind of duplication that stays expensive: every future change to slot lifetime, grouped GEMM handling, swizzle staging, or batch pointers has to remember both representations. A simpler shape would keep one slot-owned representation plus an active slot index, and only derive the legacy `m_gpuPtrs`/`m_gpuBatchPtrs` view at the `ProblemInputs` boundary.

2. Medium - The copy/reset path is over-abstracted into a plan/executor/apply framework that production does not reuse.

The model is defined in `client/include/DataInitialization.hpp:1005-1030`; the two planners duplicate pointer-selection logic in `client/src/DataInitialization.cpp:936-1149`; execution is another full pass in `client/src/DataInitialization.cpp:1216-1287`; and result application is a third pass in `client/src/DataInitialization.cpp:1289-1387`. The production wrappers immediately run plan -> execute -> apply in `client/src/DataInitialization.cpp:1389-1415` and `client/src/DataInitialization.cpp:3210-3243`.

There is no production consumer that stores, transforms, combines, or reorders these plans. The abstraction mainly exposes implementation structure to tests: `tests/DataInitializationCopyPlan_test.cpp:33-50` subclasses `DataInitialization` to reach protected planner/executor methods. The same behavior could be preserved with one direct tensor loop parameterized by destination slot and "outputs only", plus smaller helper functions for pointer selection and bounds mode handling. That would remove the internal DSL while still keeping the copy engine injectable for async/recording behavior.

3. Medium - `ClientRunScheduler` became a small OO dependency framework for one production caller.

The scheduler header defines callback/config/dependency structs and four virtual interfaces (`client/include/ClientRunScheduler.hpp:25-43`, `client/include/ClientRunScheduler.hpp:45-100`, and `client/include/ClientRunScheduler.hpp:102-122`). `main.cpp` then adds four adapter classes whose bodies only forward to `MetaResultReporter`, `DataInitialization`, `SolutionIterator`, and `SolutionAdapter` (`client/main.cpp:894-1037`), instantiates them at `client/main.cpp:1253-1256`, and passes raw pointers through `ClientRunSchedulerDependencies` at `client/main.cpp:1274-1284`.

The tests mirror that object graph with recording fakes (`tests/ClientRunScheduler_test.cpp:250-332` and `tests/ClientRunScheduler_test.cpp:407-553`). Extracting the loop is reasonable, but this is more indirection than the current extension point needs. A concrete helper/free function taking the existing collaborators plus a narrow callbacks struct for HIP-only side effects would preserve testability without making reporter/data/solution/launcher into new project-level interfaces. The pure policy pieces in `ClientRunPolicies` can remain separately testable.

4. Low - `OutputResetPlan` carries metadata that production never uses.

`reason`, `requiresPristineGpuCopy`, `usesExistingSlotContents`, `targetIsRingSlot`, and `targetSlot` are defined at `client/include/DataInitialization.hpp:1040-1056` and assigned in `client/src/DataInitialization.cpp:1152-1214`, but the production call sites branch only on `action` (`client/src/DataInitialization.cpp:4214-4239` and `client/src/DataInitialization.cpp:4452-4471`). The remaining fields are asserted by `tests/DataInitializationOutputResetPlan_test.cpp:129-139` and later expectations rather than driving runtime behavior.

If these fields are explanatory, comments would be cheaper and harder to accidentally treat as policy. If they are intended policy, production should consume them. As written, they expand the domain model without changing the runtime decision.

Caveats:
- Static review only. I did not run builds or tests for this architecture/design pass.
- I reviewed the current branch diff and focused on over-design/simplification, not functional correctness or performance measurement.
