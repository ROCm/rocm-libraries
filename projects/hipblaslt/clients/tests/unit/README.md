# Host-only client unit tests

This directory holds hand-written GTest cases for pure client helpers, e.g. the
string↔enum parsers and scaling-format helpers in `hipblaslt_datatype2string.hpp`.
"Host-only" means no device code and no GPU needed at run time, not plain host
C++: see [Why `hip::device`](#why-hipdevice) below.

## Two targets, one set of sources

Files listed in `HIPBLASLT_HOST_UNIT_TEST_SOURCES` (`CMakeLists.txt`) compile
into two binaries:

1. **`hipblaslt-test`**, so the cases run in the existing hipblaslt PR-CI lane.
   That lane runs `ctest` with label selection against the *installed* tree
   (`bin/hipblaslt/CTestTestfile.cmake`, generated by
   `apply_test_category_labels` for `hipblaslt-test` only), so adding gtest
   cases to that binary needs no install rule and no new ctest entry. See the
   `"*HostUnit*"` pattern in `../test_categories.yaml`, without which the cases
   would be built but never selected.

2. **`hipblaslt-test-hostunit`**, a standalone binary that runs these cases
   without the rest of the matmul suite, on a machine with no GPU. The
   top-level `CMakeLists.txt` installs it next to `hipblaslt-test` so it ships
   in the test artifact and can be pulled straight from a CI run. It is still
   not registered with ctest: a second labelled entry would hit the
   multi-entry sharding hazard that TheRock's `test_runner.py` documents for
   components combining a ctest `--tests-information` stride with gtest
   `GTEST_TOTAL_SHARDS`.

The `"hipblaslt-test"` prefix on the second binary's name is load-bearing.
TheRock picks what goes in the blas test artifact with a
`"bin/hipblaslt-test*"` glob in `math-libs/BLAS/artifact-blas.toml`, so a name
outside that pattern needs a matching change there. Nothing globs that pattern
to decide what to *run* (`test_hipblaslt.py` execs `hipblaslt-test` by exact
path, and `apply_test_category_labels` is called with that one target), so the
extra binary is shipped but never auto-executed.

## Why `hip::device`

Both targets link `hip::device`, not `hip::host`, even though nothing here is
device code: the client headers require compilation as HIP. Without the
`-x hip` that `hip::device` adds via `INTERFACE_COMPILE_OPTIONS` there is no
`__HIPCC__`, and without `__HIPCC__`, `hipblaslt_float8.h` hands out opaque
`struct { uint8_t __x; }` stubs for the f8 and bf8 types while
`auxiliary.hpp`, reached through `hipblaslt_datatype2string.hpp`, calls
`is_nan()` on them. `hip::device` cannot be inherited from
`hipblaslt-clients-common` either: that library is `STATIC` and takes it
`PRIVATE`, so it arrives at consumers as `$<LINK_ONLY:hip::device>`, which
carries no compile options.

## Adding a host-only test

1. Drop the source file in this directory and add it to
   `HIPBLASLT_HOST_UNIT_TEST_SOURCES` in `CMakeLists.txt`. That compiles it
   into both targets described above.
2. Name the suite with a `HostUnit` prefix (e.g. `HostUnitFoo`) so it matches
   the `"*HostUnit*"` pattern in every tier of `../test_categories.yaml`.
3. Prefix each test name with `smoke_`, matching the convention already used
   in `tests/src/caching_library_gtest.cpp`. This is belt-and-braces: it keeps
   the cases selected by `test/therock/test_hipblaslt.py`, which execs the
   binary directly with `--gtest_filter=*smoke*` on its quick tier, in case
   hipblaslt ever moves off the ctest-label path above.

## Enum coverage is enforced by the compiler

`parser_gtest.cpp` and `scaling_format_gtest.cpp` each list every enumerator of
the enum they cover exactly once, in an `X`-macro. That list is expanded
twice: into the name/expectation table the tests iterate, and into a switch
with no `default:` arm, with `-Wswitch` promoted to an error for that block.
Add an enumerator to the real enum without adding it to the list and this
file stops compiling, in the developer's own build, independent of the
enumerator's numeric value.

This matters because nothing else in the codebase raises that signal: the
`*_to_string` helpers all carry `default: return "invalid"` arms, so
`-Wswitch` never fires on them, and `string2hipblaslt_initialization` is a
ternary chain rather than a switch. The runtime sweeps in each test file are a
secondary, weaker check on top of the tripwire: they pin the "values outside
the enum report `invalid`" behavior, but can only catch an enumerator that
falls within the swept range.
