# Pre-generated JIT test kernels

Each directory under an architecture, `gfx90a/`, `gfx942/` or `gfx950/`, holds
generated kernel sources for that processor. Only the generated sources are
committed, not a library entry. `jit-publish` (`library_writer.cpp`) builds
the committed assembly for the current device and publishes its solutions into
the JIT solution library, so the JIT tests need neither Python nor a
generator:

| Path | Contents |
| --- | --- |
| `sources/<kernel>.s` | The main kernel assembly; one or more. Committed |

`readTensileSourceBundle` reads the device's `plain` directory as a source
bundle, which has no `library/` entry, and `TensileliteAssembly::make`
assembles its kernel and builds the solution record from the kernel's own
`custom.config` block (see below): the kernel name, the problem type, the
tile, split-K and scheduling values, the predicates and the argument layout
versions all come from there.
`solution_entry.hpp` publishes that solution as `plain`, for K=512. `plain-pair`
is the plain kernel as two solutions, copies of that solution with typed
fields changed in C++: the first only when K is a multiple of 512, with
WorkGroupMapping 8 and the name suffix `_K512_WGM8`, and the second for any K,
with WorkGroupMapping 1 and the suffix `_WGM1`. Both are published for K=1024,
as one entry, and the second alone for K=256. Adding an architecture needs only
its `plain` sources.

| Sources | Problem and execution policy | Generator command |
| --- | --- | --- |
| `<architecture>/plain` | FP16 A, B, C and D, FP32 compute, A and B not transposed; one wave64 per 16x16 tile, K in steps of 16, no prefetch; GlobalSplitU=1, TileProcessingStrategy=None | `python -m Tensile.SingleSolution ../clients/tests/jit/data/plain.yaml OUT --architecture <architecture> --cxx-compiler amdclang++ --source-only` (`OUT/bundle`) |

The assembly is TensileLite output (MIT licence), generated by the command
above from `plain.yaml` in this directory and the TensileLite sources at
revision `9118578c6b99df2f39ac474ef42807ff518685ef`. One recipe serves every
architecture. The command runs in `projects/hipblaslt/tensilelite` with `OUT`
a fresh directory and `PYTHONPATH` naming the `tensilelite/rocisa` and
`tensilelite` directories of a hipBLASLt build and then
`projects/hipblaslt/tensilelite`. Copy only `sources/*.s` from `OUT`. The
build does not run that command.

The `custom.config` block in each `.s` holds the kernel's complete TensileLite
solution state: every key TensileLite holds after writing the kernel, in the
form `LibraryIO.writeSolutions` writes. The assembler copies it into the code
object's metadata note, which `code_object::metadataNote` reads, and
`TensileLite::solutionFromState`
(`tensilelite/include/Tensile/msgpack/SolutionState.hpp`) builds the kernel's
`ContractionSolution` from it with no Python. Regenerating the assembly
regenerates this block from the same TensileLite run, with the solution and
kernel names equal to the kernel symbol.

The assembly is stale when the `KernArgsVersion` or `PersistentLoopArgsVersion`
in it differs from the one in
`tensilelite/Tensile/Common/GlobalParameters.py`, or the code-object version it
was generated for differs from the version the JIT builder uses. Regenerate it
with the change that made it stale.
