# Python SingleSolution timing plan

Read-only research against published checkout HEAD `bf27d85949b56da1452d376e45044e9b873f68b4`. No code edits, tests, builds, GPU work, Git/PR changes, or monitoring were performed. Paths below are under `projects/hipblaslt/tensilelite/Tensile/`.

## Recommended measurement contract

Use a request-scoped diagnostics context with independent named categories. Allocate a `time.perf_counter_ns()` collector only when the `timing` category is explicitly enabled; `progress` alone emits transitions without timing clocks. Start at the public Python callable before path resolution or request parsing; finish after the callable's normal finalization, on success or exception. Have both SingleSolution and JitGemm share the collector rather than producing nested request totals. Preserve existing CLI stdout (manifest path) and exit/error behavior.

The host's synchronous child-process elapsed time is the primary end-to-end generator invocation metric. Python totals cannot include interpreter startup or module/package imports before the first timer. The difference between host process elapsed and Python callable elapsed is aggregate launch, early import, report-writing, shutdown, and other boundary overhead; it is not a pure Python-startup metric. `_build` has a substantial lazy-import block that can be timed explicitly. Imported `Toolchain.Component` executes a `hipconfig --version` probe at class definition (Component.py:96), so this import span includes that setup work.

Prefer a small, optional collector explicitly threaded through `_generateAndBuild`, `_build`, `writeSolutionsAndKernels`, and the assembly/source builders, with scoped spans at the locations below. Reuse the existing phase boundaries but do not blindly use the existing global timing buffer: `Common/TimingInstrumentation.py:49` uses `time.time_ns()`, stores only category/duration tuples globally, and requires an explicit flush; neither SingleSolution nor JitGemm calls its flush function. A request recorder needs a monotonic clock, request scope, outcomes, and parent/child accounting. If existing timing helpers are adapted instead, preserve legacy disabled behavior/output and prevent cross-request buffer leakage.

## Explicit opt-in categories (revised user direction)

Use the umbrella `HIPBLASLT_JIT_DEBUG` on the C++ host, with the initial named categories `timing` and `progress`. Examples: `HIPBLASLT_JIT_DEBUG=timing`, `HIPBLASLT_JIT_DEBUG=progress`, and `HIPBLASLT_JIT_DEBUG=timing,progress`. Empty/unset disables both. Timing and progress are independent: timing produces the final duration report, progress emits stage transitions while work runs. Neither is implied by the other.

For direct Python CLI use, prefer the equivalent `--debug timing`, `--debug progress`, or `--debug timing,progress`, with no hipBLASLt environment dependency. Default direct output for enabled categories is human-readable stderr: one final timing report and/or flushed progress transitions. Optional explicitly requested versioned timing JSON is separate from those human outputs. These flags are a design proposal, not existing functionality.

The host reads category settings without modifying process-global environment or public C++ ABI. It passes the selected categories plus private request ID/transport paths through child argv. A managed-child transport setting suppresses child human debug output: progress goes to a unique JSONL event file and final timing goes to a separate JSON summary file in the host-owned request workspace (for example, its `.cwd` directory), outside the published bundle. The host renders one combined report and progress stream. Exact private CLI option names are an implementation choice; a transport directory can select the two fixed filenames without exposing multiple unrelated public knobs. No shared append file or global environment mutation is required.

With neither category enabled, add no collector, timestamp calls, observer thread, debug files, or output. Preserve all existing generator logs and build artifacts. With timing only, create no progress stream/observer; with progress only, create no timing summary or timing collector. A future bench flag needs a deliberate per-call propagation path and is not assumed by this plan.

## Progress transport and observation

Current `process::run` is synchronous and redirects child stdout/stderr to its existing log; those streams are not forwarded live. Minimal proposed integration is a request-local observer thread that polls/drains the dedicated progress file while the owner thread calls existing `process::run`. This does not require changes to the runner API or platform spawn/wait implementations. Start observation before launch, signal stop in the host's success/failure cleanup, join, and perform a final drain. Missing event files or truncated/malformed events must never stall cleanup or change the build result. Existing process wait behavior is unchanged; this is not a new timeout mechanism.

Use one child writer with complete newline-terminated JSON records, flushing each meaningful stage transition. A minimal record has `schema_version`, `request_id`, monotonically increasing `seq`, `kind: stage`, `stage`, `transition: start|end`, and an end `status: ok|failed|rejected`. Optional details include candidate ID and published-bundle state. Progress-only records need no timestamp or duration. Reuse the meaningful phase names in the table below, at coarse stage boundaries rather than inside inner generation loops. Candidate validation/rejection can be a child event of selection. A terminal request event says whether the wrapper succeeded and whether publication occurred.

The observer retains an incomplete trailing line until its newline arrives; after child exit it may discard/report a partial final record as incomplete. Check request ID and sequence to avoid cross-request mix-ups. Unknown or malformed records are diagnostics issues, not build failures. A killed child can leave only a stage-start event or no events; host exit/signal status remains authoritative. Direct Python stderr progress is also explicitly flushed. The current builder is serial; if broader parallel code later uses these hooks, send worker data to the parent recorder instead of allowing multiple processes to append directly to the event file.

Timing values remain raw elapsed time. Enabling flushed progress adds some reporting overhead to overall process/callable latency, so record enabled categories and do not compare combined-mode timings as if progress I/O were free. Keep inclusive stage/child accounting explicit; do not invent an overhead subtraction. The finalized timing summary remains separate so its publication measurement and failure semantics below stay intact.

## Concurrency and cache semantics

SingleSolution sets `CpuThreads=1` (SingleSolution.py:343). Its main generation and write/assembly calls use ParallelMap2, but this path is serial; the main kernel count is exactly one. The ordinary shared builder can parallelize other uses. If detailed task timing is later reused there, collect durations and outcomes in worker results and aggregate in the parent; a process-local global buffer will miss worker events. Report phase wall elapsed separately from task duration sum/count/max. Their sum can exceed wall elapsed in a parallel build. Do not infer durations from code-object count or exported symbols.

Helpers use `strict=True` (SingleSolution.py:401), which passes `useCache=False` at Run.py:613. Source.py:134 then does not construct HelperKernelCache at all: no cache eviction, key computation, restore or store. Report `helper_cache=bypassed`, reason `strict_single_solution`; a recipe that emits no helper source unit can report `not_applicable`. Do not call a bypass a miss or imply a hit. `test_toolchain_source.py:14` verifies fresh compilation and forbids cache construction. SingleSolution's existing integration test at324 forbids HelperKernelCache and, for a plain recipe, unnecessary helper emission/compilation.

The normal helper path supports `TENSILE_DISABLE_HELPER_CACHE=1` (also YES/ON/TRUE), `TENSILE_HELPER_CACHE_DIR`, and `useCache=True`; a hit restores files and skips compile/unbundle. Those controls need no new flag for this strict path. `ForceGenerateKernel` is explicitly rejected at SingleSolution.py:175 rather than serving as a runtime force-build option. Compiler launchers (`Tensile_ASM_COMPILER_LAUNCHER`, `Tensile_CXX_COMPILER_LAUNCHER`, Component.py:153,244) and OS/tool caches may still affect elapsed time, so Tensile helper-cache bypass does not prove a wholly cold build. Record relevant configuration; do not change caches or force options for timing.

## gfx1250 ScheduleIterAlg preference and timing metadata

The user's requested public preference is **ScheduleIterAlg=4** for gfx1250. It is not already the generic provider default in the reviewed code: `library/src/amd_detail/hipblaslt-jit-tensilelite-predictor.cpp:340–344` emits MatrixInstruction/DepthU/NonTemporalA/B but no schedule; JitGemm preserves supplied parameters, and BenchmarkProcess fills the existing global default ScheduleIterAlg=3. A later targeted change to provider-generated gfx1250 candidate parameters is needed; do not change the global default, silently override explicit recipes, or add fallback 4-to-3 as part of timing work.

Timing/debug metadata should record the **actual requested and resolved public schedule** separately from internal lowering. For a public SIA4 recipe, internal ScheduleIterAlg becomes 0 with StinkyTofuOptLevel=3 (`Solution.py:845–860`); record all three meanings rather than presenting internal0 as the chosen public recipe. StinkyTofu optimizer execution is real source-generation work and belongs in the generation span. Existing explicit fixtures may request SIA3 and must be reported truthfully until separately changed/validated. In particular, gfx1250 StreamK plus 1LDSBuffer=1 cannot simply be flipped to4: the independent audit found its internal0/SLW1 combination rejected; a later compatible recipe requires deliberate validation. No schedule changes were made in this plan.

## Report transport and failure behavior

When timing is enabled, use an explicitly selected child summary path in the caller-owned request workspace, outside `bundle` and separate from the progress event stream and any host report. Link them with a request ID. Emit a JSON sidecar after the builder/wrapper has completed its success/failure finalization, using a temporary file plus atomic replacement. This permits measuring the final bundle rename without a self-referential manifest update, a second modification of the published bundle, or a loader-schema change. Keep manifest schema 2 and TLJIT001 unchanged; report parsing must not become a requirement for loading a valid bundle.

Fields sufficient initially: schema version, request ID, producer=python, mode=explicit/prediction, enabled debug categories, clock=perf_counter_ns, callable elapsed_ns, status, failure phase/error type, bundle_published, phases with parent/name/elapsed_ns/status, candidate outcomes, main-kernel/helper-source-unit counts, CpuThreads, helper-cache policy, and requested/resolved public schedule plus internal schedule/optimizer level. Store integer nanoseconds; render milliseconds only for humans. Do not record GPU execution timing or confuse predicted cycles with build duration.

Stop the builder timer before serializing its timing report and state that report emission is excluded; the parent's synchronous process duration naturally includes it. Do not rewrite a report merely to include its own final write duration. Optional report-emit duration can be a separate diagnostic event if needed, but is unnecessary for the first version. Timing I/O must be best-effort and must not replace an existing build exception or turn a successful published bundle into a build failure. Every entered span closes in `finally`; unentered phases are absent/not-run, not zero-time successes. Fatal kill/crash can leave no child report or only incomplete evidence; the host retains process elapsed and exit/signal status.
