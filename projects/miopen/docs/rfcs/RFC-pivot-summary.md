# RFC 0001 — Pivot Summary

This document summarizes a set of design changes applied to the MIOpen → hipDNN Forwarding Wrapper RFC (`0001_HipdnnForwardingWrapper.md`) after the initial draft and investigation phase. It is intended for reviewers who saw the earlier draft and need a quick map of what changed, why, and what new risks the changes introduce.

The full pivoted design is in `0001_HipdnnForwardingWrapper.md`; this is the cover page.

## The four changes

1. **Build-time flag → runtime flag.** The earlier draft gated the entire wrapper behind a CMake option (`MIOPEN_ENABLE_HIPDNN_WRAPPER`, default OFF) and the flag-off build was bit-identical to today's MIOpen. The pivoted design always builds the public/private split and governs behavior at runtime via `MIOPEN_HIPDNN_FORWARDING` (values: `disabled`/`enabled`; default: `disabled`). Consumers who don't opt in see today's MIOpen semantics plus a ≈1 ns/call wrapper hop.

2. **Macro-rename header → direct source rename.** The earlier draft (and the prototype) used `-DMIOPEN_BUILDING_PRIVATE -include miopen_private_rename.h` to `#define` each public-API symbol to its `_impl` form at preprocess time. The pivoted design renames the public-API function definitions and internal headers **directly in source**, so the source tree literally contains `miopenFoo_impl`. No `#define`, no forced include, no `MIOPEN_BUILDING_PRIVATE`.

3. **Phase 4 plugin gap → Phase 1 plugin redirect.** The earlier draft's Phase 4 direct-private-API wiring assumed the existing CMake `find_package(miopen)` + conditional `MIOpen_private` link snippet would just work; the investigation showed it did not, because the provider plugin's TUs include `<miopen/miopen.h>` (unrenamed names) while `libMIOpen_private.so` exports only `_impl` names. The pivoted design installs a parallel `<miopen/miopen_impl.h>` header (exposed via `MIOpen_private`'s `INTERFACE_INCLUDE_DIRECTORIES`), and moves the provider rewire into Phase 1 so the loop hazard is structurally removed before any forwarded ops land.

4. **Provider direct private linkage → Phase 1.** Promoted from Phase 4 to Phase 1, coupled with (3). (Earlier drafts referred to this as the "provider short-circuit"; the term was reworded to be explicit about what is actually happening — the provider directly links and calls the MIOpen private API.)

## What concerns this addresses

- **CI doubling under the build-time flag.** The earlier draft expected ~4–6.5 hours per full-arch pipeline run added if both flag-off and flag-on configurations were serialized; even with the matrix parallelized, compute doubled. Single artifact removes the concern entirely.
- **Configuration divergence risk.** With two artifacts, the flag-off artifact is the one anyone ships until the default flips, so it gets the production scrutiny while flag-on (the eventual default) gets only the CI scrutiny. The runtime flag means every consumer exercises the same code paths, so the pass-through path gets continuous real-world coverage.
- **Packaging migration cost of a future default flip.** Under the build-time scheme, flipping the default required every downstream distro/wheel/container to rebuild. Under the runtime scheme it's a one-line change to the env-var parser, picked up on next process start.
- **Operator rollback during the rollout window.** A consumer who hits a regression after the default flips can set `MIOPEN_HIPDNN_FORWARDING=disabled` without rebuilding or replacing the library. The earlier draft only offered per-op opt-out (`MIOPEN_DISABLE_HIPDNN_FOR=*`); the runtime mode flag is a coarser, more obvious recovery lever.
- **Macro-rename fragility surface.** The earlier draft acknowledged two fragility modes for the `-include miopen_private_rename.h` mechanism — silent rewriting of string literals, and load-bearing forced-include order. Direct source rename collapses both to zero by removing the rewrite entirely.
- **Phase 4 plugin load failure.** The investigation discovered that the existing `find_package(miopen)` + `MIOpen_private` link snippet links the right library but `dlopen`-fails because the plugin's TUs reference unrenamed names. Addressed by installing the parallel `_impl` header in Phase 1 so the provider plugin actually loads.
- **Loop hazard between wrapper and provider.** Moving the direct private linkage into Phase 1 means the loop is structurally impossible from before any forwarded op lands. The earlier draft relied on a thread-local recursion guard during the Phase 2–3 window; that guard is no longer needed.
- **Env-var interaction-rule complexity.** Earlier drafts had both `MIOPEN_USE_HIPDNN_FOR=...` and `MIOPEN_DISABLE_HIPDNN_FOR=...`, with a "disable wins over enable" precedence rule. Operators would have had to internalize that precedence and reason about combined effects. Dropping the opt-in env var removes the interaction entirely — the compile-time forwarding set is the truth, and `DISABLE_HIPDNN_FOR` is a one-way override.
- **Redundant `disabled` mode.** Earlier drafts kept `disabled` as an explicit-name synonym for `disabled`, intended for operators who wanted to document "this process is forced to legacy MIOpen behavior." With no opt-in env var in the picture, the two modes were doing identical work; `disabled` was dropped to avoid confusion about whether they meant different things.

## New risks this entails

- **Every shipped MIOpen pays the wrapper hop.** With the build-time scheme, consumers who built flag-off had a literally byte-identical-to-today artifact. With the runtime scheme, every consumer pays the ≈1 ns/call wrapper hop (and the +6 page faults / ≤1 MB RSS cold-load cost). The prototype measurements (investigation reference §4) support this being in the noise on any real workload, but it is now non-optional. Mitigation: `abidiff` against a pre-wrapper baseline snapshot asserts the public symbol set is unchanged; the Phase 1 exit-criteria 2 measurement quantifies the overhead one more time before merging.
- **Loss of the A/B baseline.** The earlier draft used the wrapper-off build as the perf comparison baseline on every CI run. The pivoted design uses the pre-wrapper snapshot only in Phase 1 — after that, `disabled` (same build, same hardware, same day) is the comparison reference for `enabled`. See §8.1 in the main RFC for the policy. The earlier idea of comparing against the pre-wrapper snapshot in Phase 4 was dropped because, by the time Phase 4 runs, the snapshot is months stale and reflects unrelated drift in the rest of the MIOpen stack rather than just wrapper effects.
- **Source-tree churn from direct rename.** The mechanical edit to rename 263 public-API function definitions and their internal-header counterparts is a large but contained diff. It will conflict with any in-flight branch that touches the same `*_api.cpp` files. Mitigation: land the rename early in Phase 1 and communicate the merge window to feature branches. The edit is mechanical enough to be regenerated from `<miopen/miopen.h>` if a branch lands too late and needs to redo the conflict.
- **`<miopen/miopen_impl.h>` maintenance.** The parallel `_impl` header has to stay in sync with `<miopen/miopen.h>`. Generation-time tooling or a CI sync check is on the implementation team to pick. If it drifts undetected, the MIOpen provider plugin and any future `MIOpen_private` consumer breaks silently at compile time.
- **Provider-side coupling in Phase 1.** Moving the provider direct private linkage forward means Phase 1's blast radius now includes the hipDNN-side build (`dnn-providers/miopen-provider/`). The change is contained — one link-target swap and one include swap — but it is no longer a MIOpen-internal-only phase. Mitigation: the `LD_DEBUG=bindings` regression bar (§4.5) is the explicit acceptance gate; coordinate with the hipDNN team on the Phase 1 merge sequence.
- **`test_smoke_tuning_policy` becomes a structural assertion failure rather than a wrapper-induced one.** With direct source rename, the captured `MIOPEN_LOG_FUNCTION` output literally contains `_impl` because the function name in source is `_impl`. The fix chosen — relaxing the test assertion — accepts the `_impl` form as legitimate. The alternative of "normalize the log output back to the public name" was rejected because, under direct rename, that would be hiding the actual control flow rather than reflecting it. The test now asserts what the code actually does.
- **No runtime knob to opt an individual op into forwarding.** With `MIOPEN_USE_HIPDNN_FOR=...` dropped, an operator who wants to try forwarding for an op that is not yet in the compile-time forwarding set cannot do so without a MIOpen patch. This is intentional — staging an op into the forwarding set should be a deliberate MIOpen-developer decision after the op is qualified, not an ad-hoc env var flip in a customer environment — but it does mean that experimentation in the field requires more friction than the earlier two-env-var design allowed.
