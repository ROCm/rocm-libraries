*****************************
Port LLaMA 3 inference to GPU
*****************************

This tutorial walks through porting a minimal LLaMA 3 inference engine from
CPU ``std::thread`` code to GPU ``hip::wthread`` code using hipthreads. The
example lives in the ``examples/llama3.c/`` directory of the hipthreads
repository. It is organized into four incremental steps, each in its own
subdirectory, so you can diff consecutive steps to see exactly what changed.

The progression demonstrates the three core porting patterns for hipthreads:

1. Replace ``std::thread`` with ``hip::wthread`` and ``__device__`` lambdas.
2. Move data structures into GPU memory with ``hip::std::unique_ptr``.
3. Use multi-fiber (SIMD-width) execution with ``hip::wthread::max_width()``
   to parallelize reductions and element-wise loops across the SIMD lanes of
   a single thread.

For installation instructions, see :doc:`/install/install`.

Step 1: CPU baseline with ``std::thread`` parallelism
******************************************************

The first step, ``examples/llama3.c/step1-baseline/llama3.cxx``, is a
pure-CPU implementation. It uses ``std::thread`` to parallelize the
matrix-multiply (``matmul``) kernel across rows and to distribute
multi-head attention across heads. Each call to ``matmul`` creates a fresh
vector of threads, joins them, and returns:

.. code-block:: cpp

   std::vector<std::thread> threads(num_threads);
   for (int t = 0; t < num_threads; ++t) {
     threads[t] = std::thread([=]() {
       for (int i = start_row; i < end_row; ++i) {
         float val = 0.0f;
         for (int j = 0; j < n; ++j)
           val += w[i * n + j] * x[j];
         xout[i] = val;
       }
     });
   }
   for (auto &t : threads)
     t.join();

Activation buffers are allocated with ``std::unique_ptr<float[]>`` and
live in host memory.

Step 2: persistent threads with ``std::barrier``
************************************************

Step 2, ``examples/llama3.c/step2-barrier-cpu/llama3.cxx``, eliminates the
per-call thread creation overhead. It launches a fixed pool of threads once
in ``forward()`` and keeps them alive for the entire token, synchronizing
between phases with ``std::barrier``:

.. code-block:: cpp

   constexpr int num_threads = STD_NUM_THREADS;
   std::barrier sync_point(num_threads);
   std::vector<std::thread> threads(num_threads);

   for (int tid = 0; tid < num_threads; ++tid) {
     threads[tid] = std::thread([&, tid]() {
       // ... forward-pass logic ...
       matmul(s->q.get(), s->xb.get(), w->wq + l * dim * dim,
              dim, dim, tid, num_threads);
       sync_point.arrive_and_wait();
     });
   }

The ``matmul`` signature gains ``tid`` and ``num_threads`` parameters so
each thread computes its own row range without creating sub-threads. This
step is still CPU-only.

Step 3: GPU port with ``hip::wthread``
*************************************

Step 3, ``examples/llama3.c/step3-barrier-gpu/llama3.cxx``, moves execution
to the GPU. The main changes are:

Replacing ``std::thread`` with ``hip::wthread``
--------------------------------------------

The thread body becomes a ``__device__`` lambda:

.. code-block:: cpp

   threads[tid] = hip::wthread([] __device__ (Transformer *t, int token,
                                              int pos, int tid) {
     // ... same forward-pass logic ...
   }, transformer, token, pos, tid);

Device-resident Transformer struct
----------------------------------

Because CPU and GPU have separate
memory pools, the ``Transformer`` struct (containing the model config,
weight pointers, and run-state buffers) is allocated in device memory.
The ``RunState`` uses ``hip::std::unique_ptr<float[]>`` instead of
``std::unique_ptr<float[]>`` so allocations go through device-side
``hip::malloc``:

.. code-block:: cpp

   typedef struct {
     hip::std::unique_ptr<float[]> x;
     hip::std::unique_ptr<float[]> xb;
     // ...
   } RunState;

Placement-new for initialization
--------------------------------

The ``RunState`` is initialized
inside a ``hip::wthread`` using placement-new so that ``hip::std::unique_ptr``
objects are constructed properly on the device rather than default-constructed
on the host and then assigned:

.. code-block:: cpp

   hip::wthread(
     [] __device__ (Transformer *t, float *weights_ptr, int shared_weights) {
       t->weights = memory_map_weights(&t->config, weights_ptr, shared_weights);
       new (&t->state) RunState(malloc_run_state(&t->config));
     }, transformer, weights_ptr, shared_weights
   ).join();

Device-side barrier
-------------------

A device-side barrier synchronizes the 128
``hip::wthread`` instances between computation phases, replacing the
``std::barrier`` from step 2.

Keeping the scheduler alive
---------------------------

The ``generate()`` and ``chat()`` loops
construct a dummy ``hip::wthread`` (``hip::wthread _;``) whose lifetime spans
the token loop. This keeps the persistent scheduler kernel running so that
subsequent ``hip::wthread`` launches inside the loop do not incur
start-up overhead on every token.

For background on the GPU memory model and scheduler, see
:doc:`/conceptual/gpu-memory-model` and
:ref:`execution model <execution-model>`.

Step 4: SIMD parallelism with fibers
************************************

Step 4, ``examples/llama3.c/step4-simdize/llama3.cxx``, uses the multi-fiber
execution model to run multiple SIMD lanes within each ``hip::wthread``.
Threads are launched with the ``hip::wthread::max_width()`` constructor
overload:

.. code-block:: cpp

   threads[tid] = hip::wthread(hip::wthread::max_width(),
     [] __device__ (Transformer *t, int token, int pos, int tid) {
       // ...
     }, transformer, token, pos, tid);

Inside the device lambda, ``hip::this_thread::get_fiber_id()`` and
``hip::this_thread::get_width()`` are used to stripe work across SIMD
lanes. For example, ``matmul`` iterates rows with a fiber stride:

.. code-block:: cpp

   for (int i = start_row + hip::this_thread::get_fiber_id();
        i < start_row + chunk_size;
        i += hip::this_thread::get_width()) {
     // ...
   }

The ``rmsnorm`` and ``softmax`` functions are rewritten to use
block-scoped atomics for parallel reduction across fibers, with
``__syncthreads()`` to synchronize fibers within a single thread.

Build and run
*************

Build the final step:

.. code-block:: bash

   cd examples/llama3.c/step4-simdize
   cmake -B build
   cmake --build ./build

Download and export a model (requires the `Meta LLaMA 3 weights <https://huggingface.co/meta-llama/>`_):

.. code-block:: bash

   python export.py llama3.2_3b_instruct_fp32.bin --meta-llama ../llama3.2-3b-instruct/

Run inference or start a chat session:

.. code-block:: bash

   ./build/bin/llama3 ~/models/llama3.2_3b_instruct_fp32.bin \
       -z ~/models/tokenizer.bin -i "My car" -n 100
   ./build/bin/llama3 ~/models/llama3.2_3b_instruct_fp32.bin \
       -z ~/models/tokenizer.bin -m chat

The program reports tokens per second on stderr when it finishes.

Review :doc:`/conceptual/gpu-memory-model` for details on how
``hip::std::unique_ptr`` and device-side allocation work.
See the :ref:`execution model <execution-model>` for an explanation
of fibers, vcores, and the persistent scheduler kernel.

lambdas, argument types, and synchronization.
Try :doc:`/how-to/tune-scheduler-concurrency` to adjust the number of
