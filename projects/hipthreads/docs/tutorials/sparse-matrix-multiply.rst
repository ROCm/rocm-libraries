****************************************
Port sparse matrix multiplication to GPU
****************************************

This tutorial walks through the ``examples/sparse-mat-mul/`` example in the
hipthreads repository. The example multiplies a sparse matrix by itself,
squaring it, and progresses across four steps from a single-threaded CPU
baseline to a GPU-accelerated ``hip::wthread`` implementation. Along the way
you will see how sparse-matrix data structures migrate from host memory to
device memory and how ``hip::wthread`` replaces ``std::thread`` with minimal
code changes.

The complete source lives in the ``examples/sparse-mat-mul/`` directory:

- ``step1-baseline/main.cxx``, single-threaded CPU
- ``step2-cpu-threading/main.cxx``, multi-threaded CPU with ``std::thread``
- ``step2.5-gpu-data-structures/main.cxx``, GPU-resident data structures
- ``step3-hipthread-port/main.hip``, ``hip::wthread`` GPU port

Two test matrices ship with the example:
``examples/sparse-mat-mul/data/test_general.mtx`` (a small general matrix) and
``examples/sparse-mat-mul/data/shallow_water1.mtx`` (a larger symmetric
matrix). Additional matrices are available in
``examples/sparse-mat-mul/data/matrices.tgz``.

For background on how CPU and GPU memory pools interact and why data must be
explicitly transferred, see :doc:`/conceptual/gpu-memory-model`. For the full
``hip::wthread`` API, see :doc:`/reference/thread-management`.

Sparse-matrix representations
*****************************

The baseline step reads a ``.mtx``, Matrix Market, file into COO
coordinate format, three parallel arrays of row indices, column indices, and
values. Two compressed formats are then derived:

- CSR, Compressed Sparse Row, a ``row_ptr`` array of length
  ``n_rows + 1`` gives the start offset of each row in the ``col`` and
  ``values`` arrays. This is the primary storage format throughout the
  example.
- CSC, Compressed Sparse Column, a ``col_ptr`` array of length
  ``n_cols + 1`` gives the start offset of each column in the ``row`` and
  ``values`` arrays. CSC is built from a CSR matrix to accelerate the
  column-wise access pattern required by the multiply kernel.

The conversion chain is COO → CSR → CSC, and the multiply function uses CSR
for matrix A and CSC for matrix B.

Step 1: single-threaded baseline
********************************

``step1-baseline/main.cxx`` performs the entire multiply on one CPU thread.
The main routine iterates over every row and column pair, walking both the CSR
row slice and the CSC column slice in lockstep to compute the dot product:

.. code-block:: cpp

   double computeEntry(const CSRMatrix &matrixA, const CSCMatrix &matrixB,
                        uint32_t rowA, uint32_t colB) {
       const uint32_t rowA_start = matrixA.row_ptr[rowA];
       const uint32_t rowA_end   = matrixA.row_ptr[rowA+1];
       const uint32_t colB_start = matrixB.col_ptr[colB];
       const uint32_t colB_end   = matrixB.col_ptr[colB+1];
       double sum = 0;
       for (uint32_t entryA = rowA_start, entryB = colB_start;
            entryA < rowA_end && entryB < colB_end; ) {
           const uint32_t colA = matrixA.col[entryA];
           const uint32_t rowB = matrixB.row[entryB];
           if (colA == rowB)
               sum += matrixA.values[entryA] * matrixB.values[entryB];
           if (colA <= rowB) ++entryB;
           if (colA >= rowB) ++entryA;
       }
       return sum;
   }

Because both index sequences are sorted, the merge-style walk visits each
non-zero at most once, which is important for sparse matrices where most
entries are zero.

Step 2: CPU threading with ``std::thread``
******************************************

``step2-cpu-threading/main.cxx`` partitions the output rows across
``std::thread`` instances, giving each thread a contiguous slice of
rows to compute. The per-row logic is identical to step 1. Only the
outer loop is parallelized.

Step 2.5: GPU data structures
*****************************

Before threads can run on the GPU, the CSR and CSC arrays must live in
device memory. ``step2.5-gpu-data-structures/main.cxx`` replaces
``std::unique_ptr`` with device-allocated equivalents and copies the matrix
data to the GPU.

On the GPU side, hipthreads provides ``hip::malloc``, ``hip::free``, and
``hip::memcpy`` for allocations inside ``__device__`` code. Host-side
transfers typically use the HIP runtime (for example ``hipMalloc`` and
``hipMemcpy``) or Thrust utilities to move data before the ``hip::wthread``
kernel runs.

Step 3: ``hip::wthread`` GPU port
********************************

``step3-hipthread-port/main.hip`` replaces ``std::thread`` with
``hip::wthread``. The porting recipe follows the three-step pattern described
in the README:

1. Replace ``std::thread`` with ``hip::wthread``.
2. Add ``__device__`` annotations to lambdas and functions that run on the
   GPU.
3. Manage GPU memory allocation. The CSR and CSC arrays must already reside
   in device memory, prepared in step 2.5.

The multiply kernel launches one ``hip::wthread`` per output row (or a batch
of rows). Each thread calls the same ``computeEntry`` function as the CPU
version, now annotated ``__device__``, and writes its results into
device-resident output arrays. After all threads are joined, the result is
copied back to the host for verification.

Build and run
*************

To install hipthreads, see :doc:`/install/install`. To integrate it with your
CMake project, see :doc:`/how-to/integrate-cmake`.

Build the GPU port (step 3):

.. code-block:: bash

   cd examples/sparse-mat-mul/step3-hipthread-port
   cmake -B build
   cmake --build ./build

Run against the bundled test matrices:

.. code-block:: bash

   ./build/bin/sparse-mat-mul

The program prints the wall-clock time for the matrix-squaring operation for
each test matrix.

Explore the other hipthreads examples in the ``examples/`` directory for
different porting patterns.
Read :doc:`/conceptual/gpu-memory-model` for a deeper look at how host and
device memory interact.
See :doc:`/reference/thread-management` for the complete ``hip::wthread``
API reference.
To tune how many virtual cores the scheduler allocates, see
:doc:`/how-to/tune-scheduler-concurrency`.
