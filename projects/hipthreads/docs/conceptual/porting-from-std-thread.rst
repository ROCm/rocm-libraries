***********************************************
Porting from ``std::thread`` to ``hip::wthread``
***********************************************

hipthreads is designed as a near-drop-in replacement for the C++ Standard Library threading facilities. If you have working CPU code that uses ``std::thread`` and its associated synchronization primitives, you can move that code to an AMD GPU with three focused changes. The familiar threading model, spawn, synchronize, and join, is preserved.

API mapping
***********

The following table shows the ``std::`` primitives and their hipthreads counterparts:

.. list-table::
   :header-rows: 1
   :widths: 40 40

   * - C++ Standard Library
     - hipthreads equivalent
   * - ``std::thread``
     - ``hip::wthread`` (``hip::thread`` is a deprecated alias)
   * - ``std::mutex``
     - ``hip::spin_mutex``, also ``hip::pseudo_mutex``
   * - ``std::lock_guard``
     - ``hip::lock_guard``
   * - ``std::unique_lock``
     - ``hip::unique_lock``
   * - ``std::condition_variable_any``
     - ``hip::condition_variable_any``, also ``hip::spin_condition_variable`` and ``hip::pseudo_condition_variable``

To include these primitives, use the corresponding hipThreads headers, for example ``<hip/thread>``, ``<hip/mutex>``, and ``<hip/condition_variable>``.
For the full mapping with headers, see :ref:`std to hip mapping <std-to-hip-mapping>`.
The ``spin_`` variants busy-wait.
The ``pseudo_`` variants busy-wait but periodically call ``pseudo_yield()``.
Choose a ``pseudo_`` primitive only when you can guarantee no yield-loops occur.
See :ref:`limitations <limitations>`.

The three required porting changes
**********************************

Replace ``std::`` with ``hip::``
--------------------------------

Swap every ``std::`` namespace qualifier for the corresponding ``hip::`` qualifier listed in the mapping table above. For example, ``std::thread`` becomes ``hip::wthread``, ``std::lock_guard`` becomes ``hip::lock_guard``, and so on. The constructor signatures and member functions mirror the standard library counterparts, so the call sites remain structurally identical.

The SAXPY drop-in example changes only the thread type and header:

.. code-block:: cpp

   #include <hip/thread>
   // ...
   std::vector<hip::wthread> threads(hip::wthread::hardware_concurrency());
   threads[i] = hip::wthread(/* callable and arguments */);

Add ``__device__`` to lambdas and functions
-------------------------------------------

Any callable (lambda, function pointer, or functor) passed to ``hip::wthread`` runs on the GPU. You must annotate it with ``__device__`` so the compiler generates device code for it.

.. code-block:: cpp

   threads[i] = hip::wthread(
       [] __device__(uint32_t n, float a, const float *x, float *y) {
           for (uint32_t i = 0; i < n; ++i) {
               y[i] = a * x[i] + y[i];
           }
       },
       chunk_size, alpha, x.get_raw() + offset, y.get_raw() + offset);

Handle separate CPU and GPU memory
----------------------------------

CPU and GPU have separate memory pools. Data that a ``std::thread`` lambda could access directly through a host pointer is not visible to a ``hip::wthread`` lambda running on the GPU. Before spawning GPU threads, you must copy or allocate the relevant data in device memory and pass device pointers as arguments.

For instance, if your CPU code operates on a ``std::vector`` stored in host memory, you need to allocate a device buffer, copy the data to that buffer, and pass the device pointer to the ``hip::wthread`` callable. After the threads complete, copy results back to host memory if needed:

.. code-block:: cpp

   thrust::unique_ptr<float[]> y = thrust::make_unique<float[]>(N);
   thrust::copy(y_host.begin(), y_host.end(), y.get());
   // ... launch hip::wthread with y.get_raw() ...
   thrust::copy(y.get(), y.get() + N, y_host.begin());

For a deeper discussion of GPU memory constraints, see :doc:`/conceptual/gpu-memory-model`.

``TriviallyCopyable`` arguments on the host
*******************************************

When you construct a ``hip::wthread`` on the host, the callable and its arguments must be ``TriviallyCopyable``.
hipThreads transfers them to the device with a bitwise ``memcpy()``, not by invoking a copy constructor.

In practice, this means:

- Scalar types such as ``int``, ``float``, and pointers work without modification.
- Plain-old-data structs containing only scalar types or fixed-size arrays work.
- Standard library containers such as ``std::vector``, ``std::string``, and ``std::shared_ptr`` aren't ``TriviallyCopyable`` and can't be passed as arguments.
  Extract the raw pointer and size from the container on the host side and pass those scalar values instead.

Constructing a ``hip::wthread`` on the device relaxes the ``TriviallyCopyable`` requirement.
The callable and arguments must instead be move constructible and trivially destructible.
See :ref:`limitations <limitations>`.

Preserving the familiar threading model
***************************************

Beyond the three changes described above, the concurrency model is the same one you already know from ``std::thread``. You create threads, pass work to them, and join them when they finish. Mutexes and condition variables coordinate shared-state access in the same way they do on the CPU. This means you can reason about correctness using the same mental model. Data races, lock ordering, and condition-variable wait patterns all apply.

GPU hardware does impose additional constraints not present on the CPU.
For the full list, including restrictions on synchronous HIP calls and cooperative scheduling considerations, see :ref:`limitations <limitations>`.
