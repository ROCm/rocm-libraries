**************************
Synchronization primitives
**************************

hipthreads provides synchronization primitives that mirror the C++ Standard Library's threading facilities. Because GPU hardware has no operating-system scheduler to suspend and resume threads, the library uses different strategies depending on whether threads are independently scheduled or cooperatively scheduled within the same virtual-core group.

Two tiers of synchronization
****************************

hipthreads organizes its synchronization types into two tiers.

Standard synchronization
------------------------

The standard tier is intended for independently scheduled ``hip::wthread`` instances that may run on different virtual cores (vcores) and have no guarantee of cooperative yielding.

``hip::spin_mutex``
   A device-side mutual-exclusion lock that mirrors ``std::mutex``. It is implemented as a spin lock. A wthread that tries to acquire a held lock repeatedly checks the lock state in a tight loop until the lock becomes available. The spin-lock approach is the only viable strategy on GPU hardware because there is no kernel-level thread scheduler that can put a wthread to sleep and wake it later.

``hip::condition_variable_any``
   A condition variable that mirrors ``std::condition_variable_any()``. It works with any lockable type, including ``hip::spin_mutex`` through a ``hip::unique_lock``. Because wthreads can't be suspended by the OS, waiting on this condition variable involves spinning until the predicate is satisfied.

Cooperative and pseudo variants
-------------------------------

The cooperative tier is designed for threads that share a vcore group and yield proactively to one another. These variants can be more efficient because they exploit the cooperative scheduling guarantee: every thread in the group will eventually yield, so the synchronization primitive can use lighter-weight spinning or signaling.

``hip::spin_condition_variable``
   A condition variable optimized for cooperative scheduling. It assumes that the notifying thread and the waiting thread belong to the same cooperative group and that threads yield voluntarily.

``hip::pseudo_mutex``
   A mutex variant for cooperatively scheduled threads. Because cooperative threads yield by contract, the locking protocol can be lighter-weight than a full spin lock.

``hip::pseudo_condition_variable``
   A condition variable paired with ``hip::pseudo_mutex``, following the same cooperative-yield assumptions.

.. warning::

   The cooperative and pseudo variants are safe to use only when all participating threads belong to the same cooperatively scheduled group. Using them across independently scheduled threads can lead to deadlock or livelock.

Spin-lock semantics on GPU versus CPU
*************************************

On a CPU, a standard mutex implementation typically asks the OS scheduler to deschedule a wthread that can't acquire a lock and wake it when the lock is released.
GPU hardware has no equivalent mechanism.
There is no OS scheduler intervention during kernel execution.
A wthread that blocks waiting for a resource continues to occupy its SIMD lane and compute unit.

hipthreads therefore implements ``hip::spin_mutex`` as a spin lock on the GPU. A thread that calls ``lock()`` on a held mutex enters a loop that repeatedly reads the lock's atomic state variable until the owning thread calls ``unlock()``. This has two practical consequences:

- Forward-progress requirement. The thread holding the lock must be scheduled and making progress toward releasing it. If the lock holder is itself waiting on a resource held by the spinning thread, the result is a deadlock. In particular, making synchronous HIP API calls, such as ``hipMemcpy``, inside a critical section can stall the calling thread in a way that prevents the scheduler from running other threads on the same hardware, potentially causing a deadlock.

- Compute-unit occupancy. A spinning thread consumes execution resources. In workloads where many threads contend for the same lock, the spinning overhead can reduce throughput. The cooperative and pseudo variants mitigate this by relying on voluntary yielding within a vcore group.

For a full list of GPU hardware constraints that affect synchronization, see :ref:`limitations <limitations>`.

RAII lock wrappers
******************

hipthreads provides two RAII wrappers that manage mutex ownership automatically, matching the C++ Standard Library equivalents.

``hip::lock_guard``
-------------------

``hip::lock_guard`` acquires a mutex on construction and releases it on destruction. It is the recommended choice when you need to hold a lock for the entire duration of a scope and do not need to unlock or re-lock partway through.

.. code-block:: cpp

   hip::spin_mutex m;
   {
     hip::lock_guard<hip::spin_mutex> lg(m);
     // critical section
   }
   // mutex released when lg goes out of scope

``hip::unique_lock``
--------------------

``hip::unique_lock`` provides the same automatic release semantics as ``hip::lock_guard``, but it also supports deferred locking, manual unlocking, re-locking, and transferring ownership. Use ``hip::unique_lock`` when you need to:

- Pass the lock to a condition variable's ``wait()`` method (``hip::condition_variable_any`` requires a ``hip::unique_lock``).
- Release and re-acquire the lock within the same scope.
- Move lock ownership between scopes.

.. code-block:: cpp

   hip::spin_mutex mux;
   hip::unique_lock<hip::spin_mutex> lock(mux);
   // ... work while holding the lock ...
   lock.unlock();
   // ... work without the lock ...
   lock.lock();

   hip::condition_variable_any cv;
   cv.wait(lock, [] { return predicate_is_true(); });

Choosing the right primitive
----------------------------

- Use ``hip::lock_guard`` for straightforward critical sections where the lock is held for the full scope.
- Use ``hip::unique_lock`` when you need condition-variable integration or manual lock management.
- Use the standard tier (``hip::spin_mutex``, ``hip::condition_variable_any``) when threads are independently scheduled across different vcores.
- Use the cooperative or pseudo tier (``hip::spin_condition_variable``, ``hip::pseudo_mutex``, ``hip::pseudo_condition_variable``) when threads share a cooperative scheduling group and yield proactively, allowing for lighter-weight synchronization.

For the full API signatures of these types, see :doc:`/reference/mutual-exclusion` and :doc:`/reference/condition-variables`.
