### C0 — review body (@geomin12, 2026-08-06T22:02:45Z)
> "FYI these workflow files will be decommissioned soon when multi arch CI gets added. i would recommend doing some clean up and making it in a separate file to prepare for migration"

**Assessment: the most consequential comment on the PR — accept in part.** This is the only comment that asks for a change in the *shape* of the work rather than its style, and it should be resolved before the cosmetic ones, since it determines where the other edits land.

First, a scoping clarification worth raising in the reply: this PR touches no workflow YAML. The changed files are `.github/scripts/therock_matrix.py`, `therock_configure_ci.py`, their tests, and a doc. Read charitably, "these workflow files" means the CI *scripts* backing `therock-ci.yml` — which is consistent with the migration claim, since a multi-arch matrix generator would replace `therock_matrix.py`'s job-construction logic wholesale. Confirming that reading is the first thing to ask.

**How separable the change actually is.** The feature has two halves with very different migration costs:

- **Declarative and self-contained (~90 lines, `therock_matrix.py:213-303`)** — the `LABEL_GATED_CMAKE_OPTIONS` map and its documentation block, `validate_label_gated_cmake_options()`, and the loop that turns labels into a `pending_injections` dict. This depends on `collect_projects_to_run` for nothing; validation reads only `project_map` and `additional_options`. It extracts cleanly.
- **Inherently interleaved (4 sites)** — `redirect_injection` (305-309) plus its two call sites at the merge points (338, 355) and the emit-time append (385). This cannot be extracted wholesale: following an injection through the merge passes is only meaningful *inside* those passes. Moving it out would mean either duplicating the merge logic or inventing a callback protocol for a file slated for deletion.

**Plan — partial extraction.** Move the first half into a new `.github/scripts/therock_label_gating.py` holding the map, the validator, and a small helper that builds the pending-injection dict from a label list. Reduce the second half to a tiny stateful helper (`redirect(absorbed, absorbed_into)` / `options_for(project)`) that also lives in the new module, leaving three one-line call sites in `collect_projects_to_run`. Move the gating tests into a matching `tests/therock_label_gating_test.py`, keeping only the end-to-end matrix assertions (per-job isolation, absorption) in `therock_matrix_test.py` where they belong.

That buys the migration benefit the reviewer is after — the policy, the data, the validation, and their tests survive as an importable unit, and re-wiring costs three lines in whatever replaces `collect_projects_to_run` — without pretending the merge-following can be decoupled from the merges.

**Explicit counter-point to raise.** There is a real tension in "these files are going away, so restructure them." If the decommission is genuinely imminent, the cheapest correct answer may be to land this as-is and port it as part of the migration, since a separate file still has to be rewritten against a matrix generator that does not exist yet. The extraction is worth doing only if the new system will consume Python helpers from `.github/scripts/` in recognizably the same way. That is the second thing to ask.

Worth noting against deferring the PR entirely: @mousdahl-amd (C5) states the feature is needed for a number of upcoming features, so blocking it on the migration has a cost.

**Related context:** this intersects the active MIOpen CI migration from Math CI onto TheRock. Whatever is decided here should be consistent with that effort rather than decided in isolation on this PR.

### C2 — `.github/scripts/therock_configure_ci.py:196`
> "could we already use `get_pr_labels(args)`?"

**Assessment: the question is fair; the current form is deliberate but under-explained.** The added line is `pr_labels = []`, initialized before the event-type branch and populated inside it via the existing `pr_labels = get_pr_labels(args)` at line 203. The initializer exists only because the variable is read after the branch at line 267.

Two facts settle whether hoisting is safe:

- `get_pr_labels` is pure — it JSON-parses `args["pr_labels"]`, defaulting to `"{}"`, and returns names. No I/O, no failure mode on missing input.
- `.github/workflows/therock-ci.yml:100-106` sets `PR_LABELS` only under `if: ${{ github.event.pull_request }}`, and `therock_configure_ci.py:295` defaults it to `'{"labels": []}'`. So on nightly and `workflow_dispatch` the hoisted call would return `[]` anyway.

So hoisting to `pr_labels = get_pr_labels(args)` at the top is behaviorally identical today. What the branch-scoped assignment buys is defense-in-depth: it enforces "label gating is pull-request-only" in Python rather than relying on a workflow `if:`, so a future caller that sets `PR_LABELS` in another context cannot silently enable gated flags on `develop`. That guarantee is asserted by the existing test in `therock_configure_ci_test.py`.

**Plan:** keep the current structure and reply with the above — noting it matches the sibling pattern already used for `label_projects` and `label_test_type`, which are initialized the same way for the same reason. Add a one-line comment at the initializer stating *why* it is scoped to the branch, since the reviewer had to ask. If the reviewer prefers the hoist after that, it is a safe change; ask them to keep the pull-request-only test, converting it to assert on `retrieve_projects`' observable output rather than on where the assignment happens.

### C3 — `.github/scripts/therock_matrix.py:296`
> "hm... we may have other pr_labels too, no need to do `[]`. let's just check through them all as `pr_labels` is default `[]`"

**Assessment: the readability point is right; the stated premise is not.** The signature is `collect_projects_to_run(subtrees, pr_labels=None)` — the default is `None`, not `[]`, which is why line 297 reads `for label in pr_labels or []`. The default cannot simply be changed to `[]`: a mutable default argument is shared across calls and is a standard Python defect. The first half of the comment ("we may have other pr_labels too") appears to read `or []` as a filter that discards non-gated labels. It is not — it is a `None` guard, and the loop already iterates every label, skipping the ones with no entry.

**Plan:** keep `pr_labels=None` and normalize once at the top of the function:

```python
pr_labels = pr_labels or []
...
for label in pr_labels:
```

This gives the reviewer the plain loop they asked for, keeps the immutable default, and removes the `or []` that prompted the misreading. Reply clarifying that the loop never dropped labels and that `None` is intentional.

### C4 — `.github/scripts/therock_matrix.py:297`
> "how about `if label in LABEL_GATED_CMAKE_OPTIONS, continue`. otherwise, we use behavior below"

**Assessment: do not apply literally — it inverts the feature.** Current code:

```python
gated = LABEL_GATED_CMAKE_OPTIONS.get(label)
if not gated:
    continue
pending_injections.setdefault(gated["project"], []).extend(gated["cmake_options"])
```

`continue` on a label that **is** in the map would skip exactly the gated labels and fall through on the ungated ones — the injection would never happen, and the feature would be silently dead. Because the map is empty at merge and every unit test that exercises injection would fail, this would be caught immediately, but it must not be applied as written.

The charitable reading is that the reviewer wants a membership test instead of a truthiness check on the `.get()` result — i.e. `if label not in LABEL_GATED_CMAKE_OPTIONS: continue`. That is equivalent and arguably clearer, and it also removes a latent edge: `if not gated` treats a present-but-empty entry (`{}`) the same as an absent one, whereas a membership test lets `validate_label_gated_cmake_options` be the single place that rejects malformed entries.

**Plan:** rewrite in the membership form the reviewer likely meant:

```python
for label in pr_labels:
    if label not in LABEL_GATED_CMAKE_OPTIONS:
        continue
    gated = LABEL_GATED_CMAKE_OPTIONS[label]
    pending_injections.setdefault(gated["project"], []).extend(gated["cmake_options"])
```

Reply noting the polarity — that `if label in …: continue` as written would disable injection — and confirm the rewrite preserves behavior. Pair this with C3 so the loop lands in one edit.
