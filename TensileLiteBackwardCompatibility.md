# Current TensileLite libraries with hipBLASLt 1.2.1 on gfx950

Investigation performed September 23, 2026; report written September 24, 2026.

## Conclusion

Libraries generated by the investigated TensileLite `develop` revision are **not compatible as-is with hipBLASLt 1.2.1 on gfx950**. There are independent changes to the serialized solution metadata, the kernel argument layout, and the packaging of the generated files.

Selecting MessagePack instead of YAML, decompressing files, or renaming the mapping file does not resolve the metadata and kernel argument incompatibilities. Restricting generation to ordinary GEMMs also does not automatically restore compatibility: the current writer emits some new predicate types even when their associated features are disabled.

A restricted subset may be made compatible through explicit compatibility work, but unchanged output from current TensileLite is not a drop-in replacement for the device libraries shipped with hipBLASLt 1.2.1.

## Scope and pinned revisions

The question is whether a newer TensileLite **producer** can generate catalogs and GPU kernels for an unchanged older hipBLASLt **consumer**. The target GPU is **gfx950**.

| Component | Revision examined | Identification |
| --- | --- | --- |
| New TensileLite producer | `88b55761b9df68c90f6c080227115a22dd7e6eec` | GitHub `develop`, verified live on September 23, 2026 |
| Old hipBLASLt consumer | `5b515cf1bca9959fb434c2414cf79b42fe25e93b` | Source snapshot declaring `HIPBLASLT_PROJECT_VERSION "1.2.1"` |

The older revision is the commit referenced by the repository's `rocm-7.2.0` tag. Its [CMake version declaration][old-version] is the basis for identifying the examined source as hipBLASLt 1.2.1. This report describes the pinned revisions above, not subsequent changes to `develop`.

## Compatibility findings

### 1. Required problem metadata and the type predicate changed

The old reader requires this field in each solution's problem description:

```cpp
iot::mapRequired(io, "computeInputType", s.computeInputType);
```

The current producer instead serializes `computeInputTypeA` and `computeInputTypeB`. It does not emit the old `computeInputType` field.

The related `TypesEqual` predicate changed shape as well:

| Representation | hipBLASLt 1.2.1 | Current TensileLite |
| --- | --- | --- |
| Compute input type fields | `computeInputType` | `computeInputTypeA`, `computeInputTypeB` |
| `TypesEqual.value` | Five entries: A, B, C, D, compute input type | Six entries: A, B, C, D, compute input type A, compute input type B |

The old C++ predicate stores a `std::array<rocisa::DataType, 5>`. The current producer emits six entries. These are schema changes, independent of whether the enclosing file uses YAML or MessagePack, and they affect ordinary GEMMs.

The introducing source change is [commit `46488928eeb`, "f8f6f6 mix mode on hipblaslt"][compute-type-change]. Evidence: [old required field][old-problem-schema], [old five-entry predicate][old-types-equal], and [current producer][new-contractions].

### 2. New predicate types are emitted even with new features disabled

A focused probe of the current producer's predicate construction for an ordinary, non-MX, non-fused GEMM emitted the following types that the old reader does not understand:

```text
FusedGemmA2A
GateResidualDataTypeWhiteList
LaunchLimits
MXBlockA
MXBlockB
UseGateResidual
```

For example, the current writer includes `FusedGemmA2A` with a false value and `MXBlockA`/`MXBlockB` with zero values. `LaunchLimits` is added for non-Stream-K solutions. Disabling those newer features does not remove all of these serialized predicates.

The old reader dispatches predicates by their serialized type names. An unrecognized name follows its `Unknown subclass type ...` error path; a false or zero value does not make an unknown type readable.

Evidence: [current ordinary problem predicates][new-contractions], [current task predicates][new-task-predicates], and [old subclass deserializer][old-subclass-reader]. Relevant additions include [gate residual support, PR #9121][gate-pr], [fused GEMM/A2A support, PR #10925][a2a-pr], and [launch-limit checking, PR #2747][launch-pr].

### 3. The default kernel argument layout changed from version 2 to version 3

[PR #11923, commit `33c75f0b6e3`][args-pr], merged September 11, 2026, changed the default `KernArgsVersion` from 2 to 3 and reordered the positional kernel argument block.

For an ordinary GEMM, the important difference is:

| Layout | Relative argument order |
| --- | --- |
| Old layout | Sizes, D/C pointers, A/B pointers, D/C strides, A/B strides, remaining arguments |
| New layout | Sizes, A/B pointers and strides, intervening arguments including alpha/beta, D/C pointers and strides, remaining arguments |

The actual layout also contains conditional fields for features such as Stream-K. The table shows the first important divergence, not the complete argument specification.

The old host constructs the old argument order. A newly generated version-3 kernel expects the new order. Consequently, making the catalog parse is not sufficient: the host can still pass pointers and other values at incorrect offsets.

Although gfx1250 preload performance motivated the change, the default version change is not gated to gfx1250. It also affects gfx950 solutions that take the new default.

Changing only `internalArgsSupport.version` in an already generated catalog would mislabel the kernel; it would not change the compiled kernel's argument layout. The current host retains version-dependent paths, but that does not establish that selecting version 2 alone restores the complete 1.2.1 contract. For example, [PR #7585][offset-pr] also added batch-offset arguments for non-grouped generated kernels. Any proposed compatibility mode must audit the actual generated signature, kernel reads, and old host argument construction together.

Evidence: [current default][new-args-default], [current kernel signature][new-signature], [current host argument construction][new-host-args], and [old host argument construction][old-host-args].

### 4. Compression and lazy-library mapping names changed

The normal `msgpack` writer now writes zlib-compressed metadata as `<name>.dat.zlib`. The old reader opens the requested `.dat` file directly and has no zlib fallback or decompression path.

The lazy index mapping filename also changed:

| Consumer/producer | Mapping filename |
| --- | --- |
| hipBLASLt 1.2.1 expects | `TensileLiteLibrary_lazy_Mapping.dat` |
| Current gfx950 output | `TensileLiteLibrary_lazy_gfx950_Mapping.dat.zlib` |

These changes came from [compression PR #8294][compression-pr] and [per-architecture mapping PR #6840][mapping-pr]. Current output also uses per-architecture directories, so a deployment must point the old runtime at the directory containing the actual catalog and code objects.

Decompression and mapping-name adaptation are possible packaging steps. They do not repair the problem metadata, predicate, or kernel argument incompatibilities described above.

Evidence: [current MessagePack writer][new-msgpack-writer], [old file reader][old-msgpack-reader], [old mapping lookup][old-mapping], and [current per-architecture output][new-library-output].

### 5. Indexed MessagePack is an additional, optional incompatibility

[PR #11295][indexed-pr] added `--library-format msgpack-indexed`. This remains opt-in; ordinary `msgpack` is still the library-creation default.

The indexed representation replaces the root `solutions` collection with `solutions_index` and `solutions_blob`, and writes `format_version: 2`. The 1.2.1 reader requires the root `solutions` collection and does not implement the indexed representation.

Avoiding indexed MessagePack avoids this particular break, but ordinary MessagePack still has the other incompatibilities. This `format_version` is separate from the kernel's `KernArgsVersion`.

Evidence: [format choices and default][new-format-options], [indexed writer][new-indexed-writer], and [old master-library schema][old-library-schema].

## Practical implications

The straightforward options are to generate deployable libraries with the TensileLite revision paired with hipBLASLt 1.2.1, or to update the consuming hipBLASLt together with the generator.

If retaining current TensileLite and an unchanged 1.2.1 consumer is a requirement, the work needs an explicit compatibility target covering all of these contracts:

1. Emit the old required fields, predicate shapes, and supported predicate types. Reject solutions whose semantics cannot be represented by the old reader.
2. Generate kernels and helper kernels with arguments and launch requirements that the old host actually supports. Verify the resulting layout rather than relying on a version label.
3. Produce uncompressed catalogs and the mapping names/layout expected by the old runtime.
4. Validate library loading, kernel selection, and numerical correctness with the actual hipBLASLt 1.2.1 binary on gfx950 for the intended data types and GEMM modes.

There is no demonstrated general compatibility switch. `--library-format msgpack` selects an encoding, not the 1.2.1 schema. `--version 1.2.1` only embeds a version string; it does not downgrade the metadata or kernel argument contract. Feeding older logic inputs to the current producer also does not, by itself, force the producer to emit the older schema.

## Validation performed and limits

The investigation compared the pinned producer and consumer source, traced the introducing changes, and executed a focused probe of the producer's pure serialization and predicate functions. Those functions were extracted from the pinned source to avoid importing unrelated compiled `rocisa` bindings, which were stale in the local environment.

The probe confirmed:

- Missing old required field: `computeInputType`.
- `TypesEqual` entries: old reader 5, new writer 6.
- The six unsupported ordinary-GEMM predicate types listed above.
- Default `KernArgsVersion`: old 2, new 3.
- Ordinary MessagePack output is compressed `.dat.zlib`; decompression and MessagePack round-trip succeeded.
- Indexed output lacks the root `solutions` collection required by the old reader.
- The old and new lazy mapping names differ.

The diagnostic command was:

```bash
python3 /tmp/tensilelite-compat-mVZNGk/audit.py
```

It was rerun successfully when writing this report. The script and its small synthetic artifacts are temporary local diagnostics; their persistence is not guaranteed. The synthetic payload tests serialization contracts, not a complete deployable library.

No full library generation, load through an actual 1.2.1 runtime, or gfx950 GEMM execution was performed. No GPU device is exposed in this environment. Therefore, this report establishes incompatibility of unchanged output from the inspected source contracts; it does not claim a working compatibility implementation or an exhaustive list of every change that such an implementation would need.
