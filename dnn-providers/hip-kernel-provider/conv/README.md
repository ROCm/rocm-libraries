# The conv engine group

The hip-kernel-provider's convolution engines: plain HIP kernels, compiled at runtime through
HIPRTC for whatever device a plan is built on, and reached through the kernel ingestor. One
source serves every architecture, from gfx906 through current CDNA and RDNA.

The group exists so that every convolution hipDNN is asked for can be served without the
MIOpen provider, and so that each convolution algorithm is its own engine, which hipDNN's
heuristics (UHD) and autotune choose between directly. Kernels brought over from MIOpen
(and split out of `ConvHipConv`) land here, as engines of their own, until faster engines,
in rocKE and elsewhere, replace them.

| Channels-first backward-data implicit GEMM (K7) | `hipkernel:CONV_IGEMM_NCHW_BWD` | In progress | Backward data of a convolution along the width (ConvTranspose1d, as 1-D or with height and depth rows), with dy, the K C T R S filter and dx all packed channels-first and read and written in place: no staging copies and no workspace. Along depth and height (any stride and padding; a dilation at stride 1) each dx row reduces over every (dy row, filter row) pair that reaches it, one after another in the k loop, and a dx row with none is written zero: strided 1x1, patchify (filter equal to stride), 2x2x2 and 3x3x3 stride-2 backward data, as well as the one-to-one rows. The fp32 matrix-core configs (one k per lane) keep the FMA kernel's k-major tiles, stored untransposed. When nothing pads, dx is exactly the strides times dy and the width has one tap per phase, `flat` configs read the dy positions of every image as one GEMM per (depth, height) filter class, computing only the phases a tap reaches (the rest zero), so narrow planes fill whole tiles. fp32, fp16 and bf16; strides 2, 3, 4, 5, 6 and 8 at any filter width with the catalog's taps per phase, and stride 1 (1-D convolutions, HiFi-GAN residual blocks) with the taps shifted by the width dilation, the dy window's halo (`halo`) covering the farthest tap; any padding; groups 1, cross-correlation. Shapes are runtime; a config fixes the tile, the stride and the taps per phase. Each config is admitted on correctness alone; autotune picks. Descriptors are generated by `gen_igemm_nchw.py` (outside the tree). |
| Backward weights (K3) | `hipkernel:CONV_WRW` | In progress | Backward weights as a row-direct implicit GEMM on the implicit-GEMM core's atoms (MFMA on gfx908 to gfx950, WMMA on gfx11 and gfx12), x and dy read in place, both packed channels-first or both channels-last. A block owns a tile of output and input channels and a set of filter rows with every filter-width tap of each: per step it stages a dy row chunk and, per filter row, the input window the chunk's taps reach, split into width-stride phases, so the window is staged once for all its taps, which accumulate in registers. Two loops: output rows (any stride) and a row ring that keeps the last filter-height dy rows' fragments in registers so each input row serves every tap of a depth tap (a height stride runs as one ring per stride phase, over that phase's input rows and filter rows). For stems (at most 16 input channels) the output rows put the (input channel, filter-width tap) pairs on the GEMM's N axis, so a few channels still fill the matrix tile; channels-last stems are staged into the same channels-first tiles (x an element at a time, so any channel count). For narrow channels-first outputs (at most half a step's positions wide, such as ResNet's 7x7 and 14x14 stride-2 layers), the output rows can pack several rows of a plane into one step, each row padded to the taps' reach, so the reduction tile is not mostly empty. Channels-last output channel counts that are not whole vectors (a VAE's 3-channel head) run on the ring with dy units read at any element. On gfx950 the ring also runs with LDS DMA and several stages in flight (unit width stride), and 16-bit channels-last tiles can stay channels-last in LDS, read with transpose reads. Where there is no fp32 matrix core (RDNA), FMA kernels give exact fp32: a row ring for unit stride and rows of whole vectors, and output rows for any stride and any row width (16-byte or scalar units). On gfx906, which has no matrix cores, the FMA kernels also take fp16 and bf16 (accumulating in fp32), from gfx906-only packs. On gfx950 a direct loop serves 16-bit channels-last layers of unit stride and height dilation (any width dilation, groups, 3-D): an item is one image plane's 32-column strip over its rows (or a row segment), the filter height's dy rows stay in a register ring and the x row is read at every width tap; rows reach LDS by 16-byte DMA with column-swizzled channel groups so the transpose reads are conflict-free, an 8-wave ping-pong keeps the memory phase to transpose reads and DMA issue, and a persistent grid of one workgroup per CU walks (tile, item) units, optionally several items side by side (waves_q). The reduction over images and output positions is split over blocks into fp32 partials in the workspace (a config's knob sets the blocks per dispatch unit; at most 1 GiB), which a reduce kernel adds in split order and writes into dw, packed K C T R S or K T R S C, in its element type: deterministic, no atomics. For K C T R S with 2 to 64 taps, a reduce block takes one output channel's run of 64 channels by every tap and writes it contiguously. At one split into K T R S C (or a one-tap filter) the kernel writes dw itself, with no workspace and no reduce, on configs compiled with that store (the `dws` knob; off for the direct loop and for gfx12's widest WMMA tiles, which it slowed). fp32, fp16 and bf16; groups, padding, stride and dilation on every axis, 1-D/2-D/3-D, both convolution modes. Shapes are runtime; a config fixes the tile, the loop and the filter width, its stride and dilation (and, for the rings, the filter height). The host gates each config's LDS with the kernels' own arithmetic (`ConvWrwGeom.h`). Each config is admitted on correctness alone; autotune picks. Descriptors are generated by `gen_conv_wrw.py` (outside the tree). |

Forward at stride 1 and 2; backward data gathers dy into dx with the filter reflected and its channel roles swapped (the expansion kernel does it), at stride 2 by stride phases (one launch per phase, each its own expanded filter, or with `pf` configs one launch per depth phase: a workgroup stages the dy halo once, runs the four row and column phases into an LDS output tile and writes whole dx lines). 2-D and 3-D (ResNeXt3D's 3x3x3 and 1x3x3 filters: a workgroup loops the depth taps, staging each input plane's halo in turn; forward at any depth stride, backward data at depth stride 1 or 2 by phases over depth too), unit dilation, any padding, both convolution modes, channels a multiple of 16; channels-first activations staged by the implicit-GEMM engine's staging kernels, or (`cf` configs, where both activations are packed channels-first) read and written in place: the halo gathered one channel a thread-load along its rows, the output tile written out through LDS one row of columns at a time. fp16 and bf16 everywhere a 16x16 atom runs; fp32 on the CDNA fp32 atom and, everywhere (RDNA has no fp32 matrix core), on an FMA kernel compiled per channels a group (`atom` fma, knobs `cg`, `oc`, `px`): a thread owns `oc` output channels at `px` columns, output pixels run fastest across threads so a wave reads its group-diagonal filter with scalar loads, and only the group's own inputs are multiplied (no block-diagonal zeros). Shapes are runtime; a config fixes the atom, the filter (depth, rows, columns), the row and column stride, the tile and the activation form (`cf`). Each config is admitted on correctness alone; autotune picks. Descriptors are generated by `generators/gen_group.py`. |

Every engine applies its own poor-fit rule as part of applicability, so it declines problems
it would serve badly. For naive that is the workload budget, `NAIVE_MACS_PER_LANE_BUDGET` in
`ConvNaiveProblem.hpp`.

An engine with several kernel configs lists each in its catalog, admitted by its kernel match
on correctness alone. There is no shape-to-config routing table: the catalog's declared order
(most general first) is the default, and autotune, then UHD, choose per shape and device.

| Piece | Path, relative to the provider root |
|---|---|

## Building

Off by default. Enable with `-DHIPDNN_ENABLE_KERNEL_INGESTOR=ON -DHIPKERNELPROVIDER_ENABLE_CONV=ON`.
With the option OFF, the packs are not compiled, the kernels are not embedded and the
`conv/` descriptor folder is not packed (`HKP_DESCRIPTOR_FAMILIES` in
`descriptor-packaging/cmake/HkpPackaging.cmake`).

Plans built from these engines cannot be saved and loaded: plan serialization covers kpack
code objects only, and these kernels are compiled from embedded source.

## Adding an engine family

1. Put the HIP source under `descriptors/conv/<family>/kernels/`, with every shape a runtime
   argument so that one compile per element type serves every problem.
2. Register it for embedding in `HKP_CONV_KERNEL_SOURCES` and `HKP_CONV_KERNEL_KEYS`. A
   source's key is its path relative to the descriptor (`kernels/<File>.cpp`); a header is
   keyed by its bare file name, so give each header a name unique across the provider.
3. Author the family's descriptors under `descriptors/conv/<family>/`, with
   `kernel_source.kind` `embedded_source` and the key as `source_file`.
4. Add the native pack (`packs/Conv<Family>Native.cpp`) and its row in `IngestorPacks.cpp`,
   inside `#ifdef HIPDNN_ENGINE_CONV`, and its sources to the `HIPKERNELPROVIDER_ENABLE_CONV`
   block of the engine's CMakeLists.txt.
5. Test every field its matcher reads with a refusal case, and its numerics on the device
   against hipDNN's CPU reference convolution.
