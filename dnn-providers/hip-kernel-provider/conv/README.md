# The conv engine group

The hip-kernel-provider's convolution engines: plain HIP kernels, compiled at runtime through
HIPRTC for whatever device a plan is built on, and reached through the kernel ingestor. One
source serves every architecture, from gfx906 through current CDNA and RDNA.

The group exists so that every convolution hipDNN is asked for can be served without the
MIOpen provider, and so that each convolution algorithm is its own engine, which hipDNN's
heuristics (UHD) and autotune choose between directly. Kernels brought over from MIOpen
(and split out of `ConvHipConv`) land here, as engines of their own, until faster engines,
in rocKE and elsewhere, replace them.

| Channels-first backward-data implicit GEMM (K7) | `hipkernel:CONV_IGEMM_NCHW_BWD` | In progress | Backward data of a convolution along the width (ConvTranspose1d, as 1-D or with height and depth rows), with dy, the K C T R S filter and dx all packed channels-first and read and written in place: no staging copies and no workspace. | Backward weights (K3) | `hipkernel:CONV_WRW` | In progress | Backward weights as a row-direct implicit GEMM on the implicit-GEMM core's atoms (MFMA on gfx908 to gfx950, WMMA on gfx11 and gfx12), x and dy read in place, both packed channels-first or both channels-last (the generic tier below: any strides). A block owns a tile of output and input channels and a set of filter rows with every filter-width tap of each: per step it stages a dy row chunk and, per filter row, the input window the chunk's taps reach, split into width-stride phases, so the window is staged once for all its taps, which accumulate in registers. Two loops: output rows (any stride) and a row ring that keeps the last filter-height dy rows' fragments in registers so each input row serves every tap of a depth tap (a height stride runs as one ring per stride phase, over that phase's input rows and filter rows). Channels-last output channel counts that are not whole vectors (a VAE's 3-channel head) run on the ring with dy units read at any element. For K C T R S with 2 to 64 taps, a reduce block takes one output channel's run of 64 channels by every tap and writes it contiguously. At one split into K T R S C (or a one-tap filter) the kernel writes dw itself, with no workspace and no reduce, on configs compiled with that store (the `dws` knob; off for the direct loop and for gfx12's widest WMMA tiles, which it slowed). fp32, fp16 and bf16; groups, padding, stride and dilation on every axis, 1-D/2-D/3-D, both convolution modes. Shapes are runtime; a config fixes the tile, the loop and the filter width, its stride and dilation (and, for the rings, the filter height). A generic config takes the filter, strides and dilations at runtime and reads x and dy through their strides: element by element, or in 16-byte channel vectors where the channels are contiguous and whole vectors. It stages a dy chunk once per step and, per filter tap of its block, the x positions that tap reads. Each generic config lists the specialized classes the catalog serves on its architectures (its `spec`) and is declined wherever one of them serves the graph. The host gates each config's LDS with the kernels' own arithmetic (`ConvWrwGeom.h`). Each config is admitted on correctness alone; autotune picks. Descriptors are generated by `gen_conv_wrw.py` (outside the tree). |

Every engine applies its own poor-fit rule as part of applicability, so it declines problems
it would serve badly. For naive that is the workload budget, `NAIVE_MACS_PER_LANE_BUDGET` in
`ConvNaiveProblem.hpp`.

An engine with several kernel configs lists each in its catalog, admitted by its kernel match
on correctness alone. There is no shape-to-config routing table: the catalog's declared order
(most general first) is the default, and autotune, then UHD, choose per shape and device.

## Not supported

- **Mixed data types.** Every engine in the group requires x, w and y to share one data type
  (fp32, fp16 or bf16) and declines anything else, for example x fp32 / w fp16 / y fp32. MIOpen
  serves these graphs only through its naive kernels: the `ConvDirectNaiveConv*` solvers accept
  a problem when any two of in/wei/out share a type, and no optimized MIOpen solver takes one.
  Mixed-type convolution is unsupported here for now.

## Lower-precision plans (testing only)

Every engine computes as precisely as the graph asks unless a switch below is set: fp32 accumulation
of exact products and one final rounding. Plans that compute less precisely run only behind
temporary testing switches, read when a plan is admitted, because hipDNN cannot yet report a plan's
numerical notes or let a caller exclude one (draft PR #15493). Unset (the default), no such plan
is admitted.

| Variable | Covers | cuDNN note |
|---|---|---|
| `HIP_KERNEL_PROVIDER_CONV_TF32` | Every hip-kernel-provider conv engine that has a TF32 form (below). | `TENSOR_CORE` |
| `HIPBLASLT_PROVIDER_CONV_TF32` | The hipblaslt-provider's explicit-GEMM `HIPBLASLT_CONV_TF32_ENGINE` and `ROCBLAS_CONV_TF32_ENGINE` (`hipblaslt-provider/docs/OperationSupport.md`). | `TENSOR_CORE` |
| `HIPDNN_CONV_ALLOW_REDUCED_PRECISION_REDUCTION` | The hipblaslt-provider's `ROCBLAS_CONV_RPR_ENGINE` and `HIPBLASLT_CONV_RPR_ENGINE` (below). | `REDUCED_PRECISION_REDUCTION` |

The final form follows cuDNN, and these switches are not part of it:

- an engine whose plans compute less precisely reports its numerical note (table above);
- the caller excludes such engines with `Graph::deselect_numeric_notes`;
- `HIPDNN_TF32_OVERRIDE=0` turns TF32 off process-wide, and a matching process-wide switch turns
  reduced-precision reduction off.

The compute type is the least precision a plan must keep: these engines serve FLOAT and unset
compute types (and HALF on fp16 for the reduced-precision-reduction engines), as cuDNN offers
them. Neither the per-engine note reporting nor `deselect_numeric_notes` exists yet. When they
land, the switches go away.

### TF32

With the switch set, the provider admits a TF32-class config only for an fp32 graph. It sits
beside the exact configs, and autotune chooses among them. A TF32 config is never admitted for
fp16, bf16 or mixed graphs. It is never admitted without the switch.

TF32 forms:

| Engine | Directions | TF32 form | Archs |
|---|---|---|---|
| Implicit GEMM (K1) | fwd, bwd | three-bf16 everywhere; on gfx942 also xf32 MFMA, its inputs rounded to nearest | gfx908, gfx90a, gfx942, gfx950, gfx11, gfx12 |
| Halo-tile direct (K2) | fwd, bwd | three-bf16 | gfx908, gfx90a, gfx942, gfx950, gfx11, gfx12 |
| `CONV_WRW` (K3) | wrw | three-bf16 over 3N images; admitted only on the shape classes where it measured faster than exact | gfx90a, gfx942, gfx950, gfx11, gfx12 |
| NCHW implicit GEMM (K7) | bwd | three-bf16; admitted only for strided 3-D filters of 27+ taps on RDNA | gfx11, gfx12 |
| `CONV_GROUP` (K4) | fwd, bwd | three-bf16 for wide groups (17 to 64 channels a group): each depth tap multiplies the three part pairs into the same accumulators | gfx90a, gfx942, gfx950, gfx11, gfx12 |

Three-bf16 splits each fp32 operand into a high and a low bf16 part. The reduction then runs on
bf16 matrix cores over three part pairs and writes fp32 out:

- K1, K2, K3 and K7 triple the reduction channels (or K3's images) in a pre-pass.
- K4 reads three part copies of each operand.

The lo x lo term is dropped, so the error is about 2^-16 of each product. That is tighter than
TF32's 2^-11. An infinity propagates as it does in fp32.

The forms are checked against an fp64 reference within a TF32 tolerance. Every form has a test
that, with the switch unset, no TF32 config is admitted. An exact or 16-bit config compiles to
the same ISA as before the TF32 forms were added.

These stay exact fp32 with or without the switch:

- VALU and FMA configs;
- the depthwise VALU engines;
- the naive reference engine;
- every engine on gfx906, and every engine on gfx908 other than K1 and K2.

These had three-bf16 forms built, measured slower than their exact configs on every arch, and
so have none:

- `CONV_STEM_BWD` and `CONV_SMALLC` (1 to 4 input channels, bandwidth-bound): 0.25-0.75x;
- K4 small groups and K4 backward weights: 0.28-0.77x;
- `CONV_WINOGRAD` (K5): 0.21-0.58x. That form was multipass: the split after the fp32
  transforms, and a bf16 matrix-core batched GEMM. Its fp32 configs are VALU. A paying form
  needs the split inside the fused cooperative kernel.

### Reduced-precision reduction

With `HIPDNN_CONV_ALLOW_REDUCED_PRECISION_REDUCTION=1`, the hipblaslt-provider registers
`ROCBLAS_CONV_RPR_ENGINE` and `HIPBLASLT_CONV_RPR_ENGINE`. Their one form: a 1x1, unit-stride,
unpadded fp16 backward weights of several channels-first images as one GEMM per image adding into
the fp16 dw (MIOpen's `GemmWrw1x1_stride1`), so dw is rounded once per image instead of once. It
wins where the exact plans' fp32 partials are slow, mostly RDNA (gfx1100, gfx1201); elsewhere
autotune keeps the exact engines. fp16 only: bf16 has no reduced form. With the switch unset no
such engine is registered, and the plan builder declines on every call. The form is checked
against an fp64 reference within the half tolerance widened for the per-image roundings.

## Layout

| Piece | Path, relative to the provider root |
|---|---|
| This overview | `conv/` |

| Descriptor generators | `conv/generators/gen_*.py`, one per family; `conv/generators/regen_all.py` runs them all. [REGEN.md](REGEN.md) is how to regenerate and upload. |

| Kernel sources | `src/engines/kernel_ingestor_engine/descriptors/conv/<family>/kernels/`, beside the descriptors that name them. An embedded source must sit at its descriptor's folder plus `source_file`, which `descriptor-packaging/tools/hkp_verify_embedded_sources.py` checks at build time. |
| Native packs (matching, workload rule, dispatch) | `src/engines/kernel_ingestor_engine/packs/Conv<Family>*.cpp` |

## Building

Off by default. Enable with `-DHIPDNN_ENABLE_KERNEL_INGESTOR=ON -DHIPKERNELPROVIDER_ENABLE_CONV=ON`.
With the option OFF, the packs are not compiled, the kernels are not embedded and the
`conv/` descriptor folder is not packed (`HKP_DESCRIPTOR_FAMILIES` in
`descriptor-packaging/cmake/HkpPackaging.cmake`).

Fetch the catalogs before configuring (reads are anonymous):

```bash
# From the repository root.
dvc pull -r ingestor dnn-providers/hip-kernel-provider/src/engines/kernel_ingestor_engine/descriptors/conv/*/*.kdp.json.dvc
```

A family whose catalogs are missing is **not served**: configure warns (an error with
`-DHIPKERNELPROVIDER_REQUIRE_DVC_DESCRIPTORS=ON`), the family's folder is withdrawn from the
pack, its native pack is not registered and its engine suites are not built
(`conv/ConvContent.cmake`). The other families build and ship as usual.

Plans built from these engines cannot be saved and loaded: plan serialization covers kpack
code objects only, and these kernels are compiled from embedded source.

## Adding an engine family

1. Put the HIP source under `descriptors/conv/<family>/kernels/`, with every shape a runtime
   argument so that one compile per element type serves every problem.
2. Register it for embedding in `HKP_CONV_KERNEL_SOURCES` and `HKP_CONV_KERNEL_KEYS`. A
   source's key is its path relative to the descriptor (`kernels/<File>.cpp`); a header is
   keyed by its bare file name, so give each header a name unique across the provider.
3. Author the family's descriptors under `descriptors/conv/<family>/`, with
   `kernel_source.kind` `embedded_source` and the key as `source_file`. Write them with a
   generator (`conv/generators/gen_<family>.py`, added to `FAMILIES` in `regen_all.py`) and
   record its catalogs in DVC ([REGEN.md](REGEN.md)).
4. Add the native pack (`packs/Conv<Family>Native.cpp`) and its row in `IngestorPacks.cpp`,
   inside `#ifdef HIPDNN_ENGINE_CONV_<FAMILY>` (defined when the family is served), and its
   sources to the `HIPKERNELPROVIDER_ENABLE_CONV` block of the engine's CMakeLists.txt. Gate
   its suites on the family in `src/tests/engines/kernel_ingestor_engine/CMakeLists.txt`.
5. Test every field its matcher reads with a refusal case, and its numerics on the device
   against hipDNN's CPU reference convolution.
