# The conv engine group

The hip-kernel-provider's convolution engines: plain HIP kernels, compiled at runtime through
HIPRTC for whatever device a plan is built on, and reached through the kernel ingestor. One
source serves every architecture, from gfx906 through current CDNA and RDNA.

The group exists so that every convolution hipDNN is asked for can be served without the
MIOpen provider, and so that each convolution algorithm is its own engine, which hipDNN's
heuristics (UHD) and autotune choose between directly. Kernels taken from MIOpen (including
those split out of `ConvHipConv`) are engines of their own here, until faster engines, in
rocKE and elsewhere, replace them.

## Engines

Each engine family has a design doc covering what it is for, how it works, its precision, how it compares with MIOpen, and next steps: [docs/engines](docs/engines/README.md).

| Backward weights (K3) | `hipkernel:CONV_WRW`; TF32: `hipkernel:CONV_WRW_TF32` | In progress | Backward weights as a row-direct implicit GEMM on the implicit-GEMM core's atoms (MFMA on gfx908 to gfx950, WMMA on gfx11 and gfx12), x and dy read in place, both packed channels-first or both channels-last (the generic tier below: any strides). A generic config takes the filter, strides and dilations at runtime and reads x and dy through their strides: element by element, or in 16-byte channel vectors where the channels are contiguous and whole vectors. It stages a dy chunk once per step and, per filter tap of its block, the x positions that tap reads. Each generic config lists the specialized classes the catalog serves on its architectures (its `spec`) and is declined wherever one of them serves the graph. The host gates each config's LDS with the kernels' own arithmetic (`ConvWrwGeom.h`). Each config is admitted on correctness alone; autotune picks. Descriptors are generated by `generators/gen_conv_wrw.py`. |

## Fused pointwise epilogues

A forward convolution graph may chain pointwise nodes after its convolution node; the engines
that apply the chain claim the graph under their own engine id, with no added catalog config.

- **Graphs.** Node 0 is the convolution; each following node is pointwise and takes the previous
  one's result (as `in_0`, or as either input of ADD and MUL); every intermediate is virtual and
  has the convolution's dims; the last node writes the graph's only non-virtual output, of the
  convolution's element type. Up to 8 nodes, 4 tensor operands and 8 values.
- **Menu.** ADD and MUL with a per-channel (`[1, K, 1, ...]`) or one-element device tensor, or a
  pass-by-value scalar (constant or supplied at execute); RELU_FWD with any lower and upper clip
  and lower-clip slope (relu, clipped relu, clamp, leaky relu); GELU_FWD, GELU_APPROX_TANH_FWD,
  SWISH_FWD (any beta; silu at 1), SIGMOID_FWD, TANH_FWD, ELU_FWD (any alpha), ABS and
  SOFTPLUS_FWD (beta > 0). Node compute types UNSET, FLOAT, or the 16-bit type of the node's
  operand or of the output. Every other mode, attribute or tensor form declines.
- **Numerics.** The chain runs in fp32 on the convolution's accumulator and the kernel rounds once
  to the output type, whatever type the graph declares for its intermediates. relu and clamp
  propagate NaN; gates that saturate to 0 (silu, gelu at -inf) give 0. No fast-math.
- **Activation accuracy.** The activations are built from the hardware exp2, log2 and reciprocal,
  in one implementation (`ConvEpilogue.h`) that every engine of this provider compiles, in two
  forms chosen by the graph's output type: an fp32 output takes the few-ulp form (e^v corrected
  for the rounding of `v log2(e)`, GELU's argument and exponent kept to twice the float
  precision); a 16-bit output takes the faster form, whose error stays under 0.1 ulp of fp16 and
  bf16. Worst case over every fp32 input against a double reference, in fp32 ulp of the result
  before the output rounding (results of magnitude 2^-122 and up; each form bit-identical on
  gfx942 and gfx950):

  | Activation | fp32 output, \|x\| <= 8 / all | 16-bit output, \|x\| <= 8 / all |
  |---|---|---|
  | sigmoid | 2.7 / 3.6 | 9.0 / 64 |
  | silu (swish, beta 1) | 3.2 / 3.7 above -80 | 8.9 / 63 above -80 |
  | swish, beta 1.702 | 13 | 20 |
  | gelu | 8.8 / 8.8 | 119 / 310 |
  | gelu-tanh | 94 / 184 | 134 / 230 |
  | tanh | 1.6 | 1.6 |
  | elu | 1.8 | 1.8 |
  | softplus (beta 1, 2) | 4.9 | 11, 16 / 63 |

  The larger errors sit in the negative tails, where the result is a small value. gelu-tanh and
  swish with beta other than 1 carry the rounding of their fp32 argument (`u`, `beta x`) there,
  as any fp32 evaluation of those formulas does. Every error of either form stays under 1.3% of
  the fp32 pointwise tolerance (`1e-5 + 1e-5 |reference|`). Results below 2^-122 in magnitude may
  flush to zero where an intermediate underflows (an absolute error under 2e-36; silu and swish
  below `-88 / beta`, as the math library's form). NaN gives NaN; sigmoid(+-inf) is 1 and 0,
  silu(-inf) and gelu(-inf) 0, silu(inf) and gelu(inf) inf, tanh(+-inf) +-1, elu(-0) +0, as
  PyTorch. The explicit-GEMM engines' epilogue pass applies the same functions under the same
  rule, so a fused graph's activation is the same on every engine; results differ between
  engines by the convolution's summation order. On MI325X, an fp32-output fused kernel with the
  few-ulp form takes, against the fast form (geomean per family over the fused timing shapes,
  worst case in brackets): gelu 1.01-1.12x (1.26), silu 1.00-1.03x (1.26).
- **Against a separate pointwise pass.** Time of the best bare convolution plus the chain as its
  own one-pass kernel, over the fused graph's best time (above 1: fusion faster), per family of
  the engine that wins the fused graph; 114 real-model shapes per layout, chains bias, bias + relu,
  bias + gelu and bias + silu, all three data types, autotuned. Weighted by the shapes' calls per
  model run; losses are graphs below 0.98x.

  | Family | MI325X, channels-last: weighted (losses / graphs) | gfx950, both layouts: weighted (losses / graphs) |
  |---|---|---|
  | IGEMM | 1.01x (4 / 187) | 1.05x (20 / 253) |
  | DIRECT | 1.06x (1 / 35) | 1.08x (5 / 90) |
  | WINOGRAD | - | 1.18x (0 / 15) |
  | SMALLC | 1.65x (0 / 35) | 1.34x (0 / 141) |
  | GROUP | 1.33x (0 / 13) | 1.44x (0 / 21) |
  | DEPTHWISE (VALU, ROWS, MFMA) | 1.55x (0 / 49) | 1.60x (0 / 100) |
  | NAIVE | 1.52x (0 / 6) | 1.54x (0 / 11) |
  | explicit GEMM (hipBLASLt, rocBLAS) | 1.10x (29 / 131) | 1.02x (87 / 281) |

  Fusion wins wherever the convolution's output traffic matters (depthwise, small-C, grouped,
  every small and mid-size layer) and is about even on large compute-bound layers. The losses are
  1x1 and patchify layers whose bare convolution a BLAS GEMM wins by a wide margin: fused, the
  explicit-GEMM engines write an fp32 result and run a pass over it, and the in-kernel engines
  are slower than the BLAS GEMM, so the BLAS GEMM followed by a separate pass over the 16-bit
  output is faster (down to 0.84x on MI325X, 0.60x on gfx950).
- **Mechanism.** `ConvEpilogue.h` is the hook every fusing kernel calls before its single
  rounding. The pack generates the chain's code into the HIPRTC options (`CONV_EPI` and three
  generated macros) and passes `ConvEpiArgs` as the kernel's second argument: operand pointers
  and every value are runtime arguments, so one code object serves every graph of a pattern and
  the code-object key changes with the pattern only. Fusion off adds no option: the kernels'
  signatures, argument blocks and instructions are those of an unfused build. Split reductions
  write fp32 partials unchanged and apply the chain once in their reduce pass, deriving the
  channel without a division per element.
- **Coverage.** Forward only. The naive engine applies any chain but keeps its own workload
  gate, decided on the convolution alone, so fusion never widens what it claims. Per-engine
  paths: the engine docs' Fusion sections.
- **Autotune.** A fused graph is a different graph from its convolution, so it has its own
  winner records; the same config id serves both.

## Not supported

- **Mixed data types.** Every engine in the group requires x, w and y to share one data type
  (fp32, fp16 or bf16) and declines anything else, for example x fp32 / w fp16 / y fp32. MIOpen
  serves these graphs only through its naive kernels: the `ConvDirectNaiveConv*` solvers accept
  a problem when any two of in/wei/out share a type, and no optimized MIOpen solver takes one.
  Mixed-type convolution is unsupported here for now.

fp32 engines that report it when TF32 is not allowed (`aten/src/ATen/native/cudnn/Conv_v8.cpp`).
A note describes an engine, not a config, so each family's TF32 configs, and Winograd's bf16 and
F(4,3) configs, are engines of their own beside the exact ones, which list none of them
(`TestConvDescriptorShards` checks both on every shipped shard). The weight-gradient Winograd
engine mixes F(3,2), F(3,4) and F(3,6), so it names no tile.

no atomics (split reductions write fp32 partials that a reduce kernel adds in split order), so a
plan gives the same bits on every run on one device. A UED's `numerical_notes` list without
`nondeterministic` is that claim (a UED without the key is reported `NONDETERMINISTIC`), and RFC
0025 admits it only with a test: each family's device suite (`TestGpuConv<Family>`) launches
every config it runs a second time, over a re-filled workspace, and compares the output bits
(`ConvDeterminismTestSupport.hpp`). The explicit-GEMM engines
run the libraries' defaults and report `NONDETERMINISTIC`; their `*_DETERMINISTIC` siblings (rocBLAS
atomics not allowed, no hipBLASLt workspace) claim determinism, with a rerun in their tests
(`hipblaslt-provider/docs/engines/EXPLICIT_GEMM.md`). The
coverage census checks what the frontend reports for every engine a graph is offered.

### TF32

A TF32 engine serves fp32 graphs only, beside the exact engines, and autotune chooses among them.

| Engine | Directions | TF32 form | Archs |
|---|---|---|---|
| `CONV_IGEMM_FWD/BWD_TF32` (K1) | fwd, bwd | three-bf16 everywhere; on gfx942 also xf32 MFMA, its inputs rounded to nearest | gfx908, gfx90a, gfx942, gfx950, gfx11, gfx12 |
| `CONV_DIRECT_FWD/BWD_TF32` (K2) | fwd, bwd | three-bf16 | gfx908, gfx90a, gfx942, gfx950, gfx11, gfx12 |
| `CONV_WRW_TF32` (K3) | wrw | three-bf16 over 3N images; admitted only on the shape classes where it measured faster than exact | gfx90a, gfx942, gfx950, gfx11, gfx12 |
| `CONV_IGEMM_NCHW_BWD_TF32` (K7) | bwd | three-bf16; admitted only for strided 3-D filters of 27+ taps on RDNA | gfx11, gfx12 |
| `CONV_GROUP_FWD/BWD_TF32` (K4) | fwd, bwd | three-bf16 for wide groups (17 to 64 channels a group): each depth tap multiplies the three part pairs into the same accumulators | gfx90a, gfx942, gfx950, gfx11, gfx12 |
| `ROCBLAS_CONV_TF32_ENGINE`, `HIPBLASLT_CONV_TF32_ENGINE` (hipblaslt-provider) | all | the library's TF32 GEMM (hipBLASLt gfx942 / gfx950, rocBLAS xf32 on gfx942; fp32 elsewhere) | all |

Three-bf16 splits each fp32 operand into a high and a low bf16 part. The reduction then runs on
bf16 matrix cores over three part pairs and writes fp32 out:

- K1, K2, K3 and K7 triple the reduction channels (or K3's images) in a pre-pass.
- K4 reads three part copies of each operand.

The lo x lo term is dropped, so the error is about 2^-16 of each product. That is tighter than
TF32's 2^-11. An infinity propagates as it does in fp32.

The forms are checked against an fp64 reference within a TF32-class tolerance. An exact or 16-bit
config compiles to the same ISA as it does with the TF32 forms compiled out.

These have no TF32 form:

- VALU and FMA configs;
- the depthwise VALU engines;
- the naive engines;
- every engine on gfx906, and every engine on gfx908 other than K1 and K2.

These have no three-bf16 form: one measures slower than their exact configs on every arch:

- `CONV_STEM_BWD` and `CONV_SMALLC` (1 to 4 input channels, bandwidth-bound): 0.25-0.75x;
- K4 small groups and K4 backward weights: 0.28-0.77x;
- `CONV_WINOGRAD` (K5): 0.21-0.58x. The measured form is multipass: the split after the fp32
  transforms, and a bf16 matrix-core batched GEMM. Its fp32 configs are VALU. A paying form
  needs the split inside the fused cooperative kernel.

### Reduced-precision reduction

The hipblaslt-provider's `ROCBLAS_CONV_RPR_ENGINE` and `HIPBLASLT_CONV_RPR_ENGINE` report
`REDUCED_PRECISION_REDUCTION`. Their one form: a 1x1, unit-stride, unpadded fp16 backward weights
of several channels-first images as one GEMM per image adding into the fp16 dw (MIOpen's
`GemmWrw1x1_stride1`), so dw is rounded once per image instead of once. It wins where the exact
plans' fp32 partials are slow, mostly RDNA (gfx1100, gfx1201); elsewhere autotune keeps the exact
engines. fp16 only: bf16 has no reduced form; compute type unset, FP32 or FP16, as cuDNN offers
it. The form is checked against an fp64 reference within the half tolerance widened for the
per-image roundings.

## Opt-in preview

The group is a preview, off in two places:

- **Build:** `HIPKERNELPROVIDER_ENABLE_CONV` is OFF by default, so a default build (TheRock's
  included) ships no conv engine. The rocm-libraries superbuild presets `hipdnn-dev-all` and
  `miopen-hipdnn-dev-all` turn it ON, so the group is built and tested there. The group is built
  and tested on Linux only: the superbuild CI's Windows lane turns it OFF, and a Windows build
  is a follow-up.
- **Runtime:** a build that ships the group serves its engines only in a process with
  `HIP_KERNEL_PROVIDER_ENABLE_CONV` set to `1` (or `true`, `on`, `yes`). Unset, or any other
  value, the provider withdraws every `hipkernel:CONV_*` engine from its descriptor catalog
  when it first loads it (`ConvEngineGroupGate.hpp`), and serves exactly what a build without
  the group serves. The provider reads the variable once, when it loads its descriptors.

```bash
export HIP_KERNEL_PROVIDER_ENABLE_CONV=1
```

Enabled, every engine in the table above is offered for the graphs its gates accept, in fp32,
fp16 and bf16, 1-D to 3-D, forward, backward data and backward weights; the explicit-GEMM
engines live in `hipblaslt-provider` under their own build option. Selection between the
engines is autotune's: the trained heuristics (UHD) for this group, and serving it by default,
come later. The provider's own suites run with the group enabled (CTest sets the variable; the
unit binary also enables it when the variable is unset), and
`hip_kernel_provider_conv_opt_in_off` checks that none of its engines is offered when it is
not.

## Plan build: compilation, failures and workspace

- **Compilation.** Every conv config compiles its programs through HIPRTC when its plan is built, never at execution. Code objects are cached on disk and in the process ([HIPRTC code-object cache](../README.md#hiprtc-code-object-cache)); [Seeing what ran](../README.md#seeing-what-ran) shows the config each plan chose and where each program came from.
- **Failures.** A config whose program fails to compile, or cannot be compiled because HIPRTC is unavailable or disabled (`HIP_KERNEL_PROVIDER_DISABLE_HIPRTC`), costs only that config: the engine logs a warning naming the program and tries its next candidate. An engine none of whose candidates builds declines at plan build, and hipDNN finalizes the next engine.
- **Workspace.** Each plan reports, at plan build, the workspace its config needs (staged operands, split partials, transforms), and uses no more. A caller's limit below that need declines the config at plan build: `global.workspace_size_limit` on the engine config (backend API) removes the configs that need more before any is built, and an engine left with none declines; the frontend's `deselect_workspace_greater_than()` compares each built plan's reported workspace with its limit, so a plan over it is never executed (`Graph::build_plans()` documents which plans it then tries).

## gfx1250 execution contracts

Native wave32 atoms are distinct from gfx1200/gfx1201 WMMA:
`wmma125_f16` and `wmma125_bf16` multiply 16×16×32 with fp32 accumulation;
`wmma125_f32` multiplies 16×16×4 without rounding fp32 operands.
Native exact-fp32 selection needs no TF32 permission. Reduced-precision
alternatives retain their separate engines and numerical notes.
The native kernel macro `HKP_ARCH_GFX1250` is exact-target only. `gfx1251` and
`gfx12-5-generic` are not qualified for these native kernel/resource contracts;
their presence in an ISA compatibility list does not establish kernel coverage.

K1, K2, K7, WRW, small-C and stem catalogs enumerate native atoms separately,
preserving existing atom IDs. Native candidates complement rather than replace
legacy configurations. K1's automatic split policy uses gfx1250's reported CU
count without the legacy WGP-to-CU doubling; an explicit no-split HALF
backward-data candidate remains a separate choice. Native WRW and stem LDS
limits are bounded by both the architecture and the reported per-block capacity.
The reported-LDS clamp is applied only on gfx1250. Other architectures retain
their established architectural allowances: 160 KiB on gfx950, 64 KiB elsewhere,
even when a HIP stack reports a lower per-block value.

Native K32 BF16 atoms also serve K1, K7 and WRW's existing three-bf16 forms.
Those catalogs attach to the separate TF32 engines and retain their numerical
notes and geometry gates; exact native catalogs are unchanged.
Stem catalogs preserve the legacy selected configurations and add native atoms
on the existing 2-D, 3-D and space-to-depth geometry.

Grouped VALU forward, backward data and backward weights use the same portable
tile families on gfx1250, with native buffer-resource flags. Packed-half dot
products use two fp32 FMAs where the legacy `v_dot2_f32_f16` instruction is absent.
K4's block-diagonal matrix cores still require a reduction step dividing 16;
gfx1250's K32 atoms do not widen that engine's 16-bit support.

K1 `cf=2` reads packed channels-first HALF pointwise inputs directly, transposing
only the A tile in LDS and storing channels-first output without a global staging
buffer. It requires one group, unit stride, no padding, matching spatial extents,
whole eight-element spatial vectors, aligned vector loads and a reduction length
that cannot overflow the cursor's final prefetch. Other configurations retain
their existing staging contracts.

### WRW scheduling and accuracy

Loop IDs 7 and 8 retain the existing packed-row and generic double-buffered
kernels. Additional native paths have distinct IDs:

- **11:** runtime-geometry per-tap implicit GEMM, with masked 64-bit gathers and
  the actual tensor strides, including admitted nonpacked views.
- **12:** flattened filter-tap/input-channel GEMM, sharing dy tiles and an LDS
  position cache across taps to avoid small-channel matrix padding.
- **9:** packed channels-last scalar reduction for at most four output channels
  per group, with no LDS.
- **10:** an explicitly enumerated FLOAT accuracy floor. Inputs widen before
  multiplication; partials and their fixed-order fold are FP64, with one final
  rounding to FLOAT output.

Groups, spatial ranks, borders, stride, dilation and true-convolution reflection
remain runtime geometry. Split partial buffers are capped at 1 GiB.
WRW `dws=2` writes channels-first multi-tap filters directly for its bounded
one-split native configuration; multiple splits retain partials and the ordered
fold. The added small-channel, long pointwise-ring and wide direct-convolution
tiles are autotuning candidates, not shape-routing rules or new global defaults.

### Winograd

Native exact-fp32 multipass GEMM uses atom 5 for F(2,3), F(4,3) and phased
F(3,2). It masks channel and tile tails while preserving the filter/input/output
transforms, batching and U/V/M workspace contract. Existing precision gates,
cooperative-kernel options and backward-weights engines remain in effect.

`hipkernel:CONV_WINOGRAD_ND_FWD` is a separate FLOAT 2-D 3×3, unit-stride
engine requiring non-unit dilation on at least one axis and gfx1250 exact-fp32
WMMA. It applies F(2,3) within dilation-residue subgrids without materializing
space-to-batch copies. Both modes, groups, asymmetric padding and safe positive
strided views are supported. Four candidates combine `gemm_bm` 64/128 with
`chunk_tiles` 256/4096; `gemm_bn` 64 and `gemm_bk` 16 are fixed.
The transformed filter and spatially chunked V/M buffers share a 256 MiB cap.
Weights are transformed from the current binding on every execution, not cached
by pointer identity. The engine reports its Winograd numerical notes.

### Independent numerical qualification

With convolution tests enabled, `hipkernel_validate_wrw` checks whole logical
weight tensors against compensated FP64 direct convolution computed from the
stored input values. The original absolute/relative tolerances are `1e-4` for
FLOAT, `0.002` for HALF and `0.02` for BFLOAT16. MIOpen results are diagnostics,
not the numerical authority for long reductions.
The validator target is available only in the in-tree hipDNN/provider superbuild,
which supplies `hipdnn_bench_lib`. That library is not an exported SDK target,
so a standalone provider build does not build `hipkernel_validate_wrw`.

```bash
ROCR_VISIBLE_DEVICES="<device>" HIP_VISIBLE_DEVICES=0 CUDA_VISIBLE_DEVICES=0 \
  gpu-guard run --profile "WRW qualification" -- \
  build/bin/hipkernel_validate_wrw manifest.jsonl results.jsonl \
  build/lib/hipdnn_plugins/engines /path/to/libmiopen_plugin.so "<device-pci-address>"
```

Manifest rows contain `line`, `graph` and optionally `command`; each graph must
contain one real backward-weights convolution with UNSET or FLOAT compute
(HALF compute is also accepted for HALF storage). The expected PCI address and
single-visible-device check guard device selection. Qualification
uses three-iteration screening and 30-iteration refinement. Keep failed candidate
errors and timings; qualify in latency order rather than treating a rejected
configuration as proof that the graph is unsupported.

## Building

Off by default. Enable with `-DHIPDNN_ENABLE_KERNEL_INGESTOR=ON -DHIPKERNELPROVIDER_ENABLE_CONV=ON`,
and set `HIP_KERNEL_PROVIDER_ENABLE_CONV=1` at runtime (above).
With the option OFF, the packs are not compiled, the kernels are not embedded and the
`conv/` descriptor folder is not packed (`HKP_DESCRIPTOR_FAMILIES` in
`descriptor-packaging/cmake/HkpPackaging.cmake`).

Fetch the catalogs before configuring (reads are anonymous):

```bash
# From the repository root.
dvc pull -r ingestor dnn-providers/hip-kernel-provider/src/engines/kernel_ingestor_engine/descriptors/conv/*/*.kdp.json.dvc
```

A family whose catalogs are missing is **not served**: configure warns (an error with
`-DHIPKERNELPROVIDER_REQUIRE_DVC_DESCRIPTORS=ON`), the family's folder is withdrawn from the
pack, its native pack is not registered and its engine suites are not built
(`conv/ConvContent.cmake`). The other families build and ship as usual.

Plans built from these engines cannot be saved and loaded: plan serialization covers kpack
code objects only, and these kernels are compiled from embedded source.

## Adding an engine family

1. Put the HIP source under `descriptors/conv/<family>/kernels/`, with every shape a runtime
   argument so that one compile per element type serves every problem.
2. Register it for embedding in `HKP_CONV_KERNEL_SOURCES` and `HKP_CONV_KERNEL_KEYS`. A
   source's key is its path relative to the descriptor (`kernels/<File>.cpp`); a header is
   keyed by its bare file name, so give each header a name unique across the provider.
3. Author the family's descriptors under `descriptors/conv/<family>/`, with
   `kernel_source.kind` `embedded_source` and the key as `source_file`, and the UED's
   `numerical_notes` ([Numerical notes](#numerical-notes)). Write them with a
   generator (`conv/generators/gen_<family>.py`, added to `FAMILIES` in `regen_all.py`) and
   record its catalogs in DVC ([REGEN.md](REGEN.md)).
4. Add the native pack (`packs/Conv<Family>Native.cpp`) and its row in `IngestorPacks.cpp`,
   inside `#ifdef HIPDNN_ENGINE_CONV_<FAMILY>` (defined when the family is served), and its
   sources to the `HIPKERNELPROVIDER_ENABLE_CONV` block of the engine's CMakeLists.txt. Gate
   its suites on the family in `src/tests/engines/kernel_ingestor_engine/CMakeLists.txt`.
5. Test every field its matcher reads with a refusal case, and its numerics on the device
   against hipDNN's CPU reference convolution, launching each config twice
   (`relaunchReproducesOutput`) to prove the determinism its UED claims.
