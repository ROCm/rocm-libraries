# rocKE monitor: subcommands and settings

`tick` is in `SKILL.md`. "Standing rules" and "Who merges" below mean the sections of `rules.md`.

## Subcommands

| Command | Do |
|---|---|
| `on` | Run `rk resume`. On a host, then start the tick loop (`tools/tick_loop.py`, `run_in_background`; SKILL.md, Tick procedure) and the watchdog cron (`CronCreate`, `7 */2 * * *`, session-only, with the watchdog prompt under this table) in the monitor's Claude session; in the container the orchestrator runs the ticks |
| `off` | On a host, end this session's loops first (the tick loop: `TaskStop`; the watchdog cron: `CronList` / `CronDelete`); then run `rk pause` (the tick decides nothing and starts nothing new; running jobs finish). Disarm any PR we armed (`rk disarm N [REASON]`, which goes through with auto-merge off too; `merge_procedure.md`). Ticks while OFF are one-line no-ops. On a host the Claude side is stopped only from Claude Code, this way |
| `stop [--drain]` | On a host, end this session's tick loop (`TaskStop`) and the watchdog cron and stop the review driver's background shell; then run `rk stop` (`--drain`: nothing new starts, and the work in flight finishes first). It stops the driver, the work in flight, the gate, sanity and check jobs and the admin dashboard server. `rk start` resumes: then `resume`, which on a host starts the tick loop and the watchdog cron again (`<PACKAGE_DIR>/docs/restart.md`). In the container <user_login> stops and starts it from the host (`rkmon stop`, or `rkmon stop --drain` to let the work in flight finish first; `rkmon start`) |
| `start` | Run `rk start` (it starts the admin dashboard server), then `resume` (on a host it starts the tick loop and the watchdog cron again) |
| `kill` | Only on <user_login>'s instruction: end this session's tick loop and the watchdog cron, then run `rk kill`: every process the monitor started, at once, after any GitHub write in flight (never Ollama, Claude Code or a shell). It prints what it killed. `rk start` resumes |
| `watchdog` | A host session's: run `rk loop-status`. When it exits 1 while the monitor is ON, or the last tick is more than 25 minutes old, restart the tick loop. Reply with one line. The cron sends the watchdog prompt under this table, which loads no skill |
| `status` | Run `rk status` and relay it in 3–6 lines. Point to the dashboard. `rk status` says how the monitor runs now, from local files: on or off, stopped or draining, the pieces running, the parallel reviews and the parallel builds in effect (each current setting, its range and the scaler's reason), the review queue, the work in flight and the reviews stalled on verification, and which GitHub login each side uses (`GH_LOGINS`, probed at most hourly), with a `!! GH_LOGIN` line when the split does not hold (GitHub logins, below). Whether the setup is right and reaches its services is `rk doctor` |
| `gh-logins` | `rk gh-logins` probes each GitHub login now (GitHub logins, below) and prints `GH_LOGINS`, any `!! GH_LOGIN` line, and a note for a side it could not settle. Exit 1 when the split does not hold |
| `doctor [--fresh]` | `rk doctor` checks the machine's prerequisites, every configured value (secrets only as set or missing) and, read-only, each configured service, each check PASS, FAIL or WARN with the fix. The service checks are cached a few minutes; `--fresh` checks again |
| `update` | Never from this session: an update restarts the session that would run it. <user_login> updates from a shell on the host: `rkmon package update [--from DIR\|TARBALL] [--dry-run]`, then `rkmon confirm` and `rkmon apply` (the work in flight drained, the new code put in, the container made again, then the doctor, the change put back on a new failure); `rkmon rollback` goes back; for a new image `rkmon image load IMAGE_FILE`, `image.tag` set to its tag, then `rkmon confirm` and `rkmon apply` |
| `pr-slot status` | `rk pr-slot status` lists the PR runners' slots, where PR code runs in the container: each one free, taken (by which process or named work), kept for a review (its build, which the other runners read) or broken. `take`, `keep` and `free` are the job scripts' |
| `pr-run [--slot NAME [--end]] [--env FILE] [-C DIR] [--out DIR] -- CMD` | PR code by hand (a test file again, a probe): CMD in a PR runner's slot of its own (in the container; the runner reads no secret and writes only its slot; on a host, as the session user), its folders fresh, in DIR (default: the current folder), every process it left stopped and the slot freed after. Named work (`--slot pr101-probe`: `pr`, the PR's number, `-` and a lowercase word) keeps its slot and files for its next commands until `rk pr-run --slot NAME --end`, the end of that PR's review or the end of the process that started it. `--env FILE`: its environment (NUL-separated); `--out DIR`: its results copied there, as data, in new files only (a name already in DIR is refused). The checks' re-run commands start with it |
| `pr-tree DIR...` | Each DIR, missing or empty, made a folder for a tree PR code reads: in the container the PR runners' group's (2750, no ACL), the one kind of folder a PR runner reads in the scratch folder; on a host a plain folder. An agent's worktree is made so before git adds it, in the same command (the prep summary's `worktrees:` line gives it), and so is a folder for files PR code reads: the session's guard refuses `git worktree add` without it. Exit 1 when one could not be made so (a line on stderr says why) |
| `first-pass N --head SHA` | The review driver's job: the first passes `features.review_automation.passes.ci_triage_pass` and `.first_code_quality_pass` when bound to a model, leads with checked quotes into the PR's `first_pass/`, which `rk review-prep` copies (`ci_triage.md`, `quality_leads.md`); a miss is logged, never an error |
| `notice-draft N --kind overlap\|drift` | The first draft of PR N's overlap or drift notice by `features.review_automation.passes.notice_draft_pass`'s model (`notice_draft_pr<N>_overlap.md` or `notice_draft_pr<N>_drift.md` in the temporary folder, `paths.tmp`): leads only, which you check before you write the notice |
| `board` | Run `rk board` and show the table and the Needs you list as printed |
| `daylog [YYYY-MM-DD]` | Re-render and show the path and summary of a day's log, `<OUTPUTS_DIR>/rocke_daily/rocke_YYYY-MM-DD.md` (UTC). One row per event: review posted (verdict, findings, link), rebase kept, gate, hold, merged/closed, develop, incident, notice, arm, cleanup, ticket, save |
| `log KIND PR\|- TEXT` / `save PR\|- TYPE TEXT` | Hand entries (`-`: no PR). `log` adds an entry of that kind to the daily log: `log ticket - <JIRA_PROJECT>-NNNN …` when a ticket is filed. `save` records an issue the system kept out of develop, by type: finding, fixed, gate, develop, verify, other. A post, a hold and an incident record their saves by themselves |
| `cleanup [--dry-run] [--all]` | Every tick removes the worktrees, builds and outputs of merged or closed PRs that nothing is using (8 PRs per tick), plus finished job and sanity dirs older than 7 days. Shared trees are never touched. `--all` sweeps everything now |
| `queue` | Run `rk status --queue`, which recomputes the queue and the dashboard. Show the ready queue and the top blockers |
| `freeze REASON` / `unfreeze` | Run `rk freeze REASON` / `rk unfreeze`. While frozen, nothing is armed; reviews continue |
| `clear N` / `unclear N` | Run `rk clear N` / `rk unclear N`. Only on <user_login>'s instruction |
| `prioritize N [why]` / `unprioritize N` | Run `rk prioritize N [why]` / `rk unprioritize N` (from a script file when the reason has punctuation). Only on <user_login>'s instruction. Floats PR N to the top of the review and merge queues, like a develop fix (Standing rules, Your priorities) |
| `serve [--port P]` | The local service behind the dashboard's "Request PR priority" box: it serves the admin dashboard, and every request carries the access token (where it listens and who can reach it: `<PACKAGE_DIR>/README.md`, "The admin dashboard"). On <user_login>'s machine a click prioritizes at once (as `rk prioritize`), and pending requests from other teams get Approve and Decline buttons, as do the in-depth reviews waiting on the Needs you list (as `rk review-approve`, `rk review-skip`). `tools/rkweb.py` starts and stops it (below) |
| `priority-requests` / `priority-decline N` | Other teams' requests from the team dashboard's page, each waiting for <user_login>'s OK: each tick pulls them from the web host while the team dashboard is live, and where this monitor serves the page they come to it; the board lists them under Needs you. Approve with the admin dashboard's button or `rk prioritize N`; decline with `rk priority-decline N` |
| `web-host install` | Never from this session: it may not contact the web host (lessons L-340), and the guard refuses `rk web-host-install` to you. <user_login> runs it from a shell on the host: `rkmon web-host install` (on a host install, `rk web-host-install`). It installs the request service on the team dashboard's web host as a user unit with lingering on, over the web host's key, trusting only the host keys recorded for it: it looks first (what serves the page's port, the unit, lingering), copies the service and its unit, then installs it and checks that it answers. It ends INSTALLED; NOTHING TO DO with delivery "serve" or the priority box off; FAILED, nothing changed, naming the step that refused (at the look, the web host's python3 older than 3.6; another program on the port, or <user_login>'s own old `http.server` there, which they stop first; lingering their login cannot turn on); ERROR, naming the step that failed part-way; INTERRUPTED at a Ctrl-C, exit 130, saying what it leaves on the web host, then the command again. The doctor's team dashboard row asks the service at the page's address. The monitor never restarts the host's service itself. The host is shared: the install stops and changes no other server or service |
| `tools/rkweb.py [PORT \| status \| stop]` | The local monitor service: it serves the **admin dashboard** at `<ADMIN_URL>` (`features.dashboards.admin.port`) and takes its priority requests and approvals. `rk start` (or this script) starts it again after a reboot (`<PACKAGE_DIR>/docs/restart.md`) |
| `resume` | Run `rk status`, then read the journal tail and any job in flight. Continue from the recorded stage. Never repeat an action already in the ledger. In the container the orchestrator sends `resume` when it starts and keeps the ticks and the review driver itself: start nothing. On a host, start the tick loop when `rk loop-status` shows none, and create the watchdog cron when `CronList` has none (both as for `on`) |
| `stats [--week YYYY-Www]` | Run `rk stats`, which writes the weekly report to `<OUTPUTS_DIR>/rocke_weekly/rocke_weekly_<week>.md` (default: the last complete ISO week, UTC), then present it as described below |
| `spend [--day YYYY-MM-DD \| --week YYYY-Www \| --since YYYY-MM-DD] [--by part\|kind\|size\|pr] [--experiments] [--write]` | `rk spend`: review spend per UTC day and ISO week (Review spend, below): reviews (posted, kept unposted or closed without a post), covered heads, reviews $, overhead $, total $, and the mean, median, p90, min and max per review; then the selection's outliers and its breakdown by `--by` (default `part`). `--experiments` adds experiment and other tasks' spend, apart. `--write` also writes the selection's day and week files. It reads every transcript not read yet and measures every reviewed diff not measured yet (the first run takes minutes; later ones seconds), and refreshes the dashboards' card. Local: no GitHub |
| `scoreboard [--days N]` | `rk scoreboard`: the Scoreboard (below) in the terminal for the last N days (default 30): one row per PR author, sorted by Rework for others, then the team's totals and the trend. Reads `state/scoreboard_events.jsonl` only |
| `scoreboard-backfill [--days N] [--dry-run] [--no-github] [--state DIR]` | Fill `state/scoreboard_events.jsonl` with the last N days (default 21) from the records (Scoreboard, below), GitHub GETs adding the merges and develop breaks they lack (`--no-github`: none); appends only events not recorded yet, so a second run adds nothing. Prints the counts per column, found and new. `--dry-run` writes nothing; `--state DIR` reads and writes another state folder (a copy, for a rehearsal). The reading runs without the state lock; the append takes it |
| `conflict-files [--days N]` / `ci-times [--days N] [--collect]` | Insights for <user_login>. `rk conflict-files`: the files PRs conflicted on with develop most in the last N days (default 7), the PRs, and the develop PRs that last changed each. `rk ci-times`: push → CI result per PR head, by workflow, the slowest PRs, jobs and runner queue waits; `--collect` first reads heads not recorded yet (capped). Both are read-only; every tick records conflicts and, hourly, CI times (`state/conflicts.jsonl`, `state/ci_runs.jsonl`); the weekly report and the dashboard's insights card show both |
| `lessons [--week YYYY-Www]` | Run `rk lessons`, which writes the week's raw material for the lessons review to `<OUTPUTS_DIR>/rocke_weekly/rocke_lessons_raw_<week>.md`. Then run the review as in tick step 5 |
| `group N N…` / `ungroup N` | Run `rk group …` / `rk ungroup N` to pin or remove a user group. A pinned group is validated as one batch and lands in the given order (`merge_procedure.md`); the merge plan treats it as one PR and places it first among the priorities. Only on <user_login>'s instruction |
| `merge-plan` | `rk merge-plan`: the merge plan from the last queue computation, read-only: the conflict-free waves (priorities in the earliest wave they can take; each wave's union checked), who each landing makes rebase, auto-merge that may land early, and every near-merge PR's rebase advice. Use it when <user_login> asks for the merge order (`merge_procedure.md`, Merge plan). It counts the ABI pairs (two claims in one ABI lane) as conflicts and prints the ABI lanes block |
| `abi` / `abi-ok N` | `rk abi` shows the ABI lanes and each open PR's ABI notes. A note is a struct layout change in a public or generated `include/rocke/` header, an exported function removed or re-signed, with no binary bump, or abi.h and abi.py at different numbers; it is a check flag. Run `rk abi-ok N` after your review confirms that PR N's ABI-header change is append-only |
| `peer-checks N [--check NAME] [--head SHA]` | `rk peer-checks N`: the checks' peer-review sections for PR N at its state head (or SHA), every one or NAME's (flags: `threads`, `trackers`, `envdocs`, `testlists`, `cppenv`, `title`, `splittaut`, `sibimports`, `workload`, `prnumbers`, `perfnotes`, `backedges`, `abiversion`, `arraywrites`, `nanblind`, `optimports`, `mdheadings`; leads: `peerleads`, `paritypair`, `unpack`), as `review_procedure.md` (What the check script covers) gives them. The title comes from the staged `workers/prN/pr/meta.md`, else GitHub. Git and GitHub reads only |
| `incident-add …` | Record a develop break: `rk incident-add START END CULPRIT FIXED_BY --contributing A,B SUMMARY` (use `-` for unknown, END `-` if ongoing). Run it from a script file, because `#` in the summary starts a shell comment (in any shell) |
| `gate N` / `queue-advance` | The tick runs these while the merge queue is enabled (in prototype too). Run them by hand only on <user_login>'s instruction. `rk gate N` starts a local gate job for PR N on today's develop. `rk queue-advance` re-evaluates the queue and may start gate jobs (`merge_procedure.md`) |
| `arm N` / `disarm N [REASON]` / `queue-notice N` | Only as the tick directs (`ARM_READY`, `DISARM_NEEDED`, `QUEUE_NOTICE`), following `merge_procedure.md` |
| `hold N REASON` / `release N [REASON]` / `holds` | A failing queue PR is held, pending your triage (`TRIAGE`). `rk hold` confirms it is the PR's fault, and `rk request-changes` must follow. `rk release` clears it when develop or our tool is at fault, and a released gate failure is re-gated. `rk holds` lists the held PRs. See `merge_procedure.md`, "A held queue head" |
| `request-changes N FILE [--user]` | Request changes on PR N from our account: right after `rk hold N`, or on <user_login>'s explicit instruction (`--user`). Line 1 is `Automated merge-queue hold by <AUTOMATED_REVIEWER_NAME>`. Say what fails and how to fix it, and ask the author to re-request a review once fixed. It refuses on closed or merged PRs, <user_login>'s own PRs, and when <user_login> already requests changes. Only <user_login>'s explicit re-approval lifts it |
| `approvals` | `rk approvals`: the PRs ready for <user_login>'s approval (see Standing rules), then every PR close to merge with what is left and who is next: our review, requested changes, unresolved threads, missing code-owner approvals, CI, conflicts, merge analysis |
| `facts N` | `rk facts N`: the facts a verifier brief needs, read fresh and read-only, in sections: head and state; force-pushes (every head the PR had, newest last); commits; our reviews (the posts in the ledger, then the files in the outputs folder, each a `copy` or `kept unposted`); our account's reviews this deployment did not post (an older monitor's or another deployment's under the same account, or one posted by hand; in a mirror, none posted after the feed line), each with when it was posted, its light and its link: one that stands for ours (its line 1 gives this deployment's name, or none) with the head it reviewed, read from GitHub alone and said in plain words ("the commit the review names", or "the PR's head when it was posted, an estimate"), another deployment's marked "not ours to take"; our last review: header, flagged rows, findings; `rk abi`; `rk breakages`; reviews (latest per reviewer); unresolved threads; <user_login>'s hand-written comments, in full; other people's comments since our last review, in full (bots left out); worker inputs. Paste its output verbatim into the brief (lessons L-201). Exit 1 means a section could not be read |
| `classify N [--record]` | `rk classify N`: PR N's own change at our reviewed head and now (merge-only, rebase-only, rebase+re-record or substantive), as JSON. `--record` reads the PR's live head and refuses (exit 4, nothing recorded) while it is not the head the tick saw, saying so: run `rk tick`, then again. At the live head, a merge-only or rebase-only result is recorded as covered by our review, and a review of that head awaiting verification or in flight is closed without a post |
| `review-close N` | `rk review-close N`: close PR N's review awaiting verification or in flight without a post, when a review our account posted covers the head it was made for and stands for ours: its line 1 gives this deployment's name, or none (an older monitor's under the same account, or one posted by hand: `rk facts N` lists them). That review becomes our last review of the PR, as a post would, so the PR is not reviewed again at that head and a new head gets a follow-up; it says what it closed and journals it, and `rk spend` prices a review it closed awaiting verification as a review of its own. Refused (exit 4, nothing changed), saying why, when our account has no review of that head, or only another deployment's, which is not ours to take; when PR N has no review awaiting verification or in flight, or it moved on to another head while GitHub was read (run it again); and in a mirror. It reads GitHub before it takes the state lock, so a tick never waits on those reads, and writes nothing there. Stop the review's agents that still run yourself (`TaskStop`) |
| `review-prep N [--round ROUND] [--out DIR]` | Before the briefs (`review_procedure.md`, step 1). ROUND is `fr` (a first round; `fr2`, `fr3` … a first round again) or `fu` and a number (`fu1`, `fu2` …); by default `fr` before our first review of the PR, posted or kept unposted, else the next follow-up's: `fu` and the count of our reviews so far, raised past every follow-up round already used. It fills the review directory, by default `v`, N and the round in the temporary folder (`paths.tmp`; `v101fu2`): `facts.txt` (what `rk facts N` prints), `classify.txt` (`rk classify N`), `overlap_section.md` (the checks' overlap section, for the code quality pass) and `files.txt` (the PR's files, from its merge base with its base branch to its head, which `rk post --premises` reads; the base branch is the PR's `base.ref`, develop or the feature branch it targets, fetched first). It prints the prep summary: `facts exit` / `classify exit`, our last three posts, the review directories, probes, archived notes and our review files in the outputs folder, the facts' head lines, our last review, ABI lane and reviews, the classification (its kind, the old and the new head and the count of changed files, then the new commits), the checks' merge and re-probe sections and overlap leads, then `head … mb … commits …` and the file count; and the `worktrees:` line, the verifier's and the code quality pass's worktree paths in the review directory (`wt_v` or `wt_q`, then a name), each added in one command: `rk pr-tree` on the path, then `git worktree add` (a worktree added anywhere else, or not made so, is refused). Read-only apart from the review directory |
| `review-split N [--max-lines L] [--round R] [--out DIR] [--max-agents K] [--team-file F] [--head SHA]` | A review too large for one verifier (REVIEW_MANUAL; `review_procedure.md`, Split review). The PR's own diff (merge base with its `base.ref` to head) in parts each filled up to L changed lines (default 8000; 6,000–10,000 keeps a part within one verifier's reach) area by area, so a part may hold several areas; files that change together share a part, a file over L is cut into slices (a slice may share a part), generated, golden and data files (JSON lines, JSON past 200 changed lines or marked generated, long-line blobs, literal tables) summarized with their generator; a small hand-edited JSON or YAML config (200 changed lines at most, no generated mark near its top) is read like code. Writes `parts/part1.md`, `parts/part2.md` … (each with its `.files`), `parts/cross.md` and `parts/plan.json` in the review directory (default as `review-prep`'s); each part quotes the checklist lines of every area in it from the verifier team file (`paths.verifier_team_file`, derived, or `--team-file`; without it the leads only, and a `!!` line says so) and the code quality checks from the code quality reviewer's team file beside it (a `!!` line when it is not read). Prints a `SPLIT #N` line (the round, the parts, the lines to read, the data files summarized, the folder), one line per part (lines, files, about how many tokens of diff, areas), the cross file, and the dispatch plan: waves of at most K part verifiers (default 20), each running its part's code quality checks too, `no verifier for …` on a follow-up's unchanged parts, then the cross-cutting verifier, each agent with the Agent description and the brief's path to dispatch it with (`description "PR 7 fr part 2 of 9", brief …/v7fr/parts/part2.md`: they name the PR and the round, which is how the orchestrator knows the review has its verifiers), and a `cost:` line: the agents (the parts plus the cross pass) and, with review spend on, about what they cost at the mean review of the spend card's last 7 days; or `dispatch: one part, so no split`. Reads the mirror and the spend card; writes only `parts/` |
| `post N FILE --premises SPEC [--again] [--dry-run]` | Posting a verified review (`review_procedure.md`, step 4): the spec has the verifier's premises. It re-checks them live, then the post's own checks, prints each step and stops at the first change (exit 4); else it posts through `rk post`, then runs `rk save N verify`, the spec's AFTER lines and the notes archive. With review posting off, it keeps the review unposted instead (no comment, no ledger entry); then, while review automation sends nothing (prototype, standby), only the AFTER lines that run `$RK` run, and each send of theirs is kept as an unsent item; while review posting is not set up, none runs. An AFTER line that runs an rk command of <user_login>'s or rk's own never runs, and its line in the output says so (`AFTER not run: rk …`). `--dry-run` runs everything up to `rk post`'s guards and stops before the post (exit 0 when it would post); it also works without `--premises`, for `rk post`'s guards alone. `--again`: a re-review at a head we posted on or, while review posting is off, at the head of our last review (REVIEW_READY's hint says so: `post it with --again` or `keep it with --again`). Every premise and check runs, our earlier review at the head does not stop it, and the state's head must be the live head instead (`the state's head … is not the live head: run rk tick, then post: stop`); the hourly cap and the other guards still apply. A post and a keep each leave the round's copy in `paths.posts` (`pr101_fu2.md`), so a ROUND is used once: a re-review takes a new one. Every stop ends on one line that says why: what the spec or the post has, what is there now, and what to do (`premise: the CI failure set changed: now failing lint (latest attempts): re-verify: stop`). DEVBASE and CONFLICTS are about the PR's base branch (`base.ref`): develop, or the feature branch it targets, fetched into the mirror |
| `spec N --round R [--dir DIR] [--light TEXT] [--save TEXT] [--cost-verifier T] [--cost-quality T] [--out FILE]` | Writes the spec for `rk post N FILE --premises SPEC` (default `spec<N><R>.json` in the temporary folder: `spec101fu2.json`) from the review directory (default `v<N><R>` there, as `review-prep`'s) and live reads. From `notes.md`: the `premises:` line (HEAD10, DEVBASE: its develop commit, or for a PR on a feature branch `base`, the branch and its commit; MAXCANCEL; STOP; THREADS from its `a/b`, read as open/total or resolved/total, whichever the live threads match), the `FAILOK` line (`none`, `(none)`, `-` or nothing names no job; so in a spec's FAILOK or RUNOK list), `CI pending:`, the `conflict set` line and each `decide:` line, with its key, owner and members (an AFTER line, `$RK overlap-decide …`). From the round's post (`pr101_fu2.md`): LIGHT (its header's, unless `--light`) and the fill anchor, the Bots / CI row's ✓ count ("12 ✓"), extended to the left until it is unique in the post; a row with no ✓ count gets one appended in the post file ("; 12 ✓", with the live count). Live: FAILOK (the failing latest attempts the notes' FAILOK names: exact names, as GitHub gives them, a name the notes cut matched by its start), RUNOK (the runs still going), CONFLICTS (`git merge-tree` of the head with its base branch's head), <JIRA_PROJECT> (the tracker tag in the PR body; the profile's `tracker_keys`; `""` for none). SAVE is `--save`, else the round and the light (`fu2: 🟢`); COST is `--cost-verifier` / `--cost-quality`. A `CHECK:` line says where the notes and now differ (another head, a failure the notes do not account for, a run they did not see, more cancels, other threads, another conflict set); the spec keeps the verified side, so the premise stops the post. Exit 0, 3 with a CHECK line, 4 when no spec was made. GitHub GETs and the mirror; writes the spec and, for a missing ✓ count, the post |

## Settings

The monitor runs with one value per setting, each from its layer: the deploy settings file (<user_login>'s), the
package's defaults (`<PACKAGE_DIR>/config.defaults.json`, with the repository's defaults over some of them,
`<PACKAGE_DIR>/repository/<org>__<repo>/defaults.json`), the internal state (the monitor's own records, such as
`jira.accounts`), or derived from the others. With no deploy settings delivered, the monitor reads its home's
`config.json` too. `<RK> config show` prints every value under its file's name, never a secret (`--source`: the layer
each one came from), and `<RK> features` what is on and what it uses. Never edit a settings file or the state: a
deploy setting is <user_login>'s to change (`<PACKAGE_DIR>/QUICK_USER_GUIDE.md`, "Change a setting"), a package or
repository default changes in the package's source, as a pull request, and `<RK> jira-account add LOGIN ACCOUNT`
records a JIRA account. Develop breakages go to GitHub issues (`features.merge_queue.develop_guard`). JIRA is reached
through the atlassian CLI (JIRA through the atlassian CLI, below), with the project, epic, components and labels of
`features.ticket_creation`.

## GitHub logins

Two GitHub logins, each in its own gh folder:

| Login | Folder | Can write | Used by |
|---|---|---|---|
| read | `gh.read_config_dir` | no: GitHub answers 403 | every read of the toolkit (`rkmon_lib/gh.py`, `tools/ghr.py` for the shell tools), every job and check (no other login folder, token or `ATLASSIAN_CONFIG_DIR` reaches PR code), and any gh that names no folder: this session, the verification pass, the code quality pass |
| write | `gh.write_config_dir` | yes | the guarded `rk` write commands alone (`rkmon_lib/post.py`, through the `write` of `rkmon_lib/gh.py`) |

Each gh the toolkit starts gets its login's folder as `GH_CONFIG_DIR` and no token variable. In the container the split
is enforced: the write login's folder belongs to another user, and `rk`'s GitHub write commands run as that user through
the write broker (`docker/rk_write.py`), which runs the writer's commands alone (those GitHub writes, and the sends that
need the writer's secrets: `<PACKAGE_DIR>/rkmon_lib/outward.py`); `rk spec-post` and `rk post --premises` run as this
session (their premises read git, their AFTER lines run commands), and only their post goes through the broker. On a
host both folders are one user's, and the split stands only because nothing else is pointed at the write one.

`rk status`, `rk gh-logins` and every tick check the split with two writes GitHub refuses either way, so nothing is
made: a comment with no body on `gh.probe_issue`, and a branch on a commit that does not exist. GitHub answers 422 when
the login may make it and 403 when it may not; `<PACKAGE_DIR>/README.md`, "The GitHub CLI", says what each login must
and must not be able to do. The check runs at most once an hour, or at once when a folder's login file changes, and its
result is kept in `state/gh_logins.json`. A `!! GH_LOGIN` line stands while a login can do what it must not, or cannot
do what is needed of it, and names the login, its folder, what is wrong and the fix: tell <user_login>.

On a host whose gh login sits in gh's own folder, <user_login> makes the split once, between ticks, with
`tools/gh_split_apply.py`: the write login moves to its own folder (`gh.write_config_dir`), and gh's own folder gets a
copy of the read login, which stays in its folder (`gh.read_config_dir`), so a gh that names no folder only reads. It
refuses while there is no read login; `<PACKAGE_DIR>/README.md`, "The GitHub CLI", says what it checks, and
`tools/gh_split_rollback.py` undoes it. Then a git push over HTTPS whose credential helper is gh gets the read login and
is refused; <user_login> pushes with the write login's folder as `GH_CONFIG_DIR` themselves.

## JIRA through the atlassian CLI

Every JIRA read and write of the monitor goes through the atlassian CLI, never an MCP server. The session, the
verification pass and the code quality pass reach it through rk: `<RK> atlassian` runs one of the CLI's commands the
writer lists (`<PACKAGE_DIR>/rkmon_lib/writer.py`) with the CLI's login, which the session's environment never names (in
the container the writer runs it, and only the writer reads the login). Run these in Bash where the monitor runs.
Anything off the list (a command, an option such as `--verbose`, an option given twice other than `--field` and
`--field-json`, a value that starts with @) is refused, exit 4, and so is a write while follow-up tickets are off. The
site is `<ATLASSIAN_SITE>`; the project, components and labels are `features.ticket_creation`'s. A write names that site
with `--site`, and the ticket it files or changes, and the epic it links that to, are `<JIRA_PROJECT>`'s (or the
settings' epic): any other is refused, exit 4. While ticket creation sends nothing (prototype, standby), a write is kept
as an unsent item instead, and its line alone says so
(`UNSENT: a JIRA write for the JIRA project <JIRA_PROJECT>, kept as an unsent item: ...`, exit 0): no ticket is made, so
skip the steps that need its key. The CLI prints a "new version" notice first: skip that line.

| What | Command |
|---|---|

## The drafter

The first review pass of every review is the draft stage (`review_procedure.md`, Stages, with the pool, the shadow
drafter, the scaler and the smoke gate). `features.review_automation.passes.first_review_pass.model` picks the live
drafter: `default`, none (below: the verifier reviews alone; the package's default); `worker`, the local review loop
(the binding named `worker`); or another model (`opus`, `sonnet`, `haiku` or a `model_bindings` name, its `provider`
`openai_compatible`, `ollama` or `claude`), whose tool loop then drafts. The tick triage is the rule filter
(`rk tick-filter`) unless the package's defaults' `models.tick` names a model, and never follows the first review pass
(the package's README, Swapping the reviewer model). A shadow drafter, when the package's defaults'
`roles.shadow_drafter` names a binding, drafts every live review beside it, under assessment: the verifier scores it
against the verified post, and line 1 never names it.

The tool loop drafts in phases, each with its own `drafter.*` caps:
- settle (script, seconds): the merge, `rule_scan`, the CI row, and the prior items that need no model, each with
  evidence (approvals, the Threads row, rows whose cited files are unchanged since the head of our last review, closed
  rows that cite no file, saved probes giving FIXED or REPRODUCES), listed in `prior_leads.md`;
- prior (model): one short task per prior item left open, `prior_parallel` at once, each settling it FIXED, OPEN or
  PARTIAL with a quote or a run, or SKIP;
- hunt (model), at the same time: net-new findings, the files changed since our last review first; every 🔴/🟠 needs
  its evidence;
- assemble (script): the draft, each prior row with its status, settler and evidence id; then the evidence check
  (`evidence_check.md`, `prior_settled.md`).

The drafter is a setting, never the session's to change: the first review pass is <user_login>'s
(`<PACKAGE_DIR>/QUICK_USER_GUIDE.md`, "Change a setting"), and `roles` a package default. What each choice does:

- **Shadow drafter:** its drafts go to `workers/`, in `shadow_` and its binding's name, then `prN/`
  (`workers/shadow_glm/pr101/`); the live review never adopts one and never waits for one.
- **A binding as the live drafter:** line 1 names its model and effort, from the next review start on:
  `Automated review by <AUTOMATED_REVIEWER_NAME>: Model - GLM-5.3-Flash, effort: high`.
- **The local review loop as the live drafter** (`worker`): line 1 reads
  `Automated review by <AUTOMATED_REVIEWER_NAME>: Model - <WORKER_MODEL>, effort: high` with the first review pass's
  effort at high, and `effort: the model's default` on its `default`, which sends none.
- **No drafter** (`default`): the next review start stages the PR (its data and trees) and starts its checks with no
  draft: no local review loop, no tool-loop draft, no pool, no draft lint. REVIEW_READY reads "no drafter: verify
  without a draft … Verify alone"; the verifier reviews without a draft and its notes read `qwen none` (no draft to
  score; `<shadow tag> none` too when no shadow draft came), and nothing is recorded for a live drafter. Line 1 is the
  verifier's (`review_first_line_no_draft`) and the footer names the verifier with no "first pass by":
  `rk post --premises` stops a footer that credits one. A shadow drafter still drafts beside each review and is scored.
  `rk drafts` reads `drafter: default: no drafter, …` with no `problem:` line.
- Line 1 follows the live drafter (`review_first_line`) at each review start, and a review keeps the line 1 it was
  staged with: `rk post` refuses any other, so a review in flight when the first pass changes posts with its own.
- After a change, `rk drafts` shows the bindings and prints a `problem:` line for each settings error.

**The drafters' card** (`rk drafts` only; no dashboard shows it), titled with the shadow drafter's tag in capitals, else
the live drafter's, then the verifier's model family (`GLM drafter vs Opus`). It sums the verifiers' assessment lines,
which `rk post --premises` records in `state/drafter_assessment.jsonl` (one record per drafter per post), and the
drafts' records. A column per drafter, the shadow and the live one, each on its current method only, with a count of the
drafts of other methods it leaves out: prior statuses right (by settler: script or model), new findings' 🔴/🟠 and 🟡
recall, false claims per draft, tokens and minutes per draft and per phase, and the drafts missing or late at post time.

## Review spend

What each review cost, posted, kept unposted or closed without a post, from local files only (`rkmon_lib/spend.py`,
`rkmon_lib/spend_scan.py`); no model call.

- **One review = one post, one review kept unposted, or one review closed without a post.** A post is a line of the
  ledger (`state/actions.jsonl`): its kind comes from the post's note (first round, follow-up, CI update), its round
  from `state/review_cost.jsonl`, else from its verifier's brief. A review kept unposted while review posting is off
  has no ledger entry: its line of `state/review_cost.jsonl` (`unposted`) gives it, and its round its kind. So does
  a review awaiting verification that `rk review-close` closed (`closed`): a review of its own, shown as closed, so
  its verifier runs are never booked on the PR's next review.
- **Parts of a review**, priced with `features.review_automation.spend.usd_per_million_tokens` from the transcripts
  under `paths.claude_projects` (the monitor's main sessions, those holding `/rocke-monitor`, and their subagents):
  - verifier: a verifier run counts for the PR's first review at most 48 h after the run started; that review's first
    such run is its verifier, any later one its second verifier;
  - code quality pass: its runs, matched the same way;
  - orchestration: the main session's turns whose review actions name the PR (its review directory, post, spec, facts or
    worker files, the review commands and scripts with its number, a verifier or code quality agent it starts or hears
    back from), when a turn names one to four such PRs (split evenly), booked on the PR's first review within 12 h after
    the turn, else its last review within 6 h before. A PR a command uses only as another PR's template
    (`sed 's/101/102/g' facts101.sh > facts102.sh`), as a copy's source (`cp`), or whose script it only reads (`cat`, a
    Read) is no review action on it.
- **Overhead** (in the day's total, never in a review's): orchestration no review takes, verifier and code quality runs
  no review follows, overlap notices' drafts. **Not review spend** (`rk spend --experiments` only): experiment runs
  (replays, gold and batch runs, bake-offs, fan-out lenses, the Sonnet copies, the hybrid arms), the experiment ledgers
  (each `spend.jsonl` one folder down in `paths.scratch`, exact), other tasks' runs, and the main-session turns that
  only start or hear back from them.
- **Covered heads** (merge-only and rebase-only heads recorded as covered by our review) cost no Claude spend: counted
  in their own column, never in the averages.
- **Estimated output.** A transcript records a request's output tokens at the start of its stream only, so every
  transcript figure estimates output from what each request wrote (0.45 tokens per character of text and tool input,
  0.266 per character of an Opus thinking signature, 0.28 for other models). Input, cache writes and cache reads are as
  recorded. Only the experiment ledgers are exact.
- **Size tier** of the reviewed diff, in effective lines (`rkmon_lib/hybrid/size.py`; a follow-up counts the lines new
  since the head of the review it follows up on: a post's, our previous post; a kept or closed review's, our previous
  review): under 1.5k, 1.5k–10k, 10k+, `?` when the clone lacks the objects. An outlier also gets its impact tier
  (`rkmon_lib/hybrid/impact.py`, without the clash and develop signals). Both are cached in `state/spend_sizes.json`.
- **Figures.** Days and ISO weeks in UTC; a review counts on the day it was posted, kept or closed, overhead on the day
  it was spent. Per period: reviews, covered heads (merge-only / rebase), reviews $, overhead $, total $, and the mean,
  median, p90, min and max per review. Outliers: reviews above Q3 + 1.5 × IQR of their period (four reviews at least),
  with PR, round, kind, $, size tier, impact and the part that cost most. A review whose orchestration is more than its
  verifier and code quality runs together while its PR is never the only PR of a turn booked to it is marked suspect:
  its "Driven by" cell says so, a "Suspect attribution" line under the outliers lists the selection's suspects, and the
  day's review table marks its orchestration cell. Check its turns: they may name it without any review work on it.
- **Files** in `paths.spend_dir` (`<OUTPUTS_DIR>/rocke_spend`): `spend_YYYY-MM-DD.md` (the day's row, by
  part, kind and size, the outliers, every review) and `spend_YYYY-Www.md` (the week's days and total, by part, kind
  and size, the outliers, the PRs by spend). The tick writes yesterday's day file and its week's file once, 15 minutes
  after the UTC day ends; `rk spend --write` writes any selection.
- **The card "Review spend"**, on <user_login>'s dashboards only: the last section of `rocke_merge_queue.md`, and in
  the admin dashboard (the local `rocke_monitor.html`) after the Scoreboard and before Today's log; the published team
  dashboard has none of it: today and this week so far (reviews, total $, mean, median, p90, max), the last 7 days
  one row each, and this week's outliers (PR, round, $, the part that cost most). Review workload only: no experiment
  spend. A full tick refreshes it at most hourly (`state/spend_summary.json`).
- **The weekly report** has a "Review spend" section: the week's days and total, by part, kind and size, the outliers.
- **Cost to the tick.** The parsed transcripts are cached in `state/spend_cache.json` by file size and modification
  time: an unchanged file is not read again, a growing main session is read on from where the last pass stopped, and
  a main session quiet for 6 hours is not looked at again. A tick reads at most 64 MB of new transcript and spends at
  most 20 s measuring diffs; the rest waits for the next pass. A failure prints `(spend not refreshed: …)` and never
  fails the tick.

  ref}`, `author` the PR author it counts for. The card reads only this file. Each full tick derives the last 8 days'
  events from the records and appends the ones not recorded yet; an event's identity (kind and its PR, other PR or
  reference) is recorded once, so a tick run again or a backfill run again adds nothing. Its git questions are
  answered once and kept in `state.json` (in its `scoreboard`, under `git`); a tick spends at most 0.4 s of git on new
  ones, and the rest waits for the next tick. A failure prints `(scoreboard not recorded: …)` and never fails the tick.
- **Merged:** an in-scope PR merged into develop (a MERGED event, the state's merged PRs; backfill: GitHub's search).
- **Rebases forced:** another author's open PR turned CONFLICTING within 3 h of a landing, with no push of its own in
  between, and the landing is the only develop commit in that window that changed a file it conflicts on (with no file
  record: the only landing whose merge-plan forced-rebase list named it). Golden files that conflict count as a
  re-bless.
- **Rebases forced (resolved):** a develop merge on another author's PR branch resolved conflicts in files exactly one
  develop PR changed since the branch's base: that PR.
- **Re-reviews caused:** a follow-up round we posted on another author's PR whose title names one landed PR as what
  landed, or what to port or rebase over (a first round never counts).
- **Re-reviews caused (merge-only):** a follow-up round we posted whose head is a develop merge, and whose whole delta
  since our previous post on the PR resolves a conflict attributed to one landing.
- **Re-reviews caused (overlap):** the first follow-up round after the owner of an overlap group the PR got our notice
  for landed, when its title speaks of a port, a rebase or the land order.
- **Rework for others** = Rebases forced + Re-reviews caused. Each pair (landing, PR) counts one rebase; each round
  counts once; a round or a conflict with two candidate landings counts for neither.
- **Develop breaks:** a develop break filed on GitHub (of either type, rocKE) whose title says "since
  #N", or whose incident names the breaking PR, when that names exactly one in-scope landing.
- **Landed ahead of plan:** a PR that merged while the merge plan the tick last saw had an AUTOMERGE_JUMP or a
  PRIORITY_READY_EARLY on it, or from a wave after the first while its landing made a PR of an earlier wave rebase.
  Backfill: an AUTOMERGE_JUMP or PRIORITY_READY_EARLY line in the tick log at most 12 h before the merge.
- **Merged with open review items:** a MERGED_OVER_RED or HELD_MERGED for the PR (the state's `merged_over`, which the
  tick reads before it is pruned; backfill: the journal's lines for them).
- **Follow-ups:** a follow-up ticket filed for a merged PR: a `- KEY-N:` line of
  `state/followups/tickets_<N>.md` (an existing ticket only commented on does not count), or a daily-log ticket entry
  "follow-up from merged N".
- **Backfill.** `rk scoreboard-backfill` (above) derives the same events from every record, as far back as they go,
  plus the journal and the tick log; GitHub GETs add the merges and develop breaks the records lack.
