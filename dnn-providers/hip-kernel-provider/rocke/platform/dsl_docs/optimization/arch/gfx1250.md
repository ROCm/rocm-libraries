# Target Architecture Reference: gfx1250 (CDNA family, GFX12 programming model)

> Specializes the [CK DSL Optimization Runbook](../optimization_runbook.md).

gfx1250 does not fit the CDNA/RDNA split the other references assume. It is
`family="cdna"` but runs **wave32** on the **GFX12 programming model** with a
**WMMA** matrix path and **no MFMA**. Any gate that treats "cdna" as a proxy for
wave64 or for MFMA is wrong here — that has already produced two live defects
(§21.8).

Facts below are either read from `core/arch/data/arch_specs.json` or measured on
device. Anything not established is marked **unknown** rather than guessed.

| Property | Value | Source |
|---|---|---|
| family / target_family | `cdna` / `gfx12_cdna` | arch_specs |
| matrix_path | `wmma` (`has_mfma=false`) | arch_specs |
| wave_size | **32** | arch_specs + `rocminfo` |
| CUs | 256 | `rocminfo` |
| SIMDs per CU | 4 | `rocminfo` |
| Max waves per CU | 64 (→ 16 per SIMD) | `rocminfo` |
| Max workgroup size | 1024 | arch_specs + `rocminfo` |
| LDS capacity | 163840 B (160 KiB) | arch_specs |
| VGPRs addressable / wave | **1024** (fast range 256 — §21.4) | measured |
| AGPRs | **0** | arch_specs |
| waitcnt / barrier model | `split_gfx1250` / `split_named_cluster` | arch_specs |

## 21.1 WMMA atom catalog (gfx1250)

The fp16/bf16 atom is **K=32**, *not* gfx1201's K=16. Low-bit forms are K=64.

| dtype in | acc | shape | op_id |
|---|---|---|---|
| fp16 | fp32 | **16x16x32** | `wmma_gfx1250_f32_16x16x32_f16` |
| bf16 | fp32 | 16x16x32 | `wmma_gfx1250_f32_16x16x32_bf16` |
| fp32 | fp32 | 16x16x4 | `wmma_gfx1250_f32_16x16x4_f32` |
| fp8/bf8 (4 combos) | fp32 | 16x16x64 | `wmma_gfx1250_f32_16x16x64_{fp8,bf8}_{fp8,bf8}` |

For fp16 there is exactly **one** atom, so the atom is not a tuning lever here.

## 21.2 LDS specifics

160 KiB per CU; `wgp_cache_lds_shared=true`. No LDS bank-conflict counter is
exposed (§21.8), so conflicts must be inferred from the LDS layout rather than
measured.

`lds_k_pad` is the **largest single measured lever** for fp16 GEMM on this part,
and it is **not independent of tile geometry**. At `tile_k=64` the unpadded
variant runs ~2.9x slower, and the response across pad values {0, 8, 16, 24, 32}
is non-monotonic (relative {0.34, 1.00, 0.86, 1.00, 0.61}) — a bank-aliasing
signature with period-16 structure, so it cannot be tuned by hill-climbing
from 0.

Practical consequence: **ranking tile geometry at `lds_k_pad=0` gives the wrong
answer.** Every top geometry is `tile_k=32` at pad 0 and `tile_k=64` at pad 8,
a 1.33-1.54x difference. Sweep the pad together with geometry, or fix the pad
before ranking tiles.

`lds_swizzle=True` is **numerically broken** — see §21.8.

## 21.3 Cross-lane primitives

Wave32, so every cross-lane pattern is half the width of the CDNA references.
gfx1250 has a hardware transpose-LDS read, `ds_load_tr16_b128` (GPU-validated
per the arch-spec notes). Note `has_ds_read_tr=false` in `arch_specs.json`
denotes the absence of the **gfx9 ABI**, not the absence of the capability.

**`global_load_tr16_b128` assembles but has no supported usage on gfx1250.**
The *global* transpose read is a different instruction from the LDS one above,
and it is the obvious-looking way to feed WMMA operands without an LDS round
trip. It is a dead end here; recorded so the investigation is not repeated.

Probed on device it returns data to only **4 of 32 lanes** (lane `8k` gets
element `k` of each of 8 consecutive 16-byte blocks). That is invariant under
every address pattern tried — including all lanes sharing one address — and all
32 lanes are confirmed to execute, so it is not an addressing mistake.

CK explains it structurally. `ck/utility/amd_transpose_load.hpp`
(`amd_global_load_transpose_to_vgpr`) is gated `#if defined(__gfx12__)`, which
`ck/ck.hpp` **does** define for gfx1250 — so the function exists. But its only
consumer, `ABTransferWaveTiles` via `dynamic_buffer`'s `DoTranspose`, is gated
in `gridwise_gemm_wmma_cshuffle_v3_common.hpp` on `#if defined(__gfx120__)` —
which `ck/ck.hpp` defines for gfx1200/1201 only. The `#else` sets
`IsAWaveTransferApplicable = false`, so the transfer falls back to the ordinary
`ABTransferThreadTiles`. `ck_tile` goes further and `static_assert`s that
transpose loads are unsupported in the global address space, shipping only the
`ds_*` variants.

Confirmed by compiling, not only by reading: the `km_kn_mn` f16 instance (A
column-major against a required row-major **and** B row-major against a required
column-major, i.e. both operands transposed — the maximally favourable case)
built for gfx1250 yields ~57k lines of ISA with ~1040 `v_wmma` and **zero**
`global_load_tr`. The path is enabled for RDNA4 and switched off here.

Treat it as unavailable unless a future toolchain enables the `__gfx120__`-gated
path for this target. The LDS-side `ds_load_tr16_b128` is unaffected and remains
the supported transpose read.

## 21.4 Register / occupancy

0 AGPRs, 4 SIMDs/CU, 64 waves/CU → 16 per SIMD.

**A lane can address 1024 VGPRs, but indices above 255 carry extra latency.**
This is the single most misread number on this part. `arch_specs.json` reports
`limits.vgprs = 256`, which is the size of the *fast* range, not a hard cap —
allocations beyond it are legal and do not spill, they just get slower.

The practical consequence is that a register-blocked tile large enough to push
accumulators past index 255 is neither impossible nor free. Worked example: a
per-warp atom grid of `m x n` costs `m*n*8` accumulator VGPRs, so 4x4 needs 128
(all fast) while 8x8 needs 512 — legal, but with three quarters of the
accumulator in the slow range, and at one wave per SIMD.

Measured, that rarely pays: at a `256x256` tile an 8x8 grid allocates the full
1024 VGPRs and runs at **0.98** of the 4x4 baseline despite halving LDS reads
per WMMA, while a moderate 4x8 grid (256 accumulator registers) wins at 1.02.
The turnover is in §21.10.

So treat 256 as the budget to design against, and anything above it as a
deliberate, measured trade — not as a wall (which under-explores) and not as
free capacity (which over-promises).

Measured with a register-resident WMMA kernel: VGPR cost is exactly **8 per
`<8 x float>` accumulator**, so 28 independent accumulators (242 VGPR) is the
last allocation inside the fast range; 32 exceeds it and 64 spills
(`scratch_size=132`).

**Unknown:** `vgpr_per_cu` (total VGPR file per SIMD) and
`vgpr_alloc_granularity`. Neither is in `arch_specs.json`, neither is reported
by `rocminfo`, and no authoritative source was found. Consequently **there is
deliberately no `ArchCaps` entry for gfx1250 in
`utilities/tools/dsl_probes/probe_occupancy.py`**: a partial entry would make
the occupancy estimator emit confidently wrong waves/CU numbers, whereas its
absence produces a clear "unknown arch" error. Spill detection and raw
VGPR/LDS/scratch readout work regardless, since those come from the HSACO ELF
notes and need no caps.

## 21.5 Chiplet / XCD

Not applicable — `chiplet_swizzle` is rejected on the WMMA path.

## 21.6 Buffer descriptor (AMDGPU)

`buffer_load_max_dwords=4`. `src_bytes`-style descriptor sizes are 32-bit, so a
single buffer descriptor cannot address ≥ 2 GiB.

## 21.7 FP8 / quantization

fp8/bf8 WMMA atoms exist at **K=64** (all four fp8/bf8 operand combinations).
The gfx12 16x16x16 FP8 form is *not* selectable here. Block-scaled F4/block16
forms are intentionally absent from the shipped catalog.

## 21.8 Caveats specific to gfx1250

**Correctness — `lds_swizzle=True` returns wrong results.** Every configuration
tested with it on failed verification against the fp32 reference (120/120),
versus 0/121 with it off. It compiles and runs clean, and no validator rejects
it. Do not enable it on this path until fixed.

**Correctness — a race on some geometries.** Certain `tile_m=32, tile_k=64`
shapes produce `nan`/`inf` with a *varying* bad-element count across identical
runs. A single passing verification is therefore not sufficient evidence on this
part; repeat it.

**Family is not wave size, and family is not matrix path.** Two live defects came
from treating `family=="cdna"` as a proxy:
`dispatch/gemm/common.py::apply_split_k` gated on arch family and so engaged
split-K here, emitting specs the builder then rejects (`split_k > 1 is
CDNA-only`); and `dispatch/gemm/support.py` carried a WMMA gate hardcoded to the
gfx11 `16x16x16` atom, making every legal gfx1250 spec undispatchable. Both are
fixed; gate on `target.has_mfma` / `matrix_path`, never on `family`.

**Profiling — PMC counters do not populate.** `rocprofv3 --list-avail` enumerates
292 counters (including `SQ_VALU_WMMA_FLOP_FP16`) and collection completes
without error, but **every `Counter_Value` is 0** across all passes and
dispatches. This extends the documented RDNA4/gfx1201 limitation to gfx1250. Use
the §3.1a fallback: kernel-trace resources (which *do* populate) plus static ISA
from `llvm-objdump`. Also note rocprofv3 defaults to SQLite `rocpd` output here —
pass `--output-format csv` if you want CSV.

**Runtime — pin the HIP library.** On at least one host, ROCm `10.1.0a20260811`
fails a bare `hipMemcpyH2D` with `HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION`
while `10.0.0a20260729` works, and the system `/usr/bin/rocminfo` segfaults while
`/opt/rocm/bin/rocminfo` does not. Pin rocke's runtime explicitly:

```bash
export ROCM=/opt/rocm-10.0.0a20260729
export ROCKE_HIP_LIB=$ROCM/lib/libamdhip64.so
export LD_LIBRARY_PATH=$ROCM/lib
```

**Compiling and launching in one process aborts.** comgr's LLVM and the HIP
runtime's LLVM clash (`Option 'spirv-expand-step' registered more than once`).
Build HSACOs in one process (or on another host) and launch them in another.

## 21.9 Default ISA target

`amdgcn-amd-amdhsa--gfx1250`. `gfx12-generic` also enumerates on device but is
not the DSL target.

## 21.10 Tensor DMA (TDM) — descriptor-driven global↔LDS transfer

gfx1250 has a DMA engine that moves a tiled sub-region of a global tensor into
LDS (`tensor_load_to_lds`) or back out (`tensor_store_from_lds`) from a single
wave-uniform descriptor, bypassing the per-lane VGPR staging that a normal
global→LDS copy requires. Both ops are lowered by rocke
(`tile.tensor_load_to_lds` / `tile.tensor_store_from_lds`, paired with
`tile.s_wait_tensorcnt`), but rocke exposes the five descriptor groups as opaque
`vec<i32,4>` / `vec<i32,8>` operands and validates only their widths — **it has
no descriptor constructor**, which is why its own feature probe
(`examples/gfx1250/isa_features/tdm_verify.py`) is compile-only.

The descriptor layout is not opaque, though. Two independent in-repo
implementations define it field by field and agree with each other:

- `projects/composablekernel/include/ck_tile/core/arch/amd_tdm_descriptor.hpp`
  — the full reference: bitfield unions for every group, a `TDMDescriptor<DataType,
  TensorRank, IsGatherMode>` class, and `createTDMDescriptor(...)`.
- `projects/miopen/src/hipconv/src/arch/cdna5/tdm_desc.h` — a smaller
  split-init/patch wrapper that documents several semantics the first leaves
  implicit.

An upstream LLVM/MLIR view of the same intrinsic lives in the shipped
`mlir/Dialect/AMDGPU/IR/AMDGPUOps.td` (`amdgpu.make_dma_base` /
`amdgpu.make_dma_descriptor`), useful as a third cross-check on field meaning
but **not** on bit placement — the MLIR conversion pass that does the packing is
shipped only as a compiled archive.

### Group 0 (`vec<i32,4>`) — addresses and op mode

| word | fields (LSB→MSB) |
|---|---|
| 0 | `count:2` (=1), `is_restore:1`, `is_store:1`, `nv:1`, `scope:2`, `th:3`, `user_null:1`, `reserved:19`, `gather_index_size:1`, `gather_mode:1` |
| 1 | `lds_addr:32` |
| 2 | `global_addr_lo:32` |
| 3 | `global_addr_hi:25`, `reserved:5`, `type:2` (=2) |

`count=1` ("valid tensor"; 0 means NULL tensor) and `type=2` are fixed magic
values, identical in both implementations. The two references differ only in
naming, not bit placement: ck_tile lumps bits 10–29 into one `reserved_space:20`
where the other splits out `user_null:1` first.

`is_restore`, `nv`, `scope`, and `th` are all documented "must be 0" —
cache policy travels in the intrinsic's separate immediate operand (`th` in bits
0–2, `scope` in bits 3–4), **not** in this word. `is_store` also stays 0:
direction is chosen by which intrinsic you call, not by this bit.

### Group 1 (`vec<i32,8>`) — shape, stride, modifiers

| word | fields (LSB→MSB) |
|---|---|
| 0 | `workgroup_mask:16`, `data_size:2`, `atomic_barrier_enable:1`, `iterate_enable:1`, `pad_enable:1`, `early_timeout:1`, `pad_interval:3`, `pad_amount:7` |
| 1 | `atomic_barrier_address:16`, `tensor_dim0_lo:16` |
| 2 | `tensor_dim0_hi:16`, `tensor_dim1_lo:16` |
| 3 | `tensor_dim1_hi:16`, `tile_dim0:16` |
| 4 | `tile_dim1:16`, `tile_dim2:16` |
| 5 | `tensor_dim0_stride_lo:32` |
| 6 | `tensor_dim0_stride_hi:16`, `tensor_dim1_stride_lo:16` |
| 7 | `tensor_dim1_stride_hi:32` |

`tensor_dim*` are **full-tensor** element counts, `tile_dim*` the tile element
counts, and strides are in elements. Dims and strides straddle word boundaries,
so packing is not a per-word store. Decode rules:

```text
tensor_dim0 = w1[16:32] | w2[0:16]  << 16          (32-bit)
tensor_dim1 = w2[16:32] | w3[0:16]  << 16          (32-bit)
stride[0]   = w5[0:32]  | w6[0:16]  << 32          (48-bit, split at bit 32)
stride[1]   = w6[16:32] | w7[0:32]  << 16          (48-bit, split at bit 16)
```

**The two strides are not encoded the same way** — `stride[0]` is `lo32 + hi16`
and `stride[1]` is `lo16 + hi32`. Both total 48 bits, but the split point
differs, and that asymmetry is easy to miss.

⚠️ **The two references disagree here.** The MIOpen version is internally
consistent — its setter (`lo = stride; hi = stride >> 16`) and getter
(`lo | hi << 16`) round-trip. The ck_tile version writes
`tensor_dim1_stride_hi = value >> 32` into a field whose companion `lo` is only
16 bits wide, so bits [16:32] of the stride are dropped and the value cannot
round-trip; it has no getter to contradict it. The discrepancy is **masked
whenever `stride[1] < 2^16`**, which is the common case since the innermost
stride is usually 1 — so existing ck_tile callers are unaffected. Follow the
MIOpen encoding; do not copy ck_tile's shift for the second mode.

`data_size` is a 2-bit `log2(sizeof(element))` code: `0`→1 B, `1`→2 B (fp16/bf16),
`2`→4 B, `3`→8 B.

### Groups 2 / 3 / 4

Groups 2 and 3 are unioned three ways — dims 2–4 for rank > 2, *or* the gather
row-index array, *or* the iterate config (`global_addr_increment`,
`lds_addr_increment`, `iterate_count`). For a rank ≤ 2 non-gather transfer both
are all-zero. Group 4 is reserved and silently ignored; pass zeros.

### Dimension order: `dim0` is the *fastest-varying* dimension

Neither reference states this outright and it is the easiest thing to get
backwards, so it was settled on device
(`examples/gfx1250/isa_features/tdm_descriptor_verify.py`):

- **`dim0` / `tile_dim0` are the innermost, contiguous dimension** — the
  opposite of NumPy's `shape` order.
- **Stride slot `i` advances `dim(i+1)`.** There is no stride for `dim0`; it is
  implicitly unit-stride. So for a row-major 2D tensor, descriptor stride slot 0
  is the **row pitch**, and slot 1 is unused at rank 2 (setting it to 0 or to a
  bogus value changes nothing — verified).
- **The tile lands in LDS row-major and contiguous**: `tile_dim1` rows of
  `tile_dim0` elements, no implicit gap (absent `pad_enable`).

The failure signature when the order is reversed is distinctive: LDS fills with
runs of `tile_dim0` elements separated by the stride, instead of runs of the
intended inner extent. A 4x8 tile read from a 4x16 tensor with the arguments
transposed produced runs of 4 stepping by 16, then zero-fill — i.e. it silently
reads the wrong rectangle rather than faulting.

Mapping a row-major `(rows, cols)` tensor onto the descriptor:

```text
dim0 = cols      tile_dim0 = tile_cols    stride slot 0 = row pitch
dim1 = rows      tile_dim1 = tile_rows    stride slot 1 = unused (rank 2)
```

### Semantics worth knowing before designing around it

- **Out-of-bounds reads on the positive side return zero.** The engine
  bounds-checks the tile against `tensor_dim*`, so K/M/N tails need no separate
  predication — a structural advantage over a hand-rolled copy on this part.
  Confirmed on device: declaring a tensor narrower than the tile zero-fills the
  past-the-end columns rather than faulting or returning stale data.
- **Padding is LDS-side and load-only.** Both encoded fields are biased by one:
  the transfer inserts `pad_amount + 1` dwords every `2^(pad_interval + 1)`
  dwords, giving interval ∈ {2…256} dwords (power of two) and amount ∈ {1…128}
  dwords. In practice this is just an **LDS row stride**: set the interval to the
  tile's inner-dim size in dwords and the amount to
  `(lds_row_stride - tile_inner_dim)` in dwords, i.e.
  `pad_interval = ilog2(tile_dim0_dwords) - 1`,
  `pad_amount = (stride_dwords - tile_dim0_dwords) - 1`. That makes it a second,
  independent route to the same bank-aliasing relief `lds_k_pad` provides
  (§21.2) — and note §21.2's pad response is non-monotonic, so this lever
  inherits that and must be swept, not hill-climbed.
- **The descriptor must be wave-uniform.** The reference wraps every group in a
  read-first-lane before the intrinsic, i.e. the groups land in SGPRs.
- **A completion barrier can be attached** (`atomic_barrier_enable` +
  `atomic_barrier_address`), arriving once per completed transfer.

### Reference layering

ck_tile stacks this as `createTDMDescriptor` → `amd_tdm_load`/`amd_tdm_store`
(`core/arch/amd_buffer_addressing_builtins.hpp`) → `buffer_view::tdm_load` →
`tile_window::tdm_load_to_lds` → `load_tile_tdm` (`core/tensor/load_tile.hpp`) →
consumers: GEMM pipelines (`gemm_pipeline_ag_bg_cr_comp_tdm_v1`/`_v2`,
`wp_pipeline_agmem_bgmem_creg_tdm`), an FMHA pipeline, a TDM epilogue, and a
standalone `ops/tdm/kernel/tdm_kernel.hpp`. The feature gate is
`CK_TILE_ENABLE_TDM_FEATURE`, defined as `defined(__gfx125__)` — gfx1250
qualifies.

### Status in rocke

`helpers/tdm.py` builds the groups: `tdm_descriptor_groups(...)` returns the
five vectors ready for `tensor_load_to_lds` / `tensor_store_from_lds`,
`tdm_row_major_2d(...)` takes natural `(rows, cols)` and applies the
fastest-first transposition for you (prefer it — the raw form is easy to
mis-order), and `tdm_load_to_lds(...)` is the one-step form. It is pure
composition over
existing IR ops (`arith.and`/`arith.or`, `shl`, `lshr`, `trunc`, `vec_insert`,
`zero_vec`, `to_sgpr_u32`), so it adds no op to either engine — which is why it
is Python-only, matching the other composition helpers (`split_k`, `pipeline`,
`sparse_iter`).

### Measured: TDM only pays with prefetch, and it pays a lot

Two traits on the WMMA path drive it: `tdm_lds` replaces the cooperative
global->LDS copy with one wave-uniform descriptor per operand, and
`tdm_prefetch` doubles the AB LDS and issues tile N+1's descriptor before
computing tile N. All ratios below are vs the previously registered candidate
(`128x128x64 w2x2 lds_k_pad=8`, cooperative copy) at a large square shape,
idle device, interleaved attempts, run-to-run spread under 1%.

| configuration | relative |
|---|---|
| registered candidate (cooperative copy) | 1.00 |
| `wmma_async_lds` | 1.00 |
| `tdm_lds` alone, single-buffered | **0.99** |
| `tdm_lds` + `tdm_prefetch`, same geometry | 1.09 |
| + `128x256x64 w2x4` | 1.19 |
| + `256x256x64 w4x4` | 1.26 |
| + `tdm_prefetch_depth=3` | 1.33 |
| + `tdm_prefetch_depth=4` | 1.37 |
| + `w4x2` register blocking | **1.40** |

**Single-buffered TDM is a small net loss.** The descriptor is issued and
immediately waited on, so the transfer overlaps nothing and the non-issuing
waves idle at the barrier. Measuring `tdm_lds` without `tdm_prefetch` measures
the wrong thing — ck_tile never uses TDM that way either, its TDM GEMM
pipelines declare `PrefetchStages = 2`. Do not evaluate one without the other.

What the win is made of, from the ISA: per K-tile the cooperative path issues
~16 `global_load` + ~16 `ds_store`; the TDM path issues **2** `tensor_load` and
no `ds_store` at all. `ds_read` is unchanged, and is now the dominant memory
traffic.

Against the §21.2 roofline the tuned kernel reaches ~0.90 of the **LDS-fed**
WMMA ceiling (up from ~0.71), i.e. ~0.48 of the register-fed ceiling. The
remaining headroom is the 1.87x LDS-fed vs register-fed gap, which is a
read-side problem: no amount of further fill-side work touches it.

### Prefetch depth: how far to pipeline, and how to know when to stop

`tdm_prefetch_depth` is the number of tiles kept in flight (`D` AB LDS
buffers, `D-1` issued ahead). Depth > 2 needs a **partial** drain — wait until
the older tiles have landed while the newer stay outstanding. ck_tile relies on
the same property (`s_wait_tensorcnt_barrier<2>`), which is the evidence that
TDM retires in an order that makes a partial wait safe.

At `256x256x64` with `w4x4`: depth 2 → 1.00, depth 3 → 1.05, depth 4 → **1.08**.
Depth 5 is impossible — it needs more than the 320 KiB per-workgroup ceiling.

Depth interacts with the warp grid. At `w4x2` (the tuned grid) depth 3 and depth
4 measure **identically**, so depth 3 is the better choice: same throughput for
221 KB of LDS instead of 295 KB. Re-check the depth whenever the grid changes
rather than carrying the previous winner's value across.

**Depth is not a global "more is better" knob.** It interacts with tile size and
goes the wrong way on small tiles: at `128x256` depth 3 measures 0.97 of depth
2, and at `128x128` 0.97. The extra buffer only pays where there is enough
compute per tile to hide the extra transfers behind. The registered candidates
reflect this — the 256x256 entry uses depth 4, the 128x128 entry stays at 2.

**Knowing when to stop, cheaply.** Before building depth 3, ablate the wait
entirely — delete `s_wait_tensorcnt` from the loop. The result is numerically
invalid by construction (it reads stale LDS), so it is a diagnostic only, but it
upper-bounds what perfect DMA hiding could buy. Here it measured ~1.19 over
depth 2, i.e. the stall was real and worth chasing; depth 4 then captured most
of it, landing ~1.10 short of the ablation bound with no depth left to spend.
Running that one ablation first is far cheaper than implementing a deeper
pipeline to discover the stall was never the bottleneck.

### Geometry under TDM: two hypotheses that were wrong

Worth recording because both are tempting and both are false.

**`lds_k_pad=8` stays the sharp optimum — it does not become irrelevant.**
The descriptor makes the pad free to *apply* (it is a field, not instructions),
which invites the conclusion that the pad no longer matters. It matters *more*:
the pad's value was always bank-conflict avoidance on `ds_read`, which TDM does
not touch, and `ds_read` is now the dominant cost. Measured at `128x128x64`,
relative to pad 8: pad 0 → 0.36, pad 2 → 0.56, pad 4 → 0.83, pad 16 → 0.86,
pad 32 → 0.38. The same peak reproduces across six geometries; at `256x256x64`
the pad 4 / 8 / 16 spread is 0.80 / 1.00 / 0.78.

**Larger `tile_k` does not help; larger `tile_m`/`tile_n` does.** Cheap
descriptors suggest amortizing them over a deeper K tile. Measured the opposite:
`tile_k=128` is worse at every pad (0.66 at best, 0.14 at pad 0), while growing
the M/N tile is where the gain is. The fill is already ~2 instructions; what
still scales is compute intensity per tile.

The obvious rescue — pair the deeper K tile with a *shallower* prefetch ring, so
the LDS budget stays flat — does not work either. At `256x256`, `tile_k=128`
with `tdm_prefetch_depth=2` measures **0.82** of `tile_k=64` at depth 4 (0.86 at
`lds_k_pad=16`), both bit-exact. Deep-K/shallow-ring is a real point in the
trade space and it loses to shallow-K/deep-ring on this emitter.

**The pad optimum tracks the padded row in *bytes*, not the pad value.** At
`tile_k=64` the peak is `lds_k_pad=8` — a 72-element, 144 B row. At
`tile_k=128` the peak moves to `lds_k_pad=16` — 144 elements, 288 B, i.e. the
same row-byte multiple doubled. So "pad 8" is not a constant to carry across
geometries; re-derive it whenever `tile_k` changes, and expect the winner to
preserve the byte ratio rather than the element count.

### Register blocking: a narrow optimum, and the ratio formula misleads

LDS reads per WMMA are fixed by the per-warp atom grid at `(m+n)*2/(m*n)`, so
shrinking the warp count (bigger grid per warp) is the only way to improve it
without moving an operand out of LDS. At a `256x256` tile, measured relative to
the `w4x4` baseline, all bit-exact:

| warps | per-warp | atoms | acc VGPR | ds:wmma | vgpr / spills | rel |
|---|---|---|---|---|---|---|
| `w4x2` | 64x128 | 4x8 | 256 | 0.75 | 512 / 48 | **1.02** |
| `w4x4` | 64x64 | 4x4 | 128 | 1.00 | 256 / 50 | 1.00 |
| `w2x2` | 128x128 | 8x8 | 512 | 0.50 | 1024 / 128 | 0.98 |
| `w4x1` | 64x256 | 4x16 | 512 | 0.625 | 1024 / 88 | 0.96 |
| `w2x4` | 128x64 | 8x4 | 256 | 0.75 | 512 / 154 | 0.93 |

Three things to take from this.

**Throughput turns over while the ratio is still improving.** 1.00 → 0.75 gains
2%; 0.625 and 0.50 both *lose*. Past a moderate grid the >255-index VGPR
latency (§21.4) and the lost occupancy overtake the saved LDS traffic. The
ratio is a necessary but badly incomplete model.

**Orientation is not symmetric — worth ~10%.** `w4x2` and `w2x4` have identical
atom counts, accumulator size, and ratio, and differ by 9.8%. More N-atoms per
hoisted A fragment lengthens the inner run over which A is reused; the
allocator handles that far better (48 spills vs 154). Nothing in `(m+n)/(m*n)`
predicts this, so sweep both orientations rather than assuming.

**Do not tune by spill count.** `w4x2` at `tdm_prefetch_depth=2` is the only
nearby configuration that spills *nothing* (452 VGPR, 0 spills) and it is ~10%
slower than the same grid at depth 3, which spills 48. Spills here are cheap;
prefetch depth is not. Optimising the spill counter would have shipped the
slower kernel.

### LDS budget: the per-workgroup max is 320 KiB, not 160 KiB

`arch_specs.json` carries `lds_capacity_bytes = 163840` (160 KiB, per CU), but
HIP reports `sharedMemPerBlock = 327680` (320 KiB) — a WGP is two CUs sharing
one LDS block and a workgroup may take all of it, becoming WGP-exclusive above
160 KiB. Device-confirmed: a `128x512x64` tile allocating 184320 B launches and
verifies.

Two practical consequences:

- A double-buffer affordability test written against `lds_capacity_bytes`, and
  against the *unpadded* tile, is doubly wrong. The 2-WG/CU form of that test
  rejected both configurations that turned out to be fastest. Size the check
  against the real padded allocation, and against the per-workgroup budget.
- A test that assumes a **fixed 2x** double-buffer multiplier is wrong for the
  same reason once a prefetch ring can be 3 or 4 deep: it under-reserves, and a
  depth-4 tile can pass a budget check it does not actually fit. Both the
  emitter-side plan and the validity gate must read the depth and the pad from
  the spec, or they drift apart silently and the disagreement only surfaces as
  a launch failure.
- Going WGP-exclusive is legal but did not pay: `128x512x64` (184320 B) lost to
  `256x256x64` (147456 B). Square tiles beat wide ones here.

VGPR, not LDS, is the binding constraint at the tuned point: the winner reports
253/256 VGPR with 0 spills. That is also why the doubled AB LDS costs nothing —
occupancy was already VGPR-pinned to one workgroup per CU.

Current scope is **rank 1-2, non-gather, non-iterating**; higher ranks raise
rather than emit a half-correct descriptor, since groups 2/3 union three
different modes. Two constraints worth knowing:

- rocke exposes no `ptrtoint`, so the global base arrives as an **`i64` kernel
  parameter**, not a `ptr<...,global>`. LDS uses `smem_addr_of`.
- The helper emits nothing until an instance calls it, so byte-identity is
  unaffected today. **The moment a C++ instance adopts it, the same packing must
  be mirrored in `cpp/` and `tools/check_byte_identity.py` re-run** — the
  intrinsic itself is already emitted by both engines.

Validated end to end on device by
`examples/gfx1250/isa_features/tdm_descriptor_verify.py`: a sub-tile of a wider
tensor arrives in LDS exactly, and the out-of-bounds columns zero-fill. That
probe is the regression guard for the ordering rule above — a transposed
descriptor still compiles and still runs, so only a data comparison catches it.
