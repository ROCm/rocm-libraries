# gfx950 profile

Select `gfx950` to predict conflicts using its wave64 LDS rules. The b64 and
b128 reads use different address classes and lane groups from gfx90a.

## Supported requests

Use wave64 with `ds_read_b32`, `ds_read_b64`, `ds_read_b128`, `ds_write_b32`,
`ds_write_b64`, or `ds_write_b128`. Supply one instruction's accesses, with at
most one active access per lane. Addresses and access widths are in bytes.
Align each address to the opcode's full width (4, 8, or 16 bytes), and keep the
full access within the 163,840-byte LDS capacity.

Unavailable opcodes or wave sizes are unsupported. Width mismatches, misaligned
addresses, and accesses beyond the LDS capacity are invalid request data. See
[model-contract.md](model-contract.md) for the complete request and result fields.

## How accesses are grouped

The predictor groups active accesses by lane phase and address class. A lane
phase is a set of lanes considered together for the selected opcode. Accesses
in different phases are considered separately. Within a group, accesses to
different addresses produce a conflict; reads from one shared address produce
a broadcast. Inactive accesses are excluded from grouping.

For b64 and b128 reads, the address class is the byte address modulo 256. For
writes and b32 operations, it is the byte address modulo 128. Thus addresses
0 and 128 belong to different classes for a wide read, but the same class for
a write. Two accesses can conflict only when their lane phases and address
classes match.

Compared with gfx90a, gfx950 b64 and b128 reads use a 256-byte address-class
period instead of 128 bytes and group more lanes into each phase. Writes and
b32 operations use the same grouping rules as gfx90a.

## Try a read and a write

Save this request as `request.json` in the skill directory (the directory
containing `SKILL.md` and `scripts/`). It describes an eight-byte read from each
of two lanes:

```json
{
  "target": "gfx950",
  "opcode": "ds_read_b64",
  "wave_size": 64,
  "accesses": [
    {
      "access_id": 0,
      "lane": 0,
      "lds_byte_address": 0,
      "access_width_bytes": 8
    },
    {
      "access_id": 1,
      "lane": 1,
      "lds_byte_address": 128,
      "access_width_bytes": 8
    }
  ]
}
```

From that directory, use a Python environment where `rocke` is importable:

```text
python scripts/predict.py request.json
```

The command writes JSON to standard output. Both entries in `accesses` have
`classification: "normal"`, and `conflict_groups` is empty. Lanes 0 and 1 share
a phase, but their addresses belong to different classes for this read.

Change only `opcode` to `ds_write_b64` and run the command again. Both accesses
now have `classification: "conflict"`. The `conflict_groups` field contains:

```json
[
  {
    "access_ids": [0, 1],
    "group_id": 0,
    "kind": "distinct-address-conflict",
    "multiplicity": 2
  }
]
```

Multiplicity 2 counts the accesses in the group. The same addresses produce
different read and write results because the address-class periods differ.

## Validation boundary

The profile's grouping rules come from historical wave64 observations for the
listed operations. CPU tests check the implementation against expected
classifications and group membership. They do not establish current hardware
behavior, physical bank organization, or execution time. See
[validation-boundaries.md](validation-boundaries.md) before interpreting results.
