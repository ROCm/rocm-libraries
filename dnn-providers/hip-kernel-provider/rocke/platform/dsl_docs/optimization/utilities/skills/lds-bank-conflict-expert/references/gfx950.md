# gfx950 profile

Select `gfx950` explicitly. Do not substitute another target when a request is
unsupported.

## Scope

- Use wave64 with `ds_read_b32`, `ds_read_b64`, `ds_read_b128`,
  `ds_write_b32`, `ds_write_b64`, and `ds_write_b128`.
- Supply dword-aligned byte addresses and the width required by the selected
  opcode.
- Treat the profile's collision classes and lane phases as opcode-scoped
  prediction rules, not physical geometry.

## Width and direction

The b64 and b128 read rules differ from writes at the same width:

- Wide reads use a 256-byte repeating collision class. Accesses at byte
  addresses 0 and 128 are in different classes; addresses 0 and 256 return to
  the same class.
- Writes and b32 operations use a 128-byte repeating collision class.
- Wide read and write opcodes also use different lane-phase partitions. Preserve
  the exact opcode when comparing results.

For example, lanes 0 and 1 at byte addresses 0 and 128 do not conflict for
`ds_read_b64` or `ds_read_b128`, but do conflict for the corresponding write.

## Compared with gfx90a

Within the supported wave64 operations, gfx950 wide reads use a 256-byte
collision class while gfx90a uses a 128-byte class. The gfx950 b64 and b128 read
phase partitions also group more lanes into each phase than the corresponding
gfx90a partitions. These differences are specific to the wide read opcodes;
the supported writes and b32 operations retain their shared scoped rules.

## Validation boundary

The profile is grounded in historical wave64 observations for the listed
operations. CPU golden cases validate that the reviewed rules are implemented
deterministically; they are not a current hardware rerun. Do not turn these
collision semantics into a physical-bank, latency, throughput, or performance
claim.
