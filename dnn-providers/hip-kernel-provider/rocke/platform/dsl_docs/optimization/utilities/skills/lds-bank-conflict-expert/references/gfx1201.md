# gfx1201 profile

Select `gfx1201` for wave32 LDS conflict prediction. Profile v2 uses
distinct-address active-pair rules and scoped dual-address requests. It does not select `gfx1200` or
`gfx12-generic`, and wave64 is unsupported.

## Supported requests

Supply at most two active lanes, with one full-width access per address operand,
and distinct, non-overlapping byte ranges within each operand. Inactive records remain in the result.
Keep every access within the 65,536-byte LDS capacity. Align addresses as follows;
these are supported prediction alignments, not minimum hardware requirements.

| Native opcode | Access width (bytes) | Address alignment (bytes) |
| --- | --- | --- |
| `ds_load_b32`, `ds_store_b32` | 4 | 4 |
| `ds_load_b64`, `ds_store_b64` | 8 | 8 |
| `ds_load_b96`, `ds_store_b96` | 12 | 16 |
| `ds_load_b128`, `ds_store_b128` | 16 | 16 |
| `ds_load_u8`, `ds_load_i8`, `ds_store_b8` | 1 | 4 |
| `ds_load_u16`, `ds_load_i16`, `ds_store_b16` | 2 | 4 |

The existing `ds_read_b{32,64,128}` and `ds_write_b{32,64,128}` spellings are
also accepted with the corresponding load/store rules. Native spellings remain
native in the normalized result; they do not expand any gfx9 profile's support.
Same-address reads and writes, overlapping ranges, more than two active lanes,
unsupported dual-address operand spacing, transpose instructions, and other
alignments are unsupported. An unsupported request raises an error rather than returning
normal accesses. See [model-contract.md](model-contract.md) for result fields.

## Dual-address requests

Both native `ds_load_2addr` / `ds_store_2addr` and legacy `ds_read2` / `ds_write2`
b32/b64 spellings are accepted, including native `_stride64` and legacy `st64`
forms. Each active lane supplies two records with unique access IDs and explicit
`operand_index` values 0 and 1. Width is per address operand, not the combined
instruction width. Both records must be active or the lane must be inactive.
All addresses, including inactive records, are checked for alignment and capacity.

| Family | Width per operand | Required operand 1 minus operand 0 |
| --- | --- | --- |
| Ordinary b32 | 4 bytes | 64 bytes |
| Ordinary b64 | 8 bytes | 64 bytes |
| Stride64 b32 | 4 bytes | 256 bytes |
| Stride64 b64 | 8 bytes | 512 bytes |

These separations match the observed patterns. Other immediate-offset combinations,
reversed operand order, and partial active operand pairs are unsupported. The input
contains final byte addresses; it does not contain encoded instruction immediates.

```python
result = predict_lds_conflicts(
    target="gfx1201", opcode="ds_load_2addr_b32", wave_size=32,
    accesses=[
        LdsAccess(0, 0, 0, 4, operand_index=0),
        LdsAccess(1, 0, 64, 4, operand_index=1),
        LdsAccess(2, 1, 128, 4, operand_index=0),
        LdsAccess(3, 1, 192, 4, operand_index=1),
    ],
)
```

This produces two groups with access IDs `(0, 2)` and `(1, 3)`, each of multiplicity
2. Separate operand grouping models the measured fixed patterns; it is not a claim
that every dual-address instruction can be decomposed this way. Addresses in different
operands can coincide without being classified as broadcasts. For example, ordinary
b32 requests with lane address pairs `(0, 64)` and `(64, 128)` have no conflict groups.

## Grouping rules

Active accesses conflict when their address operand indices and lane phases match,
and their byte addresses have equal remainders modulo 128. Reads and writes use the same phases:

| Access family | Phase key | Wave32 lane groups |
| --- | --- | --- |
| b32 and sub-dword | `(0,)` | 0–31 |
| b64 | `(lane >> 4,)` | 0–15; 16–31 |
| b96 and b128 | `(lane >> 3,)` | 0–7; 8–15; 16–23; 24–31 |

The implementation is [Gfx1201Profile](../../../../../../python/rocke/analysis/lds/profiles/gfx1201.py).
The address period is an empirical collision class, not a physical bank count.
Multiplicity counts logical accesses in the group, not stall cycles or counter
increments. Each conflict group contains exactly two accesses; dual-address requests can
produce two separate groups.

## Example

```python
from rocke.analysis.lds import LdsAccess, predict_lds_conflicts

result = predict_lds_conflicts(
    target="gfx1201",
    opcode="ds_load_b64",
    wave_size=32,
    accesses=[LdsAccess(0, 0, 0, 8), LdsAccess(1, 1, 128, 8)],
)
```

Both accesses are classified as `conflict`, with group access IDs `(0, 1)` and
multiplicity 2. Moving the second access to lane 16 gives two `normal` accesses
because the lanes then belong to different phases. Moving its address to 8
also gives two `normal` accesses because the address classes differ.

## Validation boundary

The rules derive from wave32 active-pair observations: aligned offset sweeps,
all ordered distinct lane pairs at a 128-byte separation, and anchor checks at
larger separations. CPU golden tests exercise those partitions and the public
request, serialization, and CLI boundaries. Modulo prediction at other base
addresses and separations is model extrapolation, not an exhaustive hardware
validation of every byte address.

Pair observations do not establish broadcast behavior, sub-dword byte offsets,
arbitrary unaligned accesses, full-wave conflict composition, or repeated
instruction composition. Dual-address b32 observations share the b32 phase
partition, and dual-address b64 observations share the b64 partition, including
stride64 forms. V2 models only the fixed operand separations documented above;
arbitrary two-address instruction offsets remain unsupported. Single-address
results retain schema v1, and dual-address results use schema v2 with preserved
operand identity. Existing v1 result readers reject dual-address v2 documents
rather than dropping that identity. See
[validation-boundaries.md](validation-boundaries.md) before interpreting the
model as a claim about physical organization or performance.
