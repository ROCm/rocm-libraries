# gfx1201 profile

Select `gfx1201` for wave32, single-address LDS conflict prediction. Profile v1
uses distinct-address active-pair rules. It does not select `gfx1200` or
`gfx12-generic`, and wave64 is unsupported.

## Supported requests

Supply at most two active lanes, with one full-width access per lane, and
distinct, non-overlapping byte ranges. Inactive records remain in the result.
Keep every access within the 65,536-byte LDS capacity. Align addresses as follows;
these are supported prediction alignments, not minimum hardware requirements.

| Native opcode | Access width (bytes) | Address alignment (bytes) |
| --- | --- | --- |
| `ds_load_b32`, `ds_store_b32` | 4 | 4 |
| `ds_load_b64`, `ds_store_b64` | 8 | 8 |
| `ds_load_b96`, `ds_store_b96` | 12 | 16 |
| `ds_load_b128`, `ds_store_b128` | 16 | 16 |
| `ds_load_u8`, `ds_load_i8`, `ds_store_b8` | 1 | 4 |
| `ds_load_u16`, `ds_load_i16`, `ds_store_b16` | 2 | 4 |

The existing `ds_read_b{32,64,128}` and `ds_write_b{32,64,128}` spellings are
also accepted with the corresponding load/store rules. Native spellings remain
native in the normalized result; they do not expand any gfx9 profile's support.
Same-address reads and writes, overlapping ranges, more than two active lanes,
dual-address instructions, transpose instructions, and other alignments are
unsupported. An unsupported request raises an error rather than returning
normal accesses. See [model-contract.md](model-contract.md) for result fields.

## Grouping rules

Active accesses conflict when their lane phases match and their byte addresses
have equal remainders modulo 128. Reads and writes use the same phases:

| Access family | Phase key | Wave32 lane groups |
| --- | --- | --- |
| b32 and sub-dword | `(0,)` | 0–31 |
| b64 | `(lane >> 4,)` | 0–15; 16–31 |
| b96 and b128 | `(lane >> 3,)` | 0–7; 8–15; 16–23; 24–31 |

The implementation is [Gfx1201Profile](../../../../../../python/rocke/analysis/lds/profiles/gfx1201.py).
The address period is an empirical collision class, not a physical bank count.
Multiplicity counts logical accesses in the group, not stall cycles or counter
increments. A v1 conflict group therefore contains exactly two accesses.

## Example

```python
from rocke.analysis.lds import LdsAccess, predict_lds_conflicts

result = predict_lds_conflicts(
    target="gfx1201",
    opcode="ds_load_b64",
    wave_size=32,
    accesses=[LdsAccess(0, 0, 0, 8), LdsAccess(1, 1, 128, 8)],
)
```

Both accesses are classified as `conflict`, with group access IDs `(0, 1)` and
multiplicity 2. Moving the second access to lane 16 gives two `normal` accesses
because the lanes then belong to different phases. Moving its address to 8
also gives two `normal` accesses because the address classes differ.

## Validation boundary

The rules derive from wave32 active-pair observations: aligned offset sweeps,
all ordered distinct lane pairs at a 128-byte separation, and anchor checks at
larger separations. CPU golden tests exercise those partitions and the public
request, serialization, and CLI boundaries. Modulo prediction at other base
addresses and separations is model extrapolation, not an exhaustive hardware
validation of every byte address.

Pair observations do not establish broadcast behavior, sub-dword byte offsets,
arbitrary unaligned accesses, full-wave conflict composition, or repeated
instruction composition. Dual-address b32 observations share the b32 phase
partition, and dual-address b64 observations share the b64 partition, including
stride64 forms. Those observations do not provide a complete two-address request
contract, so such instructions remain unsupported in v1. See
[validation-boundaries.md](validation-boundaries.md) before interpreting the
model as a claim about physical organization or performance.
