# Rocke optimization wiki

Query a structured knowledge base that routes **operator family × architecture
family** to a technique, then to a rocke primitive. Modeled on KernelWiki’s
three-layer retrieval (sources → wiki → queries), scoped to AMDGPU / rocke.
gfx1250 has KernelWiki-shaped hardware / migration / pattern / technique
pages (WMMA, async-to-LDS, ASYNCcnt, split waitcnt) — analogs, not a
Blackwell corpus port.

All commands run from this directory (`dsl_docs/optimization/`). Scripts
resolve the wiki root themselves.

## When to use

- Optimizing or autotuning a rocke kernel
- A rocprof / ATT / occupancy probe named a bottleneck
- Choosing an MFMA vs WMMA atom, pipeline, LDS layout, or epilogue
- Asking “what do hipBLASLt / Tensile / stinkytofu / CK Tile do for this op?”
- The family table is exhausted and you need a new algorithm (escape hatch)
- Porting a gfx950/gfx1201 kernel to gfx1250, or a Blackwell-shaped gfx1250 question

Do **not** paste software-achieved TFLOP/s, latencies, or GB/s into the wiki
or the git repo. Methodology and levers stay here; measured numbers stay
off-repo.

## How to route a problem

```text
1. Name the operator family (gemm | attention | convolution | moe | small-ops)
   and the gfx id (from arch_specs.json / the device).
2. Exhaust existing knobs (process-optimization-loop Step 0) before redesign.
3. Classify the bottleneck with probes (process-probe-sequence).
4. query.py --symptom <stall> --operator <fam> --architecture <gfx>
5. Open the family page — it tables common tech vs arch-specific tech.
6. get_page.py the matching technique-* (common/ or cdna/rdna/gfx1250/).
7. Change one lever, verify, re-measure, record a source study — not a TFLOPS table.
8. If the catalog cannot move the limiter (same probe after ≥3 one-lever
   ISA diffs): process-escape-hatch. Invent a new mapping. Do not retile.
```

## Query paths

```bash
python3 scripts/query.py --symptom lds-stall --architecture gfx950
python3 scripts/query.py --operator gemm --family cdna
python3 scripts/query.py --type family
python3 scripts/query.py --type technique --arch-specific
python3 scripts/query.py --tag hipblaslt
python3 scripts/get_page.py family-overview
python3 scripts/get_page.py family-gemm --follow-sources
python3 scripts/query.py --symptom catalog-exhausted
python3 scripts/get_page.py process-escape-hatch
python3 scripts/query.py --architecture gfx1250 --type hardware
python3 scripts/query.py --type migration --architecture gfx1250
python3 scripts/get_page.py hw-gfx1250
python3 scripts/grep_wiki.py "compv4" --only wiki
```

## Output contract

1. Cite page **id** and path (e.g. `wiki/techniques/cdna/mfma-atom.md`, `technique-mfma-atom`).
2. Follow `sources:` to `project-*` trees under `rocm-libraries/projects` or `shared/`.
3. Name the rocke primitive (`rocke_primitive` / helper path) when proposing a lever.
4. Respect `confidence`. `verified` means ISA/probe evidence plus a passing numeric harness — not a speed number.
5. Copy snippets from technique pages; they are intended to compile.
6. Never report software-achieved performance in git. Qualitative direction only.

## Layers

1. **`sources/`** — project summaries (hipBLASLt, Tensile/TensileLite, stinkytofu, rocRoller, Origami, MIOpen, hipDNN, CK, rocke instances). Immutable pointers into the monorepo.
2. **`wiki/`** — synthesized pages: `process/`, `families/` (the routing tables), `hardware/`, `techniques/{common,cdna,rdna,gfx1250}/`, `patterns/`, `kernels/`, `migration/`.
3. **`queries/`** — auto-generated indices. Do not edit by hand.

The long-form checklist `optimization_runbook.md` remains as a deep appendix.
Agents should enter through this SKILL and the family tables, not by reading
the runbook linearly.
