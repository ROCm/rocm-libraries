# PR #10492 recipe-validation rollback handoff

## Purpose

This handoff defines a narrow rollback of recipe-specific LLVM SSA validation
from PR #10492. It does not roll back recipe schema validation or safeguards for
operations executed by the recipe VM.

The implementation base is commit
`bda8643db388544fd82359d03628f48d37fc005d`, stacked on PR #10456 commit
`c05f6bbde46bffc90259d30c712f1e48e7357c86`.

This file is a plan only. The rollback and decision-log edits belong in a
follow-up implementation commit. Remove this handoff after that work is
verified and its durable outcome has been incorporated into `DECISION_LOG.md`.

## Decision

Production recipes are trusted artifacts generated by rocKE's recorder or
roller. They are still serialized as JSON or CBOR, stored in bundles, and
decoded later by a C++ consumer, so the decoder must safely reject corrupt,
stale, version-incompatible, or structurally unusable data.

The recipe VM should validate the wire schema and the semantics it executes. It
should not partially reproduce LLVM's structural verifier. In particular,
global LLVM SSA-name uniqueness is not a recipe-decoder responsibility.

The duplicate-SSA cases raised during review are therefore not correctness
blockers for the rocKE-generated path. They demonstrate that the newly added
recipe-specific SSA ledger is incomplete by construction, not that more
per-instruction SSA checks should be added.

## Validation ownership

### Keep in the recipe decoder and VM

- JSON/CBOR parse safety and `rocke.recipe/v1` / `rocke.bundle/v1` schema checks.
- Required object, array, string, boolean, and numeric field kinds.
- Runtime spec declaration/name/kind matching.
- Register-reference resolution needed to execute a recipe.
- Nonempty result binds and unambiguous result addressing within one
  multi-result declaration.
- Conflicting `out` and `outs` rejection and exact result-count preservation.
- Division/modulo-by-zero checks and `LONG_MIN / -1` overflow checks.
- Positive compile-time loop steps and loop-increment overflow checks.
- Builder errors, unsupported opcodes/types, and allocation failures.

These checks prevent the VM itself from silently changing specialization,
looping forever, dereferencing invalid state, or losing recipe results.

### Keep in rocKE producer tests

- Live recording equals the independent `KernelDef` walk.
- Generated recipes round-trip through JSON/CBOR and bundles.
- Python expansion remains semantically equal to C++ replay.
- Generated replay is byte-identical to the normal lowering path.
- Production recorder coverage does not silently turn supported emitters into
  skips.

### Leave to shared downstream validation

- Global LLVM SSA-name uniqueness.
- LLVM operand/result type consistency beyond the recipe's own addressing
  requirements.
- LLVM instruction legality and verifier rules.
- AMDGPU lowering and code-object validity.

If earlier LLVM-structure diagnostics become necessary, add one generic
`KernelDef`/LLVM verification boundary shared by every producer. Do not add
more recipe-only mirrors of LLVM verifier rules in this rollback.

## Implementation plan

### 1. Remove the recipe-specific global SSA ledger

File: `cpp/portable_ir/recipe_vm.cpp`

- Remove `rvm_t::ssa_defs`, `n_ssa_defs`, and `cap_ssa_defs`.
- Remove `rv_ssa_defined()` and `rv_ssa_define()`.
- Remove the forward declaration of `rv_fail()` if it becomes unnecessary after
  deleting those helpers.
- Restore `rv_name()` to naming exact concrete values without registering their
  names in a second validation table.
- In the `param` path, keep `bind` as the recipe register-table key but stop
  treating it as an LLVM SSA definition. `rocke_b_param()` owns the emitted
  parameter name.
- In the single-result `emit.out` path, retain the requirement that `bind` is a
  nonempty string after placeholder resolution. Remove only the
  `rv_ssa_defined()` rejection.
- In the multi-result `emit.outs` path, retain nonempty binds and duplicate
  detection within the current result declaration. Do not add a lookup against
  prior LLVM SSA names.
- Remove `free(vm.ssa_defs)` from cleanup.

Do not change fresh-name behavior, exact naming for valid concrete recipes,
register-table rebinding, operation construction, or lowering output for any
rocKE-generated recipe.

### 2. Remove tests that assert recipe-level LLVM verification

File: `tests/portable_ir/recipe_vm_replay.cpp`

- Remove the rejection case for a repeated concrete single-result bind.
- Remove the rejection case in which an alias masks a prior register-table
  binding before a same-named result.
- Remove comments and helper code whose only purpose is proving global LLVM SSA
  uniqueness at the recipe boundary.
- Keep rejection coverage for missing, empty, and non-string result binds.
- Keep multi-result coverage for missing binds, duplicate binds within one
  `outs` array, placeholder-resolved duplicates within that array, and the valid
  17-result operation.
- Keep at least one positive single-result lowering check so explicit result
  names remain covered.
- Remove any helper that becomes unused after pruning the SSA-policy cases.

Do not add a regression asserting that malformed duplicate-SSA input is
accepted. The absence of recipe-level LLVM verification is an ownership
boundary, not a behavior that callers should depend on.

### 3. Rewrite the durable decision-log entry

File: `python/rocke/portable_ir/DECISION_LOG.md`

Replace the section `2026-08-06: require safe single-result bindings` with the
following durable decision, adjusted only for final verified test counts:

```markdown
## 2026-08-06: validate result addressing, defer LLVM verification

Decision: every `emit.out` and `emit.outs` result requires a nonempty string
bind after placeholder resolution. A multi-result declaration must address each
of its results distinctly. Global LLVM SSA-name uniqueness is not enforced by
the recipe VM.

Reason: production recipes are trusted rocKE-generated serialized artifacts.
The VM validates fields needed to decode and execute those artifacts, while
LLVM structural validity belongs to shared downstream verification. A partial
recipe-specific SSA ledger duplicated LLVM rules and handled only selected
value-producing instructions.

Regression: the hermetic replay test rejects missing, empty, non-string, and
same-declaration duplicate result binds. Valid explicit single-result binds and
the 17-result inline-assembly operation replay and lower intact. Generated
recipes remain byte-identical across the parity matrix.
```

- In `Coverage model`, describe the decoder work as schema and VM-execution

- In `Known boundaries`, add that production recipes are rocKE-generated and

- Preserve the recorded support counts and verification evidence unless the
  implementation rerun changes them.
- Do not remove the documented numeric-cast, add/sub/mul overflow, region,
  rolling, coverage, target, or provider-integration boundaries.

## Acceptance criteria

- No recipe-specific global SSA-definition table remains.
- Valid rocKE-generated recipes produce byte-identical output before and after
  the rollback.
- Missing, wrong-kind, and ambiguous same-declaration result binds are still
  rejected.
- VM-executed safety checks and schema validation remain unchanged.
- Focused C++ tests, Python portable-IR tests, online build/load, and the parity
  matrix pass.
- `DECISION_LOG.md` records the trusted-producer boundary and downstream LLVM
  validation ownership without overstating malformed-input support.
- The PR description matches the implemented boundary and is read back after
  update.
- The completed implementation deletes this temporary handoff.

## Non-goals

- Adding a generic `KernelDef` or LLVM verifier.
- Making arbitrary third-party recipes a supported or security-hardened input.
- Removing decoder memory-safety, schema, runtime-spec, or VM-execution checks.
- Changing the recipe or bundle schema version.
- Changing generated recipes, rolling inference, emitted LLVM, or provider
  integration.
