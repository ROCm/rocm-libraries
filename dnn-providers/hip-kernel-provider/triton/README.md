# Triton AOT generator (RMSNorm)

Compiles the RMSNorm `@triton.jit` kernel (`kernels_src/rmsnorm.py`) to AMDGPU code
objects for `gfx942` and `gfx950`, then emits the descriptors the hip-kernel-provider
packs. Compilation needs no GPU. The objects are kept in git under
`src/engines/kernel_ingestor_engine/descriptors/Triton/rmsnorm/<arch>/`, with a generated
`<arch>.SOURCE.md` beside each arch folder.

Pins (`generators/_contract.py`, `requirements.txt`): `triton==3.8.0` and `msgpack==1.2.3`,
each with a wheel hash.

## Environment

The pinned Triton wheel is a CPython 3.12 wheel. Create a venv that holds exactly the two
pinned wheels:

```
python3.12 -m venv /path/to/triton-aot-gen-venv
/path/to/triton-aot-gen-venv/bin/python -m pip install --no-deps --require-hashes \
    -r dnn-providers/hip-kernel-provider/triton/requirements.txt
```

`--no-deps --require-hashes` is what enforces the wheel hashes. At run time the generator
only checks that `triton.__version__` is `3.8.0`, that `triton` is imported from
site-packages (not shadowed by a local directory), and that `requirements.txt` and
`_contract.py` carry the same wheel hash. `triton_wheel_sha256` in the manifest is that
pinned hash, not a measurement of the imported wheel.

The hipDNN dev image (`projects/hipdnn/dockerfiles/Dockerfile.ubuntu24`) provides the same
venv at `/opt/triton-aot-gen-venv`, off `PATH`; call `/opt/triton-aot-gen-venv/bin/python`
explicitly. The `triton-aot-pin-sync` pre-commit hook keeps the Dockerfile pins equal to
`requirements.txt`.

`gen_descriptors.py` does not import `triton`; any interpreter with `msgpack` runs it.

### `llvm-objdump`

The erratum check disassembles every object with `llvm-objdump`, resolved in order:
`$ROCM_PATH/llvm/bin/llvm-objdump`, `/opt/rocm/llvm/bin/llvm-objdump`, then `PATH`.
If none is found the run fails with `TRITONGEN-ENV`.

### Environment variables

Before importing `triton`, the generator:

- sets `TRITON_DISABLE_LINE_INFO=1` and a fresh `TRITON_CACHE_DIR` per compile;
- fails with `TRITONGEN-ENV` if `TRITON_INTERPRET` or `TRITON_KERNEL_OVERRIDE` is set;
- clears `TRITON_OVERRIDE_ARCH`, `TRITON_ALWAYS_COMPILE`, `TRITON_HIP_*`, `AMDGCN_*` and
  `*_FP_FUSION` (recorded in the manifest as `env.cleared`).

Other `TRITON_*` variables are not cleared and can change the generated bytes
(`TRITON_F32_DEFAULT` is recorded in the manifest as `unset` or its value). Regenerate in a
clean environment and diff, as below.

## Regenerate

Run from this directory. `--out` and `--in` are content roots (the folder that contains
`rmsnorm/`) and default to the committed `descriptors/Triton/`.

```
cd dnn-providers/hip-kernel-provider/triton
VENV=/opt/triton-aot-gen-venv       # or the venv created above
$VENV/bin/python -m generators.gen_rmsnorm --arch gfx942 --arch gfx950 [--out <content-root>]
$VENV/bin/python gen_descriptors.py [--arch ...] [--in <content-root>] [--out <content-root>]
```

- `gen_rmsnorm` verifies every object, then writes `<out>/rmsnorm/<arch>/<instance>.hsaco`,
  `<out>/rmsnorm/<arch>/manifest.json` and `<out>/rmsnorm/<arch>.SOURCE.md`. Each arch is
  built in a temporary sibling folder and swapped in only on success. The swap replaces the
  whole `<arch>/` folder, so run `gen_descriptors` afterwards.
- `gen_descriptors` reads each `<in>/rmsnorm/<arch>/manifest.json` and its objects, emits the
  op-level descriptors plus each arch's KDP and UKDs, copies the manifests, objects and
  `SOURCE.md`, validates the staged tree with `hkp_pack`, then swaps it into `<out>`
  (stale descriptors are removed). It has no `--check` mode.

To regenerate the committed tree, run both commands with the defaults.

### Verify

Regeneration is byte-reproducible. To check the committed tree:

```
$VENV/bin/python -m generators.gen_rmsnorm --arch gfx942 --arch gfx950 --out /tmp/regen
$VENV/bin/python gen_descriptors.py --in /tmp/regen --out /tmp/regen-full
diff -r /tmp/regen-full <committed>      # expect no output
```

A difference in a `.hsaco` or `manifest.json` means the environment (wheel, LLVM,
`TRITON_*` variables) differs from the one that produced the committed objects.

## Manifest

`<arch>/manifest.json` (sorted keys, no paths or timestamps) records:

- `toolchain`: `triton_version`, `triton_wheel_sha256`, `llvm_commit` (from the objects'
  `.comment`), `env` (the variables above) and `hip_options`;
- `instances`: per object, the name, dtype, `block_n`, priority, file, symbol, size, SHA256,
  `num_warps`, `warp_size`, block and grid rule, `shared`, scratch sizes,
  `kernarg_segment_size`, `erratum_guard` and the kernarg layout (`args`).

`<arch>.SOURCE.md` is rendered from the manifest.

## Error codes

Every generator failure carries one of these prefixes:

| Code | Meaning |
| --- | --- |
| `TRITONGEN-ENV` | Refused knob, wrong or shadowed `triton`, HIPOptions pin differs from the wheel default, no `llvm-objdump`, pin mismatch between `requirements.txt` and `_contract.py` |
| `TRITONGEN-ARCH` | The object's `amdhsa.target` is not the arch it is filed under |
| `TRITONGEN-ABI` | The kernarg tuple (including both scratch slots), kernel symbol or kernarg segment size differs from the contract |
| `TRITONGEN-SCRATCH` | Non-zero global or profile scratch |
| `TRITONGEN-ERRATUM` | Packed-FP32 instructions (`v_pk_{fma,mul,add}_f32`) beside `v_mfma*`/`v_smfmac*` in the disassembly (gfx950 erratum) |
