## 6. Codegen gaps found and the levers that close them (all default off)

Disassembly diff direct vs COMGR (same IR):

- `tile.dpp_xor` masks 7 / 15 went through `ds_swizzle_b32` (+ an LDS wait each); LLVM uses row_half_mirror /
  row_mirror DPP and folds the DPP move into the add (`v_add_u32_dpp`). Levers `dppmirror` (register DPP for 7, 8,
  15) and `dppcombine` (`target/gfx9/dpp.rs`, the GCNDPPCombine fold). After both, the toy wave sum is instruction-for-
  instruction the COMGR sequence.
- No LDS quad merge on gfx950 (8 `ds_read_b32` where COMGR has 2 `ds_read_b128`). Lever `ldsquads`.
- The head loop splits each load group among the MFMAs; LLVM keeps the loads ahead. Lever `vmemfirst` (`rir/post.rs`).
- Remaining (not addressed): more 64-bit SALU address math and VGPR copies in the toy publish path; the direct poll
  is a single narrowing loop where COMGR peels a first check.

Why d8w0 wins: after the DPP levers the wave sum is LLVM's, and the rest of the hop is shorter on the direct side:
the uniform hop address math stays in SALU after the readfirstlane (COMGR goes back to VALU), the poll is one
EXEC-narrowing loop (COMGR peels a first check and nests two EXEC save/restores), and the publish address/data setup
is shorter. Remaining head gap: same main-loop instruction mix (320 cvt_scalef32, 80 MFMA, 80 ds_read_b128, 44
buffer loads on both), so it is ordering inside the loop plus a slightly larger epilogue (more VALU address adds,
18 ds_read_b32); not closed by `vmemfirst`.

## 7. Levers (`ROCKE_DIRECT_LEVERS`, `+`-joined; docs in `src/rir/mod.rs` `lever()`)

| lever | what | status |
|---|---|---|
| `storewait` | exact vmcnt placement for stores (no drain before barriers) | kept off: no win |
| `nopause` | no `s_sleep` pause in the poll | kept off: no win |
| `nofence` | `tile.sched_barrier` no scheduling boundary | kept off: loss |
| `dppmirror`, `dppcombine` | LLVM's DPP forms for the wave sums | WIN on toy d8w0 (x2), big recovery on d4w8_l2; candidate for default-on in a follow-up |
| `ldsquads` | gfx950 LDS quad merge | recovers d4w8_l2 to neutral (no change on d8w0); candidate with the DPP levers |
| `vmemfirst` | vector loads first in the list scheduler | kept off: head 1.0072 -> 1.0064, within noise |

Unhoistable poll with sc1 is the IR form already (`tile.tagged_poll` lowers to an EXEC-narrowing loop with sc1 loads;
LLVM likewise does not hoist the inline asm), so it is not a separate lever. Register pinning beyond the kernarg
preload and `=s,0` pins was not feasible without a register-allocator change (the pins already compile).
Every lever is byte-identical off (census) and passes numerics on.

## 8. Recommendation

Keep as an off knob; do not commit the full 4-6 week track yet.

- For: the direct path is correct on hardware for the true-mono building blocks (bitwise, hazards, spills, mutation
  all clean), and on the sync-bound toy chain it beats COMGR once two LLVM idioms are matched (d8w0 0.973-0.982,
  replicated); the cross-CTA hop it models is the true mono's sync-bound path.
- Against: the bandwidth-bound head (lm_head GEMV) is a consistent small loss (about 0.5-0.7%) under every lever, and d4w8_l2 is only neutral. Each gap so far needed a targeted
  LLVM-parity pass (DPP forms, LDS quads), which is the 4-6 week track's real content: the full mono will hit more of
  these (GEMV main-loop scheduling, MoE / GDN bodies not yet compiled directly).
- Proposed bounded follow-up (about 1-2 weeks, decision gate at the end): (1) promote `dppmirror+dppcombine+ldsquads`
  to the direct default (they only change direct objects; census untouched), (2) close the head main-loop ordering
  gap (target ratio <= 1.000 at m = 1 and 4), (3) compile one real layer stage (the hop path of the true mono) IR-only
  directly and time it paired. Commit the full track only if (2) closes and (3) shows a rule WIN; otherwise the
  direct path stays a default-off knob.

### Caveats

1. **The head "loss" holds under DESIGN 9.1 only in w2-r2-gpu2.**
   - In gpu3 and gpu4, head m1 `D` (1.0072, 1.0068) and the best lever arm (1.0055, 1.0060) fall inside the controls'
     maximum + 0.002 (1.0078, 1.0069). By the rule they are NEUTRAL, not LOSS.
   - The direction is consistent all the same: 0 rounds below 1 in every job. In no job is the head a WIN, so the
     conclusion holds.
   - Read "small loss" in the summary as "consistently slower, NEUTRAL/LOSS by rule".
2. **No mutant covers the lever code the WIN rests on** (`dppmirror`, `dppcombine` in `target/gfx9/dpp.rs`,
   `ldsquads`, `vmemfirst`).
   - Every mutant in `r2_mutants.py` targets the base lowerings. The only lever with a mutant is `storewait`
     (CPU-only), and the GPU mutant job ran no lever arms.
   - The DPP arms pass the exact-integer 2,000-replay toy check, and the head object does not change under them.
     Still, no run has shown that the gate catches a wrong DPP fold.
   - Before `dppmirror+dppcombine+ldsquads` become the direct default (section 8 step 1), add must-fail mutants
     for them: a wrong row_mirror / row_half_mirror control, a dropped `bound_ctrl`, and a wrong quad merge offset.
     Each must fail the toy replay.
3. **For lever arms and spill builds, "bitwise" means the fused-argmax output and workspace, not the logits.**
   - Logits are compared bitwise only for the plain direct build of the `logits` epilogue.
   - The summary line "every lever arm direct == COMGR bit for bit" is true only of the fused outputs. R2's own
     table states this correctly.
4. **Every timing job ran on one node, smci355-ccs-aus-n01-09.**
   - The d8w0 WIN is replicated across two jobs but not across nodes; n07-17 was used only for the mutant job.
   - Before any step-3 decision in section 8, repeat a timing job on n07-17 as well.
5. **The new knob-off identity covers 15 builds.** The census covers the crate's outputs for every build. The
   Python-side COMGR identity covers these 15 builds plus R2's pytest gates (62 / 290 / 136 / 23). It does not
   cover every library build.
6. **Small omission:** the R2 "Files" list leaves out `w2-r2-gpu4`, the confirmation job. Its results are in
   `hackathon-prep/logs/q38/results/w2-r2-gpu4/`.
