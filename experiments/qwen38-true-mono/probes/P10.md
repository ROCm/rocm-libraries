# P10: the fused MoE's router window at wider routers (null-byte build, phase stamps; gfx950)

DESIGN.md 8.2, probe P10 (review M8, budget line G6 of 2.2 / 2.3, N3's bitwise twin in 12.3): measure the router window
of the hybrid's rocKE fused MoE at the router widths the current M3 structure can reach, with the null-byte build
(`w_null`: every expert weight load reads zero bytes, so the MoE is its fixed overhead) and the phase stamps, and report
the sign. This file gives ratios, shares and counts only. Absolute times:
`hackathon-prep/private-perf/qwen38-true-mono/probes/P10.md`.

Status: **done, gate met.** Numerics bitwise on hardware (every width, every schedule variant, delta and delta_ple) with
mutants that must fail (they all did), then timing per DESIGN 9.1: three runs, both rocke nodes, three seeds, 24
shuffled rounds per process with two controls. The question has a clear answer (section 1). One side finding is larger
than the probe's own lever (1.3).

## 1. What D0 gets from P10

1. **G6 has no usable sign. Book G6 = 0 at K=3 and K=0 (K=0 range 0 to 0.0015 hybrid units), and N3's bitwise twin
   ("G6, wider router rows: 0.005") at 0. No work package for G6.**
   - **K=3 (rows 4, r4s):** the mono's router (130 tasks: 8 router rows x 2 request rows each) is already the widest
     router that fits one task per CTA. Anything wider needs 258 (`m3_ept=4`) or 260 (one request row a task) tasks on
     256 CTAs. The only other one-task-per-CTA widths both LOSE, in situ, on both nodes, under both schedules: half the
     router bytes per CTA (129 tasks, 4 router rows x 4 request rows: `m3_ept=4, m3_rows=4`) 1.015-1.021 of the layer,
     and the narrower 65 tasks 1.021-1.028. Their windows get longer (stamped routing done +0.018 to +0.020 and +0.020
     to +0.046 of the plain mono's MoE).
   - **K=0 (rows 1, r1):** the wider router exists (`m3_ept=4`: 129 tasks of 4 router rows instead of 65 of 8). It
     shortens the stamped window (routing done -0.009 to -0.023 of the plain mono's MoE, last router task -0.014 to
     -0.025), but the layer barely moves: 0.9973-0.9992 of the served width in all 8 processes (17-24 of 24 rounds below
     1), never past the controls by the 0.002 margin: TIE every time. Null bytes: 1.0015-1.0046 (TIE). A lookback on the
     placement (the 129 router CTAs wrap onto the combine CTAs) does not turn it into a win (4.4). Upper bound about 0.002
     of the delta / delta_ple r1 layers, i.e. about 0.0015 hybrid units at K=0.
2. **The window is latency-bound, not bytes-bound.** The null-byte build has the same window as the real one (routing
   done within 0.004, last router task within 0.008, of the plain mono's MoE in every pair), and halving the router
   bytes per CTA at rows 4 makes it longer. The window is the M2 -> M3 hop plus each router task's post-poll chain (the
   request rows a task are what cost: 4 rows a task lose to 2) plus the `lg` hop, top-10 and the route barriers
   (routing done minus the last router task: 0.06-0.09 of the plain mono's MoE). Routing ends at 0.20-0.21 (r4s,
   numa=1) to 0.29-0.30 (r1, `best`) of the plain mono's MoE after M2's end. That is what N3 (P15: router K-split into
   M2's epilogue, or an MFMA N-split over all CTAs with a redundant per-CTA top-10) must remove: hops and the per-task
   chain. Re-spreading the mono's router code is exhausted.
3. **Side finding: the served schedule's holds, not the width, move this window and the layer (H line of 2.2).**
   - **r1, `hold.m4=64` (WIN, both kinds, both nodes):** `best` sleeps the M4 task CTAs 64 units at M4 entry. With the
     fused MoE linked, M4 is an empty extern stage, so the sleep lands after the fused body, at the end of the layer.
     Dropping only `hold.m4` (keeping `hold.b1=32, hold.m3=32`) makes the delta r1 layer **0.963-0.969** of `best`
     (4 of 4 comparisons, 24/24 rounds) and the delta_ple r1 layer **0.972-0.975** (2 of 2, 24/24). This root-causes
     `RP/E2E_COMPOSED.md`'s open item "the fused MoE's K=0 gain is gone on `best`" (NF/N 0.999 vs F/N 0.975) at layer
     level. On `best` the fused MoE at r1 is even slower than the `best` mono's own MoE (1.021-1.026, unstamped).
   - **r4s, `hold.m3=128`:** it holds the mono's 130 M3-task CTAs, which are exactly the fused router's CTAs, and
     delays the window by 0.024-0.028 of the plain mono's MoE (stamped last router task 0.167-0.173 vs 0.139-0.145).
     Without it the delta r4s layer is 0.9968 / 0.9914 of `best` (24/24 rounds in both runs), TIE by the margin rule
     both times (wide controls in run g). About 0.3-0.9 % of the r4s delta layer, not proven.
4. **What this changes in the D0 budget:**
   - G6 -> 0 (both K). N3's fallback -> 0. N3 keeps its 12.3 booking (P15 decides it); P10 adds that its gain cannot
     come from bytes or width, only from removing hops and the per-task row chain.
   - H (hold re-tune): the true mono must not inherit `best`'s holds onto stages its fused bodies empty (`hold.m4`; also
     check `hold.m5` if any set gains one), and `hold.m3` must be re-derived for the fused router (it now holds the
     router itself). Gate every inherited hold in situ before WP3.
   - **The competitor can move (2.6):** the pinned hybrid carries the `hold.m4` sleep on every delta and delta_ple r1
     layer (K=0 decode; not the K=3 cells: their r1 layers are QSA drafter layers with `hold.q1` only). Dropping it is a
     one-line `best` change worth about 0.03 of those layers, about 0.02 hybrid units at K=0 if it carries to serving
     (layer level only here; not measured end to end). If the hybrid adopts it, the K=0 target (<= 0.78 of the hybrid's
     per-token time, PLAN decision 7) gets about 2 % harder. Recorded as "hybrid-adoptable"; the pinned baseline stays as
     measured (WP0b).

## 5. Answers to the review / design questions

- **M8 ("G6 has no mechanism"):** confirmed by measurement. Wider router rows shorten the stamped window only at r1, and
  that reaches the layer as at most about 0.2 %, inside the controls in 8 of 8 processes; at r4s no wider width exists
  and the alternatives lose 1.5-2.8 %.
- **"WP only if it moves":** it does not move. No WP. The knobs stay registered and default-off with their measured
  values: `m3_ept=4` at rows 1 (TIE, 0.997-0.999; a WP11 lookback candidate on the true-mono bodies), `m3_ept=4,
  m3_rows=rows` and `m3_rows=rows` at rows > 1 (LOSS).
- **For N3 / P15:** the window to beat at the served widths is routing done at 0.20-0.21 (r4s numa) to 0.29-0.30 (r1
  best) of the plain mono's MoE, of which 0.14-0.21 is the router tasks (hop from M2 + per-task chain) and 0.06-0.09
  the `lg` hop + top-10 + barriers. Both are latency; P15's variants must remove a hop or the per-task row chain.
- **For H / WP3 (hold re-anchoring):** `best` is not a valid schedule for layers with the fused MoE linked: its r1
  `hold.m4` is a pure end-of-layer sleep there (0.025-0.037 of the layer). The true mono's holds start from `numa=1`
  and are re-climbed (DESIGN 9.2) on the rocKE bodies; no FlyDSL-tuned hold is carried over unmeasured.

## 7. Limits

- Synthetic weights (random routing at served-like U); delta and delta_ple layers. QSA r4s and the drafter layers run
  the same fused body and router code, so the width result transfers; the hold result is per kind and variant (qsa r1
  has only `hold.q1`; qsa r4s and delta_ple r4s have `hold.m3=64` / `128`, like delta r4s).
- The `hold.m4` effect is measured at layer level in situ (bitwise arms, shuffled rounds, two controls, two nodes), not
  end to end in a served model; the about 0.02 hybrid units at K=0 is a projection (0.03 x the delta-type share of the
  K=0 layer time, about 0.65 hybrid units).
- Stamped and unstamped measurements disagree on the r1 wide router's MoE end and on `hold.m3`'s sign at r4s; the
  verdicts use the unstamped bench (DESIGN 9.1), the stamps only locate the window.

### 8.1 What was checked

- **Gate vs DESIGN 8.2.** P10's gate is "G6 sign; WP only if it moves". Section 1 answers exactly that: no wider width
  exists at K=3, and the alternatives LOSE; at K=0 the result is TIE. No extra gate was claimed.
- **Numerics on hardware, with mutants that must fail.** The job logs (`P10-raw/*/job.out`) contain 32 `CHECK_PASS`,
  5 `HOLDS_CHECK PASS`, no FAIL and no non-zero rc. The comparator (`moe-fused/fused_ab.py check`, reference = the
  plain FlyDSL mono layer `full`) requires all of these bitwise: h_out (non-zero), the `lg` / `sg` / `dn` payloads,
  the scratch outside `ss`, every state pool, and NUMA copy 1 == copy 0. A mutant passes only if its h_out differs.

### 8.4 Corrections to the text above

1. **Section 1.3 and the builder's summary.** "WIN ... both kinds, both nodes" was not supported for delta_ple when it
   was written: there was one run, on n01-09. It is true now, through 8.3.
2. **"The window is latency-bound, not bytes-bound" (1.2, 4.2) is stronger than the evidence.** `w_null` zeroes only
   the expert weight loads (`moe_fused._off`), not the router weights. So "null-byte window = real window" shows only
   that expert traffic does not slow the router; it says nothing about router bytes.
   - At r1, half the router bytes and rows per task (w129) does finish the router 0.014-0.025 earlier.
   - At r4s, w129 also doubles the request rows per task, so bytes and rows are confounded.

   Supported reading: shorter router tasks shorten the stamped window, but the saving does not reach the layer
   (TIE). G6 = 0 is unchanged.
3. **The K=0 upper bound is slightly low.** w129 medians reach 0.9973-0.9975 (run g), i.e. 0.25-0.27 % of the layer,
   about 0.0018 hybrid units at the 0.65 delta-type share, not 0.0015. Still TIE, and negligible against G6's 0.015
   ceiling.
4. **`best` vs `numa=1` at delta_ple r1 depends on the node.** It was TIE in run g (0.9994) and is LOSS here (1.0073).
   So "best and numa=1 within 0.007" (4.3) holds on n01-09 only. The H-line advice (start from `numa=1` and re-climb
   the holds; never inherit `hold.m4`) is unchanged.

### 8.5 Residual weakness (not a gate failure)

No mutant targets the router itself. The mutants are null expert weights and a swapped combine order, and both are
caught through h_out. The router's outputs (`lg` / `sg`) are compared bitwise for every real arm, so a router error
would fail the check. But no planted router fault has yet shown that the `lg` comparison catches one. P15 should add a
router mutant (e.g. swapped K-part order, or a top-10 tie broken high) before its tolerance variants.
